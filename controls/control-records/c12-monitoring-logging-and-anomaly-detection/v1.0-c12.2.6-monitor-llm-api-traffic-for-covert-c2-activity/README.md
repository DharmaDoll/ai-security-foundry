# AI APIを隠れた通信路に使う兆候を監視する

AISVS Verification Level: 3

学習資料：[C12.2 検知と通知](../../../learning/c12-monitoring-logging-and-anomaly-detection/v1.0-c12.2-detection-and-alerting.md)

## Upstream basis

AISVS `v1.0-C12.2.6`は、LLM APIへの通信を監視し、隠れた通信路の兆候と
通信パターンから、マルウェアやC2活動を見つけられるかを問う。**C2**は、
侵害された端末に攻撃者が指令を送り、結果を受け取る通信を指す。
**隠れた通信路**は、正規に見える通信を別の情報の運搬に悪用する経路である。

対応するAISVS Researchは、AI APIを指令・情報搬出に使う事例を挙げ、
通常使わない端末や処理からの接続、宛先、送受信の間隔、符号化された
データなどを調べる方法を提案する。ただし正規要件は、特定の攻撃事例、
通信の全内容の取得、製品、検知ルール、しきい値を指定していない。

## Interpretation

対象環境からLLM APIへ出る通信について、不正な指令や情報の受け渡しに
悪用された場合の兆候を、実際に観測・評価できるようにする。例えば、
普段AIを使わない処理がAI APIへ一定間隔で通信し、同じ形の要求と応答を
繰り返すなら、通常の利用と区別して調査できる必要がある。

単なる接続数の保存や、投稿文へのプロンプト攻撃の検査だけでは足りない。
送信元、宛先、時刻、通信の形など、対象環境で取得できる情報を使い、
隠れた通信やC2を疑う理由を評価する。要求や応答の内容を安全に観測できる
構成なら、それも判断材料になり得るが、全文取得を一律には要求しない。

## Security objective

AI APIが通常の業務通信に紛れた指令・情報搬出の経路になっても、その兆候を
調査担当者が見つけ、対象の端末や処理を絞れるようにする。監視だけで
攻撃の阻止や、全てのC2通信の発見を保証するものではない。

## Applicability

管理対象のアプリ、Agent、端末、サーバーなどからLLM APIへ通信できる環境に
適用する。自社のAI機能が使う正規のAPI経路だけでなく、同じ管理範囲から
直接外へ出られる経路も確認する。APIキーが不要な接続や、普段はAIを使わ
ない処理からの接続も、対象範囲に入るなら評価する。

### Non-applicability

評価対象の環境からLLM APIへの通信経路がなく、それを構成と実際の通信の
両面で確認できる場合は対象外にできる。「契約したAI提供者がいない」
「APIキーを発行していない」だけでは、外部AI APIへ接続できない証拠に
ならない。管理外の端末や一般のWeb閲覧を含めるかは評価範囲を明示し、
観測できない範囲まで本Controlの合格を広げない。

## Scope and assumptions

- 「LLM API通信」は、モデルへの要求・応答を運ぶAPI接続を指す。Researchに
  はWebサービスを悪用した例もあるが、全ての一般Web閲覧を本要件へ自動的に
  含めない。境界上の通信は、評価対象に含める理由を明示する。
- 「兆候」や「通信パターン」は一つの固定文字列とは限らない。送信元、
  宛先、繰返し間隔、要求・応答の形、内容の符号化などを組み合わせられる。
  符号化や大量通信だけで攻撃と決めない。
- HTTPSなどで本文が見えない場合、端末・ネットワーク・API仲介処理の
  どこに観測点を置くかを示す。見えない内容を「検査済み」とは扱わない。
- 指令内容そのものの完全な復号やマルウェアの特定は要件にない。
  観測できる兆候と見逃し得る経路を記録する。

## Assets, actors, identities, and trust boundaries

守る対象は端末・サーバーの安全と、AI APIを通じて外へ出され得る情報。
関わるのは管理対象の処理、利用者、AI API提供者、通信の観測点、検知処理、
調査担当者。攻撃者は端末や処理を侵害し、正規のAI APIに見える通信で
指令や結果を運ぼうとする。

主な境界は、管理対象の処理から外部LLM APIへの出口、暗号化された通信と
観測点、観測結果から検知・調査の仕組みへの受け渡しである。アプリの
正規Gatewayだけを見ている場合、端末からの直接接続は別の経路になる。

## Required security properties

| ID | 必要な性質と確かめ方 |
|---|---|
| SP-1 | 評価対象からLLM APIへ出る主要な経路と観測点が分かり、対象経路の通信が実際に監視へ届く。 |
| SP-2 | 隠れた情報の送受信やC2を疑う通信の特徴を、対象環境で取得できる信号から評価できる。接続件数の保存だけで終わらない。 |
| SP-3 | 疑わしい通信を検知したとき、送信元・宛先・時刻と疑った理由を調査担当者が辿れる。取得できない項目は明示する。 |
| SP-4 | 監視経路や検知処理の停止・欠落が分かり、観測していない期間を「異常なし」と誤認しない。 |

## Scope calibration and adjacent assurance

| 観測 | 本Controlでの扱い |
|---|---|
| AI APIの呼出し数だけを保存し、不審な通信の特徴を評価しない | Fail。C2や隠れた通信路を見つける監視になっていない。 |
| 正規アプリのGatewayだけを監視し、管理対象端末からの直接接続を見落とす | 対象範囲にその経路があるならFail。監視範囲を狭く見せない。 |
| 無害な模擬通信の繰返しや予期しない送信元を検知し、調査情報へ辿れる | Pass候補。未試験の手法まで検知できるとは主張しない。 |
| 暗号化通信の本文は見えないが、送信元・宛先・時刻・通信間隔等を評価する | 有効な監視となり得る。本文が見えない限界を明示する。 |
| 不正の兆候を見つけるが、通信を自動停止しない | 本要件の直接のFailではない。封じ込めは別の保証として評価する。 |
| 正規の画像送信などを符号化データだけを理由に疑う | 誤検知を測り、判断の質を改善する。符号化そのものをC2の確証にしない。 |

## Threat and failure-mode rationale

侵害された処理が一般的なAI APIへ指令を取りに行ったり、結果を質問の形で
送ったりすれば、AI利用として見過ごされ得る。特にAPIキーの有無だけで
接続の安全を判断すると、別の接続経路を見落とす。反対に、正規の画像や
長い文書も符号化・大容量になり得るため、単一の特徴だけで不正と決めると
誤検知が増える。外部の脅威IDとの厳密な対応付けはまだ評価していない。

## Verification

### Architecture and configuration review

管理範囲の端末・処理からLLM APIへの経路を洗い出し、正規Gatewayと直接接続
の両方を確認する。通信をどこで観測するか、どの信号を取得するか、検知処理
にどう渡すか、検知結果を誰が調べるかを追う。暗号化による見えない部分、
監視の停止時に何が残るか、保管する情報の機密性も確認する。特定の製品や
TLS復号、全通信の本文保存を必須にはしない。

### Positive verification

本番のマルウェアを使わず、無害な合成通信で試す。普段AIを使わない試験用の
処理から、試験用LLM API宛に一定間隔の要求と応答を繰り返す。通常利用の
通信も並べ、疑わしい方について送信元・宛先・時刻・判定理由を調べられるか
確認する。正規Gateway経由と直接接続の両方が対象なら、両方を試す。

### Negative and abuse-case verification

| ID | 試すこと | 期待する確認結果 |
|---|---|---|
| N-1 | 正規Gatewayを通らず、管理対象の試験処理からLLM APIへ接続する | 対象経路なら通信が観測され、検知評価に入る。SP-1。 |
| N-2 | APIキーを持たない試験処理から、接続可能なLLM API宛に模擬通信を送る | キーの有無だけで監視対象から外さない。SP-1、SP-2。 |
| N-3 | 正規の要求に似せた一定間隔の模擬通信を送る | 繰返しや送信元など、定めた兆候を評価して調査できる。SP-2、SP-3。 |
| N-4 | 正規の画像など、符号化された無害な入力を送る | 符号化だけでC2と断定しない。誤検知を記録する。SP-2。 |
| N-5 | 監視経路または検知処理を試験的に止める | 欠落が分かり、監視していない期間を正常と見なさない。SP-4。 |
| N-6 | 疑わしい通信の記録から送信元・宛先または判定理由を消す | 調査不能な検知結果を発見する。SP-3。 |

### Failure conditions

対象のLLM API経路を観測できない、通信を記録するだけで隠れた通信やC2の
特徴を評価しない、合成した兆候を検知しても発生元・宛先・理由を調べられない、
または監視停止を異常なしと扱う場合はFail。全マルウェアを特定できないこと、
特定製品やTLS復号を使わないこと、自動遮断しないことだけでFailにはしない。

## Evidence expectations

| 証拠 | 作成元 | 対象 | 確認する時期 | 保護上の注意 | 合格の目安 |
|---|---|---|---|---|---|
| 出口経路と観測点の図 | ネットワーク・アプリ・監視の担当者 | 管理対象からLLM APIへの正規経路と直接経路 | 経路やAPI提供者の変更時 | 実際の秘密や内部宛先を載せない | 対象経路と観測できない範囲を説明できる。 |
| 検知条件と調査項目 | 監視の担当者 | 隠れた通信・C2の兆候、送信元・宛先・時刻 | ルール変更時 | 通信本文や個人情報の収集を最小限にする | 通信をどう評価し、疑いの理由をどう示すか説明できる。 |
| 無害な模擬通信の試験結果 | 試験・監視の担当者 | N-1〜N-6、通常利用との比較 | リリース時・監視変更時 | 本番マルウェアや実データを使わない | 対象経路の通信が届き、検知と調査が実際に行える。 |

## Known limitations and uncertainty

正規要件は「隠れた通信路の兆候」「通信パターン」の具体的な項目を列挙して
いない。暗号化、共有端末、直接接続の不可視性、正規通信への偽装により
見逃し得る。一定間隔の通信や符号化は正規業務でも起こるため、検知結果は
侵害の確証ではない。監視の範囲を広げるほどプライバシーと運用費用への
影響も増える。`verifiable`は本書の成熟度であり、実製品の適合結果ではない。
