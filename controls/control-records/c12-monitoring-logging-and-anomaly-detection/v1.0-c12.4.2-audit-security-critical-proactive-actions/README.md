# 自律的な重要操作と承認判断を監査記録で追う

AISVS Verification Level: 2

学習資料：[C12.4 Agentが自ら始める行動の監視](../../../learning/c12-monitoring-logging-and-anomaly-detection/v1.0-c12.4-proactive-security-behavior-monitoring.md)

## Upstream basis

AISVS `v1.0-C12.4.2`は、Agentが自ら始めるSecurity上重要な操作を
監査記録に残し、承認者のIdentity、時刻、操作の引数、判断結果を
含めることを求める。**監査記録**とは、後から誰が何を判断・実行したかを
確認するための記録であり、単なる「処理あり／なし」の集計ではない。

対応するAISVS Researchは、予定起動・Event起動・他Agentからの依頼を
調べ、起動、承認、Tool呼出し、実行結果を結び付ける検証を提案する。
拒否・取消し・Timeout・失敗の経路も重要とする。一方、Researchにある
特定のLog製品、Field名、Hash方式、保存方式は要件本文の必須条件ではない。

## Interpretation

対象の操作ごとに、Agentが何を提案し、誰またはどの信頼できるPolicyが
どう判断し、その対象操作が実際にどうなったかを辿れるようにする。
例えば夜間のAgentが「取引先Aへ10万円を送金する」と提案し、担当者が
拒否して未実行となった場合、監査記録から送金先と金額、拒否した担当者、
判断時刻、拒否結果を確認できる必要がある。「送金なし」だけでは、
提案がなかったのか、拒否されたのか、Toolが失敗したのか分からない。

承認者Identityは、Agentの文章や請求書の記載ではなく、承認を受け付けた
信頼できる仕組みから得る。人の承認がない自動判断なら、存在しない人を
「承認者」として記録せず、承認者なしであることと判断したPolicy等を
区別して残す。複数の記録へ分けてもよいが、同じ操作について提案、判断、
実行結果を結び付けて再構成できなければならない。

## Security objective

重要な自律操作について、承認の迂回、引数の差し替え、失敗や拒否の
隠蔽を後から調べられるようにする。このControlは記録の保証であり、
承認前の実行を技術的に止める保証そのものではない。

## Applicability

Agentが自発的に資金移動、外部送信、権限変更、データ削除などSecurity上
重要な操作を提案・実行し得る機能に適用する。実際に実行された操作だけ
でなく、対象操作の承認・拒否・取消し・Timeoutの判断も調べる。どの操作が
重要かは、資産、権限、外部への副作用、回復困難さに基づいて定義する。

### Non-applicability

自律的にSecurity上重要な操作を起こす能力も経路もない機能は対象外と
できる。今は承認されなかった、実行に至らなかった、または担当者が
別の画面で結果を知っているという理由で、対象の提案や判断を除外しない。

## Scope and assumptions

- 「Security上重要な操作」を先に特定する。Tool名だけでなく引数や対象に
  よって影響が変わる場合は、その違いを分類へ反映する。
- 時刻は判断・操作を行った信頼できるComponentで付ける。Agentが生成した
  自由文の時刻や承認者名だけでは監査の根拠にならない。
- 操作の引数は、何を承認・拒否・実行したかを再構成できる粒度で扱う。
  Secretや個人情報を広い閲覧権限のLogへ全文保存する必要はない。保護された
  別保管先を使う場合は、その参照と完全性を維持する。
- 人の承認を求めない操作では、承認者がいない事実と、自動判断に使った
  信頼できるPolicyの識別情報を残す。人の承認が必要かはC9.2で別に確認する。
- 一つのLog Eventに全項目を詰める必要はない。ただし別々のEventが操作単位
  で結び付き、欠落や取り違えが分かる必要がある。

## Assets, actors, identities, and trust boundaries

守る対象は操作先の資金・データ・権限と、承認・実行を調査するための証拠。
Agent、起動を管理する仕組み、承認者、承認Service、実行Tool、監査記録の
保管者が関わる。攻撃者は請求書やTool応答を通じて危険な操作を提案させ、
またはAgentの自己申告へ偽の承認者・引数を書かせる可能性がある。

境界は、Agentの提案から信頼できる承認判断へ、承認判断から実行Toolへ、
各地点から監査記録へ渡すところにある。Agentだけが書けるLogにある
「承認済み」を、承認Service自身の記録と同一視しない。

## Required security properties

| ID | 必要な性質と確かめ方 |
|---|---|
| SP-1 | 対象の自律的な重要操作について、提案または実行された操作とその時刻を監査記録から特定できる。 |
| SP-2 | 誰が、またはどの信頼できる自動判断が、何を承認・拒否・取消し・Timeoutとしたかを、判断時刻とともに確認できる。 |
| SP-3 | 承認・判断の対象となった引数と、実行に渡された引数・結果を、同じ操作として結び付けて比較できる。 |
| SP-4 | 対象経路で拒否や失敗を含む記録の欠落を見つけられ、記録の取得・閲覧がSecurity上必要な範囲で維持される。 |

## Scope calibration and adjacent assurance

| 観測 | 本Controlでの扱い |
|---|---|
| 送金を拒否したが、Logは「送金なし」だけ | Fail。提案、承認者、引数、拒否結果を再構成できない。 |
| 承認Serviceの記録に担当者と判断時刻があり、実行側の記録と同じ操作へ辿れる | Pass候補。別Eventでも必要な項目を結び付けられる。 |
| Agentが出力した承認者名だけをLogへ保存する | Fail。信頼できる承認者Identityの根拠がない。 |
| 正しく記録できるが、未承認でも送金APIを実行できる | 本Controlの記録とは別に、C9.2の承認GateがFail。全体として安全ではない。 |
| 実行は拒否されるが、承認判断の記録がない | C9.2がPass候補でも、本ControlはFail。 |
| 機密の引数をLog本文から隠し、権限制限された保管先へ確実に辿れる | 必要な操作内容を再構成できればPass候補。単に引数を消しただけならFail。 |
| 緊急停止の発動だけが記録されない | 停止・Overrideの記録はC12.4.3で別に評価する。 |

## Threat and failure-mode rationale

拒否された送金提案や承認Timeoutが記録されなければ、攻撃者による試行と
正常な「操作なし」を区別できない。承認者名をAgentに書かせると、偽装や
誤帰属を招く。提案時と実行時の引数を照合できなければ、別の送金先への
差し替えも調査しにくい。Researchは監査記録と実行境界の結合を強調するが、
Hash方式や特定の独立Log製品まで本要件の唯一の実装とはしない。
外部の脅威IDとの厳密な対応付けはまだ評価していない。

## Verification

### Architecture and configuration review

Security上重要な操作の分類と、Schedule、外部Event、他Agentからの依頼、
再試行などの経路を確認する。提案、承認・拒否・Timeout、Tool呼出し、
実行結果をどのComponentが記録し、どの識別子で結び付けるかを追う。
承認者Identityと時刻の出所、引数を隠す場合の保管先、記録の欠落・改ざんを
どう発見するかも確認する。Agentの自由文と実行側の記録を区別する。

### Positive verification

模擬送金をAgentに提案させ、人が内容を確認して承認する。監査記録から
提案された送金先・金額、承認者、判断時刻、承認結果、実行側に渡った
引数と実行結果を一つの操作として再構成する。次に同じ種類の提案を
拒否し、未実行と拒否判断を区別できることを確かめる。実際の送金や
顧客情報は使わない。

### Negative and abuse-case verification

| ID | 試すこと | 期待する確認結果 |
|---|---|---|
| N-1 | Agentの提案を人が拒否する | 拒否した信頼できる承認者、時刻、対象引数、拒否結果を再構成できる。SP-1〜SP-3。 |
| N-2 | 承認待ちをTimeoutまたは取消しにする | 成功した実行と区別し、判断の経緯と未実行を辿れる。SP-2、SP-3。 |
| N-3 | Agentの文面に偽の承認者名や「承認済み」を入れる | 承認者は承認ServiceのIdentityと照合され、自己申告を根拠にしない。SP-2。 |
| N-4 | 承認画面の送金先と、Toolへ渡す送金先を変える | 記録上、承認対象と実行引数の差を検出できる。実行を防ぐ保証は別に評価する。SP-3。 |
| N-5 | Tool実行を失敗させる、または別経路から対象操作を呼ぶ | 成功Eventだけでなく、失敗・別経路の対象操作も記録される。SP-1、SP-4。 |
| N-6 | 監査記録の保管先を一時的に使えなくする | 対象操作の記録を失ったまま成功扱いにしない。持続的な保留・再送等でもよい。SP-4。 |
| N-7 | 人の承認を要しない自動判断を行う | 架空の承認者を作らず、承認者なしと判断したPolicy等を区別して残す。SP-2。 |

### Failure conditions

対象操作の提案・実行を辿れない、承認者・時刻・引数・判断結果のいずれかが
確認できない、Agentの自己申告しかない、拒否や失敗の記録を欠く、または
分散した記録を同じ操作へ結び付けられない場合はFail。監査記録の障害で
実行済み操作の記録が失われる場合もFail。単一の製品やEvent形式を使わない
こと、全Agentの自由形式の思考過程を保存しないことだけではFailとしない。

## Evidence expectations

| 証拠 | 作成元 | 対象 | 確認する時期 | 保護上の注意 | 合格の目安 |
|---|---|---|---|---|---|
| 対象操作と記録設計 | 業務・Security・AI機能の担当者 | 重要操作、各起動経路、各Eventの結合 | 操作・経路の追加や変更時 | 内部の権限構成を限定公開 | 承認者、時刻、引数、判断結果の信頼できる出所が分かる。 |
| 承認・実行の合成Trace | 承認Service・Tool・監査基盤 | 承認、拒否、取消し、Timeout、失敗 | Release時・記録経路変更時 | 模擬引数を使用し、実データを残さない | 判断と実行を同じ操作へ辿り、引数を比較できる。 |
| 欠落・改ざん耐性の確認 | 監査基盤・試験担当者 | N-3〜N-6 | Log基盤や連携方式の変更時 | 閲覧権限を絞り、必要以上に本文を保存しない | 自己申告やLog障害で記録の欠落を隠せない。 |

## Known limitations and uncertainty

監査記録があっても危険な操作の実行は止まらない。記録の改ざんや時刻の
ずれ、分散System間の相関失敗、Logに保存した機密引数の漏えいが残る。
保存範囲と調査可能性には両立の難しさがあり、単なるHashだけでは操作内容を
再構成できない場合がある。`verifiable`は本書の成熟度であり、実製品の
適合結果ではない。
