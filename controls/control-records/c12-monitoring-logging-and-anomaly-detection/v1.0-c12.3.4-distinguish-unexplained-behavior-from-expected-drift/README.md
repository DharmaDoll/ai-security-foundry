# 説明できない振る舞いの変化を、想定内の変化と分ける

AISVS Verification Level: 3

学習資料：[C12.3 入力と出力の変化](../../../learning/c12-monitoring-logging-and-anomaly-detection/v1.0-c12.3-model-data-and-performance-drift-detection.md)

## Upstream basis

AISVS `v1.0-C12.3.4`は、説明できないAI Systemの振る舞いの変化を、
緩やかで想定内の運用上の変化と区別できることを求める。変化の検知だけでも、
すべての変化を攻撃と呼ぶことでもない。

対応するAISVS Researchは、観測した変化をDeployment、Prompt、検索Data、
Providerの経路、Feature Flag、Policy、季節性などの変更・運用情報と
照らし合わせる方法を示す。これは原因を調べる例であり、特定の製品、
変化点検出Algorithm、固定の記録項目を正規要件に追加するものではない。

## Interpretation

まず、どの振る舞いが、いつ、どの利用者・用途・質問群で、どの程度変わったか
を明らかにする。次に、変更履歴や業務上の変動を原因候補として照合し、
観測した方向・範囲・大きさまで説明できるか確かめる。説明できれば
「想定内の変化」と判断する根拠を残す。説明できなければ、変更記録が同じ
時期にあっても「説明不能」として調査を続ける。

例えば社内RAGで、誤答の疑いがある回答の割合が5％から15％へ上がった。
同じ週に文書Indexの更新と採用シーズンの質問増加があったとしても、
それだけでは想定内とは言えない。質問の種類ごとの割合、取得文書の版、
検査器の版などを比べる。同じ種類の質問では回答品質が安定し、質問の構成の
変化で全体の割合を説明できるなら、想定内の候補になる。特定Topicだけが
急に悪化し、更新内容でも説明できないなら、調査対象のまま残す。

「急変＝説明不能」「緩やか＝想定内」という分類ではない。予定された切替えで
急に変わることも、汚染が少しずつ進むこともある。ここでの「説明」は、
変化の原因を示す検証可能な証拠に基づく判断であり、単なる命名ではない。

## Security objective

モデル、検索資料、設定、利用状況などに起きた予期しない変化を、正常な
運用変動に紛れ込ませない。同時に、根拠のある想定内の変化を一律に事故と
扱わず、調査の優先順位を付けられるようにする。この区別だけで攻撃の
有無を確定することはできない。

## Applicability

運用中のAI機能について、入力や出力、行動、品質の変化を観測する場合に
適用する。RAGの回答、AgentのTool選択、拒否率、失敗率など、用途に応じた
振る舞いを対象とする。変化を測る仕組みの精度は別に確認する。

### Non-applicability

観測対象となるAI機能が運用されていない場合は対象外とできる。変更履歴が
存在しない、Providerの内部変更が見えない、または現時点で原因が分からない
ことは対象外の理由ではない。説明不能として扱い、分かる範囲を記録する。

## Scope and assumptions

- 比較する期間と利用範囲を明確にする。利用者層や質問の種類が違う集団を
  混ぜると、変化の原因を誤認しやすい。
- 検査器、抽出方法、Model、Prompt、Indexなど、測定値やAIの振る舞いを
  変え得る要素の版・変更時期を、確認可能な範囲で追う。
- 変更履歴は原因の候補である。対象の場所、変化の方向と大きさが合うかを
  独立した観測結果と照らし合わせる。
- 自動処理で時刻・版・対象範囲を突き合わせてもよいが、相関だけで因果関係
  や安全性を証明したことにはならない。説明が足りなければ未解決とする。

## Assets, actors, identities, and trust boundaries

守る対象はAI機能の安全性と品質、それに頼る利用者と後続の処理、調査の
判断である。運用担当者、変更の担当者、監視・評価の担当者が関わる。
攻撃者は検索文書や質問を汚染することがあり、正規の運用変更も同様に
観測値を動かし得る。

主な境界は、AI Systemの実際の振る舞いから監視指標へ、その指標と変更履歴
から「想定内／説明不能」の運用判断へ渡す地点である。AI自身の説明や、
単独の変更記録を、確認済みの原因として扱わない。

## Required security properties

| ID | 必要な性質と確かめ方 |
|---|---|
| SP-1 | 変化を時期、対象範囲、方向、大きさとともに把握し、同じ条件で比較できる。 |
| SP-2 | 想定内と判断するときは、変更や業務上の変動が観測結果をどう説明するか、裏付けとともに示せる。 |
| SP-3 | 説明が足りない変化を自動的に正常扱いせず、未解決として識別・調査できる。 |
| SP-4 | 測定方法や検査器の変更による見かけの差を、AIの振る舞いの変化から区別できる。 |

## Scope calibration and adjacent assurance

| 観測 | 本Controlでの扱い |
|---|---|
| 回答のFlag率が上がり、同じ週にIndex更新があったので調査せずCloseする | Fail。時期の一致だけでは原因を説明していない。 |
| 予定された更新で急に振る舞いが変わり、対象Topic・方向・大きさが試験結果と合う | 想定内の候補。急変というだけで説明不能とはしない。 |
| 数週かけて特定の文書群だけ回答が悪化する | 緩やかでも、根拠がなければ説明不能として扱う。 |
| 検査器を厳しくした後にFlag率だけ上がり、同じ回答の再評価では品質が変わらない | 測定方法の変更として区別する。AIの劣化と即断しない。 |
| Provider側の変更内容が非公開で原因を確かめられない | 未解決と記録する。変更があり得るという推測だけで想定内とはしない。 |

C12.3.1は入力分布の変化、C12.3.2は個々の誤答の疑い、C12.3.3はその
割合の時系列を扱う。本Controlは、それらを含む観測結果の**説明可能性**を
評価する。C12.2の不審な利用者行動の検知や、障害対応の完了判定とは別である。

## Threat and failure-mode rationale

検索資料の汚染、意図しない設定変更、Provider側の予期しない変更、
攻撃による振る舞いの変化を「いつもの揺れ」と誤分類すると調査が遅れる。
反対に正常な季節性を攻撃と断定すれば、不要な対応が増える。Researchは
急な変化だけを見る方法では緩やかな攻撃を見落とし得ると注意している。
外部の脅威IDとの厳密な対応付けはまだ評価していない。

## Verification

### Architecture and configuration review

監視する振る舞い、比較対象、変更・運用情報の取得元、分類の判断基準、
説明できない変化の扱いを確認する。変更履歴と指標を結び付ける時刻や
対象範囲が合うか、利用者層やTopicなどの重要な一部を調べられるかも見る。
特定の変化点検出方式、Dashboard、Alert製品を必須とはしない。

### Positive verification

合成したRAG運用の二つの期間を用意する。採用シーズンに質問の構成が
変わったが、同種質問の品質は維持されている例と、文書更新後に特定Topicの
品質だけが悪化し、更新内容では説明できない例を比べる。前者には
比較結果と根拠を残して想定内と判断し、後者は説明不能として対象範囲を
明らかにして調査へ渡せるか確かめる。

### Negative and abuse-case verification

| ID | 試すこと | 期待する確認結果 |
|---|---|---|
| N-1 | 急な変化を作り、対応する変更・運用上の説明を用意しない | 説明不能と識別し、単なる正常な揺れとしてCloseしない。SP-1、SP-3。 |
| N-2 | 同時期のIndex更新記録を加えるが、悪化したTopicや変化の大きさは更新内容と合わない | 時期の一致だけで想定内にせず、食い違いを調べる。SP-2、SP-3。 |
| N-3 | 既知の季節性で質問構成が変わり、同種質問の品質は安定している | 比較可能な範囲で根拠を示し、想定内と判断できる。SP-1、SP-2。 |
| N-4 | 特定Topicを少しずつ汚染し、全体の変化は緩やかにする | 遅い変化というだけで想定内にせず、対象範囲の悪化を調べる。SP-1、SP-3。 |
| N-5 | 検査器の版だけを変えてFlag率の見かけ上の急増を作る | 測定条件の変更とAIの振る舞いの変化を分ける。SP-4。 |
| N-6 | Provider側の状態が不透明で原因を確認できない変化を作る | 可能性を仮説として記録し、確認できない間は未解決に残す。SP-2、SP-3。 |

### Failure conditions

変化の検知だけで分類しない、時期が近い変更記録だけで正常と決める、
説明できない変化を未解決として追えない、または測定方法の切替えを隠して
AIの変化とみなす場合はFail。すべての変化の原因を直ちに特定できない
ことや、特定の監視製品を使わないことだけではFailとしない。

## Evidence expectations

| 証拠 | 作成元 | 対象 | 確認する時期 | 保護上の注意 | 合格の目安 |
|---|---|---|---|---|---|
| 監視と分類の手順 | AI機能・運用の担当者 | 対象指標、比較範囲、判断と未解決の扱い | 運用開始・重要な変更時 | 実際の機密回答を例示しない | 何を根拠に想定内とし、何を調査へ残すか説明できる。 |
| 変更・比較の記録 | 変更担当者と監視担当者 | 変化の時期・範囲、変更候補、裏付け、未解決の理由 | 変化の調査時 | 文書本文や利用者情報への閲覧権限を絞る | 変更の存在だけでなく、観測結果との一致・不一致を示せる。 |
| 合成した分類試験 | 試験担当者 | N-1〜N-6と判断結果 | 監視や分類方法の変更時 | 合成した質問・回答を使う | 想定内と説明不能、測定方法の変更を取り違えない。 |

## Known limitations and uncertainty

観測する指標が足りない場合、実際の変化を見逃し得る。Provider側の非公開の
変更、少ない標本、複数の変更が重なる期間では、原因を確定できないことが
ある。説明が付いても安全性や回答の正しさを証明したことにはならない。
`verifiable`は本書の成熟度であり、実製品の適合結果ではない。
