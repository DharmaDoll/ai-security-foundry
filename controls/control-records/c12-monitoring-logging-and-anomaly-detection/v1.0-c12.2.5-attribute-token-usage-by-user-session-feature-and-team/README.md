# AIのトークン使用量を利用者・会話・機能・組織へ結び付ける

AISVS Verification Level: 2

学習資料：[C12.2 検知と通知](../../../learning/c12-monitoring-logging-and-anomaly-detection/v1.0-c12.2-detection-and-alerting.md)

## Upstream basis

AISVS `v1.0-C12.2.5`は、AIのトークン使用量を、利用者、セッション、
機能のエンドポイント、チームまたはワークスペースごとに追えることを求める。
ここでの「トークン」はAIが処理する文章等の量を数える単位であり、ログイン用の
認証トークンとは別物である。「機能のエンドポイント」は、例えば文書検索や
要約など、呼出し元の機能を区別する入口を指す。

対応するAISVS Researchは、費用の急増や大量の質問によるモデル抽出を想定し、
二つの組織にまたがる集計試験を提案する。しきい値による通知や予算上限も
提案するが、正規要件の本文はそれらを必須とはしていない。

## Interpretation

AIへの各呼出しで消費した量を、信頼できる実行情報に基づき四つの切り口へ
結び付けて記録・集計する。後から「誰が、どの会話で、どの機能を使い、
どのチームまたはワークスペースの利用として消費したか」を調べられる状態にする。
四つの切り口は一回の処理について対応が保たれ、別人や別組織の消費と混ざらない。

例えば同じ利用者が「文書検索」と「要約」を別の会話で使った場合、全体の
合計だけでなく、それぞれの会話・機能の量を取り出せる必要がある。
利用者が複数のチームに所属するなら、所属一覧から推測するのではなく、
その呼出しが実際にどのチームの仕事だったかを信頼できる情報で決める。

## Security objective

消費の急増や大量の質問が起きたとき、影響した主体・機能・組織を調べられる
ようにする。また、誤った帰属によって他組織の利用量を混ぜたり、責任のない
利用者に費用や疑いを押し付けたりしない。

## Applicability

AI推論でトークンを消費する機能に適用する。直接のチャット、RAG、Agentが
内部で繰り返すモデル呼出し、再試行など、利用量に含める経路を確認する。
人が直接操作しない定期処理なら、実際のサービス主体と処理単位を明示し、
存在しない人間の利用者や会話を捏造しない。

### Non-applicability

対象の機能がAI推論を行わず、トークンを消費しない場合には適用しない。
外部のAI提供者が計数する場合や、チームが一つだけの場合も、それだけで
対象外にはしない。四つの切り口のうち意味を持たないものがある構成は、
その理由と代わりに識別できる実行単位を明示して評価する。

## Scope and assumptions

- 使用量は実際に消費した推論量を基準にする。入力・出力の別や提供者ごとの
  計数方法が異なる場合は、集計の意味を定義する。推定値しかない場合は
  実測値と区別する。
- セッションは一回の会話や処理を追う単位である。モデル呼出しを繰り返す
  Agentや再試行でも、元の処理との関係を失わない。
- `team or workspace`は少なくともどちらかの組織単位を指す。両方の分類を
  一律には要求しない。
- 応答が中断されて提供者の使用量を取得できない場合、未知を`0`として
  扱わない。未取得分がどの程度あるかも分かるようにする。
- 利用者・組織・機能の値は、認証や信頼できるアプリの経路から得る。
  プロンプト本文、モデル出力、利用者が自由に書ける欄だけを正本にしない。

## Assets, actors, identities, and trust boundaries

守る対象は利用量の正しい帰属と、そこから分かる利用者・組織の活動情報。
利用者、アプリ、Agent、推論を仲介する処理、AI提供者、集計基盤、調査担当者
が関わる。主な境界は、認証済みの呼出し元から推論処理、提供者の計数結果から
利用量の記録、記録から組織別の集計・表示である。

## Required security properties

| ID | 必要な性質と確かめ方 |
|---|---|
| SP-1 | 対象のトークン消費を、利用者、セッション、機能のエンドポイント、チームまたはワークスペースの各切り口で取り出せる。 |
| SP-2 | 帰属先は実際の呼出し元・処理経路と対応し、入力者やモデルが書いた偽の識別子で置き換わらない。 |
| SP-3 | 再試行や内部の追加呼出しを含め、既知の使用量は重複・取りこぼしなく集計され、未取得分は明示される。 |
| SP-4 | 異なる利用者、会話、機能、組織の使用量が混ざらず、各切り口から同じ対象範囲の消費を説明できる。 |

## Scope calibration and adjacent assurance

| 観測 | 本Controlでの扱い |
|---|---|
| 組織全体の合計だけが分かり、誰のどの会話・機能か分からない | Fail。四つの切り口を満たさない。 |
| 利用者別・組織別の数字はあるが、会話別と機能別に分けられない | Fail。集計軸が不足する。 |
| 四つの切り口で実際の消費を辿れ、合計も整合する | Pass候補。自動通知や上限設定の有無とは分ける。 |
| 値は揃うが、プロンプトに書いた別人の名前で帰属が変わる | Fail。帰属を信頼できない。 |
| 四つの切り口は追えるが、急増の通知がない | 本要件の帰属追跡とは別に、検知・運用上の不足として評価する。 |
| 別組織の担当者が利用量画面を読める | 帰属の正確さと、画面の閲覧権限は別の保証。情報漏えいとして報告する。 |

## Threat and failure-mode rationale

攻撃者や誤動作したAgentが大量の質問を送ると、推論費用が急増し、モデルの
振る舞いを写し取る試行にもなり得る。合計量しか分からなければ、対象の
利用者・会話・機能を絞って調査しにくい。逆に帰属を誤ると、別の組織の
利用が混ざり、対応先を間違える。大量消費そのものは攻撃の証拠ではなく、
本Controlは攻撃の検知や費用上限を直接保証しない。外部の脅威IDとの
厳密な対応付けはまだ評価していない。

## Verification

### Architecture and configuration review

全ての推論経路、呼出し元の識別方法、セッションの引継ぎ、機能名の決め方、
組織単位の選び方、提供者の使用量を受け取る地点、集計への経路を確認する。
再試行・Agentの追加呼出し・中断時の計数方法と、実測不能な場合の扱いも
確認する。特定の監視製品やしきい値を必須にしない。

### Positive verification

同じワークスペースの二人が複数の会話・機能を使い、別ワークスペースの
一人も利用する合成試験を行う。各呼出しの既知の使用量が、正しい四つの
切り口へ入り、合計と内訳が一致するか確かめる。Agentの追加呼出しと
再試行も含め、元の処理に結び付くかを確認する。

### Negative and abuse-case verification

| ID | 試すこと | 期待する確認結果 |
|---|---|---|
| N-1 | 会話IDまたは機能名を記録しない経路を作る | 欠落が分かり、四つの切り口の追跡に合格しない。SP-1。 |
| N-2 | 質問本文へ別人・別組織の識別子を書く | 帰属先は変わらず、信頼できる実行情報が使われる。SP-2。 |
| N-3 | Agentの追加呼出し、再試行、二重送信を起こす | 実際に発生した消費を取り込み、同じ計数結果を二度足さない。SP-3。 |
| N-4 | 提供者の応答を中断させ、使用量の戻り値を欠落させる | 未取得を明示し、実測`0`と取り違えない。SP-3。 |
| N-5 | 二つのワークスペースで同時に利用する | 各組織の値が混ざらず、内訳と合計が対応する。SP-4。 |
| N-6 | 別組織の役割で使用量画面・集計APIを見る | 閲覧制限は別の保証として検査し、漏えいがあれば報告する。 |

### Failure conditions

対象の推論経路で四つの切り口のいずれかが失われる、別の主体・機能・組織へ
誤って帰属する、既知の消費を重複または欠落させる場合はFail。未知の量を
`0`へ置き換えて正確な合計と見せることもFail。予算上限、急増の通知、
特定の製品がないことだけを本ControlのFailとはしない。

## Evidence expectations

| 証拠 | 作成元 | 対象 | 確認する時期 | 保護上の注意 | 合格の目安 |
|---|---|---|---|---|---|
| 帰属と計数の設計 | アプリ・推論・監視の担当者 | 全推論経路、四つの切り口、使用量の取得元 | 経路・提供者・組織モデルの変更時 | 実利用者名や秘密を載せない | 各値の決定元と未取得時の扱いを説明できる。 |
| 合成実行と集計の照合結果 | 試験担当者 | 二組織、複数利用者・会話・機能、再試行 | リリース時・計数処理の変更時 | 合成IDと無害な質問を使用 | 既知の消費が各切り口で正しく集計される。 |
| 欠落・偽装・中断の試験 | 試験担当者 | N-1〜N-5 | 経路・集計処理の変更時 | 利用状況の閲覧範囲を制限 | 不明値を隠さず、偽の識別子や別組織の値が混ざらない。 |

## Known limitations and uncertainty

提供者や推論方式によってトークンの数え方、使用量が返る時点、中断時の
測定可能性が異なる。合計が正しくても費用計算と一致するとは限らない。
大量消費は正規業務でも起こり、計数だけで攻撃や抽出を判定できない。
帰属情報は利用状況を示すため、閲覧制限や保存期間の設計が別に必要。
`verifiable`は本書の成熟度であり、実製品の適合結果ではない。
