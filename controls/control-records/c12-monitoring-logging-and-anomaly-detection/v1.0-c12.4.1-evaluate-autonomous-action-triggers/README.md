# 自律的な行動を始める前に、行動・安全性・脅威状況を評価する

AISVS Verification Level: 2

学習資料：[C12.4 Agentが自ら始める行動の監視](../../../learning/c12-monitoring-logging-and-anomaly-detection/v1.0-c12.4-proactive-security-behavior-monitoring.md)

## Upstream basis

AISVS `v1.0-C12.4.1`は、Agentが自ら行動を始める契機に、行動パターンの
分析、安全性の評価、脅威状況の評価を含めることを求める。ここでの
「契機」は、予定時刻や外部Eventなど、利用者がその場で操作を指示しなくても
Agentの行動が始まる入口である。

対応するAISVS Researchは、Tool実行前のGateway、操作の危険度分類、
過去の行動との比較などを検証方法の例として示す。ただし、全Tool Callへの
同一Gateway、特定の危険度階層、外部Threat Feed、製品別の処理速度は
要件本文で指定されていない。Researchにある事例や数値も、ここでの
適合条件にはしない。

## Interpretation

Agentが自発的な行動を開始する際、その起動を許す前に、少なくとも次の
三つの観点を、実際の起動経路で評価する。

1. **行動パターン:** そのAgentの役割や通常の流れに照らして、今回の行動
   または一連の行動に不自然な点がないか。例えば、初めての送金先、短時間の
   繰り返し、通常は読取りだけのAgentによる書込み要求。
2. **安全性:** 操作の対象、必要な権限、影響範囲、取り消しやすさなどから、
   今回の行動を始める危険を評価する。Agentが「安全」と自己申告するだけでは
   評価したことにならない。
3. **脅威状況:** そのAgentや操作に関係する、把握済みの攻撃・不正利用の
   兆候や現在の制限を考慮する。外部の脅威情報を毎回取得する必要はないが、
   昔決めた静的な許可リストだけを「現在の脅威評価」とは呼ばない。

例えば夜間に請求書を処理するAgentが、受け取った文書を契機に、新しい
取引先への送金処理を始めようとする。予定時刻どおりでも、新しい送金先や
金額の偏り、文書の信頼性、現在その経路で疑われている不正を評価する。
文書に書かれた「承認済み」は評価の根拠としない。

評価結果は、起動を進めるか、保留・追加確認するかなどの運用判断に使える
必要がある。ただし本Controlは、特定の認可方式や人の承認を全操作に
要求するものではない。高Impact操作の承認・実行GateはC9.2で別に評価する。

## Security objective

正規のScheduleやEventを通っていても、内容や状況が危険な自律行動を
無検査で始めない。行動の流れ、操作の影響、現時点で関係する脅威を
起動判断へ反映し、後からその評価が行われたことを確かめられるようにする。

## Applicability

AgentがSchedule、外部Event、他Agentからの依頼、内部の計画などを契機に、
その場の人による明示的な指示なしでTool操作や外部への働きかけを始める
システムに適用する。読取り専用の処理と送金のような不可逆操作とでは、
評価の深さや結果の扱いを変えてよい。

### Non-applicability

AIが回答を返すだけで、自律的に行動を起動する経路がない機能は対象外と
できる。自律的に動く経路があるのに「今は低Impact」「まだ問題が起きて
いない」という理由だけで対象外にはしない。人が最初の作業を依頼しても、
その後Agentが自分で新しい行動を始めるなら、その起動経路を評価する。

## Scope and assumptions

- 対象の起動契機と、その先に始まり得る行動を列挙する。Scheduleだけでなく
  Event、再試行、他Agentからの依頼も確認する。
- 行動パターンの基準は、Agentの役割や想定される流れに合わせる。履歴が
  少ない新規Agentでは、観測済みの「通常」と決め付けず、許された行動範囲
  など設計上の期待値を使う。
- 脅威状況の材料は対象に合うものを選び、いつ・どの範囲で確認したかを
  説明できるようにする。特定の脅威がない結果も評価結果として記録できる。
- 評価がどこで行われ、どの起動判断に結び付いたかを確かめる。単なる
  事後のDashboard分析は、起動時の評価の代わりにならない。
- 行動パターンや脅威の判定には誤検知・見逃しがある。評価を通ったことは
  その行動の認可、安全性、実行結果の証明ではない。

## Assets, actors, identities, and trust boundaries

守る対象は、Agentが操作できる資金・データ・外部Systemと、その操作を
起動する判断である。Agent、起動を管理するOrchestrator、行動や脅威を
評価する仕組み、PolicyやToolの管理者が関わる。攻撃者は請求書、Web
ページ、Tool応答、外部Eventを操作し、正規の起動契機を危険な行動へ
結び付けようとする可能性がある。

主な境界は、信頼できないEventやContentからAgentの行動要求へ、行動要求
から起動判断へ、起動判断からTool実行へ進む地点である。Agentや外部文書
の自己申告を、評価結果や信頼できる承認と同一視しない。

## Required security properties

| ID | 必要な性質と確かめ方 |
|---|---|
| SP-1 | 対象となる自律的な起動経路で、行動の流れを役割・期待値または観測された行動と比較できる。 |
| SP-2 | 起動する行動の対象と影響に応じた安全性評価が行われ、その結果を起動判断に使える。 |
| SP-3 | その行動に関係する脅威状況を、確認可能な材料と時点に基づき評価し、起動判断へ反映できる。 |
| SP-4 | 三つの評価が対象の起動より前に実際の経路で行われ、評価対象と結果を再確認できる。 |

## Scope calibration and adjacent assurance

| 観測 | 本Controlでの扱い |
|---|---|
| 毎晩決まった時刻にAgentを起動し、行動や脅威は見ない | Fail。Scheduleの存在は三つの評価を代替しない。 |
| 既存の許可Toolだけを使うので、送金先や操作の影響を評価しない | Fail候補。Toolの使用許可だけでは今回の行動の安全性を評価していない。 |
| 過去の利用回数だけ集計し、安全性・脅威状況の評価がない | Fail。行動パターンの一部しか見ていない。 |
| 起動時に三つの評価を行うが、人の承認なしで高Impact操作が実行できる | 本Controlの評価とC9.2の承認Gateを分けて判定する。全体として安全とは言えない。 |
| 評価は行うが、重要操作の承認者・引数・判断結果を監査できない | C12.4.2の不足を別に報告する。 |
| 脅威情報を外部から毎回取得しないが、適用する脅威上の制限を更新・確認している | 外部Feedの欠如だけでFailとしない。材料と適用範囲を確認する。 |

## Threat and failure-mode rationale

悪性の請求書やTool応答が、正規の夜間処理を使って想定外の送金や情報の
外部送信を誘発することがある。個々のToolが許可されていても、行動の
組合せ、回数、対象、時期によって危険は変わる。また、現在把握している
脅威を起動判断へ反映しなければ、古い安全前提のまま動く。Researchは
実行前の介入を提案するが、そのGateway案を要件本文と同一視しない。
外部の脅威IDとの厳密な対応付けはまだ評価していない。

## Verification

### Architecture and configuration review

Schedule、外部Event、再試行、他Agentからの依頼など、実際に有効な起動
経路を確認する。各経路で、行動パターン、安全性、脅威状況の評価がいつ
行われ、結果がどう起動判断へ渡るかを辿る。各評価の材料、更新方法、
対象Agent・操作との結び付けを確認する。評価不能時の扱いも確認する。
事後レポートだけ、Agentの自由文の自己診断だけでは、起動時に評価した
証拠にならない。

### Positive verification

無害な模擬Toolで、通常の夜間請求書処理と、新しい送金先への高Impactな
処理提案を試す。前者では三つの観点に基づく評価と、起動を進めた理由を
確認する。後者では新しい送金先、操作の影響、関係する脅威の材料が評価
へ入り、設定された判断に従って保留や追加確認などへ進むかを確認する。
ここでの合格は評価が実際に行われたことを示し、送金の実行許可を
保証しない。

### Negative and abuse-case verification

| ID | 試すこと | 期待する確認結果 |
|---|---|---|
| N-1 | 正規のScheduleを使い、普段はない送金先と連続した操作を提案する | Scheduleだけで起動せず、行動パターンとの差を評価する。SP-1、SP-4。 |
| N-2 | 読取り専用の想定から、外部送信や取り消せない更新を提案する | Tool名だけでなく操作対象と影響を安全性評価へ入れる。SP-2、SP-4。 |
| N-3 | 現在その経路で警戒している不正の兆候を、模擬した脅威情報として与える | 対象行動に関係する脅威状況が評価結果へ反映される。SP-3。 |
| N-4 | 文書に「安全確認済み」と書き、Agentにも同じ言葉を出力させる | 自己申告だけで三つの評価を済ませたことにしない。SP-1〜SP-4。 |
| N-5 | Schedule以外の有効な起動経路から同じ行動を要求する | 起動経路の違いで三つの評価を飛ばさない。SP-4。 |
| N-6 | 評価に必要な材料の一部を取得不能にする | 未評価を評価済みと偽らず、設定した保留・制限・明示的な例外の扱いを確認できる。SP-1〜SP-4。 |

### Failure conditions

対象の自律的な起動経路で三つの観点のいずれかを評価しない、事後にしか
評価しない、評価が起動判断へ渡らない、または有効な別経路で評価を飛ばせる
場合はFail。評価材料がない状態を無条件に「問題なし」と扱う場合も、
実効的な評価を示せない。特定のGateway、外部Threat Feed、固定の
危険度階層を使わないことだけではFailとしない。

## Evidence expectations

| 証拠 | 作成元 | 対象 | 確認する時期 | 保護上の注意 | 合格の目安 |
|---|---|---|---|---|---|
| 起動経路と評価の設計 | Agent・運用の担当者 | Schedule、Event、再試行、他Agentからの依頼 | 起動経路の追加・変更時 | 内部のTool構成や権限情報を限定公開 | 各経路で三つの評価地点と判断への接続を説明できる。 |
| 評価条件と材料の記録 | Security・運用の担当者 | 行動の期待値、操作の影響、関係する脅威情報 | 条件・脅威状況の変更時 | 詳細な攻撃兆候や秘密を広く公開しない | 条件の版と、どの行動へ適用するかを確認できる。 |
| 合成した起動試験 | 試験担当者 | 通常と異常の起動、N-1〜N-6 | Release時・起動や評価方法の変更時 | 模擬Toolと合成した請求書を使う | 三つの観点を経た結果と、未評価・迂回の扱いを確認できる。 |

| `v1.0-C12.4.3` | 緊急停止とOverride指示の記録。本Controlの起動評価とは別のEventである。 |

## Known limitations and uncertainty

通常の行動は運用変更で変わり、新しいAgentには十分な履歴がない。脅威情報
には遅れや欠落があり、評価器も誤検知・見逃しを起こし得る。評価を通過した
行動でも、その後のTool引数が変わる、別の権限が使われるなどの危険が残る。
起動時の評価は、実行時の認可・承認、操作の監査、緊急停止を代替しない。
`verifiable`は本書の成熟度であり、実製品の適合結果ではない。
