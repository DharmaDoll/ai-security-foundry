# AI特有の攻撃を個別のルールで見つける

AISVS Verification Level: 2

学習資料：[C12.2 検知と通知](../../../learning/c12-monitoring-logging-and-anomaly-detection/v1.0-c12.2-detection-and-alerting.md)

## Upstream basis

AISVS `v1.0-C12.2.3`は、協調した脱獄（Jailbreak）の試行、Prompt Injection、
内部指示（System Prompt）を引き出す試行について、AI特有の攻撃の形を
個別に定めたルールで検知できることを求める。ここでいう「脱獄」はAIの
安全上の制限を回避させる試みであり、「協調」は複数の利用者や会話に
試行を分ける場合などを含む。

対応するAISVS Researchは、単発の質問だけでなく、利用者や会話をまたぐ
行動、Agentの操作記録も検知材料になり得ると説明する。一方、Researchに
列挙された製品、特定の脅威分類、検知率や具体的なルール例は、要件本文の
必須条件ではない。内部指示の引き出しと、AIモデルの動きを大量の質問で
複製する「モデル抽出」は別の問題として扱う。

## Interpretation

自分たちのAIシステムで起こり得る攻撃の道筋に合わせ、何を組み合わせたら
疑わしいかをルールとして明確にする。そのルールを実際の入力や行動の記録に
適用し、協調した脱獄、Prompt Injection、内部指示の引き出しという対象の
試行を見つけられることを確かめる。ルールは三つ別々でも、一つの仕組みで
複数を扱ってもよい。製品の初期設定を置くだけでは、個別のルールが働いた
証拠にならない。

例えば、三つのアカウントが同じAIの制限を、少しずつ違う文面で短時間に
探る。一人ずつ見ると回数は少なくても、同じ対象への試行としてまとめれば
協調した動きが見える可能性がある。ただし、同じ対象を調べる複数の正規
利用者もいるため、件数だけで悪意を断定しない。

## Security objective

既知の一文への反応や一人の行動の異常だけでは見えにくい、AI固有の攻撃試行
を発見する。検知結果は調査の手がかりであり、攻撃が成功した証明でも、
攻撃を阻止した証明でもない。

## Applicability

利用者の質問、取得文書、Toolの返答などがAIの動きに影響し得るシステムに
適用する。複数の利用者・会話を持つシステムでは、協調した試行を見つける
ために、対象をまたぐ観測経路も確認する。外部文書を使わない場合でも、
利用者の入力からの攻撃可能性は残る。

### Non-applicability

AIとのやり取りがない機能には直接適用しない。外部文書を読まないなら、
その入口を使う攻撃例だけが対象外となる。製品の既定ルールがない、現在の
利用者が一人しかいない、攻撃がまだ観測されていない、という理由で要件
全体を対象外にしない。隠した内部指示が存在しない場合は、抽出対象の有無
を確認し、その部分の適用範囲を明記する。

## Scope and assumptions

- 「個別のルール」は、対象システムで守る資産や実際の入力経路に合わせて
  条件と検知結果を定義したもの。手書きのプログラムや特定製品は必須ではない。
- 協調した試行をつなぐ手がかりには、対象機能、時刻、検知の理由、認証済み
  主体などがあり得る。IPアドレスや文面の似かよりだけで同一人物と断定しない。
- Prompt Injectionは、信頼できない文章に指示を混ぜてAIを操る試みを指す。
  実際に存在する入口を対象にし、単純な禁止語検索だけで全てを検知できる
  とは主張しない。
- 要件本文は攻撃試行の検知を求める。結果を監視・調査に渡す設計は重要だが、
  特定の通知方法や自動遮断を、この要件の必須条件として加えない。

## Assets, actors, identities, and trust boundaries

守る対象はAIの内部指示、利用可能なToolやデータ、攻撃試行を発見する能力。
攻撃者は利用者の質問や外部文書を操作でき、複数のアカウントに試行を
分散させることもある。AIアプリ、記録を集める仕組み、ルール管理者、
検知結果を見る担当者が関わる。

境界は、利用者・外部文書・Toolの返答からAIへの入口と、実際の操作から
検知用の記録へ渡る地点にある。攻撃者が入力に書いた「安全」「管理者」
などの自己申告を、検知を外す条件や信頼できる主体情報にしない。

## Required security properties

| ID | 必要な性質と確かめ方 |
|---|---|
| SP-1 | 対象の攻撃経路に合わせたルールの条件、使う記録、検知結果を説明できる。 |
| SP-2 | 協調した脱獄、Prompt Injection、内部指示の引き出しのうち対象システムに当てはまる各試行を、合成した試験で実際に見つけられる。 |
| SP-3 | ルールが必要とする入力・行動の記録が検知処理へ届き、結果からどの条件と対象に反応したか確認できる。 |

## Scope calibration and adjacent assurance

| 観測 | 本Controlでの扱い |
|---|---|
| 単発の既知文面だけ検査し、複数アカウントに分けた試行を見ない | 協調した試行の検知を示せずFail。C12.2.1だけでは代替できない。 |
| 一人の会話の再試行を見つけるが、対象に合う個別の攻撃ルールがない | C12.2.2の行動異常と、本Controlの個別ルールは別に評価する。 |
| 外部文書がAIへ指示する攻撃例に、設定したルールが反応する | Prompt Injectionの対象経路についてPass候補。全ての変種を保証しない。 |
| 内部指示の開示を要求する試行を検知したが、実際の開示はなかった | 「試行の検知」として評価できる。成功した漏えいは必要条件ではない。 |
| 検知結果は出たが、元の質問や文書を担当者が辿れない | 検知の確認と調査可能性を分け、後者の不足も報告する。 |
| ルールは働くが、AIが不正なTool操作を実行できる | 検知の評価と、実行前の認可・制限を分ける。 |

## Threat and failure-mode rationale

攻撃者は試行を複数人や複数の会話に分け、単発・一人単位の検査をすり抜け
られる。また、信頼できない文書に指示を埋め込んだり、内部指示を様々な
言い方で引き出そうとしたりする。対象システムの入口や攻撃の目的を考慮
したルールがなければ、記録が残っても意味のある攻撃の形として見つけ
られない。外部の脅威IDとの厳密な対応付けはまだ評価していない。

## Verification

### Architecture and configuration review

利用者の質問、取得文書、Toolの返答、AIからの操作要求など、実在する経路を
確認する。各ルールがどの攻撃を対象とし、どの記録を使い、どこで評価され、
結果をどこへ出すかを追う。複数アカウントの試行を結び付ける条件があるか、
ルール変更の権限と変更後の試験があるかも確認する。Researchにある特定の
検知製品や脅威分類への対応付けは必須にしない。

### Positive verification

無害な合成データで、対象とする三種類の試行を再現する。複数アカウントに
分散した脱獄の試行、外部文書または利用者の入力に混ぜた不正な指示、
内部指示を引き出そうとする質問を流す。単発の文面検索だけでは反応しない
ケースも含め、各ルールの結果から検知理由と対象を確認する。似た操作を
行う正規利用も試し、誤検知を測る。

### Negative and abuse-case verification

| ID | 試すこと | 期待する確認結果 |
|---|---|---|
| N-1 | 脱獄の試行を三つのアカウントに分け、一人ずつの回数は低くする | 協調した対象への試行を、定義した条件で見つける。SP-2、SP-3。 |
| N-2 | 取得文書やToolの返答に、AIへ権限外の動作を求める指示を混ぜる | 実在する間接入力の経路で、該当ルールが反応する。SP-2、SP-3。 |
| N-3 | 内部指示を言い換えて引き出そうとし、実際には開示させない | 成否ではなく抽出の試行を検知できる。SP-2、SP-3。 |
| N-4 | 攻撃と同じ件数で、複数の正規利用者が同じ機能を使う | 件数や対象の一致だけで攻撃と断定せず、誤検知を測る。SP-1、SP-2。 |
| N-5 | 入力に「管理者の許可済み」「安全」と書き、検知の除外を狙う | 入力者の自己申告でルールを無効化しない。SP-3。 |
| N-6 | ルールに必要な記録の配送を止める | 必要な記録が欠け、検知できない状態を発見する。SP-3。 |

### Failure conditions

対象システムに合わせたルールがない、適用する攻撃の型に対応する合成試験へ
反応しない、または必要な記録が届かずルールを評価できない場合はFail。
設定画面にルール名があるだけ、単発の文面検索だけ、攻撃成功後の報告だけ
では十分ではない。特定製品、固定のしきい値、全ての未知の攻撃の検知、
自動遮断がないことだけではFailとしない。

## Evidence expectations

| 証拠 | 作成元 | 対象 | 確認する時期 | 保護上の注意 | 合格の目安 |
|---|---|---|---|---|---|
| 対象経路とルールの一覧 | AIアプリ・検知担当者 | 三種類の攻撃と実在する入口 | 経路・ルール変更時 | 内部指示や秘密を載せない | 条件、必要な記録、検知結果の行き先を説明できる。 |
| 合成した攻撃・正常利用の試験 | 試験担当者 | N-1〜N-5 | リリース時・ルール更新時 | 実際の秘密や顧客情報を使わない | 対象の試行に反応し、正規利用での誤検知も測れる。 |
| 記録と検知結果の対応 | 記録・検知の担当者 | N-1〜N-3、N-6 | 連携や保管条件の変更時 | 調査する人だけが詳細を見られるようにする | どの対象と条件に反応したか確認でき、記録欠落も分かる。 |

## Known limitations and uncertainty

ルールは観測できる経路と記録に依存する。複数のアカウントを確実に同じ
攻撃者へ結び付けることはできず、無関係な利用者を一つの攻撃と誤認する
こともある。ルールで見つけた事象は疑いであり、悪意や実害の確証ではない。
新しい攻撃や言い換えは見逃し得る。内容を詳しく記録するほど調査はしやすい
が、個人情報や内部情報が監視側へ集まる。`verifiable`は本書の成熟度であり、
実製品の適合を示さない。
