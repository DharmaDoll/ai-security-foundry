# 推論後の出力に対する受取権限の強制

AISVS Verification Level: 2

## Upstream basis

AISVS `v1.0-C5.2.4`、Verification Level 2を解釈する。
原文は、推論後のFilteringによって、Requesterが受け取る権限を持たないDataを
Responseへ含めないことを求める。特定のDLP製品や出力形式は指定しない。
NormativeとC5.2 ResearchはMetadataの固定Revisionを参照する。

同RevisionのResearch（Last Researched: 2026-07-14）の該当行を確認した。
Researchは、受取人の権限と出典情報に基づく評価、送信前の強制、言い換えや
Streaming・Cache等の試験を補足する。検出器だけでは業務上の受取権限は決まらない。
Researchが挙げるログ等の保護も重要だが、本Controlの直接の対象はRequesterへのResponseである。
Requesterへ返らない保存先全体の保護は、隣接する保証として区別する。

以降は、その要求を検証可能にするRepository interpretationである。
Research中の製品機能や個別Framework Mappingは採用せず、必須条件へ昇格させない。

## Interpretation

**Modelが生成した内容を、まだ送信してはいけない候補として扱い、受取人に許可された
情報だけを、推論後・送信前の境界で通す。**

例えばAliceはBobの人事評価を読めるが、給与は読めない。
Modelが「評価は4、給与は1,200万円」と生成した場合、給与をそのまま返してはならない。
給与を比較表現や別言語へ変えても、受取権限は新たに生じない。
一方、架空の給与を生成しただけなら、実在Dataの未認可開示と断定せず、誤情報の問題を分ける。

削除、許可Fieldだけの投影、Response全体の拒否など、方式は選べる。
投影とはRecordから必要なFieldだけを選ぶことである。許可部分を残す場合は、
残した文章・数値・添付等にも未認可情報が含まれないことを確認する。

## Security objective

推論、Tool結果、別Session、Cache等からResponse候補へ混入した未認可Dataが、
Requesterの境界を越えることを防ぐ。
「機密情報らしいか」の検出と、「この人が受け取ってよいか」の認可を混同しない。

本Controlの本質はDLP製品の導入ではない。DLPはData Loss Preventionの略で、
定義した情報種別や特徴に基づく漏えい対策を指す。組織の権限情報と連携した製品もあり得るが、
単に個人情報や秘密らしい文字列を検出するだけでは、Aliceの受取権限を証明できない。

## Applicability

推論結果をHuman、Agent、Service等のRequesterへ返すSystemに適用する。
Responseには本文だけでなく、構造化Data、引用、Preview、添付、Download Link、
音声・画像・File等、実際に情報を渡す構成要素を含める。
Email、Webhook、Export等がResponseの配送手段なら、その経路も確認する。

### Non-applicability

推論に由来するResponseを提供しないComponent単独の評価では、対象外の根拠を記録できる。
「RAGがない」「DLPを使わない」「検索時に認可した」ことだけを除外理由にしない。

公開情報のみで受取制限がないSystemでは、保護対象の有無と入力・Model・Tool・Cacheの
前提を確認する。非公開のSessionや運用Dataもないという根拠が必要であり、公開Corpusだけを
見てN/Aとしない。適用性の判断と、Filteringを実装してPassしたという主張は分ける。

## Scope and assumptions

- Requesterと実際の配送先を信頼できる情報で特定する。Service Credentialだけを見て、
  背後の受取人の権限まで推定しない。
- 保護対象は、組織が定めたObject・Field・分類・派生情報等の受領Policyに従う。
  原文は「許可Dataからのあらゆる推測を禁止」とは定めていない。比較・集計情報の公開可否は明示する。
- Provenanceは情報の由来を示す情報である。認可の根拠にするなら、信頼する処理系が保持し、
  ModelやCallerの自己申告だけでは成立させない。
- 出典IDが真正でも、Modelが自由生成した文章の全内容がその出典だけに由来する証明にはならない。
- Policyの更新・失効がいつ配送へ効くかを定義する。原文は一律の失効時間を指定しない。
  有効なローカルPolicyを使うことと、判断不能時に無検査で送信することを分ける。

## Assets, actors, identities, and trust boundaries

人事の例では、保護対象は給与・健康情報と、それを含む文章や添付である。
ActorsはAlice、HR Tool、Model、出力認可Component、配送Component、Policy管理者である。

信頼境界は次の二つに分ける。

1. 未信頼のResponse候補から、信頼する認可・組立処理へ。
2. 認可・組立処理から、Requesterが観測できる配送経路へ。

**PDP**はPolicyを評価する場所、**PEP**はその結果を実際の送信へ強制する場所である。
Modelが「送ってよい」と判断することはPDPの代替ではない。
正しい拒否判断があっても、添付やStreamingがPEPを通らず送られれば保証は成立しない。

## Required security properties

| ID | 必要な性質 | 観測できる成立条件 |
|---|---|---|
| SP-1 | 受取人とPolicyの結び付け | 実際のRequester・配送先について、受取可能な情報を評価する |
| SP-2 | 判断根拠と内容の整合 | 自己申告のLabelや出典を信頼せず、実際に送る内容に対する許可根拠を確認できる |
| SP-3 | 推論後・開示前の強制 | 未認可情報が最初に観測可能になる前に除去または遮断する |
| SP-4 | 全Response経路での維持 | 本文以外の添付・引用・配送、Cache、Retry、Error等でも同じ受取制限を維持する |
| SP-5 | 不確実な判断を許可へ変えない | 必要な根拠が欠落・失効・検証不能なら、該当部分またはResponse全体を遮断する |

Schema検証は形式検査であり、SP-1やSP-2を単独では満たさない。
また「Unknownなら遮断」は認可に必要な根拠が不明な場合を指し、公開定型文にまで
存在しないDocument IDを付ける要件ではない。

## Scope calibration and adjacent assurance

| 状況 | 本Controlの評価 | 別途考えること |
|---|---|---|
| 検索認可はあるが、適用対象のResponseに推論後の強制がない | 不成立 | C5.2.2の防御だけで本要件を代替しない |
| 数字はMaskするが、Policy上非公開の給与比較を返す | Fail | 言い換えは認可の代替ではない |
| 許可Fieldだけを信頼する処理で組み立て、全配送経路で確認する | Pass候補 | Model自由文やTemplateを使うなら、その内容も別に保証する |
| 正式な出典IDを付けた自由文に、別の未認可情報が混ざる | Fail | 出典の真正性と、出力内容の安全性は別 |
| 本文を止める前に給与がStreamingされる | Fail | 送信後の削除では回復しない |
| 認可対象の根拠が不足し、安全性を検証できない | Passを裏付けられない | 脆弱性の実証とは区別する |
| Requesterへ出ない内部ログに情報を保存する | 本要件単独で直ちにFailとはしない | ログのアクセス制御・保持・再利用は別途評価する |

実現例として、Modelには使用したいFieldを提案させ、信頼する処理が認可後に値を
埋め込む方式がある。ただし自由なTemplateや文字列をそのまま残すと、そこが漏えい経路になる。
これは一つの選択肢であり、本Controlは特定のRendererや構造化方式を義務付けない。

## Threat and failure-mode rationale

攻撃者は、給与を読めない正規利用者、またはModelへ入る文書・Tool出力を操作できる者とする。
認可Policyや信頼する出典情報の管理権限は持たない。

代表的な経路は、過剰なTool結果をModelに復唱させる、給与を比較表現に変える、
許可されたField由来と偽装する、別人のCacheを再利用する、添付やStreamingから先に送ることである。
結果は未認可情報の開示であり、Modelが指示に従ったかどうかではなく配送された情報で評価する。

本改訂では外部脅威IDのMappingを主張しない。Prompt Injectionや情報漏えいの分類だけでは、
出力の受領権限がどこで失われたかを十分に表せないため、具体的な失敗経路を直接記述する。
`threat_mappings`が空でも、脅威の説明を省略する意味ではない。

## Verification

### Architecture and configuration review

1. Response候補の全入力元と、Requesterが観測できる全出力経路を列挙する。
2. 各出力種別に対して、実際の内容と受取Policyを結び付ける方法を確認する。
3. 判断根拠の作成主体、改ざん可能性、最終Bytesへの変換を追跡する。
4. Streamingの送出単位、添付、配送先、Error、Cache、RetryのPEPを確認する。
5. Policy変更、失効、評価障害時の扱いを確認する。

### Positive verification

模擬Recordの評価はAliceとHR担当者へ、給与はHR担当者だけへ許可する。
同じResponse候補に対し、Aliceには評価だけ、HR担当者には許可された給与も渡ることを検証する。
一律に全員をBlockするだけで完成とせず、正規の開示が意図したPolicyどおり成立することを確認する。

### Negative and abuse-case verification

| ID | 試験 | 期待結果 | Property |
|---|---|---|---|
| N-1 | Alice向け候補に給与・健康情報と許可済み評価を混在させる | 未認可部分を安全に除去するか全体を拒否し、給与等を渡さない | SP-1, SP-3 |
| N-2 | 非公開給与を比較、要約、別言語、Encoding、複数Fieldに分散して表現する | Policyで保護した情報を迂回して開示できない。判定できない形を暗黙に通さない | SP-2, SP-5 |
| N-3 | 未認可内容に許可出典IDを付ける、必要なLabelやRequesterを改ざんする | 自己申告で権限が広がらず、内容と根拠の不一致を通さない | SP-1, SP-2 |
| N-4 | 給与をStream冒頭、複数送出単位、添付、引用Preview、配送Linkに置く | 外部から観測できる前に遮断する。単位を結合した漏えいも確認する | SP-3, SP-4 |
| N-5 | HR担当者としてCacheを作りAliceへ再利用、または生成後にGrantを失効させる | 受取人と定めた有効条件に従って再評価し、他人・失効済みの許可を流用しない | SP-1, SP-4, SP-5 |
| N-6 | 有効な判断ができない状態にし、Timeout、Retry、Error、Fallbackを発生させる | 未検査の元出力やDebug内容を返さない | SP-4, SP-5 |
| N-7 | Schema内の自由文字列、未知Field、入れ子、Model指定Templateに秘密を入れる | 形式が正しくても未認可情報を通さず、Field名だけの認可で完了しない | SP-2, SP-3 |

試験は許可された環境の模擬Dataで実施する。Modelに秘密を生成させる試験だけでなく、
出力境界へ固定の悪性候補を入力する試験でPEP自体を再現可能に検証する。
その上で実際の生成から配送までを確認し、単体試験だけで迂回がないと結論しない。
本文の見た目やHTTP Statusではなく、実際に受取側へ届いた内容を観測する。

### Failure conditions

受取権限のない情報の開示、送信後だけの検査、自己申告の認可根拠の採用、
迂回する配送経路、評価不能時の無検査送信は不成立を示す。
必要な試験・出典・配送先の情報が足りない場合は、証拠不足としてPassを保留し、
実証された開示と区別して記録する。

| 出力Data flowと境界一覧 | System Owner | 全候補入力、受取人、配送経路 | 出力経路・Model/Tool構成変更時 | Revision管理、内部識別子の公開を避ける | 各開示経路のPEPと対象Policyが特定できる |
| 受領Policyと出力Contract | Policy/出力処理管理者 | Object・Field・派生情報・公開定型文 | Policy/Schema変更時 | 改ざん防止、適用Revisionを保持 | 実際の内容を認可する根拠があり、自由文の限界も明示される |
| 根拠と最終出力の対応 | 信頼するRuntimeと検証者 | Provenance、認可判断、Renderer、配送 | 評価するBuild/Policyと一致 | 模擬Dataを用い、秘密を含むTraceを公開しない | Modelの自己申告だけに依存せず、判断した内容と送信内容が一致する |
| Positive/Negative結果 | Test Harnessと検証者 | N-1〜N-7または根拠ある同等試験 | 関連実装・Policy変更時と定期回帰時 | 試験入力・Build・Policy・結果を追跡 | 許可情報は届き、未認可情報は全配送経路で届かない |
| 障害・Cache・失効結果 | 運用/Policy管理者 | 配送前、再利用、代替経路 | 有効条件や運用方式変更時 | 時刻・受取人・構成を対応付ける | 許可根拠を失った出力が配送されない |

実際の本番Evidence、Credential、顧客情報はこのRepositoryへ置かない。
ログの有無ではなく、最終的な開示を検証できることを求める。

## Known limitations and uncertainty

- 完全な自由文について、すべての言い換え・符号化・推測からの開示を検出できるとは主張しない。
  有限のNegative Test成功は完全防止の証明ではない。
- 信頼する出典情報も、生成文章の意味の完全な追跡を自動的には実現しない。
  強い保証が必要なら、開示内容を判断できる出力形式・処理範囲を選ぶ必要がある。
- 本Controlは特定のDLP、Policy Engine、Handle、Rendererを要求しない。
  手段より、出力種別ごとに主張する保証と検証の整合を評価する。
- 推論前の漏えい、ログやBackup全体、認可済み操作の悪用、誤情報、安全性の全般は別に評価する。
- 欠落したProvenanceを単に「高信頼のModelだから」で補わない。
  安全な出力を構成できない場合の拒否や機能制限と、その利用上の制約を明示する。
