# AI資産へのJIT特権付与と自動失効

AISVS Verification Level: 3

## Upstream basis

AISVS `v1.0-C5.2.6`、Verification Level 3を解釈する。Model Weight、Training Pipeline、
本番AI設定への特権を必要時に付与し、最大Session時間を定義して自動失効させることを要求する。
Zero Standing Privilege（常時有効な特権をなくすこと）は原文で推奨されており、別の絶対条件へ変えない。

固定RevisionのC5.2 Research（Last Researched: 2026-07-14）の該当行を確認した。
ResearchはRoleの有効化、更新による期限迂回、Resource側での期限後の拒否を補足する。
Task終了時の即時失効や特定PAM製品を、原文の一律な必須条件にはしない。
以下は特権Lifecycleを検証するRepository interpretationである。

## Interpretation

**重要なAI資産への強い権限を、必要な作業のために開始し、定めた時間を超えて使わせない。**

管理画面は60分で終了するが、そこで得たCLI Tokenは24時間使えるなら、60分という上限は成立しない。
また、15分Tokenを恒久的なAdmin権限で無条件に再発行できるなら、Tokenだけが短命である。
評価単位は、特権の開始、発行、更新、終了、Resource側の拒否までのLifecycle全体とする。

## Security objective

通常時や作業終了後に残る特権を悪用して、Modelの取得・変更、学習の改変、本番設定の変更を
継続できる機会を減らす。短い時間内の不正操作そのものを防ぐとは主張しない。

## Applicability

対象AI資産への特権操作を行うHuman、Agent、Service、CI/CD、管理・Recovery経路に適用する。
特権は、資産や本番動作へ重大な影響を与える読取・変更・実行等としてSystemごとに定義する。
Weight読取/Exportも重要になり得るため、Writeだけに限定しない。

### Non-applicability

対象資産への特権操作を持たない範囲では、操作一覧と責任分界を示してN/Aを判断する。
Emergency Accountだから自動で除外しない。常時有効の例外が残る場合は範囲と根拠を記録し、
全経路がJITに適合したと主張しない。

## Scope and assumptions

- JIT（Just in Time）は必要時の付与。Eligible（付与対象になれること）とActive（今使えること）を分ける。
- Activationは作業・Job等の条件を検証して特権を有効にすること。毎回Human承認が必須という意味ではない。
- 最大時間はTaskとRiskから説明し、Token、Role、既存Connection等の実効的な期限で測る。
- 正当な継続作業は再評価による新Activationを認め得る。単なるRefreshで期限を無制限に延ばさない。
- 期限前に完了した変更を元に戻す要求ではない。期限後に新しい特権操作ができるかを確認する。
  長時間Jobの継続と新しい特権利用を区別し、委任されたBackground権限の終了条件を明示する。

## Assets, actors, identities, and trust boundaries

AssetsはWeight、学習Pipeline、本番設定、特権Role/Credential。
Actorsは操作者、Job、Activation Policy、Credential発行者、ResourceのPEP。
境界は通常Identityから特権Activation、ActivationからCredential、Credentialから実操作である。
Enforcementは発行側の時間制限だけでなく、Resource側または迂回できないProxyで行う。

## Required security properties

| ID | 必要な性質 | 成立条件 |
|---|---|---|
| SP-1 | 必要時の付与 | 定義した作業条件の評価を通じて特権が開始される |
| SP-2 | 最大時間の定義 | 対象作業・資産ごとに上限と根拠を確認できる |
| SP-3 | 自動失効 | 人の手作業なしに、最大時間後の特権利用が止まる |
| SP-4 | Lifecycle全体で上限維持 | 更新、派生Credential、Session、代替経路が上限を迂回しない |

## Scope calibration and adjacent assurance

| 状況 | 評価 |
|---|---|
| UIは60分で終わるが同じActivation由来のCLIで8時間後も特権を使える | Fail |
| 作業後に担当者がRoleを手動削除するだけ | Fail |
| 承認Jobの条件で30分だけ特権を付与し、Resource側でも期限を強制する | Pass候補 |
| 30分上限は守るがJobが10分で終わっても残り20分有効 | 直ちにFailとしない。即時終了は追加保証として評価 |
| 正しくJIT付与した特権が別環境でも使える | 時間保証とは別のScope/認可Gap。System全体の安全ではない |
| Permanent Adminから短命Tokenを無条件に繰り返し発行する | JITを満たす根拠にならない |
| 常時特権の緊急経路を例外承認する | Risk受容であり、その経路が本要件に適合したという意味ではない |

## Threat and failure-mode rationale

攻撃者は操作者のSessionやService Credentialを取得した者、または侵害されたJobとする。
古いCredentialの継続使用、Refreshによる上限延長、障害時の固定AdminへのFallbackを試す。
影響は重要AI資産への不正操作を長く継続できることである。
外部脅威IDはMappingせず、特権Lifecycleの具体的な失敗経路を根拠とする。

## Verification

### Architecture and configuration review

対象資産・操作・全主体を列挙し、Activation、発行、更新、終了、PEPまで追う。
緊急、Rollback、Recovery、Batchを含め、最大時間をどこが強制するかを確認する。

### Positive verification

通常時は対象特権を使えず、正当な模擬Job条件を満たした後だけ利用できることを確認する。
許可Window内の操作と、期限後の正当な新Activationを検証する。
独立した必要性評価なしに同じ権限を常時得られる設計になっていないか確認する。

### Negative and abuse-case verification

| ID | 試験 | 期待結果 |
|---|---|---|
| N-1 | 作業条件なし、終了済みJob、偽造したActivation情報で要求する | 特権を有効化しない |
| N-2 | 最大時間後にUI/API/CLIから同じ特権を使う | Resource側で拒否 |
| N-3 | Refresh、交換、派生Roleで期限を延ばす | 新たな適正Activationなしに上限を迂回しない |
| N-4 | 期限前のConnectionやQueueから期限後の新規特権操作を行う | 古いActivationを根拠に継続できない |
| N-5 | JIT機構を停止し、Recoveryや固定Key経路を使う | 無期限のAdminへ自動Fallbackしない |
| N-6 | 失効処理を遅延・失敗させる | 別の期限強制等で上限が守られ、人の後処理待ちにならない |

試験は模擬資産と許可された環境で行い、画面上のLogoutではなくResourceの実操作を観測する。

### Failure conditions

SP-1〜SP-4に反する特権取得・継続、手動終了だけの構成、迂回経路は不成立。
上限やJob継続の扱いが不明なら、Passの証拠不足として未確認範囲を残す。

## Evidence expectations

| Evidence class | Producer | Scope | Freshness | Integrity and sensitivity | Acceptance criteria |
|---|---|---|---|---|---|
| 特権Lifecycle一覧 | 資産/Identity Owner | 通常・緊急・自動化経路 | 経路/Role変更時 | Revision管理 | Activationから拒否まで追跡可能 |
| Activationと上限Policy | Policy管理者 | 操作・Task・時間・更新 | Policy変更時 | 改ざん防止、秘密なし | 必要性と最大時間の根拠がある |
| 有効化/失効と実操作Trace | Broker/PEP/Resource | 成功と期限後拒否 | 評価構成と一致 | 時刻と相関ID、Token本体除外 | 実効期限が上限以内 |
| 試験結果 | Test Harness/検証者 | N-1〜N-6または同等 | 関連変更時・定期回帰 | 模擬資産・Build/Policy記録 | 全経路で上限と自動失効を維持 |

## Related requirements

- `v1.0-C5.2.5`: Agentからの認可判断基盤の隔離。

## Known limitations and uncertainty

時間制限は、付与判断の業務上の正しさ、Credential窃取やAgent侵害の防止を保証しない。
特権を得る条件と期限を守るための強制は本Controlに必要だが、認証・認可全体の保証は別に残る。
原文に一律の最大分数はなく、極端に長い上限を「定義したからJIT」とは扱わない。
常時特権の排除を推奨する記述と、対象操作のJIT要件を混同して例外を隠さない。
`verifiable`はArtifactの成熟であり、実環境の適合やEngineering Mappingではない。
