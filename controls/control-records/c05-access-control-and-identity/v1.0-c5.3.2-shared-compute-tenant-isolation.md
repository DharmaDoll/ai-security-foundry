# 共有計算基盤を通じたTenant間の観測・干渉の防止

AISVS Verification Level: 3

## Upstream basis

AISVS `v1.0-C5.3.2`、Verification Level 3を解釈する。共有計算資源を通じて他Tenantの
処理を観測・干渉できないことを求め、通常の実現手段としてHardware分割、
Confidential Computing、Tenantごとの専用計算資源を例示する。

固定RevisionのC5.3 Research（Last Researched: 2026-07-13）の該当行を確認した。
ResearchはGPU内部や接続経路の共有、時間差による漏えい、メモリ攻撃等を補足する。
ただし、特定製品の必須化や「専用GPUだけが完全に安全」という強い記述を、
原文の条件やRepositoryの保証として採用しない。未検証のCVEや性能数値も転載しない。
以下の評価範囲、証拠、Pass条件はRepository interpretationである。

## Interpretation

**Application上でTenantを分けるだけでなく、共有する計算基盤から他Tenantの保護対象の
処理を覗いたり、不正に変えたりできないことを確認する。**

例えばA社とB社のAPI、結果、Cacheは分離されている。しかしA社が自分の処理時間を測ることで、
B社の秘密の処理の実行有無を実用的な精度で識別できるなら、直接Dataを読めなくても観測が成立する。
専用GPU等の名前ではなく、何が残って共有され、何を可能にするかで評価する。

## Security objective

計算資源を共有する正規Tenantや侵害されたWorkloadが、他Tenantの処理の機密性・完全性を
破ることを防ぐ。機密性は保護情報を知れないこと、完全性は処理や状態を不正に変えられないこと。
不正な資源干渉も対象にするが、通常の共有負荷による遅延をすべて攻撃とみなさない。

## Applicability

Tenant間でCPU/GPU、Memory、接続経路等を共有するAI計算基盤と、その選定・運用に適用する。
自社運用では実装・検証、外部API利用では提供者の保証・構成・責任分界を確認する。
同じModelを使うこと自体や、Resource名が同じこと自体はFailではない。

### Non-applicability

評価範囲に異なるTenantの計算処理との共有がないことを確認できる場合、N/Aの根拠にできる。
専用VM、Container、GPUという名称だけで非共有とは判断しない。
外部Providerの内部が見えないことは、依存する保証が不要という意味ではない。
Provider部分を評価範囲外にする場合も、未確認の依存とSystem全体の保証限界を残す。

## Scope and assumptions

- Tenant、保護対象の処理情報、攻撃者が許可される操作と観測を明示する。
- Hardware、Driver、Firmware、仮想化、配置方式の組合せを評価対象として特定する。
- Side channelは処理時間等の間接的手掛かりから情報を得る経路。
  単なる揺らぎではなく、どの保護情報を、どの条件・精度で得られるかを判断する。
- Confidential Computingは処理中Dataの保護をHardwareの信頼領域で支える技術群である。
  あらゆる時間差・共有通信経路の漏えいを自動的に防ぐものとして扱わない。
- Attestationは期待する基盤・構成等を確認する証拠。採用する場合もApplication全体の無欠陥を証明しない。
- 有限の試験で全Side channelの不存在は証明できない。仮定と残余不確実性を残し、
  既知の成立する攻撃を単にRisk受容しただけで本要件に適合したと主張しない。

## Assets, actors, identities, and trust boundaries

AssetsはTenantの計算状態、入力/出力、Memory、非公開の処理の実行有無。
Actorsは各Tenant、計算Job、Scheduler、基盤管理者、Hardware/Cloud提供者。
境界はTenantの実行領域間と、Tenantから配置・Memory管理等の制御面へ。
Enforcementは配置制約、Hardware/Memoryアクセス分離、基盤構成の制約等にある。
具体技術は選択できるが、単なる利用規約やModelへの指示は境界を強制しない。

## Required security properties

| ID | 必要な性質 | 成立条件 |
|---|---|---|
| SP-1 | 実際の共有範囲の把握 | 配置・Memory・接続等の共有点と対象Tenantを特定できる |
| SP-2 | 観測・干渉の制限 | 定義した攻撃者能力で他Tenantの保護対象へ到達できない根拠がある |
| SP-3 | 構成と運用で分離を維持 | 再配置、拡張、復旧、資源再利用でも必要な制約が失われない |
| SP-4 | 保証条件の検証 | 採用する分離方式の成立条件と検証結果を、実構成へ結び付ける |

## Scope calibration and adjacent assurance

| 状況 | 評価 |
|---|---|
| 他Tenantの秘密処理を共有資源の時間差から実用的に判別できる | Fail |
| 専用GPUと説明されるが周辺共有経路は未確認 | Passの根拠不足。直ちに脆弱性ありとは断定しない |
| 隔離構成、残る共有経路の対策、脅威別検証が揃う | 明示した評価範囲内でPass候補 |
| 通常負荷で遅延するが保護情報の推測や不正操作は未確認 | 遅延だけでFailと断定しない |
| GPUは完全に別だが結果APIから他人のJob結果を取得できる | Serving/認可の別Gap。基盤分離だけでSystem全体は安全にならない |

## Threat and failure-mode rationale

攻撃者は自Tenantの計算やQueryを実行できる正規利用者、または侵害されたTenant Workload。
他TenantのCredentialや基盤管理権限は当初持たない。
共有資源の計測、Memory再利用時の残存Data読取、配置制約の回避、共有状態への不正変更を考える。
具体的な実現可能性はHardwareと許可される攻撃者能力で変わるため、未検証の一般化はしない。
本改訂では外部脅威IDへのMappingを確定せず、この境界を直接検証する。

## Verification

### Architecture and configuration review

Tenantから物理/仮想Resourceまでの配置を追い、何が専用で何が共有かを記録する。
分離を担う制御、必要な基盤Version、再配置・再利用時の扱い、提供者の保証範囲を確認する。
暗号化やAttestationを根拠とする場合は、対象・鮮度・検証主体・鍵解放条件まで確認する。
これらの技術を採用しない方式に、同じArtifact名だけを要求しない。

### Positive verification

管理下の二つの模擬Tenantで、分離制約を保って正規処理が実行できることを確認する。
配置変更や復旧後も、同じ制約と保証条件が成立することを確認する。

### Negative and abuse-case verification

| ID | 試験 | 期待結果 |
|---|---|---|
| N-1 | 模擬Tenant AからBの秘密処理の有無を計測で識別する試験を行う | 事前に定めた保護対象・判別基準で有効な漏えい経路が成立しない |
| N-2 | 資源再利用後に別TenantのMemoryや計算状態へのアクセスを試す | 読取・変更できず残存Dataを取得しない |
| N-3 | 再配置、Scale、復旧で禁止された同居や制約欠落を誘発する | 配置が拒否されるか必要な分離が維持される |
| N-4 | 採用する保証に必要な構成・証拠を欠落/不適合にする | その保証を必要とするWorkloadを未検証状態で実行しない |
| N-5 | Aの権限でBの処理状態や共有制御面を変更しようとする | 権限外の変更を拒否し、Bの計算が不正に変わらない |

N-1は通常の遅延比較だけではない。秘密状態の有無を制御したFixture、対照条件、反復、
ノイズと誤判定の扱いを定める。実顧客へProbeを送らず、許可された専用試験環境で行う。
危険なFault injection等が必要なら専門評価と許可範囲を別に定め、一般運用中に実施しない。

### Failure conditions

成立する保護情報の観測、不正な計算状態変更、必要な分離条件の迂回は不成立。
試験が困難、Provider証拠がない、共有点が不明の場合はPassの証拠不足として記録する。
一つの攻撃が再現しないことだけではSP-1〜SP-4の成立を示せない。

## Evidence expectations

| Evidence class | Producer | Scope | Freshness | Integrity and sensitivity | Acceptance criteria |
|---|---|---|---|---|---|
| 共有Resource/配置表 | 基盤Owner/Provider | 実Deploymentと全Tenant境界 | 構成/配置方式変更時 | Version管理、機密Topologyの公開を避ける | 専用・共有点と責任分界を説明できる |
| 分離設定と保証の根拠 | 基盤/Hardware提供者 | 当該構成・Version・前提 | 基盤更新時 | 信頼元・対象構成・有効条件を検証 | 採用方式の保証を実構成へ結び付ける |
| 正常/異常試験結果 | 専門検証者/Test Harness | N-1〜N-5または根拠ある同等 | 関連変更時・定期評価 | 模擬Tenant、条件・測定方法・限界を記録 | 既知の有効な漏えい/干渉経路を残さない |
| 運用変更/復旧結果 | Scheduler/基盤運用者 | Scale、復旧、再利用 | 運用方式変更時 | 時刻・構成Revisionを保持 | 変更後も分離条件が成立する |

本番Dataや内部証拠はRepositoryに置かず、期待するEvidenceの種類だけを定める。

## Related requirements

- `v1.0-C5.2.1`: 計算Resourceへの明示的なアクセス許可。
- `v1.0-C5.3.1`: Serving状態、結果、Cache等のTenant分離。境界は重なり得るが同一ではない。

## Known limitations and uncertainty

Hardware/Software/運用の組合せに依存し、全Side channelの不存在を保証できない。
専用GPU、VM、Confidential Computing等の名称だけで適合としない。
Residual Riskの受容と要件充足は別であり、保証範囲から都合の悪い共有点を除かない。
本Controlの範囲外にあるAPI認可や出力制御の不備は、独立したGapとして評価する。
`verifiable`は検証基準が揃ったArtifactの状態であり、全製品で容易に検証できるという意味ではない。
Engineering Mappingは未評価である。
