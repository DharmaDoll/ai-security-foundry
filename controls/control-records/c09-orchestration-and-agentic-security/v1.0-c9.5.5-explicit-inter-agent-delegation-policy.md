# Agent間のタスク委任を明示的Policyで制限する

AISVS Verification Level: 2

## Upstream basis

AISVS `v1.0-C9.5.5`を解釈する。要件本文はAgent間のタスク委任を明示的な認可Policyで制限することを求める。
採用済みstable v1.0の固定Revisionで本文と対応Researchの要件別検証・限界を確認した。
最新の版・製品への追従を意味しない。

Researchは委任方向、未登録Agent、権限の狭まり、Agentと委任元双方の制約を補足する。特定ProtocolやRegistry製品は必須にしない。
以下の具体例・Property・検証条件はRepository interpretationである。
Researchの製品、統計、事件、外部Framework Mappingを未検証のまま転記せず、
例示された実装方式を一律の適合条件にしない。

## Interpretation

どのAgentがどの相手へ、何をどの範囲で委任できるかを定め、相手を認証できるだけで全委任を許可しない。親が持たない委任権限を子の広い能力で補わない。

調査Agentから分析AgentへのRead委任は許しても、分析Agentから送金Agentへの委任は許さない。返信を受けられることと、その相手にタスクを依頼する権限は別。

## Security objective

複数Agentの接続が権限昇格・横展開の自由な経路になることを防ぐ。

## Applicability

他Agentへタスクを送信・委任・再委任する構成。

### Non-applicability

Agent間の委任能力がない範囲は対象外。Tool内に隠れた子AgentへのDispatchも確認する。

## Scope and assumptions

委任元・先・方向・Task種別・Scope・再委任条件を定義する。両者の制約と委任元の範囲を保持するための信頼するIdentityを必要とする。

対象構成・採用Policy・許容する動作と評価境界を検証前に固定する。
不明な構成を安全と仮定せず、未確認範囲をEvidenceの不足として残す。

## Assets, actors, identities, and trust boundaries

資産は委任権限とTask Scope。送信Agent、受信Agent、Peer認証、Policy、Task Queueを分ける。強制点は送信・受付で、代替入口も含めた実効認可を評価する。

## Required security properties

Security Invariantは守るべき性質、Enforcement Pointはそれを実際に強制する場所を指す。

| ID | 必要な性質と観測条件 |
|---|---|
| SP-1 | 委任関係とScopeを明示したPolicyがある。 |
| SP-2 | 相手と元主体を検証しPolicy外委任を拒否する。 |
| SP-3 | 再委任・返信・Queueで方向やScopeを拡大できない。 |

## Scope calibration and adjacent assurance

認証成功は委任許可ではない。全Agentに同じ権限がある場合でも明示Policyと実強制を確認する。ユーザTokenの伝播はC9.5.2。

## Threat and failure-mode rationale

侵害した低権限Agentが強いAgentに仕事を依頼し、自身にはない能力を使わせる。

この保証の分析では外部脅威IDを付与する追加価値を確定していない。
攻撃者能力・失敗経路を具体化し、`threat_mappings`は空とする。
ResearchのMappingを自動採用せず、必要時に一次Sourceの固定版で別途評価する。

## Verification

### Architecture and configuration review

Peer一覧、委任Policy、Task受付、再委任、戻りMessage、Queue、同一主体の扱いを追う。

### Positive verification

許可された方向・Task・Scopeで委任し、受信側がその範囲でだけ処理することを示す。

### Negative and abuse-case verification

許可された試験環境と模擬Dataを用いる。モデルが協力することに依存せず、
必要に応じて実行境界へ試験要求を直接与える。

| ID | 条件・操作 | 期待結果・対応Property |
|---|---|---|
| N-1 | 未登録AgentからTaskを送る | Policy外なら拒否。SP-1, SP-2 |
| N-2 | 一方向許可を逆向きに使う | 逆委任を拒否。SP-2 |
| N-3 | Readだけの委任をWriteで再委任 | Scope拡大を拒否。SP-3 |
| N-4 | Queueや返信Messageを新Taskに見せる | 認可を迂回しない。SP-2, SP-3 |

### Failure conditions

上表の期待結果に反する観測やSPの不成立は、本ControlのFailを裏付ける。
試験未実施、構成不明、結果を追跡できない場合はPassを裏付ける証拠不足であり、
実証された回避と区別する。隣接要件の不備だけで本Controlの意味を広げない。
