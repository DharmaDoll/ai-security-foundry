# C9.2.4：分類を実際の実行制限につなげる

AISVS Verification Level: 2

[Control本文：解釈・検証・証拠・限界](README.md)

## 要件と資料の位置づけ

対象は`v1.0-C9.2.4`。採用済みAISVSの固定Revisionは
`78775233666a2022dcfb82037e5e029116955c00`。

原文の中心部分：

> the agent runtime enforces reversibility classifications by blocking, requiring approval, or restricting actions

全文の日本語訳：Agentの実行基盤が、操作の影響と元に戻せるかどうかに基づき、操作を阻止する、
承認を求める、または制限することで、可逆性の分類を強制していることを確認する。
英語全文は[要件本文の9.2.4][normative]を参照する。

Normativeは要件本文、Researchは補足、具体構成とツールの使い分けはRepository interpretation、
対話の整理は学習上の洞察である。学習完了はControl成熟度や製品適合を変更しない。

## 具体例と位置づけ

運用Agentが本番データの完全削除を要求する。台帳は「不可逆」、組織のルールは
「Agent経由の完全削除は禁止」としている。しかし画面に警告するだけで削除APIへ要求を送れば、
正しい分類とルールがあってもデータは失われる。

C9.2.3は分類の信頼性を扱い、C9.2.4は分類に応じた制限を実行へ反映する。
Runtime（実行基盤）は、Agentの要求を受けてツールやAPIを実際に呼ぶアプリケーション側の仕組み。
実行前にルールを確認し、禁止なら要求を先へ送らない。

| 操作と分類 | 組織が定めるルールの例 |
|---|---|
| 未公開設定の変更：可逆 | 所定の承認を確認して実行する。 |
| 外部への注文：外部依存で可逆 | 取消条件と所定の承認を確認する。 |
| 本番原本の完全削除：不可逆 | Agentからの実行を拒否する。 |

これは例示であり、不可逆なら常に全面禁止という一律の要求ではない。
他の適用要件で必要な承認・認可も維持する。

## 脅威・信頼境界・強制

外部入力に誘導されたAgentが「安全です」と説明したり、別のAPIや再試行経路を使ったりして、
操作に必要な制限を避ける場合を考える。保護対象は本番データと、分類に応じた実行制御である。

Trust Boundary（信頼境界）はAgentの提案と、操作を許可・実行する側の間。
Security Invariant（守るべき性質）は、説明や呼び出し経路が変わっても制限が外れないこと。
Enforcement Point（強制する場所）は実際の副作用が生じる前の実行経路である。
Researchも代替経路による迂回や、分類不明時の無条件許可を問題として扱う。[Research][research]

## 検証と保証範囲

禁止された削除が下流へ届かず、データも削除されないことを確認する。拒否ログや警告だけでは
実行を阻止した証拠にならない。承認待ち・許可についてもルールどおりの下流結果を照合する。

Negative Test（不正や失敗条件を意図的に試す検証）では、未承認要求、再試行、直接呼び出し、
分類の欠落や取得失敗を試す。分類・適用ルール・判断・実際の操作結果を対応付ける。
分類が正しくても制御が働かない問題と、分類そのものが誤っている問題を区別する。

## 対話の再構成

**問い：通常経路で拒否する削除を、分類チェックがない再試行処理から実行できる。適合するか。**

学習者：「No」

整理：再試行で制限が外れるためFail。再試行は実行制限の例外ではない。

**問い：分類管理サービス停止時、分類を確認できず対象操作を保留した。この挙動は適切か。**

学習者：「はい。可用性の要件ではないので」

整理：今回の保留は適切。分類不明のまま制限を省いて実行しない。
ただし可用性を考えなくてよいわけではない。継続が必要なら、有効性を確認できる分類の
キャッシュなど、制限を維持できる代替手段を設計する。キャッシュは無条件の解決策ではなく、
失効・変更・鮮度・実対象との対応を確かめる必要がある。

**所感：個々の要件は単純だが、俯瞰すると複雑になる。観点の軸を持つため個別理解が重要。**

整理：分類の誤り、承認不足、実行制限の迂回を切り分けられるようになる。
実装は一つの仕組みで複数要件を支えてもよく、要件ごとに製品を導入する必要はない。

**質問：具体的にどのようなソリューションやツールで制御するのか。**

以下の構成と使い分けを説明した。

## 実装へ結び付ける考え方

```text
Agentの要求
  → ツール実行API／Gateway
      → 実対象に対応する信頼できる分類を取得
      → 操作者・対象・分類・承認状態から判断
      → 拒否／承認待ち／実行
  → 許可された場合だけ下流APIへ
```

PDP（Policy Decision Point）は許可・拒否を判断する仕組み。
PEP（Policy Enforcement Point）はその判断に従って実行を止める場所。
分類はAgentの自己申告をそのまま使わず、管理された根拠から取得する。

| 選択肢 | 担わせる役割・利用場面 |
|---|---|
| アプリケーション内の条件分岐 | 操作やルールが少ない段階で、分類と承認状態を確認し実行を制限する。 |
| OPA（Open Policy Agent） | 操作・分類・対象環境などのデータでルールを評価する。判断結果はAPI側で強制する。 |
| Cedar | 主体・操作・対象と属性や条件に基づいて認可を判断する。結果の適用はアプリケーション側が担う。 |
| Amazon Bedrock AgentCore Gateway＋Policy | Gatewayを通るツール呼び出しへCedarによる制御を適用する選択肢。 |

製品機能の参照日は2026-09-10。特定版への実装検証や、この要件への製品適合を示すものではない。
OPAの外部データとAPI連携、Cedarの判断とアプリケーションの関係、AgentCoreの認可経路は
下記の公式資料を参照した。採用時には利用版・構成を再確認する。

これらが業務操作の可逆性を自動で正しく決めるわけではない。承認画面・通知・承認状態の保存も
別途設計する。Agentが別の資格情報で下流APIを直接呼べるなら、Gatewayの拒否を迂回できる。
下流の認可と資格情報の配置を含めて、制御を通る経路に限定する。

小規模なら一つの実行APIに明示的なルールを置き、必要性が増したら判断を共通化する、という
進め方を提案した。これは設計上の選択肢であり、特定製品の導入要件ではない。

## 洞察と後から使う問い

- 分類に応じた制限は、再試行時や障害時にも維持する。
- 判断エンジンの導入と、実際の実行阻止は別の確認事項である。
- 個別要件を理解することで、複雑な構成のどの保証が欠けたかを切り分けられる。

設計レビューでは「分類は誰から取得するか」「どこで実行を止めるか」「別経路はあるか」
「分類が取得できない場合はどうなるか」「下流で何が起きなかったと実証できるか」を確認する。
