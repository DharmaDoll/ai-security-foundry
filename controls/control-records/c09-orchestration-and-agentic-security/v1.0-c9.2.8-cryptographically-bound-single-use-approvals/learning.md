# C9.2.8：承認を具体的な操作へ結び付け、一度だけ使う

AISVS Verification Level: 3

[Control本文：解釈・検証・証拠・限界](README.md)

## 要件と資料の位置づけ

対象は`v1.0-C9.2.8`。採用済み固定Revisionは
`78775233666a2022dcfb82037e5e029116955c00`。

> Verify that approvals are cryptographically bound to action parameters, requester identity, execution context, and a unique single-use nonce.

日本語訳：承認が、操作パラメータ、要求者の識別情報、実行コンテキスト、および固有の一回限りの
nonceに、暗号的に結び付けられていることを確認する。[要件本文][normative]

Normativeは要件本文、Researchは補足。具体例と設計への翻訳はRepository interpretation、
対話からの整理は学習上の洞察である。学習完了はControl成熟度や製品適合を変更しない。

## 具体例と用語

担当者が「注文Aについて顧客へ1万円返金する」というAgentの要求を承認した。
承認データが単なる「承認済み」なら、別の注文や金額へ使い回せる可能性がある。

| 結び付ける情報 | 具体例 |
|---|---|
| 操作パラメータ | 注文A、返金先、金額1万円、通貨。 |
| 要求者の識別情報 | どの認証済み主体の要求か。 |
| 実行コンテキスト | どのサービス・環境・実行セッションで使うか。 |
| nonce（ノンス） | この一回の承認を識別する固有値。使用済みを判定するために使う。 |

暗号的な結合は、例えば全情報をまとめてデジタル署名し、改変や偽造を検出できるようにすること。
暗号化して読めなくすることとは別である。署名は実装例であり特定方式を必須としない。

Replay（リプレイ）は正しい承認をコピーして再送・再利用すること。
署名を壊さずに繰り返せるため、署名検証だけでは再利用防止にならない。

## 脅威・信頼境界・強制

攻撃者や侵害されたAgentが承認データを入手し、別の金額・対象・要求者・実行先へ転用したり、
同じ返金を繰り返したりする場面を考える。資産は承認データ、検証鍵、使用済み状態、返金対象の資金。

Trust Boundary（信頼境界）は承認発行元、承認を運ぶAgent、実行するAPIの間にある。
Security Invariant（守るべき性質）は、この承認で受付できるのは、指定された主体・場面・操作の
一回だけであること。Enforcement Point（強制点）は、副作用の前に検証と使用済み管理を行う実行側。

1. 信頼する発行元の署名として正しいかを確認する。
2. 承認内容と実際の操作・要求者・実行先が一致するかを確認する。
3. 未使用確認と使用済みへの更新を一体で扱い、成功した一つの処理だけを実行へ進める。

署名が正しくても別操作への使用は拒否する。承認時と実行時で、値や対象の解釈も一致させる。
Researchは正規化、実行前検証、並列再利用、使用済み状態の保持を補足する。[Research][research]

## 検証と隣接する保証

| 試験・観測 | 評価 |
|---|---|
| 正規承認に一致する返金を一度受付し、再利用を拒否する | 内容の結合と一回性を裏付ける。 |
| 1万円の署名を検証するが、実行では別途渡された10万円を採用する | 署名と実行の対応がなくFail。 |
| 注文・要求者・実行先を変更した要求を拒否する | 転用防止を裏付ける。 |
| 同じ承認を並列送信すると両方受付される | 一回性を維持できずFail。 |

Negative Test（不正や失敗条件を意図的に試す検証）では各項目の差し替え、並列再送、再起動、
使用済み管理の障害を試す。承認内容、実要求、検証結果、nonceの消費、下流結果を対応付けて残す。

C9.2.2は人が見る内容の完全性、C9.2.9は承認発行鍵の隔離を扱う。
暗号的に正当でも、人が誤った返金を承認したという業務判断の間違いまでは防がない。

## 対話の再構成

**問い：署名された承認は注文Aへの1万円返金だが、APIは署名の正しさだけを確認し、
Agentが別途指定した10万円を返金する。適合するか。**

学習者：「Fail.署名検証とAPI実行は結び付けておく必要がある。」

整理：正しい署名と実行内容の一致は別の確認であり、両方必要。

**所感：リプレイ攻撃対策の思想ではないか。未使用確認と使用済み更新を一体で扱うことが
実装上重要だと感じた。**

整理：そのとおり。本要件には、別操作への差し替え防止と、同じ承認の再利用防止の二本柱がある。
確認と更新が別々だと、次の競合が起きる。

```text
処理A：未使用と確認
処理B：未使用と確認
処理A：使用済みに更新 → 返金
処理B：使用済みに更新 → 返金
```

途中への割り込みによる二重取得を許さず、未使用から使用済みへ変更できた一つの処理だけを
進める性質を原子性と呼ぶ。単にランダムな値を付けるだけでは達成しない。

## 障害復旧と一回性の限界

使用済みにした後で通信が切れると、返金が成功したか不明になる場合がある。
そこで安易にnonceを未使用へ戻すと、再実行により二重返金する危険がある。
結果照会や、同じ取引IDでは重複処理しない下流APIの仕組みを含めて復旧を設計する。
同じ要求を繰り返しても追加の効果を生まない性質は冪等性と呼ぶ。

nonceの消費と外部APIの返金は、常に一つの不可分な処理にできるわけではない。
承認を一度だけ受付する仕組みを作ったことだけで、外部システム全体の処理が必ず一度だけ
成功するとは主張しない。この復旧設計は今回の実装上の補足であり、特定DBや製品を必須にしない。

## 洞察と設計レビューへの問い

**署名の正しさ、実行内容の一致、一回限りの使用をつなげる。**

- 承認した値と、APIが実際に使う値は一致するか。
- 要求者・実行先を差し替えても正しい署名として通っていないか。
- 並列処理・再起動でも使用済み状態を維持するか。
- 結果不明の操作を、未使用扱いに戻して再実行していないか。

承認の一回性と業務処理の重複防止をつなぐところに、実装の難しさがある。
