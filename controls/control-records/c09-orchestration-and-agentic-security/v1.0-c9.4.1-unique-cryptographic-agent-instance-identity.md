# 各Agent Instanceを固有の暗号的Identityで認証する

AISVS Verification Level: 2

## Upstream basis

AISVS `v1.0-C9.4.1`を解釈する。要件本文は各Agent Instanceが固有の暗号的Identityを持ち、下流Systemへ独立した主体として認証することを求める。
採用済みstable v1.0の固定Revisionで本文と対応Researchの要件別検証・限界を確認した。
最新の版・製品への追従を意味しない。

Researchは同じPrincipalに異なる鍵を発行しても個体識別にならない点、下流で認められるIdentityを確認する方法を補足する。
以下の具体例・Property・検証条件はRepository interpretationである。
Researchの製品、統計、事件、外部Framework Mappingを未検証のまま転記せず、
例示された実装方式を一律の適合条件にしない。

## Interpretation

どのAgent個体かを下流側が暗号的に確認できるようにする。『agent-1』という自己申告Headerや、全Agentが共有するService Accountだけでは個体を識別できない。

2つのWorkerが別証明書を持っていても、下流では同じPrincipalに解決されるなら個体の区別が失われる。下流が受理した識別子と実際のInstanceを照合する。

## Security objective

Agentのなりすまし・共有資格情報による主体の混同を減らし、個体単位の責任と制御を可能にする。

## Applicability

下流Systemを利用するAgent Instance。単体でも対象。

### Non-applicability

独立したAgent実行・下流認証のない範囲は対象外とできる。利用者の資格情報で動くことは代替にならない。

## Scope and assumptions

Instanceの生成・再起動・置換・終了の境界とID再利用方針を定める。暗号的に確認した個体IDが信頼するGateway経由で下流へ保たれる構成も、その対応を評価する。

対象構成・採用Policy・許容する動作と評価境界を検証前に固定する。
不明な構成を安全と仮定せず、未確認範囲をEvidenceの不足として残す。

## Assets, actors, identities, and trust boundaries

資産は個体Identityと資格情報。発行Authority、実行Instance、仲介者、下流Verifierを分ける。強制点は発行時の対応確認と下流認証。

## Required security properties

Security Invariantは守るべき性質、Enforcement Pointはそれを実際に強制する場所を指す。

| ID | 必要な性質と観測条件 |
|---|---|
| SP-1 | 各稼働Instanceを固有の暗号的Identityへ対応付ける。 |
| SP-2 | 下流が自己申告ではなく信頼する資格情報から個体を認証する。 |
| SP-3 | 仲介や共有資格情報で個体の区別を失わない。 |

## Scope calibration and adjacent assurance

利用者の委任IdentityはAgent個体と別に必要になる場合がある。個体認証が成功しても認可やユーザScopeは保証されない。

## Threat and failure-mode rationale

侵害Agentが別個体を名乗り、共通資格情報を利用して他Agentの操作として記録・認可される。

この保証の分析では外部脅威IDを付与する追加価値を確定していない。
攻撃者能力・失敗経路を具体化し、`threat_mappings`は空とする。
ResearchのMappingを自動採用せず、必要時に一次Sourceの固定版で別途評価する。

## Verification

### Architecture and configuration review

全稼働Instanceから発行記録、受理されたPrincipal、仲介での属性変換まで追跡する。

### Positive verification

2 Instanceの呼出しで下流が異なる個体を認証し、各発行記録へ追跡できることを示す。

### Negative and abuse-case verification

許可された試験環境と模擬Dataを用いる。モデルが協力することに依存せず、
必要に応じて実行境界へ試験要求を直接与える。

| ID | 条件・操作 | 期待結果・対応Property |
|---|---|---|
| N-1 | 別Instanceの名前をHeaderで名乗る | 認証されたIdentityは変わらない。SP-2 |
| N-2 | 別鍵だが共通Principalで2体を起動 | 個体識別不足として検出。SP-1 |
| N-3 | 仲介が全呼出しを共通Serviceへ潰す | 個体の信頼可能な対応が失われるならFail。SP-3 |
| N-4 | 未信頼発行者・不正資格情報を提示 | 個体として受理しない。SP-2 |

### Failure conditions

上表の期待結果に反する観測やSPの不成立は、本ControlのFailを裏付ける。
試験未実施、構成不明、結果を追跡できない場合はPassを裏付ける証拠不足であり、
実証された回避と区別する。隣接要件の不備だけで本Controlの意味を広げない。

## Known limitations and uncertainty

資格情報自体を盗まれた場合の利用阻止は別保証が必要。固有IDだけでHardware個体の真正性や権限妥当性を証明しない。

`verifiable`は本Artifactに解釈・脅威・検証・証拠期待値が揃った状態を表す。
製品試験の実施・製品適合・学習完了を意味しない。有限の試験で未知の攻撃を全て否定しない。
Engineering PatternとMappingは独立して評価し、その存在を本Controlの成熟条件にしない。
