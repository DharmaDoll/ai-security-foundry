# 長時間Agentの各特権操作を現在のPolicyで再評価する

AISVS Verification Level: 3

## Upstream basis

AISVS `v1.0-C9.5.6`を解釈する。要件本文は長時間Agent Sessionが各特権操作で現在のBackend認可Policyを再評価することを求める。
採用済みstable v1.0の固定Revisionで本文と対応Researchの要件別検証・限界を確認した。
最新の版・製品への追従を意味しない。

Researchは有効Tokenや既存接続だけで権限を維持する問題、Queue・再開・失効通知の遅れを補足する。
以下の具体例・Property・検証条件はRepository interpretationである。
Researchの製品、統計、事件、外部Framework Mappingを未検証のまま転記せず、
例示された実装方式を一律の適合条件にしない。

## Interpretation

Session開始時に許されたことを、その後の全操作の許可としない。実行直前の特権操作ごとに、現在の役割・Scope・Resource Policyを反映した判断を得る。

Aliceの書込権限を取り消した後、AgentのTokenがまだ有効でも次の更新操作は拒否する。WebSocketが接続済みだから更新を続けられる構成は不足。

## Security objective

長時間実行・再開・既存接続が失効した権限を温存することを防ぐ。

## Applicability

長時間Session、Background Worker、Queue、再開可能なAgentの特権操作。

### Non-applicability

持続するSessionも特権操作もない範囲は対象外を検討できる。『短いToken』だけで長い実行Lifecycleを除外しない。

## Scope and assumptions

現在のPolicy版を確認する境界と失効の伝播を明示。Cache利用は現在性を確認できる場合に限定し、古いTTL内だから許可するだけでは再評価にならない。伝播遅延の実測を隠して即時と表現しない。

対象構成・採用Policy・許容する動作と評価境界を検証前に固定する。
不明な構成を安全と仮定せず、未確認範囲をEvidenceの不足として残す。

## Assets, actors, identities, and trust boundaries

資産は現在の認可状態。Policy正本、更新通知・Cache、Agent Session、PEP、Resourceを分ける。強制点は各特権操作の受付・実行前。

## Required security properties

Security Invariantは守るべき性質、Enforcement Pointはそれを実際に強制する場所を指す。

| ID | 必要な性質と観測条件 |
|---|---|
| SP-1 | 各特権操作で現在のPolicyによる判断を行う。 |
| SP-2 | 未期限Token・既存接続・再開でも失効済み許可を使い続けない。 |
| SP-3 | 現在性を確認できない場合に古いAllowへFallbackしない。 |

## Scope calibration and adjacent assurance

定期Credential Rotationは現在Policyの再評価ではない。既に確定した操作の取消や全Systemの瞬時失効までは同じ保証にしない。

## Threat and failure-mode rationale

退職・権限縮小・Agent停止後も古いSessionが残り、Queueや長期接続から特権操作を続ける。

この保証の分析では外部脅威IDを付与する追加価値を確定していない。
攻撃者能力・失敗経路を具体化し、`threat_mappings`は空とする。
ResearchのMappingを自動採用せず、必要時に一次Sourceの固定版で別途評価する。

## Verification

### Architecture and configuration review

全特権経路の評価時点、Policy正本と版、通知遅延、Cache、再開・Queue・持続接続を確認する。

### Positive verification

現在のPolicyで許可された操作を継続でき、Scope縮小後は新しい範囲内の操作だけが成功することを示す。

### Negative and abuse-case verification

許可された試験環境と模擬Dataを用いる。モデルが協力することに依存せず、
必要に応じて実行境界へ試験要求を直接与える。

| ID | 条件・操作 | 期待結果・対応Property |
|---|---|---|
| N-1 | Token期限内にユーザ・Agent権限を取り消す | 次の特権操作を現在Policyで拒否。SP-1, SP-2 |
| N-2 | 既存接続・Queue・再開から実行 | 同じ再評価を通る。SP-2 |
| N-3 | Policy更新通知を欠落・遅延させる | 現在性を確認できなければ再照会または拒否。SP-3 |
| N-4 | 別対象・別主体のAllow Cacheを使う | 要求一致と現在性を検証し流用を拒否。SP-1, SP-3 |

### Failure conditions

上表の期待結果に反する観測やSPの不成立は、本ControlのFailを裏付ける。
試験未実施、構成不明、結果を追跡できない場合はPassを裏付ける証拠不足であり、
実証された回避と区別する。隣接要件の不備だけで本Controlの意味を広げない。

## Evidence expectations

| Evidence class | Producer | Scope | Freshness | Integrity and sensitivity | Acceptance criteria |
|---|---|---|---|---|---|
| 再評価経路と現在性設計 | Policy・Runtime管理者 | 全特権経路 | 対象機構・Policy変更後、定期回帰時 | 評価Revision・時刻・試験IDを保持。アクセス制限し模擬Dataを使う | 正本・版・評価時点が明確 |
| 失効と操作の時系列 | Resource・検証者 | 接続・Queue・再開 | 対象機構・Policy変更後、定期回帰時 | 評価Revision・時刻・試験IDを保持。アクセス制限し模擬Dataを使う | 更新後の操作結果と遅延を追跡 |
| 通知・Cache障害試験 | 検証者 | 現在性が不明な状態 | 対象機構・Policy変更後、定期回帰時 | 評価Revision・時刻・試験IDを保持。アクセス制限し模擬Dataを使う | 古いAllowを根拠にしない |

成功と失敗の両方について、設定だけでなく実際の結果を採用構成へ対応付ける。
本Repositoryには期待値のみを置き、本番Evidence、Secret、顧客情報は保存しない。
特定の監査製品やログ形式は、本Controlが明示する性質を満たすための唯一の方式ではない。

## Known limitations and uncertainty

分散SystemでPolicyの現在性を保証するには整合性と可用性のTrade-offがある。許容した失効遅延を要件充足の証明と混同せず、保証範囲と残る窓を明示する。

`verifiable`は本Artifactに解釈・脅威・検証・証拠期待値が揃った状態を表す。
製品試験の実施・製品適合・学習完了を意味しない。有限の試験で未知の攻撃を全て否定しない。
Engineering PatternとMappingは独立して評価し、その存在を本Controlの成熟条件にしない。
