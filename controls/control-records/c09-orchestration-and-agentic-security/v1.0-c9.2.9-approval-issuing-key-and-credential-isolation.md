# 承認を発行する鍵・資格情報をAgentから隔離する

AISVS Verification Level: 3

## Upstream basis

AISVS `v1.0-C9.2.9`を解釈する。要件本文は承認発行に使う暗号鍵・資格情報をAgent Runtimeから隔離することを求める。
採用済みstable v1.0の固定Revisionで本文と対応Researchの要件別検証・限界を確認した。
最新の版・製品への追従を意味しない。

Researchは非Export鍵でも署名APIを自由に使えると承認を偽造できる点、Signerが有効な承認判断を検証する必要を補足する。
以下の具体例・Property・検証条件はRepository interpretationである。
Researchの製品、統計、事件、外部Framework Mappingを未検証のまま転記せず、
例示された実装方式を一律の適合条件にしない。

## Interpretation

Agentが秘密鍵を読めないだけでなく、同じ権限で任意の承認を発行できない境界を作る。鍵保管先の名称や別Processであることだけでは隔離を証明しない。

鍵をKMSに置いてもAgentが任意の内容をSignできれば、鍵を取り出さずに偽承認を作れる。署名Serviceは承認済みの正当な要求だけを受け付ける必要がある。

## Security objective

Agent侵害から承認の発行権限まで奪われることを防ぐ。

## Applicability

暗号的承認を発行する鍵・API資格情報を使う構成。

### Non-applicability

承認発行に暗号鍵・資格情報がない範囲では本境界は対象外とできるが、暗号的承認を要求するC9.2.8の欠落を正当化しない。

## Scope and assumptions

Agent Runtime侵害を仮定して実効権限を評価する。鍵の読取、署名、管理、Policy変更、復旧・再発行の経路を含める。特定HSM等を必須にしない。

対象構成・採用Policy・許容する動作と評価境界を検証前に固定する。
不明な構成を安全と仮定せず、未確認範囲をEvidenceの不足として残す。

## Assets, actors, identities, and trust boundaries

資産は鍵、署名権限、承認者の資格情報。Agent、承認Service、鍵管理者、管理・Deploy基盤を分ける。強制点は秘密取得と承認発行・管理の認可境界。

## Required security properties

Security Invariantは守るべき性質、Enforcement Pointはそれを実際に強制する場所を指す。

| ID | 必要な性質と観測条件 |
|---|---|
| SP-1 | Agentから鍵・発行資格情報を取得できない。 |
| SP-2 | Agentの要求だけで任意承認を発行できない。 |
| SP-3 | 鍵・発行Policy・Serviceを同じ権限で置換・再配置・管理できない。 |

## Scope calibration and adjacent assurance

鍵が隔離されても承認判断の入力が偽造可能なら全体は安全ではない。発行機能をAgentへ無制限公開する構成は、本Controlの実効的隔離を欠く。

## Threat and failure-mode rationale

Runtime侵害者が環境変数・Disk・Logから鍵を取得するか、署名APIをOracleとして利用し承認を偽造する。

この保証の分析では外部脅威IDを付与する追加価値を確定していない。
攻撃者能力・失敗経路を具体化し、`threat_mappings`は空とする。
ResearchのMappingを自動採用せず、必要時に一次Sourceの固定版で別途評価する。

## Verification

### Architecture and configuration review

読取とSign、管理・Deploy・Backupの権限を別々に確認し、Agentが有する全資格情報で到達性を調べる。

### Positive verification

人の承認済み要求だけがSignerで署名され、Agentを介さず検証可能な承認が発行されることを示す。

### Negative and abuse-case verification

許可された試験環境と模擬Dataを用いる。モデルが協力することに依存せず、
必要に応じて実行境界へ試験要求を直接与える。

| ID | 条件・操作 | 期待結果・対応Property |
|---|---|---|
| N-1 | Agent権限で鍵・資格情報を読む | 取得できない。SP-1 |
| N-2 | 承認記録なしにSignを要求 | 拒否される。SP-2 |
| N-3 | Signer設定・Deploy・復旧APIを操作 | 権限外操作を拒否。SP-3 |
| N-4 | Log・Trace・Dumpから鍵を探す | Agent境界に秘密が漏れない。SP-1 |

### Failure conditions

上表の期待結果に反する観測やSPの不成立は、本ControlのFailを裏付ける。
試験未実施、構成不明、結果を追跡できない場合はPassを裏付ける証拠不足であり、
実証された回避と区別する。隣接要件の不備だけで本Controlの意味を広げない。

| 鍵・API・管理権限Matrix | 鍵基盤管理者 | 読取・Sign・Deploy | 対象機構・Policy変更後、定期回帰時 | 評価Revision・時刻・試験IDを保持。アクセス制限し模擬Dataを使う | Agentに発行支配権がない |
| 取得・偽発行試験 | 検証者 | 実効資格情報と経路 | 対象機構・Policy変更後、定期回帰時 | 評価Revision・時刻・試験IDを保持。アクセス制限し模擬Dataを使う | 秘密非取得と任意署名不可 |

## Known limitations and uncertainty

鍵基盤の管理者侵害や暗号方式の破綻まで本境界だけでは保証しない。鍵Rotation・復旧で一時的に権限が広がらないようにする。
