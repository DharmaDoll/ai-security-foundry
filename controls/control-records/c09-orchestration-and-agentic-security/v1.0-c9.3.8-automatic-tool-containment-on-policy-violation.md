# Policy違反時にツールを自動的に封じ込める

AISVS Verification Level: 3

## Upstream basis

AISVS `v1.0-C9.3.8`を解釈する。要件本文はPolicy違反が自動的なTool封じ込めを起動することを求める。
採用済みstable v1.0の固定Revisionで本文と対応Researchの要件別検証・限界を確認した。
最新の版・製品への追従を意味しない。

Researchは違反検出から無効化・隔離・後続呼出し阻止までの実経路、処理中要求、誤検出の影響を補足する。
以下の具体例・Property・検証条件はRepository interpretationである。
Researchの製品、統計、事件、外部Framework Mappingを未検証のまま転記せず、
例示された実装方式を一律の適合条件にしない。

## Interpretation

違反を記録・通知するだけでなく、該当Toolが被害を続ける能力を自動的に制限する。何を止めるかと回復条件を定義し、検出イベントが実際の制御へ到達することを試験する。

Toolが未許可Pathへ書こうとしたら、対象の実行停止や資格情報制限を起動し、次の呼出しも拒否する。担当者が翌朝Logを読むだけでは自動封じ込めでない。

## Security objective

違反後もToolが継続利用されることによる被害拡大を抑える。

## Applicability

Policyに基づいて実行・権限を制限するTool環境。

### Non-applicability

Toolがない範囲は対象外。検出機構がないことは自動封じ込め不要の理由ではない。

## Scope and assumptions

対象Policyと違反イベント、封じ込め単位、遅延、進行中処理、解除手順を定める。既知のPolicy違反の自動処理を評価し、全未知攻撃の検出とは分ける。

対象構成・採用Policy・許容する動作と評価境界を検証前に固定する。
不明な構成を安全と仮定せず、未確認範囲をEvidenceの不足として残す。

## Assets, actors, identities, and trust boundaries

資産はTool能力と隔離状態。Tool、検出機構、封じ込めController、復旧管理者を分ける。強制点は実行・通信・資格情報・受付等。

## Required security properties

Security Invariantは守るべき性質、Enforcement Pointはそれを実際に強制する場所を指す。

| ID | 必要な性質と観測条件 |
|---|---|
| SP-1 | 対象Policy違反から自動制御への対応がある。 |
| SP-2 | 封じ込めが実際の能力・後続実行を制限する。 |
| SP-3 | 再試行・再起動・イベント障害で未確認の正常状態へ戻らない。 |

## Scope calibration and adjacent assurance

通常の認可拒否と侵害を疑う違反の扱いは明示する。人の通知だけは不足。全群停止はC9.1.3の別範囲。

## Threat and failure-mode rationale

侵害Toolが一度の拒否後に別経路・再試行で不正操作を続ける。検出と制御の配線漏れで警告だけが出る。

この保証の分析では外部脅威IDを付与する追加価値を確定していない。
攻撃者能力・失敗経路を具体化し、`threat_mappings`は空とする。
ResearchのMappingを自動採用せず、必要時に一次Sourceの固定版で別途評価する。

## Verification

### Architecture and configuration review

違反分類、イベント配信、強制API、進行中処理、解除と再登録を追う。

### Positive verification

正常Toolは継続し、模擬違反したToolだけが定めた範囲で封じ込められることを確認する。

### Negative and abuse-case verification

許可された試験環境と模擬Dataを用いる。モデルが協力することに依存せず、
必要に応じて実行境界へ試験要求を直接与える。

| ID | 条件・操作 | 期待結果・対応Property |
|---|---|---|
| N-1 | 模擬Policy違反を発生 | 人の介入前に制御が起動。SP-1 |
| N-2 | 封じ込め後に同じToolを再呼出し | 隔離を保つ。SP-2 |
| N-3 | 再起動・再登録で復活を試す | 未承認解除を防ぐ。SP-3 |
| N-4 | 制御APIの障害・遅延を起こす | 封じ込め未完了を明示し安全な代替制限を適用。成功と偽らない。SP-2, SP-3 |

### Failure conditions

上表の期待結果に反する観測やSPの不成立は、本ControlのFailを裏付ける。
試験未実施、構成不明、結果を追跡できない場合はPassを裏付ける証拠不足であり、
実証された回避と区別する。隣接要件の不備だけで本Controlの意味を広げない。

## Evidence expectations

| Evidence class | Producer | Scope | Freshness | Integrity and sensitivity | Acceptance criteria |
|---|---|---|---|---|---|
| 違反と制御の対応表 | Security運用 | 対象Policy | 対象機構・Policy変更後、定期回帰時 | 評価Revision・時刻・試験IDを保持。アクセス制限し模擬Dataを使う | 自動処理が具体的 |
| 封じ込め実測 | 検証者・Controller | 検出から能力停止 | 対象機構・Policy変更後、定期回帰時 | 評価Revision・時刻・試験IDを保持。アクセス制限し模擬Dataを使う | 遅延と残る処理が確認可能 |
| 解除・障害試験 | 運用者 | 再起動・制御障害 | 対象機構・Policy変更後、定期回帰時 | 評価Revision・時刻・試験IDを保持。アクセス制限し模擬Dataを使う | 未確認の復帰がない |

成功と失敗の両方について、設定だけでなく実際の結果を採用構成へ対応付ける。
本Repositoryには期待値のみを置き、本番Evidence、Secret、顧客情報は保存しない。
特定の監査製品やログ形式は、本Controlが明示する性質を満たすための唯一の方式ではない。

誤検出は可用性を損なう。進行中外部取引を取り消せない場合があり、停止の達成範囲を明記する。

`verifiable`は本Artifactに解釈・脅威・検証・証拠期待値が揃った状態を表す。
製品試験の実施・製品適合・学習完了を意味しない。有限の試験で未知の攻撃を全て否定しない。
Engineering PatternとMappingは独立して評価し、その存在を本Controlの成熟条件にしない。
