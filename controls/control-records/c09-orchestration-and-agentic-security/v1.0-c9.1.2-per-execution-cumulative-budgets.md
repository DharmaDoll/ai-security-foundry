# 実行全体の累積予算をRuntimeで強制する

AISVS Verification Level: 1

## Upstream basis

AISVS `v1.0-C9.1.2`を解釈する。要件本文は実行ごとの予算を設定しRuntimeで強制することを求める。再帰深度、Token、金額は例示である。
採用済みstable v1.0の固定Revisionで本文と対応Researchの要件別検証・限界を確認した。
最新の版・製品への追従を意味しない。

Researchは個別呼出しの小ささに隠れる累積消費、並列Workerの共有計数、課金計測の遅延を補足する。
以下の具体例・Property・検証条件はRepository interpretationである。
Researchの製品、統計、事件、外部Framework Mappingを未検証のまま転記せず、
例示された実装方式を一律の適合条件にしない。

## Interpretation

一つの実行に属する呼出し・再試行・委任を追跡し、予算を使い切った実行が別の呼出しで消費を続けないようにする。単一Requestの制限や月末の請求通知では代替できない。

調査Agentが1回は安価な検索を繰り返す例で、実行上限20回なら同じ実行の21回目を止める。子Agentを作成しただけで計数をゼロへ戻さない。20回は説明用であり上流指定ではない。

## Security objective

ループ・再帰・並列展開から生じる無制限の費用と資源消費を抑える。

## Applicability

複数回の推論・ツール実行を行うAgentに適用する。自律的でなくても再試行や委任を行う範囲を含む。

### Non-applicability

Agent実行のない範囲は対象外。再帰のない構成では深度の項目を除外できるが、Tokenや費用等の該当する予算まで不要とはしない。

## Scope and assumptions

『一実行』の開始・終了・再開・子処理の帰属を定義する。予算の単位、予約分、実績との差、最大超過幅を設計する。実績が後で判明する消費は、上限予約や保守的見積もり等で強制可能な範囲を示す。

対象構成・採用Policy・許容する動作と評価境界を検証前に固定する。
不明な構成を安全と仮定せず、未確認範囲をEvidenceの不足として残す。

## Assets, actors, identities, and trust boundaries

保護対象は実行予算、課金枠、計数状態。Agentが実行ID・計数を自由に改変する境界と、Runtimeの受付・計数・遮断を分ける。強制点は消費を開始する前の受付と、必要な実行中制御。

## Required security properties

Security Invariantは守るべき性質、Enforcement Pointはそれを実際に強制する場所を指す。

| ID | 必要な性質と観測条件 |
|---|---|
| SP-1 | 実行IDに対象消費と子・再試行の帰属が結び付く。 |
| SP-2 | 設定した累積上限・深度をRuntimeが強制し、通知だけで終わらない。 |
| SP-3 | 並列・再開・計数障害でも予算が不正にリセット・二重使用されない。 |

## Scope calibration and adjacent assurance

Token TTLやツールごとのTimeoutは累積予算ではない。上限で止めることと、すでに完了した外部取引を取り消すことも別。

## Threat and failure-mode rationale

攻撃者や誤動作Agentが相互委任・再試行を繰り返し、小さい呼出しを積み上げる。Workerごとに独立したCounterでは全体上限を超えられる。

この保証の分析では外部脅威IDを付与する追加価値を確定していない。
攻撃者能力・失敗経路を具体化し、`threat_mappings`は空とする。
ResearchのMappingを自動採用せず、必要時に一次Sourceの固定版で別途評価する。

## Verification

### Architecture and configuration review

消費の受付、計数更新、予約・精算、子実行、再開、課金の観測経路を追う。予算変更は誰ができるか確認する。

### Positive verification

上限未満の実行を完了させ、複数呼出しの合計が予算台帳と一致することを確かめる。別の正規実行は独立した予算で扱う。

### Negative and abuse-case verification

許可された試験環境と模擬Dataを用いる。モデルが協力することに依存せず、
必要に応じて実行境界へ試験要求を直接与える。

| ID | 条件・操作 | 期待結果・対応Property |
|---|---|---|
| N-1 | 小さい呼出しを累積上限まで繰り返す | 次の消費を拒否し、進行中分も宣言した最大幅内に制御する。SP-2 |
| N-2 | 複数子Agent・Replicaを同時に動かす | 合計が同一実行へ帰属し、各Replicaが満額を使えない。SP-1, SP-3 |
| N-3 | 実行を再開・再試行しIDの差替えを要求する | 同じ実行の予算をリセットできない。SP-1, SP-3 |
| N-4 | 計数Storeを利用不能にする | 保証できない追加消費を止めるか、事前予約した範囲だけに限定する。SP-2, SP-3 |

### Failure conditions

上表の期待結果に反する観測やSPの不成立は、本ControlのFailを裏付ける。
試験未実施、構成不明、結果を追跡できない場合はPassを裏付ける証拠不足であり、
実証された回避と区別する。隣接要件の不備だけで本Controlの意味を広げない。

## Evidence expectations

| Evidence class | Producer | Scope | Freshness | Integrity and sensitivity | Acceptance criteria |
|---|---|---|---|---|---|
| 実行帰属・予算設定 | Runtime管理者 | 親子・再試行・再開 | 対象機構・Policy変更後、定期回帰時 | 評価Revision・時刻・試験IDを保持。アクセス制限し模擬Dataを使う | 全消費の帰属と単位が明確 |
| 累積・並列試験の台帳 | 検証者・計数基盤 | 消費受付から精算 | 対象機構・Policy変更後、定期回帰時 | 評価Revision・時刻・試験IDを保持。アクセス制限し模擬Dataを使う | 受付拒否と実消費の上限を照合できる |
| 計測遅延と障害試験 | 基盤管理者 | 進行中消費・Store障害 | 対象機構・Policy変更後、定期回帰時 | 評価Revision・時刻・試験IDを保持。アクセス制限し模擬Dataを使う | 最大超過幅と強制方法が測定される |

成功と失敗の両方について、設定だけでなく実際の結果を採用構成へ対応付ける。
本Repositoryには期待値のみを置き、本番Evidence、Secret、顧客情報は保存しない。
特定の監査製品やログ形式は、本Controlが明示する性質を満たすための唯一の方式ではない。

## Known limitations and uncertainty

厳密な金額は提供者の課金単位や遅延に依存する。未知の無限超過を『概算』として許容しない。予算内の有害な操作の正当性は別評価。

`verifiable`は本Artifactに解釈・脅威・検証・証拠期待値が揃った状態を表す。
製品試験の実施・製品適合・学習完了を意味しない。有限の試験で未知の攻撃を全て否定しない。
Engineering PatternとMappingは独立して評価し、その存在を本Controlの成熟条件にしない。
