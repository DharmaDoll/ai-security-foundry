# 利用者の委任Contextを各下流呼出しで維持・強制する

AISVS Verification Level: 2

## Upstream basis

AISVS `v1.0-C9.5.2`を解釈する。要件本文は利用者の代理として動くAgentについて、完全性保護されたScope限定Tokenで利用者の認可Contextを伝播し、全下流呼出しで強制することを求める。
採用済みstable v1.0の固定Revisionで本文と対応Researchの要件別検証・限界を確認した。
最新の版・製品への追従を意味しない。

Researchは同じBearer Tokenを転送することとContextを維持することの違い、Audience・主体・Scopeの各境界での検証を補足する。
以下の具体例・Property・検証条件はRepository interpretationである。
Researchの製品、統計、事件、外部Framework Mappingを未検証のまま転記せず、
例示された実装方式を一律の適合条件にしない。

## Interpretation

Agentが下流へ進んでも、誰のどの範囲の権限で動くかを失わない。下流ごとに適したTokenで必要Contextを保ち、受取側が検証・認可する。単にユーザ名をLogへ付けるだけでは不足。

利用者Aliceが文書Aだけを読める場合、Agent→仲介API→文書APIでもAだけに制限する。仲介の広いService資格情報に置き換えてBを読めるなら委任Contextが失われている。

## Security objective

代理実行で利用者の制限が消え、仲介者の広い権限を使える混乱した代理人の問題を防ぐ。

## Applicability

利用者に代わって下流ServiceやToolへアクセスするAgent。

### Non-applicability

利用者の代理ではなく、明示された自身のService権限でのみ動く範囲はこのユーザContext要件の対象外とできる。ユーザ起点を便宜的にService操作へ付け替えない。

## Scope and assumptions

Tokenは自己完結型・参照型等を想定できるが、Contextの完全性と受理先を保証する。特定のOAuth交換方式・Claim名を必須にしない。Tenant等の必要属性はSystemの境界から決める。

対象構成・採用Policy・許容する動作と評価境界を検証前に固定する。
不明な構成を安全と仮定せず、未確認範囲をEvidenceの不足として残す。

## Assets, actors, identities, and trust boundaries

資産は利用者の権限範囲。利用者、Agent、発行者、仲介、各Resourceの認可を分ける。強制点は各下流のToken検証とPolicy評価。

## Required security properties

Security Invariantは守るべき性質、Enforcement Pointはそれを実際に強制する場所を指す。

| ID | 必要な性質と観測条件 |
|---|---|
| SP-1 | 利用者Contextと委任Scopeを完全性保護したTokenに結び付ける。 |
| SP-2 | 各下流が受理先・発行者・必要Contextを検証し制限を強制する。 |
| SP-3 | 仲介・交換・再試行で委任Scopeを拡大または脱落させない。 |

## Scope calibration and adjacent assurance

署名検証だけで認可は完成しない。Agent自身の権限も別制約として残る。Tokenの短命性や継続的失効は別要件。

## Threat and failure-mode rationale

仲介がユーザContextを失い広い資格情報で操作するか、攻撃者が別Audience・TenantのTokenを転用する。

この保証の分析では外部脅威IDを付与する追加価値を確定していない。
攻撃者能力・失敗経路を具体化し、`threat_mappings`は空とする。
ResearchのMappingを自動採用せず、必要時に一次Sourceの固定版で別途評価する。

## Verification

### Architecture and configuration review

各Hopの発行者、受理先、主体、Scope、必要属性、検証位置をCredential Flowで追う。受理したTokenをそのまま他Resourceへ転送していないか確認する。

### Positive verification

限定ユーザの正常要求が全Hopを通って成功し、最終Resourceが同じ委任範囲へ制限することを示す。

### Negative and abuse-case verification

許可された試験環境と模擬Dataを用いる。モデルが協力することに依存せず、
必要に応じて実行境界へ試験要求を直接与える。

| ID | 条件・操作 | 期待結果・対応Property |
|---|---|---|
| N-1 | 主体・Scope・必要Tenantを欠落・改変 | 該当Hopで拒否。SP-1, SP-2 |
| N-2 | 別AudienceへTokenを転用 | 受理しない。SP-2 |
| N-3 | 仲介で広いScopeを要求 | 元の委任を越えて発行・実行しない。SP-3 |
| N-4 | 広い権限のAgentで限定ユーザの対象外Dataを読む | 最終Resourceで拒否。SP-2, SP-3 |

### Failure conditions

上表の期待結果に反する観測やSPの不成立は、本ControlのFailを裏付ける。
試験未実施、構成不明、結果を追跡できない場合はPassを裏付ける証拠不足であり、
実証された回避と区別する。隣接要件の不備だけで本Controlの意味を広げない。

## Evidence expectations

| Evidence class | Producer | Scope | Freshness | Integrity and sensitivity | Acceptance criteria |
|---|---|---|---|---|---|
| Token Flowと契約 | Identity・Resource管理者 | 各Hop | 対象機構・Policy変更後、定期回帰時 | 評価Revision・時刻・試験IDを保持。アクセス制限し模擬Dataを使う | 完全性とScopeの維持を追跡 |
| 各受理先の認可結果 | Resource側 | 正常とScope外 | 対象機構・Policy変更後、定期回帰時 | 評価Revision・時刻・試験IDを保持。アクセス制限し模擬Dataを使う | 利用者制約が最終操作へ反映 |
| 欠落・改変・転用試験 | 検証者 | 仲介・交換・再試行 | 対象機構・Policy変更後、定期回帰時 | 評価Revision・時刻・試験IDを保持。アクセス制限し模擬Dataを使う | Context喪失を許さない |

## Known limitations and uncertainty

Tokenが正しくてもPolicyや発行者の判断が誤れば危険。複数Hopの全てに観測がない場合、End-to-endの適合は断定しない。

`verifiable`は本Artifactに解釈・脅威・検証・証拠期待値が揃った状態を表す。

Engineering PatternとMappingは独立して評価し、その存在を本Controlの成熟条件にしない。
