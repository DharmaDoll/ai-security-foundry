# Tool Manifestに権限・資源・出力検証要件を宣言する

AISVS Verification Level: 2

## Upstream basis

AISVS `v1.0-C9.3.3`を解釈する。要件本文はTool Manifestが必要権限、資源制限、出力検証要件を宣言することを求める。
採用済みstable v1.0の固定Revisionで本文と対応Researchの要件別検証・限界を確認した。
最新の版・製品への追従を意味しない。

ResearchはTool名や説明だけでは必要能力が分からない点を補足する。ResearchのRuntime強制案はC9.3.4へ分ける。
以下の具体例・Property・検証条件はRepository interpretationである。
Researchの製品、統計、事件、外部Framework Mappingを未検証のまま転記せず、
例示された実装方式を一律の適合条件にしない。

## Interpretation

ツールに何を許し、どれだけ使わせ、何を返す契約かを管理可能な宣言として残す。Manifestは説明付きの設定・契約であり、書いてあるだけで実行権限が制限されるとはしない。

文書変換Toolの宣言に『指定PathのReadと一時領域Write、通信なし、実行期限、出力Schema』を示す。『安全なTool』という自然言語の説明だけでは不足。

## Security objective

必要能力が不明なままツールを導入し、暗黙の広い権限を与えることを防ぐための検証可能な契約を作る。

## Applicability

Runtimeに登録・実行されるツールのManifest。

### Non-applicability

ツールがない範囲は対象外。標準Manifest形式がないことは未宣言の理由にならず、ローカル契約で補える。

## Scope and assumptions

必要な権限・資源・出力要件を用途に応じて定義。不要な能力も『不要』と分かるようにする。Tool版との対応を管理する。

対象構成・採用Policy・許容する動作と評価境界を検証前に固定する。
不明な構成を安全と仮定せず、未確認範囲をEvidenceの不足として残す。

## Assets, actors, identities, and trust boundaries

資産はツール契約。作者の自己申告、Repositoryの採用確認、登録情報、実行物を分ける。強制対象は宣言の完全性と版の対応。

## Required security properties

Security Invariantは守るべき性質、Enforcement Pointはそれを実際に強制する場所を指す。

| ID | 必要な性質と観測条件 |
|---|---|
| SP-1 | 権限・資源制限・出力検証の3種類を宣言する。 |
| SP-2 | 宣言が特定Tool・版・実行物に対応する。 |
| SP-3 | 欠落・矛盾・無制限な曖昧記述を特定できる。 |

## Scope calibration and adjacent assurance

宣言が完全でも実強制がなければC9.3.4は不成立。宣言の必要権限が最小かはC9.3.1等も参照。

## Threat and failure-mode rationale

暗黙の通信や広いFile権限が宣言されず、運用者が誤った前提でToolを登録する。

この保証の分析では外部脅威IDを付与する追加価値を確定していない。
攻撃者能力・失敗経路を具体化し、`threat_mappings`は空とする。
ResearchのMappingを自動採用せず、必要時に一次Sourceの固定版で別途評価する。

## Verification

### Architecture and configuration review

登録済みToolの一覧とManifestを突合し、版・権限・上限・出力Schemaへの参照を確認する。

### Positive verification

正常Toolについて宣言から必要能力と検証契約を再構成し、実装の用途と照合する。

### Negative and abuse-case verification

許可された試験環境と模擬Dataを用いる。モデルが協力することに依存せず、
必要に応じて実行境界へ試験要求を直接与える。

| ID | 条件・操作 | 期待結果・対応Property |
|---|---|---|
| N-1 | 権限・資源・出力の各欄を欠落 | 不完全なManifestとして検出。SP-1, SP-3 |
| N-2 | Tool版だけを変更 | 旧宣言との不一致を検出。SP-2 |
| N-3 | Read-onlyとWrite権限を同時宣言 | 矛盾を解消するまで完全と扱わない。SP-3 |
| N-4 | 説明のみで全制限を曖昧にする | 検証可能な契約不足と判断。SP-1, SP-3 |

### Failure conditions

上表の期待結果に反する観測やSPの不成立は、本ControlのFailを裏付ける。
試験未実施、構成不明、結果を追跡できない場合はPassを裏付ける証拠不足であり、
実証された回避と区別する。隣接要件の不備だけで本Controlの意味を広げない。

## Evidence expectations

| Evidence class | Producer | Scope | Freshness | Integrity and sensitivity | Acceptance criteria |
|---|---|---|---|---|---|
| Manifestと実行物対応 | Tool管理者 | 全登録Tool | 対象機構・Policy変更後、定期回帰時 | 評価Revision・時刻・試験IDを保持。アクセス制限し模擬Dataを使う | 3種の要件と版を追跡 |
| 宣言レビュー | 採用管理者 | 必要能力と用途 | 対象機構・Policy変更後、定期回帰時 | 評価Revision・時刻・試験IDを保持。アクセス制限し模擬Dataを使う | 曖昧さ・矛盾が解消 |
| 欠落・版差分試験 | 検証者 | 契約管理 | 対象機構・Policy変更後、定期回帰時 | 評価Revision・時刻・試験IDを保持。アクセス制限し模擬Dataを使う | 不完全な宣言を検出 |

成功と失敗の両方について、設定だけでなく実際の結果を採用構成へ対応付ける。
本Repositoryには期待値のみを置き、本番Evidence、Secret、顧客情報は保存しない。
特定の監査製品やログ形式は、本Controlが明示する性質を満たすための唯一の方式ではない。

## Known limitations and uncertainty

Manifestは自己申告になり得る。署名されていても内容が正しいとは限らない。物理的な隔離や実行拒否まで本要件単独では保証しない。

`verifiable`は本Artifactに解釈・脅威・検証・証拠期待値が揃った状態を表す。
製品試験の実施・製品適合・学習完了を意味しない。有限の試験で未知の攻撃を全て否定しない。
Engineering PatternとMappingは独立して評価し、その存在を本Controlの成熟条件にしない。
