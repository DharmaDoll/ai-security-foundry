# C9.4.3：Agentの資格情報を定期更新する

AISVS Verification Level: 3

[Control本文：解釈・検証・証拠・限界](README.md)

## 要件と資料の位置づけ

対象は`v1.0-C9.4.3`。採用済みAISVS v1.0の固定Revisionは
`78775233666a2022dcfb82037e5e029116955c00`。

> Verify that agent identity credentials rotate on a defined schedule.

日本語訳：AgentのIdentity資格情報が、定義されたスケジュールで更新されることを確認する。[要件本文][normative]

Normativeは定めた周期での更新を要求する。Researchは実際の発行・更新の確認や失効との違いを補足する。
以下の移行期間・障害シナリオはRepository interpretation、運用コストの考察は対話から得た洞察である。
Researchの製品・統計・事件・Mappingは本ノートで採用していない。
学習完了はControl成熟度や製品適合を変更しない。

## 具体例と用語

社内APIを呼ぶAgentの認証用APIキーが盗まれたとする。攻撃者はそのキーを提示し、Agentになりすまして
APIへアクセスする。同じキーを無期限に受理する構成では、そのアクセス能力も長く残る。

資格情報（Credential）は、主体が自分の身元を証明するための秘密鍵・証明書・Tokenなどである。
Rotationは新しい資格情報へ切り替えること。旧新併存期間は、無停止で移行するために両方を受理する期間を指す。
失効は資格情報を利用できなくする処理であり、定期更新とは別に漏えい発覚時にも必要になる。

```text
新資格情報を発行 → Agentが切替 → 下流APIが受理 → 移行期間後に旧資格情報を拒否
```

守るべき資産はAgentとして認証できる能力である。Trust Boundaryは発行基盤からAgentへの配布と、
Agentから下流APIへの認証にある。Security Invariantは、定義した切替・終了条件を超えて古い資格情報が
使われ続けないこと。Enforcement Pointは発行基盤、Agentの資格情報取得処理、下流APIの認証処理となる。

C9.4.1の個体識別、C9.4.2の操作証拠に対し、本要件は資格情報の時間的なLifecycleを扱う。
C5.1.2のTokenの短命性・Scopeや、C5.2.6のJIT特権とも評価軸が異なる。

## 対話の再構成

### 新しいキーを発行しても古いキーが使える

問い：毎日APIキーを更新しAgentも切り替えるが、障害回避のため下流APIは過去の全キーを無期限に受理する。

学習者：「Fail」

整理：正しい。盗まれた古いキーの利用期間が終わっていない。

> 更新の完了は、古い資格情報が使えなくなるところまで確認する。

### 更新基盤が停止したらどうするか

問い：証明書の有効期間は60分、更新は30分ごと。更新基盤が停止しても有効期間内は処理を継続し、
期限切れ後は下流APIが認証を拒否する。Agentは要認証操作を停止し通知する。

学習者：「Yes」

整理：期限を無制限に延ばさず、障害時にも古い資格情報の利用を終了できている。
ただし予定どおりの更新自体には失敗している。安全な障害処理が成立したことを、
更新Schedule全体に適合したという意味へ広げない。

30分・60分は説明用の数値であり、要件が指定する周期ではない。
期限前の余裕を持った更新、再試行、通知、発行基盤の冗長化は、可用性と両立させるための設計上の選択肢である。

## 運用コストとLevelについての所感

学習者：「Level 3だけあって、普通のサービスではここまでやるのは厳しいと思った。」

複数Agentと下流サービスをまたぐ更新・切替・旧資格情報の拒否・障害対応は負担が大きい。
既存の発行・更新基盤を利用できる場合と、長期APIキーを前提としたサービスを組み合わせる場合では、
導入コストが異なる。まず対象となるAgent資格情報を特定し、更新周期と切替条件を設計する。
全ての下流サービス用秘密を無条件に本要件と同一Scopeにせず、その役割を区別する。

> 資格情報の定期更新は、鍵を交換する処理よりも、交換を続けながらサービスを運用する仕組みが難しい。

Level 3という値は上流の事実だが、この運用負荷がレベル選定の理由であるという説明は私たちの推論である。
本文は特定の更新間隔や製品を指定していない。Researchの時間単位の推奨を一律の適合条件へ昇格させない。

## 検証と保証の限界

正常時は、定めた周期で新資格情報へ切り替わり、新しい認証が成功し、旧資格情報が期限内に終了することを確認する。
Negative Testでは次を確認する。

- 移行期間後に古い資格情報を提示しても認証できない。
- 更新基盤が停止しても旧資格情報を無期限に受理しない。
- 再起動やReplica追加によって古い資格情報へ戻らない。

定期更新だけで漏えい直後の悪用や、侵害されたAgentによる新資格情報の取得を防ぐことはできない。
緊急失効、侵害元の隔離、現在の認可Policyの評価は別に必要となる。
秘密鍵の更新と、同じ鍵の証明書を再発行することも区別し、何を更新するPolicyなのか明示する。

## 設計レビューへの問い

- どの資格情報を、どの周期で更新するか。
- 古い資格情報は各下流でいつ拒否されるか。
- 更新失敗を誰が検知し、期限切れ時に何が停止するか。
- 正常な更新と安全な障害処理の両方を実際に確認できるか。
