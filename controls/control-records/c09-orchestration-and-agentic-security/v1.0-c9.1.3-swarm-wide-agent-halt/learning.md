# C9.1.3：Agent群全体の停止

AISVS Verification Level: 2

[Control本文：解釈・検証・証拠・限界](README.md)


## 要件と資料の位置づけ

対象は採用済みAISVS v1.0の`C9.1.3`。固定Revisionは
`78775233666a2022dcfb82037e5e029116955c00`。

> Verify that a swarm-level kill-switch exists that can halt all active agent instances.

日本語訳：稼働中のすべてのAgentインスタンスを停止できる、Agent群単位のキルスイッチが
存在することを確認する。[要件本文][normative]

この文書は講義と対話の再構成であり、製品適合の判定記録ではない。
Normativeは要件本文、Researchは停止・復活・分断時の検証観点を補う資料、具体例や
実装への翻訳はRepository interpretation、対話で得られた整理は学習成果として区別する。

## C9.1の中での位置づけ

| 要件 | 制限・制御の対象 |
|---|---|
| C9.1.1 | ツールごとの資源使用量と実行期限。 |
| C9.1.2 | 一つの仕事に属する呼び出し・再試行・委任を含む累積予算。 |
| C9.1.3 | 停止対象の群に属する全稼働Agent。 |

予算内でも危険な行動は起こるため、予算到達を待たずに介入して止める手段が必要になる。
本要件の中心は停止の範囲。停止経路をAgent自身から隔離する保証はC9.6.3で扱う。

## 具体例と保護対象

利用者が「競合3社を比較して」と依頼し、親Agentが3つの子Agentへ調査を分担する。
悪意あるページの影響で、一つの子Agentが社内資料を外部へ送信しようとしていると分かった。

管理者が停止ボタンを押しても、親だけ終了し、別サーバーの子Agentが検索や送信を続けるなら、
群の停止は成立していない。保護したいのはデータ、実行権限、資源・費用に加え、
運用者が実行を制御できる状態である。「止めたつもり」と実際の継続の差が被害を広げる。

## 用語

| 用語 | この例での意味 |
|---|---|
| Swarm（群） | 協調して動くAgentの集まり。親と、その仕事を分担する子Agent。 |
| Instance（インスタンス） | 実際に稼働する個々のAgent。同じプログラムから起動しても別の個体。 |
| Kill-switch | 実行を止める制御機能。物理ボタンである必要はない。 |
| Queue | 実行待ちの仕事を保持する仕組み。停止後の再配信が再開の原因になり得る。 |
| 自動復旧機能 | 終了した処理を再起動する仕組み。障害停止と意図的停止を区別する必要がある。 |

## 脅威、信頼境界、強制

攻撃者が制御できるのはAgentの読むページであり、それを介して危険な行動へ誘導する。
その行動自体への認可・封じ込めは別途必要だが、本要件では、異常を検知した後に
管理者が群全体を停止できるかを評価する。Agentが自ら停止に協力するとは仮定しない。

Trust Boundary（信頼境界）は、動作中のAgent群と、構成員・仕事の受付・実行を管理する基盤の間。
Security Invariant（守るべき性質）は、停止対象から稼働Agentが漏れず、停止操作が
有効なままの間に自動復旧や再配信によって活動を再開しないこと。
Enforcement Point（強制する場所）は、各Agentの実行基盤と仕事を配る管理機構。

実装への翻訳として、次を一組で設計する。[Research][research]

1. 停止対象の群を識別し、新しい仕事や構成員の追加を制限する。
2. 稼働中の全構成員を停止する。
3. 再試行・Queue・自動復旧が停止を取り消さないようにする。
4. 対象一覧と実行状態を照合し、停止完了を確認する。

停止直前に追加された子も、対象に含めるか起動を拒否する。
固定の一覧や親プロセスの終了だけでは、動的に増える構成員を把握できない場合がある。
特定の製品・通信方式をAISVSが指定しているわけではない。

## 正常・異常の検証と証拠

| 観測 | 評価 |
|---|---|
| 親と複数の子が稼働中に停止し、全員の終了と再開しないことを確認する | 群停止の有効性を裏付ける。 |
| 親は終了したが、子が動き続ける | 停止範囲が不足してFail。 |
| 全員が終了した後、自動復旧によって再開する | 意図的な停止が維持されずFail。 |
| あるAgentと通信できず、停止したか分からない | 停止完了の証拠不足。成功扱いしない。 |
| 停止前に送信完了したメールが受信箱に残る | この事実だけではFailにならない。停止と過去の操作の取消は別。 |

証拠は、群の構成員一覧、各Agentの実行・停止状態、停止時刻、再起動・再配信試験の結果。
停止要求を受け付けたログだけでは完了を示せない。
意図的な再開の手続きと、停止中の勝手な復活も区別する。

## 対話の再構成

**問い：親と子3つは停止したが、10秒後に自動復旧機能が子を再起動し、処理を再開した場合は。**

学習者：「Fail。」

整理：そのとおり。一度終了しても、活動が自動再開するなら群の停止を維持できていない。
「障害で落ちたので復旧する」と「意図して止めたので動かさない」を実行基盤が区別する必要がある。

**問い：全Agentが停止し再起動も防げているが、停止直前に送信完了したメールが受信箱に残る場合は。**

学習者：「しない。この要件には該当しない領域。」

整理：この事実だけでFailと判定しないという判断は正しい。C9.1.3は稼働Agentの停止を
扱い、完了済みの操作を取り消す保証ではない。一方、停止後も未把握の子Agentが送信を
続けていたなら、停止範囲の漏れとして問題になる。

## 洞察と保証の限界

- 対象を漏れなく止め、意図せず復活させない。過去の行動を巻き戻すこととは別。
- 停止命令の実装だけでなく、止めるべき構成員を把握することが重要。
- 可用性を高める自動復旧が、セキュリティ上の意図的な停止を妨げる場合がある。
- 停止の受付、各Agentの実停止、群全体の停止完了を区別する。
- ネットワーク分断下の瞬時停止を一律に保証しない。未停止・未確認の構成員と遅延を明示する。
- Agentがすでに依頼した外部Jobの継続も調べるが、取消不能な外部副作用を
  群停止だけで解消したとはしない。停止範囲と残余リスクを明確にする。
- 子やReplicaを生成しない単一Agentなら群停止を対象外とできるが、手動停止等の保証は別途残る。

## 後から使う設計レビューの問い

1. 群の識別と全構成員の把握は、動的な追加・委任にも対応するか。
2. 親だけでなく、別サーバーの子・Replicaも停止できるか。
3. Queue再配信、再試行、自動復旧で勝手に再開しないか。
4. 停止受付と完了を区別し、未確認の構成員や停止遅延を表示・検証できるか。
5. 完了済みの操作、進行中の外部Job、停止経路の隔離などの別保証を混同していないか。
