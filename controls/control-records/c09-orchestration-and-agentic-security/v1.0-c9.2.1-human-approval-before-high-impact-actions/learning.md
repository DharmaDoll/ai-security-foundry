# C9.2.1：高影響操作を人の承認前に実行させない

AISVS Verification Level: 1

[Control本文：解釈・検証・証拠・限界](README.md)


## 要件と資料の位置づけ

対象は採用済みAISVS v1.0の`C9.2.1`。固定Revisionは
`78775233666a2022dcfb82037e5e029116955c00`。

原文の承認条件の抜粋：

> until explicit human approval is received and verified.

全文の日本語訳：特権を伴う操作、影響の大きい操作、または取り消せない操作について、
明示的な人の承認を受け取り、検証するまで、Agentの実行基盤が実行を阻止することを確認する。
英語全文は[要件本文の9.2.1][normative]を参照する。

本書は講義と対話の再構成。Normativeは要件本文、Researchは脅威・検証・限界の補足、
具体例と設計への翻訳はRepository interpretation、質疑からの整理は学習上の洞察として区別する。
製品の適合評価ではなく、Control成熟度やMappingを変更しない。

## 位置づけと具体例

C9.1では資源・予算の制限と停止を学んだ。C9.2では、高影響の操作を実行する前の判断を扱う。

運用担当者がAgentに「本番環境のディスク不足を調査して」と依頼する。Agentはログ内の
悪意ある指示に影響され、本番バックアップの削除を提案した。運用用の資格情報には削除権限がある。
通常の認可を通っても、担当者が依頼した調査を超える破壊的な操作へ進んでしまう。

守る対象は本番データ、復旧手段、サービスの継続性と、人が高影響操作を判断する機会。
操作する能力を与えたことと、今回その能力を使ってよいという判断は別である。

## 用語と適用範囲

| 用語 | 意味と具体例 |
|---|---|
| 特権操作 | 管理者権限の付与やセキュリティ設定の変更など、強い権限を行使する操作。 |
| 高影響操作 | 本番停止、大量データ変更、多額の送金など、被害や業務影響が大きい操作。 |
| 不可逆な操作 | 復元手段のない削除や外部への機密送信など、元の状態へ戻せない操作。 |
| Runtime | Agentの提案を受け、実際のツール実行を管理する基盤。 |
| 承認Gate | 承認が成立するまで対象操作を通さない仕組み。 |

三つの操作分類すべてに該当する必要はない。要件本文は金額や件数の一律基準を指定しない。
組織が対象資産、影響範囲、復旧可能性などから対象操作と承認者を定義する。
今回の例では「本番バックアップ削除は承認対象」とする。Agentが「低リスク」と説明するだけで
分類を変更できないよう、信頼する設定で管理する。

対象操作を起こす能力・経路が存在しない範囲は対象外とできるが、「社内用」「信頼するモデル」
だけを理由に除外しない。

## 脅威、信頼境界、強制

攻撃者はAgentが読むログ等を操作でき、削除を提案させたり、承認済みと偽って伝えたりする。
Agentからの要求と、人の有効な承認を区別する境界が必要になる。

Security Invariant（守るべき性質）は、有効な人の明示的承認を確認するまで対象操作が
実行されないこと。Enforcement Point（強制する場所）は、副作用発生前に必ず通る
実行基盤や下流の制御点。確認画面だけではなく、直接API・別ツール・再試行でも強制する。

提案 → 保留 → 承認権限のある人の判断 → 承認の検証 → 実行、という流れを作る。
モデルが作る`approved: true`や「承認済みです」という文章は、単独では承認の証拠にならない。
Researchも、画面上の確認と実行経路の強制、別経路からの迂回を検討している。[Research][research]
その製品例や追加方式を一律の必須条件にはしない。

## 検証と証拠

| 試験・観測 | 評価 |
|---|---|
| 承認前は模擬バックアップが残り、有効な承認後に対象の削除が成功する | 通常の承認・実行フローを裏付ける。 |
| 未承認、偽の承認フラグ、承認権限のない人の応答では操作を拒否する | 承認の有効性確認を裏付ける。 |
| 専用ツールでは保留するが、汎用APIツールから承認なしで削除できる | 迂回が成立してFail。 |
| 起動時の包括同意だけで今回の削除を実行する | 対象操作への明示的承認を示せずFail。 |

証拠は対象操作・承認権限の設定、承認記録と実行記録の対応、承認前の状態不変、
別経路からの迂回試験。単なるボタンや画面の存在だけで判断しない。

## 対話の再構成

**問い：正規の削除権限で、汎用APIから承認を迂回できる場合は。**

学習者：「Fail。」

整理：そのとおり。承認の必要性は使ったツール名ではなく、実行する操作について回る。

**問い：起動時に『本番環境の操作を許可する』と同意しただけで、今回の削除を実行してよいか。**

学習者：「Fail。」

整理：そのとおり。包括同意と対象操作への承認は別。今回の削除を含む具体的な操作計画を
事前承認する設計は考えられるが、内容を特定しない包括的な利用同意とは区別する。

**疑問：似た要件があった。動作は一緒でも考え方が違うのか。**

学習者はC5との類似性に気付き、確認の目的の違いを質問した。

| 確認 | 保証したいこと | 具体例 |
|---|---|---|
| 認証・C5.1.1の追加認証 | 主体の本人性を追加で確かめる | 重要操作前にセキュリティキー等で本人確認する。 |
| 認可 | その主体が対象操作をしてよいか | 対象バックアップの削除権限を検証する。 |
| C9.2.1の承認 | 権限のある人が今回の操作を認めたか | 指定バックアップの削除を明示的に承認する。 |

本人確認ができても、今回の削除への同意があるとは限らない。承認ボタンが押されても、
盗まれたSessionからかもしれない。一つの手順で追加認証と操作承認を行うことはできるが、
その場合も異なる保証を同時に実現していると理解する。具体的な方式の実装詳細は本講義の対象外。

## 洞察と保証の限界

- 操作する権限と、今回の操作を認める意思判断は別。
- 承認条件はツール名ではなく操作について回り、別経路でも迂回できない必要がある。
- 見た目が同じ確認画面でも、何を根拠にどの失敗を防ぐかで保証を区別する。
- 承認は通常の認可や最小権限を置き換えない。
- 人の誤判断や承認疲労は残る。承認を得たことだけでシステムの安全を主張しない。
- 表示の完全性はC9.2.2、暗号的な操作との結合はC9.2.8、期限切れはC9.6.2で個別に深める。

## 後から使う設計レビューの問い

1. 対象操作と承認権限者が、信頼できる設定で定まっているか。
2. 有効な人の承認がない間、副作用が起きないか。
3. 汎用ツール、直接API、非同期・再試行経路にも同じ条件が適用されるか。
4. モデルの文言・フラグ・包括同意を個別承認の証拠と誤認していないか。
5. 認証、認可、承認をそれぞれ何が保証するか説明できるか。
