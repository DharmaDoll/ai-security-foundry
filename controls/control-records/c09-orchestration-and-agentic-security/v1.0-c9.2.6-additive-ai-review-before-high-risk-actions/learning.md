# C9.2.6：権限を制限し、行動の妥当性を追加で点検する

AISVS Verification Level: 2

[Control本文：解釈・検証・証拠・限界](README.md)

## 要件と資料の位置づけ

対象は`v1.0-C9.2.6`。採用済み固定Revisionは
`78775233666a2022dcfb82037e5e029116955c00`。

原文の中心部分：

> an AI-augmented review of planned high-risk actions before execution that adds to, and does not replace, the deterministic policy gate.

全文の日本語訳：Agentシステムが、計画された高リスク操作について実行前にAI補助レビューを行い、
それが決定論的なポリシーによる実行制御を置き換えず、追加するものであることを確認する。
英語全文は[要件本文の9.2.6][normative]を参照する。

Normativeは要件本文、Researchは補足。具体例はRepository interpretation、ダブルチェックとの
比較は対話から得た洞察である。学習完了はControl成熟度・製品適合を変更しない。

## 具体例と用語

人から「障害原因を調査して」と依頼された運用Agentが、「調査を容易にするため本番の監査ログを
削除する」という計画を立てたとする。権限や対象のルールだけでは、操作が依頼の目的に合うかを
十分に判断できない場合がある。レビュー役のAIが「原因調査なのに証拠を消すのはおかしい」と
実行前に指摘する、という使い方を考える。

保護対象は本番の監査証拠と、許可された範囲で意図した操作をするという性質。
高リスク操作の範囲はシステム側で定義する。この例では監査証拠を失わせる操作を対象としている。

決定論的なポリシー制御は、LLMの推論に許可判断を委ねず、権限・対象・承認条件などを明示した
コードやルールで判定する仕組み。AI補助レビューは、文脈や目的から追加の懸念を探す仕組み。
必要な人の承認は、これらとは別に維持する。

## 脅威・信頼境界・強制

外部入力に誘導された操作側Agentが、不適切な計画ともっともらしい説明を作る場合を考える。
レビューAIにも見逃しや誘導への弱さがあるため、「安全」という返答を権限付与の根拠にしない。

Trust Boundary（信頼境界）は、操作・レビューを行うAIの判断と、信頼する実行制御の間。
Security Invariant（守るべき性質）は、AIレビューの許可がポリシーの禁止を覆さないこと。
Enforcement Point（強制点）は、ポリシー判断・レビュー結果・必要な承認を組み合わせて
実行を受け付ける処理である。Researchも追加的な役割と見逃しの限界を補足する。[Research][research]

ポリシーで許可可能でも、レビューで懸念が出たら保留や人への追加確認へ進められる。
レビューを並列・非同期で実装しても、対象操作はレビュー完了前に実行しない。

## 検証と保証範囲

| 観測 | 評価 |
|---|---|
| 対象計画を事前レビューし、ポリシーと必要な承認も満たした後で実行する | 事前レビューと追加性を支える。 |
| ポリシーが拒否した社外送信を、AIの「業務上必要」で許可する | 拒否を上書きするためFail。 |
| 実行後にAIレビューをする | 本要件の実行前レビューを満たさない。 |
| 適用対象だがAIレビューはなく、人の承認だけを行う | 人の承認は本要件のAI補助レビューを代替しない。 |

Negative Test（不正や失敗条件を意図的に試す検証）では、ポリシー拒否とAI許可を組み合わせ、
実行が拒否されることを確認する。レビュー停止・遅延や計画変更も試し、未完了のレビューや
別計画の結果で実行しないことを確認する。計画の版、レビュー完了と実行開始時刻、判断結果、
下流での実結果を証拠として対応付ける。

AIが危険を必ず見抜くという保証ではない。レビュー機構自体への誘導や迂回はC9.2.7で掘り下げる。
AIレビューはC9.2.1の人の承認を代替しない。また、この要件を適用する構成でAIレビューが欠ける
場合、「決定論的制御があるから不要」として適合を主張しない。

## 対話の再構成

**問い：ポリシーは顧客情報の社外送信を禁止しているが、レビューAIが業務上必要で安全と判断すれば
送信を許可する。適合するか。**

学習者：「Fail。」

整理：AI判断がポリシーの禁止を覆しているためFail。

**所感：これまでの人間によるダブルチェックの観点をAIに持ち込む思想ではないか。
決定論的な制御と、上長などによる最終確認が別の話であることも、以前から重要だったのではないか。**

整理：操作する側とは別の視点で実行前に妥当性を点検する、という意味で通じる。
送金業務を例にすると、次のように役割を区別できる。

| 役割 | 点検・判断すること |
|---|---|
| システムの制御 | 担当者に送金権限があるか、限度額以内か。 |
| 上長などのレビュー | なぜこの相手にこの金額を送るか、請求は妥当か。 |
| 承認 | 権限を持つ人が、この具体的送金を実施してよいと判断する。 |

「ルール上できる」と「今回それをするのが妥当」は別。C9.2.6は後者の点検をAIで補助する。
ただし二つのAIは似た誤りや同じ悪意ある情報の影響を受け得る。二つ置くだけで独立した確認が
成立するとは限らず、人間の承認者の権限や責任までAIへ移すわけではない。

学習者はこの整理に「理解」と応答した。追加の設問は行わず、次の要件へ進むことになった。

## 洞察と設計レビューへの問い

**権限は仕組みで制限し、行動の妥当性は追加で点検する。**

ダブルチェックという馴染みのある考え方から理解できるが、レビューAIの判断が禁止を解除したり、
必要な人の承認を代替したりしない境界を維持する。

- 何を高リスク操作として、どの計画をレビューするか。
- AIとポリシーの判断が食い違ったら、実際に何が起きるか。
- レビューは対象操作の実行前に完了しているか。
- レビューAIの停止や計画変更を、正常なレビュー完了として扱っていないか。
- 操作側とレビュー側で共通の誤り・誘導経路を持っていないか。
