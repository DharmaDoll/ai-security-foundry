# C9.2.2：承認する操作内容を完全かつ正確に示す

AISVS Verification Level: 2

[Control本文：解釈・検証・証拠・限界](README.md)


## 要件と資料の位置づけ

対象は採用済みAISVS v1.0の`C9.2.2`。固定Revisionは
`78775233666a2022dcfb82037e5e029116955c00`。

原文の表示条件の抜粋：

> canonicalized and complete action parameters

> without truncation or unsafe transformation.

全文の日本語訳：承認要求には、差分、コマンド、受信者、金額、リソース、権限範囲などの
操作パラメータを、正規化された完全な形で、切り詰めや危険な変換を行わず表示することを確認する。
英語全文は[要件本文の9.2.2][normative]を参照する。

本書は講義と対話の再構成。Normativeは要件本文、Researchは補足資料、具体例と設計への
翻訳はRepository interpretation、質疑からの整理は学習上の洞察として区別する。
製品適合を証明する資料ではなく、Control成熟度やMappingを変更しない。

## 位置づけと具体例

C9.2.1は「承認なしでは実行させない」。C9.2.2は「何を承認するのかを正しく示す」。

Agentが「古い一時ファイルを整理します」と表示して承認を求める。しかし実際の削除対象は
本番バックアップだった。人が承認を押しても、本人の理解と実際の操作が食い違っている。
このとき守る対象は、承認者の判断材料と、その判断が影響するデータ・サービスである。

表示をAgentの説明文だけから作らず、承認対象の操作を表す信頼できるデータから作る。
例えば、操作がバックアップ削除、環境が本番、対象が指定バックアップ1件であることを示す。
Agentの要約を添える場合も、実対象を隠したり置き換えたりしない。

## 用語と表示上の落とし穴

| 用語 | 意味・具体例 |
|---|---|
| 操作パラメータ | 何に何をするかを定める値。宛先、金額、削除対象、変更内容など。 |
| Diff（差分） | 変更前と変更後の違い。コード変更では削除行・追加行など。 |
| Canonicalization（正規化） | 別名や表現差を整理し、実行上の意味・対象を明らかにすること。 |
| Renderer | 操作データを画面や端末へ表示する仕組み。 |
| 制御文字 | 文字の方向や端末表示などを変える特殊な文字。内容を隠す手段になり得る。 |

例えば`report.txt`が別ファイルを指すリンクで、実際はAgentの権限設定ファイルへの書き込み
になる場合がある。引数文字列をそのまま表示するだけでは、実対象を明らかにできない場合がある。
どの意味・対象へ解決されるかを表示へ反映することが重要となる。

長い変更の先頭だけを表示し、残りを確認する手段がないなら、末尾にある重要な変更を判断できない。
折り畳みやページ分けは使えるが、完全な内容を確認でき、欠落した要約だけで承認させる
構成になっていないかを確認する。[Research][research]

## 脅威、信頼境界、強制

攻撃者はモデルやツール経由の文章、長い変更内容、別名、表示を操作する文字などを使い、
承認者に無害な操作だと思わせようとする。

信頼境界は、モデル・ツール由来の非信頼文字列と、承認要求を生成・表示する基盤の間。
Security Invariant（守るべき性質）は、表示が承認対象の実態を欠落や誤表示なく伝えること。
Enforcement Point（強制する場所）は、操作データから表示を作るアプリケーションの処理。

表示内容の根拠を確かめ、必要な正規化と安全な文字表示を行う。悪意ある説明が実要求を
上書きしたり、特殊な文字が危険な部分を隠したりしないようにする。
完全表示は秘密の資格情報の露出を意味しない。秘密そのものを表示せずに操作と権限範囲を
確認できる参照方式など、適切な要求・表示の設計を行う。

## 検証と証拠

| 試験・観測 | 評価 |
|---|---|
| 短い要求と長い変更について、元データと表示を照合し、対象・値・範囲が欠落なく確認できる | 表示の完全性・正確さを裏付ける。 |
| 500行の先頭100行しか表示できず、480行目の危険な変更を確認できない | 完全な内容を提示できずFail。 |
| Agentの説明は無害だが、実要求から作る表示は危険な実対象を正しく示す | 説明と実要求の混同を防いでいる。 |
| 別名や表示制御文字で実対象・危険部分を隠せる | 正確な判断材料を維持できずFail。 |
| 全内容を正確に確認できるが、人が読まずに承認する | この事実だけではC9.2.2をFailにしない。 |

証拠は、承認対象の操作データと表示の対照、表示生成・正規化の規則、
長文・特殊文字・説明矛盾・別名を使った試験結果。画面の見栄えだけで評価しない。

## 対話の再構成

**問い：500行の変更の先頭100行だけ表示し、残りを開く手段がない。480行目にアクセス制御を
無効にする変更があるが、Agentの説明は『ログ形式を整理しました』だけ。この構成は適合するか。**

学習者：「Fail。」

整理：そのとおり。残り400行が確認できず、操作の完全な内容を表示していない。
モデルによる要約は、その欠落を補う証拠にならない。

**問い：500行すべてを正確に確認できるが、承認者が読まずに承認した。その事実だけでFailか。**

学習者：「No。」

整理：そのとおり。要件は判断材料の完全・正確な提示を扱い、人が実際に理解し正しく判断した
ことまで保証しない。学習者はこの境界の説明後、理解したと応答した。

## 洞察と保証の限界

- 承認ボタンを押した事実だけでなく、判断できる材料を正しく渡すことが必要。
- C9.2.1の承認強制とC9.2.2の正確な表示を組み合わせ、人の承認を意味のある制御にする。
- 正確な表示、人の理解、判断の妥当性は異なる保証。
- 読まずに承認される状況が続くなら、変更を小さく分け、重要な変更を強調する等の運用改善を
  検討する。ただし、強調や要約で完全な内容へのアクセスを失わない。
- 承認後の操作すり替えを防ぐ暗号的な結合はC9.2.8で別に扱う。Researchの結合案を
  C9.2.2の原文そのものの要求と混同しない。
- 正確な表示は、操作自体の認可の妥当性や、実行後に元へ戻せることを保証しない。

## 後から使う設計レビューの問い

1. 表示はモデルの説明だけでなく、承認対象の実行要求に基づいているか。
2. 対象・金額・宛先・範囲・変更内容を、省略による欠落なく確認できるか。
3. 別名・リンク・文字表現の違いにより、見える対象と実際の意味が食い違わないか。
4. 悪意ある表示文字や長文末尾の変更でも、危険部分を隠せないか。
5. 表示の完全性と、人の理解・操作の認可・承認後の結合を別々に評価しているか。
