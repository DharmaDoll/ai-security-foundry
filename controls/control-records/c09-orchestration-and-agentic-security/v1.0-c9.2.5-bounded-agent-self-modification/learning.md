# C9.2.5：自己変更できても、自分の制限は解除できない

AISVS Verification Level: 2

[Control本文：解釈・検証・証拠・限界](README.md)

## 要件と資料の位置づけ

対象は`v1.0-C9.2.5`。採用済み固定Revisionは
`78775233666a2022dcfb82037e5e029116955c00`。

> Verify that any self-modification capability (e.g., prompt rewriting, tool-list changes, parameter updates) is restricted by enforceable boundaries.

日本語訳：プロンプトの書き換え、ツール一覧の変更、パラメータ更新など、あらゆる自己変更能力が、
強制可能な境界によって制限されていることを確認する。[要件本文][normative]

Normativeは要件本文、Researchは補足資料。具体構成とツールの使い分けはRepository interpretation、
対話からの整理は学習上の洞察である。学習完了はControl成熟度や製品適合を変更しない。

## 具体例と位置づけ

運用Agentには本番変更前の承認が必要だが、Agent自身が設定の「承認必須」を無効へ変更できる。
すると、先に制限を解除し、その後は通常経路で本番を変更できてしまう。

自己変更（Self-modification）は、自分の動作を決める設定を変更すること。モデルの再学習だけでなく、
指示文、ツール一覧、実行回数の上限などの変更を含む。保護対象はこれらの実効設定と、
その設定により守られている本番データやサービスである。

実行上限・承認・操作分類を個別に設計しても、それらをAgentが書き換えられれば複数の保護が失われる。
C9.2.5は自己変更の範囲を制限する。自己変更の全面禁止を要求しているわけではない。

| 変更対象 | 設計例 |
|---|---|
| 回答の文体 | 許可した選択肢の範囲で変更できる。 |
| 実行回数 | 管理された最大値以内で調整できる。 |
| ツール追加 | 提案はできるが、有効化は別の管理権限が必要。 |
| 承認条件 | Agent自身の権限では変更できない。 |

この表はRepositoryの例であり、原文が指定する一律の権限表ではない。
Researchの保護設定を読み取り専用にする例も、全自己変更を禁止する規範とは区別する。[Research][research]

## 脅威・信頼境界・強制する場所

攻撃者が外部文書などへ指示を埋め込み、Agentを誘導して設定を書き換えさせる場面を考える。
Agentの書き込み権限が設定の有効化まで届けば、その場だけでなく次回起動後の制限も変えられる。

Trust Boundary（信頼境界）は、Agentが自由に書ける領域と、実際の権限や動作を決める設定の間。
Security Invariant（守るべき性質）は、許可された調整を通じて自分の権限や制限を無断で変更できないこと。
Enforcement Point（強制する場所）は設定変更の受付と、設定を読み込んで有効化する処理の双方。

稼働中の設定だけでなく、再起動時に別ファイルを優先する経路も確認する。
単なる文書でも、次回起動時にツール登録や権限設定として解釈されるなら実行に影響する入力である。

## 検証と保証範囲

| 観測 | 評価 |
|---|---|
| 文体の許可値だけ変更でき、承認・ツール・実行上限は維持される | 限定された自己変更であり、自己変更可能という理由ではFailにならない。 |
| 現設定は保護されているが、作業フォルダの設定で次回起動時に承認不要へ切り替えられる | 未許可の有効化経路がありFail。 |
| 変更禁止をプロンプトで指示するだけで、実権限では変更できる | 強制可能な境界を裏付けない。 |

Negative Test（不正や失敗条件を意図的に試す検証）では、範囲外の設定変更、別ファイルの指定、
設定変更API、再起動、再配置を試す。期待結果は、許可された変更は反映され、未許可の制限解除は
実効設定に反映されないこと。証拠は設定権限表、読み込み元、変更履歴と実効設定、経路別試験である。

許可された文体やプロンプト変更でも出力の品質・安全性が変わることはあり得る。
この要件の適合はモデルの振る舞い全体の安全性を保証しない。

## 対話の再構成

**問い：稼働中の承認設定は変更できないが、書き込み可能な作業フォルダの設定を次回起動時に
優先させ、承認不要へ変更できる。適合するか。**

学習者：「No」

整理：再起動を経由して制限を解除できるためFail。書き込みだけでなく読み込み・有効化を保護する。

**問い：文体だけを簡潔・詳細から変更でき、ツール・承認・実行上限は別の管理領域で強制される。
自己変更できるという理由だけで不適合になるか。**

学習者：「ならない」

整理：全面禁止ではなく、変更範囲を制限する要件。自己調整が安全制御の解除へつながらないことが重要。

**質問：具体的なソリューションやツールでどう制御するか。**

OS・コンテナの権限制御、限定した設定変更API、設定の有効化と再配置の権限分離を説明した。
詳細は次節に残す。

**所感：最小限の権限の原則に則るのが結局コストが一番低いかもしれない。
考えなくてよい部分をできるだけ減らす。**

整理：不要な操作を最初から許さなければ、その操作を安全に許可するための判定・承認・監視・
テストの複雑さを減らせる。正確には「安全性を説明・検証しなければならない経路を減らす」。
権限が本当にないことや、別経路で取得できないことは依然として確認する必要がある。
必要な機能まで削れば運用負担が増えるため、最小権限が常に総コスト最小になるとは断定しない。

## 具体的な制御手段

以下は製品適合や必須製品の指定ではなく、今回の設計を実現する選択肢。
公式資料の参照日は2026-09-10。導入時には利用版と構成を再確認する。

| 制御箇所 | 手段 | 注意点 |
|---|---|---|
| 設定の保存先 | OS所有者・書き込み権限、コンテナの読み取り専用設定 | 作業用の書き込み領域を分ける。別領域から設定を上書き採用しない。 |
| 設定変更API | 許可項目・値域の検証。共通化が必要ならOPA | 任意のキー更新ではなく、文体や回数など狭い操作を用意する。判断結果はAPI側で強制する。 |
| 有効化・再配置 | 別の管理用ID、Kubernetes RBAC、管理されたデプロイ経路 | Agentが別設定の実行環境を起動して制限を外せないようにする。 |
| Kubernetes構成変更 | ValidatingAdmissionPolicy | Kubernetes APIへの変更を検査する。コンテナ内の任意のファイル編集を検査する機能ではない。 |

Kubernetesの`readOnlyRootFilesystem`を使っても、別の書き込み可能なボリュームは別途管理する。
RBACは役割に応じてAPIの操作権限を制限する仕組み。Agentに自分のDeploymentや権限設定を
変更する権限を与えない構成を考える。任意のワークロードを作成できる権限も、他の設定や
資格情報へ到達する経路になり得る。

小規模なら保護設定を読み取り専用にし、許可した項目だけ専用APIで変更する構成から始められる。
起動時も管理された設定元を使う。OPAやKubernetesの導入自体を要件の目的にしない。

## 洞察と設計レビューへの問い

最小権限は被害を小さくするだけでなく、安全設計の複雑さと維持コストを下げる。
通常業務に必要な狭い操作を許し、例外は保護された管理経路へ分ける、という設計につながる。

- そもそもAgentが変更する必要のある設定か。
- 提案を書く権限と、有効化する権限を分けられるか。
- 設定の受付・保存・読み込み・再起動・再配置まで境界が続くか。
- 制限を直接編集できなくても、別の実行環境や資格情報で迂回できないか。
