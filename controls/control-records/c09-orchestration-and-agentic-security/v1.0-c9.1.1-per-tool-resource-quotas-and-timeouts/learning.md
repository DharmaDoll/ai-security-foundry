# C9.1.1：ツールごとの資源上限と実行期限

AISVS Verification Level: 1

[Control本文：解釈・検証・証拠・限界](README.md)

## 位置づけと具体例

C5で扱った「この操作を許可してよいか」に続き、C9.1.1は「許可したツールが、どこまで
資源を使ってよいか」を扱う。

社内Agentが利用者のPDFを解析する。文書を読む権限はあるが、細工されたPDFによって
解析ツールが大量のメモリを消費すると、同じサーバーの他の利用者まで処理できなくなる。
巨大な入力やソフトウェアの不具合でも同じ障害が起きる。守る対象は計算・記憶・通信資源と、
それを共有する利用者の可用性、つまり必要なときにサービスを利用できること。

## 用語と制限の例

| 用語 | 意味・PDF解析での例 |
|---|---|
| Quota | 使用量の上限。メモリ512MB、一時ファイル100MBなど。 |
| CPU | 計算処理能力。解析ツールが占有できる能力を制限する。 |
| Egress | 外向き通信。通信量や速度の制限と、送信先の認可は別の保証。 |
| Timeout | 処理の期限。例えば解析を30秒以内に制限する。 |
| Runtime | ツールの起動と実行を管理する基盤。 |
| 子プロセス | 解析ツールがさらに起動した処理。親の応答終了だけでは停止を保証できない。 |

数値は説明用であり、AISVS指定ではない。資源の例示をすべての構成へ機械的に適用せず、
実際の消費と強制可能な範囲を明確にする。

## 脅威、信頼境界、強制

攻撃者が制御するのは入力PDF。その入力がツールに異常な消費を起こさせ、共有基盤へ
影響を広げる経路を考える。ツールも正常に終了するとは仮定しない。

Trust Boundary（信頼境界）は、非信頼入力を処理するツールと、その資源を管理する基盤の境目。
Security Invariant（守るべき性質）は、ツールが異常動作しても、設定した資源・時間の
制限が実際に働き、無制限の消費を続けられないこと。

Enforcement Point（強制する場所）はOS、コンテナ、実行管理機能など。
モデルへの「使いすぎないで」という指示や、利用量を表示するだけの監視では代替できない。
Researchも、要求の応答期限と実処理の終了、子処理、資源別の計測を検討している。[Research][research]

## 正常・異常の検証と証拠

| 観測 | 評価 |
|---|---|
| 正常なPDFが制限内で完了する | 通常利用が成立することを示す。これだけで異常時の強制は証明できない。 |
| 異常な処理に対して上限が働き、期限後の処理継続も制限される | 設定と実測を対応付け、適合を裏付ける。 |
| 30秒でエラーを返すが、裏の解析が無期限に続く | 実行時間の強制が不成立でFail。 |
| 終了要求は送ったが、停止したかは不明 | 強制の有効性を裏付ける証拠不足。 |

確認する証拠は、対象ツール・子処理の有効設定、資源使用量、終了時刻、残存処理、
後続の書き込みなど。瞬時停止を前提とせず、許容する停止遅延と実測を確認する。
遠隔サービスでは、呼出側と提供側の責任分界、観測できない範囲も明示する。

## 対話の再構成

**問い：タイムアウトを返すが、子プロセスが動き続ける構成は適合するか。**

学習者：「Fail。timeout時にはプロセスも終了させるロジックを組み込むべき。」

整理：そのとおり。さらに、終了要求と実際の終了を区別する。フリーズしたツール自身の
終了処理だけに頼らず、実行基盤から強制できることと、その結果を確認する。

**問い：各回の制限を守る解析を1万回繰り返した事実だけで、C9.1.1をFailとできるか。**

学習者：「Fail。時間だけでなく回数も制限するべき。」

整理：回数制限を追加すべきという設計判断は有用。ただし、設問では個々の資源・時間制限が
成立している。一連の仕事の累積消費はC9.1.2で評価し、隣接要件の不備だけでC9.1.1をFailにしない。

**問い：この要件はDoS対策か。**

整理：主に資源枯渇によるDoS（Denial of Service：サービス不能）を防ぎ、影響を限定する
対策の一部と理解できる。攻撃だけでなく誤動作や不具合にも効く。費用の暴走を抑える効果も
あるが、全体予算や大量同時実行への対策を単独で代替しない。

**説明の訂正：「ツールごと」と「一回ごと」。**

講義では具体例として「一回の解析」と表現した。原文はあくまで「ツールごと」である。
呼び出し単位の期限、ツール実行環境単位の資源枠など、具体的な制限単位は設計で定義する。
「一回ごとだけを制限すればよい」という意味に狭めない。

## 洞察と保証の限界

- ツールを使う許可には、資源を無制限に使う許可まで含めない。
- 一つのツールの異常を、システム全体の障害に広げない。
- 待つのをやめること、終了を要求すること、実際に終了することは別。
- 制限内でも情報漏えいや不正操作は起こり得る。資源制限は認可の代替ではない。
- ツール別の制限だけでは、大量の呼び出し・並列実行による全体の資源枯渇を否定できない。

## 後から使う設計レビューの問い

1. どのツールの、どの資源を、どの単位で制限しているか。
2. その制限はツールが異常動作しても働くか。
3. Timeout後の子処理・非同期処理と副作用を確認できるか。
4. 設定値と実測結果は対応し、停止遅延や外部側の未確認範囲が明示されているか。
5. 累積予算・同時実行・認可など、別途必要な保証を見落としていないか。
