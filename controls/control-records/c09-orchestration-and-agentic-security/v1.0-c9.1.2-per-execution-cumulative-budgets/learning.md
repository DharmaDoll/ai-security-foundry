# C9.1.2：実行全体の累積予算

AISVS Verification Level: 1

[Control本文：解釈・検証・証拠・限界](README.md)


## 要件と資料の位置づけ

対象は採用済みAISVS v1.0の`C9.1.2`。固定Revisionは
`78775233666a2022dcfb82037e5e029116955c00`。

日本語訳：実行ごとの予算（例：最大再帰深度、トークン使用量、金銭的支出）が設定され、
実行基盤によって強制されていることを確認する。
正確な英語原文は[要件本文の9.1.2][normative]を参照。

この文書は講義と対話の再構成である。Normativeは要件本文、Researchは補足資料、
具体例と設計上の判断はRepository interpretation、対話からの洞察は学習成果として区別する。
学習の進捗とControl成熟度、Mapping、製品適合は独立している。

## 位置づけと具体例

利用者が調査Agentへ「競合3社のサービスを比較して」と依頼する。Agentは検索、ページの
取得、推論を繰り返す。取得ページの悪意ある指示で追加検索へ誘導される場合も、単に
「まだ情報が足りない」と判断し続ける場合もある。

各処理は短時間でも、1円の処理を1万回行えば1万円になる。C9.1.1のツール別の資源上限に
加えて、この依頼全体の消費を制限するのがC9.1.2である。
保護対象は費用・資源の予算と、その残額・帰属を管理する状態。

## 用語と実行の範囲

| 用語 | 意味・調査Agentでの例 |
|---|---|
| 一実行 | 「競合3社の比較」という依頼を処理する一連の仕事。開始・終了・再開の境界を設計で定義する。 |
| 累積予算 | その仕事に属する消費を合計した上限。例えば全体300円。 |
| トークン | モデルが処理する文章等の単位。複数回の入力・出力を合計して制限する。 |
| 再帰深度 | 処理がさらに同種の処理を呼ぶ入れ子の深さ。子Agentがさらに委任する深さなど。 |
| Runtime | 要求を受け付け、実行と消費量を管理する基盤。 |
| 予算予約 | 実行開始前に予算の一部を確保し、他の処理が同じ残額を使えないようにすること。 |

数値は説明用。回数制限も実現方法の一つだが、単価が変動する場合は回数だけで費用上限を
示せない。再帰しない構成では深度の項目を対象外にできるが、該当する他の予算まで不要にはならない。

## 脅威、信頼境界、強制

攻撃者が検索結果へ指示を埋め込み、Agentに追加検索・再試行・委任を続けさせる経路を考える。
子Agentや再開処理ごとに計数をリセットすると、元の仕事の上限を迂回できる。

信頼境界は、処理を提案するAgentと、実行の帰属・残額・受付を管理する基盤の間にある。
守るべき性質は、仕事を分割・再試行しても元の予算から逃れられず、基盤が累積上限を強制すること。
Agentが実行IDを書き換えたり「別の仕事」と宣言したりするだけで上限をリセットできてはならない。

強制点は追加消費を開始する前の受付と、必要に応じた実行中の制御。
計数を画面へ表示するだけ、予算超過メールを送るだけでは強制にならない。
Researchも、小さい呼び出しの累積、並列実行の計数、課金情報の遅延を検討している。[Research][research]

## 並列実行と障害時の設計

残り100円を2つの処理が同時に確認し、それぞれ80円使うと160円になる。
確認と予算確保が競合しないようにし、実行後に予約額と実績を精算する方法がある。
事後に費用が確定する場合も、進行中の消費と計測遅延を考慮して上限を実効的にする。
予約は実装例であり、AISVSが特定の台帳や製品を指定しているわけではない。

| 制限 | 守る対象 | 単独では残る問題 |
|---|---|---|
| 累積予算 | 一つの仕事全体の総消費 | 予算内で多数の処理が一斉に始まることによる瞬間的な負荷。 |
| 並列数 | 同時に動かす処理の数 | 一つずつ延々と処理すれば総消費は増え続ける。 |

並列数の制限は学習者から提案された追加対策であり、今回の原文で個別に指定された方式ではない。
全体の安全性のため、累積予算と組み合わせて評価する。

予算管理の故障時は、保証できない新しい消費を止める。事前に確保済みの枠があれば、その範囲で
継続する設計も可能。残額不明を理由に予算確認を省くと、上限が強制されなくなる。

## 正常・異常の検証と証拠

| 観測 | 評価 |
|---|---|
| 正規の仕事が予算内で完了し、親・子・再試行の合計を追える | 正常な利用と予算帰属を示す。 |
| 合計上限に従って追加処理を拒否し、進行中分も定義した範囲に抑える | 強制の有効性を裏付ける。 |
| 全体300円に対して子3つへ300円ずつ与え、合計900円使える | 設定した全体予算が強制されずFail。 |
| 残額不明でも、予約なしで確認を省略して追加処理を許す | 障害時に上限を迂回する設計でFail。 |
| 計数や拒否の結果を観測できず、強制の成否も不明 | 証拠不足。N/Aや実証済みFailと混同しない。 |

予算設定、実行の親子関係、予約・実績台帳、受付拒否、並列・再開・障害試験を照合する。
本番の秘密や課金情報ではなく、安全な試験データを使う。

## 対話の再構成

**問い：全体300円の仕事で、子3つが各300円、計900円使った場合は。**

学習者：「Fail。全体での300を超えてしまっている。Agent自体の並列数も制限入れられるとよい。」

整理：Fail。子の個別予算が守られても元の全体予算は不成立。並列数の制限も、瞬間的な
負荷を抑える別の軸として有用。累積予算の代替にはならない。

**問い：予算管理が故障し、事前確保もなく予算確認なしで新しい処理を受け付ける場合は。**

学習者：「N/A。」

訂正：Fail。制限対象のAgent実行は存在しており、故障によって適用対象から外れない。
単に残額を観測できないだけでなく、設問には強制を迂回して受け付ける動作が示されている。
新しい消費を拒否する、あるいは事前予約済みの範囲だけ継続するなどの設計が必要になる。

**学習者の整理：「C9.1.1はツール毎、C9.1.2は実行毎。」**

その整理が正確。実行ごととは、一回のAPI呼び出しではなく、再試行・子への委任・並列処理を
含む一連の仕事の境界である。C9.1.1について講義で使った「一回の解析」という表現は
具体例であり、原文の「ツールごと」を狭めるものではない、と説明を訂正した。

## 洞察と保証の限界

- 一回が小さいことは、一連の仕事が小さく収まる保証ではない。
- Agentが仕事を分割・再試行しても、元の仕事に与えた予算から逃れられないようにする。
- 残額の確認だけでなく、並列処理による同じ予算の二重使用を防ぐ。
- 制限を確認できないときにも無制限にならない。障害は適用除外の理由ではない。
- 予算内の情報漏えいや不正操作は別の保証。停止しても支払い済み費用や完了済み取引は戻らない。
- 一実行の予算だけで、全利用者・全実行を合算したシステム全体の容量を保証するわけではない。

## 後から使う設計レビューの問い

1. 一実行の開始・終了・再開と、親子・再試行の帰属を定義したか。
2. モデルがIDや予算を書き換えて上限をリセットできないか。
3. 通知だけでなく、追加消費の拒否と進行中分の制限を確認できるか。
4. 並列実行・計数障害・事後課金でも、保証する予算範囲を維持できるか。
5. 累積上限とは別に、同時実行による瞬間的な負荷を評価したか。
