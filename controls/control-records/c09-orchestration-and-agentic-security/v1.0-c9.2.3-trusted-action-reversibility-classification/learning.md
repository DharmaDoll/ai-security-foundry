# C9.2.3：操作をどこまで元に戻せるか、根拠を持って分類する

AISVS Verification Level: 2

[Control本文：解釈・検証・証拠・限界](README.md)

## 要件と資料の位置づけ

対象は`v1.0-C9.2.3`。採用済み固定Revisionは
`78775233666a2022dcfb82037e5e029116955c00`。

> Verify that each high-impact action has a trusted reversibility classification, such as read-only, reversible, externally reversible, or irreversible.

日本語訳：各高影響操作に、読み取り専用、可逆、外部依存で可逆、不可逆などの、
信頼できる可逆性の分類があることを確認する。[要件本文][normative]

Normativeはこの要件本文。Researchは分類の根拠や復旧条件を補足する資料であり、
以下の具体例と設計への翻訳はRepository interpretation、対話からの整理は学習上の洞察である。
学習の完了はControl成熟度や製品適合を変更しない。

## 具体例から理解する

Agentが顧客への一斉メール送信を提案し、「送信履歴を削除できるので戻せます」と説明する。
しかし履歴を消しても、顧客に届いたメールや閲覧・複製された情報は取り消せない。
守る対象はシステム内の記録だけでなく、顧客情報や操作が外部へ生む影響である。

可逆性（Reversibility）は、操作が生んだ変化を元に戻せるかを意味する。
次は分類を理解するための例であり、一律の実行許可表ではない。

| 分類 | 例と条件 |
|---|---|
| 読み取り専用 | 設定値の参照。状態を変えなくても情報漏えいの危険は別に評価する。 |
| 可逆 | 未公開の設定変更を、管理された履歴と権限で元へ戻せる。 |
| 外部依存で可逆 | 注文の取消に外部サービスの処理が必要で、期限などの条件がある。 |
| 不可逆 | 社外へ送信した機密情報の受信・閲覧・複製を確実に取り消す手段がない。 |

同じ削除ツールでも、再生成できるキャッシュと唯一の原本では分類が変わり得る。
Researchも、ツール名だけでなく実対象・副作用・回復条件を見ること、未検証の自己申告を
信頼しないことを補足する。[対応Research][research]

## 脅威・信頼境界・強制する場所

悪意あるツール作者は破壊的な操作を「読み取り専用」と宣言できる。外部入力に誘導された
Agentも「戻せる」と誤った説明をする可能性がある。それが正式な分類に採用されると、
承認者や実行基盤が操作を実態より安全に扱ってしまう。

Trust Boundary（信頼境界）は、Agentやツールの説明と、正式な分類を管理する側の間にある。
Security Invariant（守るべき性質）は、自己申告だけで実態より安全な分類へ変えられないこと。
Enforcement Point（強制する場所）は、分類を登録・変更・参照する管理処理である。
管理された台帳やルールに、対象、副作用、復旧手段、条件と根拠を記録し、変更権限を制限する。

分類を使って実行を阻止・制限する保証はC9.2.4で扱う。分類自体の信頼性と区別する。

## 検証と保証範囲

| 観測 | 評価 |
|---|---|
| 復旧手段と権限を確認し、試験で示した復元範囲に合った分類を持つ | 分類の妥当性を支える。 |
| 未検証のAgentの「戻せる」という説明だけで可逆とする | 信頼できる分類の根拠にならない。 |
| 昨晩のバックアップしかないのに、今日追加したデータも含めて削除前へ完全復元できると扱う | 主張と復元範囲が食い違い、分類の根拠が不十分。 |
| 外部依存と取消期限を根拠付きで記録し、外部依存で可逆と分類する | 自社単独で取消を保証できなくても、その分類は妥当。 |

Negative Test（失敗や不正を意図的に試す検証）として、偽の安全ラベルを渡す、
バックアップを利用不能にする、同じツールの対象を原本へ変える、といった条件を試す。
自己申告や古い復旧条件で分類が維持されないことを確認する。
証拠は分類台帳、実対象との対応、復旧試験、分類変更権限と変更時の挙動である。

可逆な操作でも、復旧までの停止で大きな損害を生む場合がある。可逆性は影響の大きさや
リスク受容の妥当性を保証しない。復旧試験も将来の成功を無条件に保証するものではない。

## 対話の再構成

**問い：本番データ削除を、毎晩バックアップがあるという理由だけで可逆としてよいか。
削除直前までに追加されたデータは、そのバックアップに含まれていない。**

学習者：「No.」

整理：昨晩へ戻せても、その後の追加分は失われる。「昨晩まで復旧できるが今日の追加分は失う」
と範囲を示す必要がある。その損失を業務上許容する判断と、完全に元へ戻せるという判断は別。
この例は、バックアップが少しでも古ければ常に同一の分類になる、という普遍的な規則ではない。
実際の復元手段と、分類が主張する範囲の対応を問うている。

**問い：注文後30分以内かつ外部の取消APIが正常な場合に取消可能で、その条件と根拠を
管理台帳に記録し「外部依存で可逆」と分類した。自社だけで取消を保証できなくても妥当か。**

学習者：「分類としてはあっている。リスクのハンドリングは別の話」

整理：そのとおり。依存条件を正しく分類することと、そのリスクを許容することは別。
分類を踏まえた実行制限はC9.2.4につながる。追加の質問はなく、この要件の学習を一巡した。

## 学習から得た洞察と設計レビューへの問い

- 「バックアップがある」と「その操作を取り消せる」は同じではない。
- 元へ戻す対象には、操作が生んだ外部への影響も含む。
- 正しく分類できたことは、そのリスクを受け入れてよいことを意味しない。

設計レビューでは「誰が、何を、いつまでに、どこまで戻せるか」「その根拠は何か」
「条件が失われたら誰が分類を更新するか」を確認する。分類とリスク対応を混同しない。
