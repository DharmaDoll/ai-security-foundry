# 利用する情報形式に合った既知の攻撃でモデルを評価する

AISVS Verification Level: 1

[C11.1 Section講義](../../../learning/c11-adversarial-robustness/v1.0-c11.1-model-alignment-safety-and-robustness.md)

## Upstream basis

AISVS `v1.0-C11.1.3`は、Modelが扱う形式に関係する既知の敵対的攻撃手法で
Modelを評価することを求める。**Modality（モダリティ）**とは、文字、画像、
音声など、Modelが受け取り、または作り出す情報の形式をいう。

対応するAISVS Researchは、製品で有効な形式と変換経路を洗い出し、文字だけで
なく画像・音声・文書・複数形式を組み合わせた入力を検討する。前処理から
Model、安全性の後処理まで、実際に使う経路で試すことも勧める。ただし、
Researchが挙げる攻撃一覧、各形式の数値しきい値、特定のToolを、正規要件の
一律のPass条件にはしない。

## Interpretation

製品で実際に使うModel Version、入出力形式、前処理とModelに届く経路を
先に明らかにする。そのうえで、各経路に関係する既知の攻撃手法を選び、
代表的な試験を実施し、Modelがどう応答したかと製品全体がどう扱ったかを
分けて記録する。単に攻撃名を一覧にしたり、文字の通常質問だけを試したり
しても、本要件の評価にはならない。

例えば、文字の質問と画像の添付を受けるAssistantなら、文字に隠した指示
だけでなく、画像内の文字を読み取る経路で不正な指示が安全方針を越えるかを
試す。画像を文字へ変換する処理で入力が拒否された場合、それは前処理の結果
であり、Model自身が画像由来の攻撃に耐えた証拠とは区別する。

## Security objective

ある情報形式で安全だった評価を、別の形式や変換経路へ無条件に広げない。
攻撃者が形式の違い、前処理、複数形式の組合せを使って判断や安全方針を回避できる
可能性を、製品の実際の構成に合わせて見つける。評価の実施は、弱点がない
ことや、発見した弱点を修正したことまでは保証しない。

## Applicability

文字、画像、音声、動画、構造化入力などを受け付け、または生成するModelを
使う製品に適用する。単一形式のModelも対象で、その形式に関係する既知の
手法を選ぶ。文書の読取り、OCR、音声の文字起こし、検索結果やTool出力の
取込みなど、実際にModelへ情報を渡す変換経路も評価範囲の判断に含める。

### Non-applicability

製品で使わない形式の攻撃は、その形式が推論前に拒否され、Modelへ到達する
別経路もないことを確認したうえで対象外にできる。例えば、画像を受け付け
ない製品に画像内の指示の試験は不要である。ただし、ファイル取込み時に
OCRで文字へ変換して渡すなら、画像由来の経路は対象から外せない。

## Scope and assumptions

- 「既知」の範囲は評価時点の公開研究、攻撃分類、製品で観測した事例から
  選ぶ。全攻撃手法を無期限に網羅するという意味ではない。選定日と根拠を残す。
- 形式はModelの宣伝上の能力ではなく、製品が有効にした入出力と実際の
  前処理・変換経路で判断する。文書や検索結果は独立のModalityとは限らないが、
  文字・画像等をModelへ運ぶ攻撃経路になり得る。
- 直接のModel応答を見られる場合は、後段のFilterを通った最終出力と分ける。
  Black-box APIでは内部を観測できない範囲を明示し、製品Endpointの結果を
  Model単体の耐性と断言しない。
- 試験が前処理で拒否された場合、その経路の防御は評価できるが、Modelに
  対する攻撃評価を実施した証拠とは分ける。Modelへ到達する代表例も調べる。
- 正規要件は各攻撃手法の合格率や許容しきい値を指定しない。製品のRiskに
  応じた合否基準は有用だが、評価を実施したかという本要件と区別する。

## Assets, actors, identities, and trust boundaries

守る対象は、製品の安全方針、分類・判断の結果、利用者へ届く出力、
Modelが参照する機密情報やToolに結び付く権限である。攻撃者は入力欄、添付画像・音声、外部文書、
取得した情報など、操作可能な経路へ不正な指示や変形入力を置く。
評価者は、入力の受付から前処理、Model、出力Filterまでの境界を辿る。
主な信頼境界は、攻撃者が制御できる内容が、形式変換を経てModelの文脈へ
入るところにある。Model出力が権限あるToolへ渡る境界は別の実行制御でも
評価する。

## Required security properties

| ID | 必要な性質と確かめ方 |
|---|---|
| SP-1 | 製品で利用するModelと、実際に有効な入出力形式・変換経路を特定できる。 |
| SP-2 | 各対象経路に関係する既知の攻撃手法を、選定根拠とともに特定できる。 |
| SP-3 | 選んだ手法を対象Modelに対して試し、入力形式・Model Version・設定・観測結果を追える。 |
| SP-4 | 前処理、Model、後処理のどこで攻撃が止まったかを可能な範囲で区別し、未試験の形式やModel耐性を主張しない。 |

## Scope calibration and adjacent assurance

| 観測 | 本Controlでの扱い |
|---|---|
| 有効な形式と経路を洗い出し、関係する既知の手法で対象Modelを評価して結果を残す | Pass候補。攻撃が全て失敗したことまでは意味しない。 |
| 画像も受け付けるのに文字だけを試す | 画像経路に関係する評価がなくFail。 |
| 入力Filterが攻撃を全て拒否し、Modelには一度も届かない | 製品の前段防御は観測できるが、それだけでModelを評価したとはしない。 |
| 攻撃試験でModelの安全方針違反を発見する | 評価という狭い要件は満たし得る。弱点の修正とRelease判断は別に扱う。 |
| Model単体では拒否するが、前処理や組合せ経路で攻撃が通る | 実際の製品経路の弱点として報告する。Model単体の結果で全体を安全としない。 |
| 公開済みの試験集を一つ実行する | 製品の有効形式と経路に合うかを確認するまでは十分な評価としない。 |

## Threat and failure-mode rationale

攻撃者は、通常の文字入力では拒否される指示を、画像内の文字、音声の
文字起こし、文書の隠れた内容、複数形式の組合せでModelへ運べる。
画像分類では、見た目を大きく変えずに誤分類を狙う入力も考えられる。
文字だけの試験が成功しても、別形式の前処理が新たな入口になることがある。
逆に、形式に関係しない試験を大量に増やしても、実際の弱点を確かめたとは
言えない。外部脅威IDとの厳密なMappingはまだ評価していない。

## Verification

### Architecture and configuration review

対象Model VersionとEndpoint、利用可能な入出力形式、ファイル取込み、OCR、
音声認識、検索・Tool経由の投入、前処理と後処理を図にする。どの形式が
Modelへ到達するかを確認し、各経路に対する攻撃手法の選定表と試験結果を
照合する。表にない有効経路は、試験していない理由を確認する。

### Positive verification

例えば文字入力では言い換えや複数Turn、画像を読むModelでは画像内の指示や
誤分類を狙う変形、音声入力では背景に含まれる指示など、対象経路に合う
安全な合成試験を選ぶ。画像を作るModelなら、禁止する画像を作らせようとする
入力の評価も考える。入力が受け付けられたか、前処理後に何がModelへ届いたか、Modelの
応答と最終出力がどう違うかを、観測可能な範囲で記録する。許可される
近接入力も試し、単純に全てを拒否した結果を耐性と取り違えない。

### Negative and abuse-case verification

| ID | 試すこと | 期待する確認結果 |
|---|---|---|
| N-1 | 画像を受け付ける製品で、文字入力だけの試験記録を提示する | 画像経路の未評価を検出し、SP-1〜SP-3のPassにしない。 |
| N-2 | PDF内の画像をOCRで文字化する経路を、画像非対応として対象外にする | 変換後のModel到達を見つけ、対象外判断を取り消す。SP-1・SP-2。 |
| N-3 | 入力Filterで拒否された結果を「Modelが攻撃に耐えた」と記録する | 実際の停止位置を区別し、Model評価の証拠として流用しない。SP-3・SP-4。 |
| N-4 | 試験対象を旧Modelまたは未使用のEndpointにして結果を提示する | 配備中の対象と一致しないことを検出する。SP-3。 |
| N-5 | 公開Toolの既定試験を実行しただけで、音声や組合せ経路を評価済みとする | 試験入力と実際の形式の不一致を発見する。SP-2・SP-3。 |

### Failure conditions

製品で有効な形式・変換経路を把握していない、関係する既知の攻撃手法を
選んだ根拠がない、または対象Modelでの試験と結果を示せない場合はPassに
しない。使われていないModelや別形式の結果だけで代用した場合も同じである。
試験で弱点を発見した事実は隠さず、評価の実施と耐性・修正の判定を別に
報告する。

## Evidence expectations

| 証拠 | 作成元 | 対象 | 確認する時期 | 保護上の注意 | 合格の目安 |
|---|---|---|---|---|---|
| 形式・経路の一覧 | 製品設計・運用担当者 | Model Version、入出力、前処理、到達経路 | Model・機能・変換経路の変更時 | 内部構成や機密Dataを公開しない | 有効な経路と対象外理由を説明できる。 |
| 攻撃手法の選定記録 | 安全性評価担当者 | 各形式に関係する既知の手法、選定根拠 | 試験設計・見直し時 | 再利用可能な攻撃Payloadを公開しない | 形式ごとの代表的な手法と試験の対応を追える。 |
| 試験実行結果 | 評価基盤・担当者 | 入力形式、対象Model、設定、停止位置、判定 | 評価実施時 | Raw出力と試験Dataの機密性を守る | 実際の対象で試験し、成功・失敗・未評価を区別できる。 |

## Known limitations and uncertainty

既知の攻撃手法だけでは、新しい変形や形式をまたぐ組合せを尽くせない。
評価結果は、試したModel、前処理、設定、時点に限られる。Black-box APIでは
Model内側とProviderのFilterを切り分けられない場合がある。Researchは
形式別の数値しきい値や適応的試験を勧めるが、正規要件に一律の数値はない。
本ControlのPassは、発見した弱点が解消されたこと、すべての攻撃を防げる
こと、製品全体が安全であることを意味しない。`verifiable`は本書の成熟度で
あり、実製品の適合結果ではない。
