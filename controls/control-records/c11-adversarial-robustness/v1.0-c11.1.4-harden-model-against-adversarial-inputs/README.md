# 敵対的入力に対するモデルの耐性強化を確認する

AISVS Verification Level: 2

[C11.1 Section講義](../../../learning/c11-adversarial-robustness/v1.0-c11.1-model-alignment-safety-and-robustness.md)

## Upstream basis

AISVS `v1.0-C11.1.4`は、敵対的入力に対してModelが強化されていることを
確かめる要件である。**敵対的入力**は、普通の利用よりもModelの誤判断や
安全方針の回避を狙って細工した入力を指す。

対応するAISVS Researchは、C11.1.3で見つけた攻撃の種類と強化策を対応させ、
訓練・前処理・分類器・文脈の分離など、採用した層が実際に働くか試すことを
勧める。変更前や対策を外した状態との比較、対策を知る攻撃者による再試行、
通常の利用への悪影響の確認も挙げる。これらは検証に役立つ方法だが、
特定の対策、試験Tool、全製品共通の数値しきい値が正規要件で指定されて
いるわけではない。

## Interpretation

製品で起こり得る敵対的入力と守るべき結果を明らかにし、その失敗を減らす
具体的な強化策を、実際に使うModelと推論経路へ適用する。攻撃を試した結果、
対策が狙った失敗を抑えることを確かめる。普通の質問に答えられることや、
対策の設定が存在することだけでは耐性を示せない。

例えば、社内文書を読むAssistantが文書内の命令を利用者の指示より優先して
しまう場合、文書を信頼できないDataとして扱う境界や、危険な出力・操作を
制限する層を設ける。そのうえで、文書からの誘導を変形した試験を通し、
Modelの応答と最終的な操作を観測する。外付けFilterで止まったなら、
製品の防御効果は示せても、Model自身の重みが強化されたとは言わない。

## Security objective

攻撃者が入力を言い換えたり、形式を変えたり、何度も試したりしても、
重要な誤判断や安全方針の回避が起きにくい状態にする。強化策がどの経路の
どの失敗を抑えたかを示し、設定だけの安心感を避ける。すべての攻撃を
防げるという意味ではない。

## Applicability

利用者、外部文書、画像、音声、検索結果、Tool出力などから、敵対的入力を
受け得るModelとその推論経路に適用する。文章生成だけでなく、画像・音声の
認識や分類で細工された入力により判断が変わる場合も対象とする。
製品が有効にした形式と、Modelが接続する機能を前提に範囲を決める。

### Non-applicability

対象の推論経路が存在せず、Modelが敵対的入力を受ける可能性がない場合に
限り、その境界を示して対象外とできる。特定の攻撃形式を製品が推論前に
拒否し、迂回経路もないなら、その形式について対象外とする余地がある。
Provider内部の訓練が見えないことや、自社でFine-tuningしないことだけを
理由に対象外とはしない。観測できない範囲は証拠の限界として残す。

## Scope and assumptions

- **Hardening（耐性強化）**は、ModelまたはModelに接続する安全性の層を
  変更し、対象とする敵対的入力による失敗を抑えることと解釈する。
  外付けの層による効果とModel自身の性質を混同しない。
- 対象の攻撃の種類は、実際に使う形式・経路と守るべき結果から選ぶ。
  C11.1.3の評価は有用な入力だが、別Controlの成熟を形式的な前提条件に
  しない。
- 強化策の前後比較または対策を外す試験が可能なら、同じ条件で効果を比べる。
  Provider API等で比較できない場合も、対象攻撃に対する観測結果と
  具体的な対策の根拠は必要である。
- 試験の合否基準は、攻撃者の能力と失敗時の影響を踏まえて先に定める。
  一律の攻撃成功率をAISVSが要求しているとは扱わない。
- 防御を知る攻撃者が入力を変形・再試行できることを想定する。固定の例で
  一度拒否できても、十分な耐性があると断定しない。

## Assets, actors, identities, and trust boundaries

守る対象は、Modelの判断・安全方針、利用者へ渡す出力、後続のToolやDataに
及ぶ権限である。攻撃者は質問、添付物、取得される文書、Toolの返却内容など
一部の入力を操作する。Model開発者・Provider、製品開発者、試験担当者、
運用者は異なる層の強化と証拠を担う。

信頼境界は、攻撃者が制御する内容が前処理を経てModelに入り、その結果が
後処理やToolへ渡るところにある。どの層で失敗を抑えたかが分からなければ、
別の経路や層の停止時に同じ効果が続くか判断できない。

## Required security properties

| ID | 必要な性質と確かめ方 |
|---|---|
| SP-1 | 対象の敵対的入力、守るべき結果、採用した強化策の関係を説明できる。 |
| SP-2 | 強化策が、評価対象のModel Versionと実際の推論経路で有効になっている。 |
| SP-3 | 関係する敵対的入力を使った試験で、対象の失敗を抑える効果を観測し、判断基準と結果を残す。 |
| SP-4 | Model自身と外付けの層の効果を区別し、迂回経路や層の停止で保証が失われる状態を見落とさない。 |

## Scope calibration and adjacent assurance

| 観測 | 本Controlでの扱い |
|---|---|
| 強化策が実経路で働き、関係する敵対的試験で事前に定めた重要な失敗を抑える | Pass候補。未知の攻撃まで防げるとは言わない。 |
| 安全性の訓練を受けたとの説明だけで、敵対的入力では試していない | 効果の証拠が不足する。C11.1.1の訓練根拠だけで代用しない。 |
| 攻撃を評価したが、対策を導入せず同じ失敗が残る | C11.1.3の評価はあっても、本Controlの耐性強化は示せない。 |
| 外付けFilterが攻撃を止めるが、Modelは危険な応答を生成する | 製品のその経路での効果として評価し、Model単体の耐性とは呼ばない。他経路とFilter停止時も確認する。 |
| 平均の攻撃成功率は改善したが、高影響の攻撃経路が残る | 重要な失敗を抑えたとは言えない。平均値だけでPassにしない。 |
| 攻撃をすべて拒否するが、正規の利用もほぼ拒否する | 本要件の数値条件ではないが、実用上の対策として成立するか別に確認する。 |
| Prompt Injectionから権限あるTool操作へ進めてしまう | Model耐性に加え、Tool側の決定論的な認可を別に評価する。 |

## Threat and failure-mode rationale

普通の入力や公開済みの固定試験にだけ成功するModelは、言い換えや複数Turn、
形式の変換を使う攻撃者に破られ得る。対策名があるだけでは、実経路で働くか、
既知の失敗を減らすか、別の形式で迂回できるかが分からない。単一のFilterへ
依存すると、その層が停止・迂回されたときに守りが失われる。
外部脅威IDとの厳密なMappingはまだ評価していない。

## Verification

### Architecture and configuration review

対象Modelと設定、利用する形式・前処理・後処理、採用した強化策、保護する
出力・判断を洗い出す。各対策がどの攻撃経路で有効か、別EndpointやFallbackに
抜け道がないかを確かめる。Provider資料は採用した層の説明として使えるが、
製品での有効性を単独で証明しない。

### Positive verification

関連する敵対的入力を安全な合成Dataで用意し、対象Modelと実際の推論経路で
試す。可能なら対策前または対策を外した条件と比べ、Modelの応答、後段の
結果、攻撃の成功・失敗を記録する。対策を知る攻撃者が入力を変える条件も
加え、事前に定めた重要な失敗が抑えられるか確認する。正規の近接入力も
試し、全拒否を耐性と取り違えない。

### Negative and abuse-case verification

| ID | 試すこと | 期待する確認結果 |
|---|---|---|
| N-1 | 普通の質問での成功と対策の設定名だけを証拠にする | 敵対的入力での効果が未確認と分かり、SP-3のPassにしない。 |
| N-2 | 対策を外す、または対策を通らないFallbackへ切り替える | 実経路ごとの強化状態と失敗の変化を観測し、抜け道を見落とさない。SP-2・SP-4。 |
| N-3 | 固定試験を知る攻撃者として入力を言い換え、複数Turnや形式の変換を使う | 当初の試験だけに依存した弱点を発見し、残る失敗を報告する。SP-3。 |
| N-4 | Filterの依存先が停止した状態で同じ攻撃を試す | 実際の停止時の扱いを確認し、保護されない経路を保護済みと主張しない。SP-2・SP-4。 |
| N-5 | 攻撃成功率の平均だけで判断し、重要な一種類の失敗を隠す | 影響の大きい経路を個別に評価し、全体平均で上書きしない。SP-1・SP-3。 |

### Failure conditions

対象の攻撃と強化策の関係が説明できない、実際の推論経路に対策がない、
敵対的入力で効果を確かめていない、または定めた重要な失敗が残る場合は
Passにしない。対策前との比較が難しいことだけで直ちにFailとはしないが、
「強化された」と判断できる観測と根拠がなければ証拠不足とする。
通常利用への影響、Release承認、Tool認可は関連する別の保証として報告する。

## Evidence expectations

| 証拠 | 作成元 | 対象 | 確認する時期 | 保護上の注意 | 合格の目安 |
|---|---|---|---|---|---|
| 強化策と攻撃の対応表 | Model・安全性担当者 | 対象Model、攻撃経路、対策、守る結果 | 対策の採用・変更時 | 内部構成や攻撃Payloadを公開しない | 各重要経路に対策と判断基準が結び付く。 |
| 配備設定と経路確認 | 製品・運用担当者 | 対策の有効状態、Endpoint、Fallback | 配備・変更時 | Secretや内部EndpointをRepositoryへ置かない | 試験した層が実際の経路でも有効と確認できる。 |
| 敵対的試験の結果 | 評価担当者 | Model Version、対策Version、攻撃の種類、成功・失敗、正規入力の結果 | 採用・重要変更時 | 実際の有害出力や機密Dataを公開しない | 重要な失敗を抑える効果と限界を、対象経路ごとに判断できる。 |

## Known limitations and uncertainty

有限の試験で未知の攻撃や適応的な攻撃者に対する完全な耐性は証明できない。
固定試験への最適化、Model更新、Provider内部の変更で効果が変わり得る。
強化策は正規の質問を過度に拒否したり、特定の言語・形式で性能を落としたり
する可能性もある。Researchは比較試験や形式別のしきい値を勧めるが、
正規要件は共通の数値を指定していない。外付けの層で守れた場合もModel自身の
耐性と区別し、Tool操作の決定論的認可は別に必要である。`verifiable`は
本書の成熟度であり、実製品の適合結果ではない。
