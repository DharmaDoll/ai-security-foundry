## 1. この章で保証したいこと

例えば、問い合わせ対応Agentが社内文書を読み、顧客情報を確認し、返金を提案するとする。
正しい利用者として認証されていても、返金先のすり替え、過大な金額、無限の再試行、
別Agentへの権限の引き継ぎ、停止後も続くバックグラウンド処理が問題になる。

C9は、こうした自律的・複数段階の行動について、許可された範囲、意図、実行量を
保ちながら、人が介入・停止できることを扱う。[要件本文][normative]

このRepositoryでは、次の問いへ翻訳して理解する。

- その操作を、その引数で実行してよいか。
- 人が確認する必要のある操作が、確認前に実行されないか。
- 非信頼データを処理した結果が、強い権限を持つ実行機能へ無制限に流れないか。
- 委任、再試行、長時間実行でも、権限・実行量・追跡可能性を維持できるか。
- 失敗や侵害が起きても、被害を限定し、停止できるか。

ここでRuntimeとは、モデルの提案を受け、ツール呼び出しや処理の継続を制御する実行基盤。
Trust Boundaryは、データや要求をそのまま信頼せず、検証・認可が必要になる境界を指す。
この章の分析では、モデル、Runtime、ツール、下流API、人の承認・運用機能の境界を追う。

IDとLevelは[要件本文][normative]、検討観点は対応ResearchとRepositoryの解釈に基づく。
LevelはAISVSの検証レベルであり、実装順序やControl成熟度ではない。

## 3. Researchから持ち帰る検討観点

章概要と全6節の要件別Threat／Verification／Gapsを中心に確認した。
以下はResearchを踏まえた検討観点であり、すべてを各要件の必須条件にはしない。

- **C9.1**：呼び出し元のタイムアウト後も処理が続く場合や、子Agent・再試行の消費量が
  集計から外れる場合を検証する。停止通知の成功と実際の消費・副作用の停止を区別する。[R1][r1]
- **C9.2**：承認画面が示す操作と実際の操作が同じか、別API経由で承認を迂回できないかを
  確認する。AIによるレビューの追加は、人の承認や決定論的認可の代替にはならない。[R2][r2]
- **C9.3**：ツールの制約を宣言する文書と、実際の権限・通信・出力検証を照合する。
  正しい形式のツール出力にも悪意ある指示が含まれ得るため、形式検証と能力分離を分ける。[R3][r3]
- **C9.4**：共通サービスIDや単なるTrace IDでは、個体の識別や記録の真正性を証明できない。
  保存データの完全性があっても、正規経路から書かれた内容が安全とは限らない。[R4][r4]
- **C9.5**：呼び出し先ツールだけでなく引数を評価し、委任元の制限を下流へ保つ。
  有効期限内のTokenと、現在も許可される操作は同一ではない。[R5][r5]
- **C9.6**：画面を閉じる、親処理だけを止める、といった操作で下流処理まで停止するとは
  限らない。停止範囲、遅延、残る処理、安全な再開の条件を明らかにする。[R6][r6]

Researchには製品機能、攻撃事例、統計、他標準への参照が大量に含まれる。
本分析ではそれらの最新性・真偽を一括認定せず、数値や製品推奨を転記しない。
個別Controlで根拠に使うものだけ、元の一次資料を確認する。

要求範囲の混同にも注意する。例えばResearchのC9.2.2の検証案には暗号的なパラメータ結合が
含まれるが、要件本文では表示内容がC9.2.2、暗号的結合がC9.2.8に分かれる。
C9.3.2のResearchにはツール引数の検証案もあるが、要件本文の対象はツール**出力**のSchema検証。
補足を読んで、一つの要件へ隣接要件の保証を無条件に取り込まない。

## 4. C5との違いと接続

C5はAI資源・利用者のIdentity、アクセス制御、データ・Tenant境界を扱う。
C9はAgentの行動連鎖と実行基盤を中心に、その権限が行動時にも守られるかを扱う。
重なりはあるが、次の保証を同一視しない。

| C5で整備した保証 | C9で追加して確かめること |
|---|---|
| C5.2.5：認可判断を担うPDPをAgentの支配から隔離する | C9.5.3：モデルではなくApplication／Policy Engineで強制する。C9.5.1：ツール・引数にどの制約を強制するか。 |
| C5.2.1：明示的AllowとDefault Deny | C9.5.1：許可済みツールでも対象・金額・送信先などの引数に制約が必要。 |
| C5.1.1：高Risk操作前の追加認証 | C9.2.1：具体的な操作への人の承認。本人確認を追加しても、その操作への同意を得たとは限らない。 |
| C5.1.2：Agent Tokenの短命・最小Scope・署名、C5.2.6：特権のJIT化 | C9.5.2／9.5.5／9.5.6：委任で制限を失わず、長時間実行でも現在の権限で評価する。C9.4.3の資格情報更新も別の観点。 |
| C5.2.2：利用者に認可された範囲での検索・組立 | C9.3.5／9.3.6：読む権限がある内容でも、非信頼データから操作能力への影響を制限する。 |
| C5.3：Tenant間の分離 | C9.1／9.6：境界内の正規処理でも、実行量を限定し、必要時に停止する。 |

C5側の意味は[既存Control一覧](../README.md#c5-control-records)を正本とする。
上表は保証範囲の比較であり、代替可能性やEngineeringへのMappingを主張しない。

## 5. 最初のControl：v1.0-C9.5.1（Level 2）

要件の要旨は、Runtimeが細粒度のPolicyでAgentの呼び出せるツールと指定できる引数値を制限すること。
正確な原文は[要件本文のC9.5][normative]を参照する。

例えば、`refund`という返金ツールが許可されていても、すべての注文、金額、返金先への実行が
許可されるわけではない。利用者が扱える注文か、金額が上限内か、返金先が認められるかを
モデル外の信頼できる情報とPolicyで判断する。この具体例はRepositoryの説明用である。

この要件を選ぶ理由は次のとおり。

1. C5の認可判断の隔離から、判断する内容の粒度へ自然に進める。
2. 読み取り、更新、送信、インフラ操作に共通し、特定Protocolや製品に依存しない。
3. 正常なツール呼び出しと、同じツールへの許可範囲外の引数を比較でき、検証結果が明確になる。
4. 人の承認、委任、予算、停止を別要件として残したまま、レビューできる範囲に絞れる。

比較した候補は、C9.5.3（L2）、C9.2.1（L1）、C9.1.2（L1）。C9.5.3はC5.2.5との
境界整理に有用だが、初手として増える検証観点が少ない。C9.2.1は重要だが、承認対象の定義を
先に明確にしたい。C9.1.2は累積予算という新しい保証を加えるため、その次の独立した題材とする。

これはC9での最初の代表要件の選定であり、Repositoryの初期Golden ControlであるC5.2.5を置き換えない。

### 次の作業で明らかにすること

- 適用境界：ツール一覧の公開・非公開と、実行時の認可を区別する。
- Security Invariant（守るべき性質）：実行可能なツールでも、Policyに反する引数では副作用を起こさない。
- Enforcement Point（強制点）：実際にツールを呼ぶ前に、信頼できる実行基盤・下流処理が拒否できる位置。
- Negative Test：許可ツールの対象ID・金額・送信先の変更、別経路からの呼び出し、モデルによる許可主張。
- Evidence：適用Policy、実際に評価した引数、判断記録、下流で操作が起きた／起きなかった証拠。
- 限界：Policy内の悪用や業務意図の取り違えまで、引数認可だけで防げるとはしない。

型やJSON形式が正しいことは認可の根拠にならない。一方、業務固有の上限値や返金ルールを
AISVSそのものの要求と表現しない。具体的な検証案とEvidenceの受入条件は個別Controlで詰める。

## 6. 小さく進める順序

| 段階 | 対象 | 狙いと終了条件 |
|---|---|---|
| 今回 | C9全体の分析と代表要件の選定 | 6節の保証範囲、C5との差、初手をこの文書に残す。 |
| 次 | C9.5.1 | 一つのControlを既存Templateで整備し、Catalogへ追加。解釈・適用境界・脅威・検証・証拠・限界が揃ってから`verifiable`とする。 |
| 続く代表要件 | C9.2.1 → C9.1.2 → C9.3.5 → C9.4.1 → C9.6.3 | 承認、累積予算、非信頼処理の能力分離、個体Identity、独立した停止経路を一件ずつ深め、6節で異なる保証を確かめる。 |
| 各節の拡充 | 残る要件 | 代表要件で得た知見を使い、表示と承認結合、宣言と強制、単体停止と群停止などの境界を一件ずつ整理する。順序は利用上の需要で見直す。 |

参照先のControlが未整備でも、関連する要件本文とResearchを読んで意味を確認する。
先行Controlの完成を形式的な依存条件にしない。全34件の詳細ファイルや空のCatalog行は先に作らない。
この一覧だけでCatalog上の成熟度を進めない。個別Control整備後の状態はCatalogを正本とする。

学習は別の流れで、希望時に[共通学習方針](learning/README.md)に従って実施する。
学習の一巡や質疑応答をControl成熟の条件にはしない。Engineeringも独立して進め、
両側の成果物を理解できた段階でMappingを評価する。
