# C5.2.2 Retrieval／AssemblyにおけるEnd-user Authorization 学習ノート

## この文書について

この文書は、AISVS `v1.0-C5.2.2`を題材に行った学習セッションを、後から単独で
参照できる講義として再構成したものである。

これはControl本文、製品の適合判定、またはAISVS原文の代替ではない。次を分離する。

- **Normative:** AISVS v1.0が実際に要求していること。
- **Research:** AISVS Researchが示す脅威、Pipeline stage、検証上の補足。
- **Repository interpretation:** 現場のArchitecture Reviewへ適用するための解釈。
- **Derived insight:** 具体例と質疑から得た、Requirement外を含むSecurity上の洞察。

対応するControl本文は
[`v1.0-C5.2.2 End-user Authorization Across Retrieval and Assembly`](../../../control-records/c05-access-control-and-identity/v1.0-c5.2.2-end-user-authorization-retrieval-assembly.md)
にある。学習の完了によってControl maturityは変更しない。

## 1. Normative Requirement

- Versioned ID: `v1.0-C5.2.2`
- AISVS Verification Level: `2`

> Verify that retrieval pipelines (e.g., RAG queries, embedding lookups) enforce
> the end-user's authorization context at each retrieval and assembly stage,
> rather than relying solely on the service account's permissions.

意味を崩さない日本語訳:

> Retrieval Pipeline（RAG QueryやEmbedding Lookup等）が、Service Accountの
> Permissionだけに依存せず、RetrievalとAssemblyの各段階でEnd UserのAuthorization
> Contextを強制していることを検証する。

原文が直接要求しているのは、特定製品や一つの認可方式ではない。最終的な回答だけで
なく、Dataを検索、追加、拡張、再利用してModel Contextを組み立てる各段階において、
依頼したEnd Userの権限範囲を失わないことである。

## 2. C5における位置づけ

C5.2.1は、Vector CollectionやEndpoint等のAI Resource自体が明示的AllowとDefault
Denyで保護されることを求める。C5.2.2は、そのResourceを正当に利用できるRAG Service
であっても、代理元のEnd Userより広いDataを取得してはならないことを求める。

```text
C5.2.1: このRAG ServiceはVector DBへQueryしてよいか
C5.2.2: このRAG ServiceはAliceの依頼で、どのDataをQuery／Assemblyしてよいか
```

両方にPassする必要がある。Service AccountがVector DBへ接続できることは、Aliceが
Vector DB内のすべてのDocumentを読めることを意味しない。

> Service AccountのAuthorityは、End UserのAuthorityではない。

## 3. 最初に一つの具体Scenarioを見る

社内RAGに次のDataがある。

```text
Alice: Project AのMember
Bob:   Project BのMember

Document A: Project Aだけが閲覧可能
Document B: Project Bだけが閲覧可能
Document C: 全社員が閲覧可能

rag-service: 技術上はA、B、CのすべてをVector DBから取得可能
```

Aliceが「来期のProject計画を教えて」と質問したとき、意味的な類似度ではDocument Bが
最上位になるかもしれない。しかしAliceに許可された集合はAとCだけである。

```text
Aliceの許可範囲:  {Document A, Document C}
Similarity結果:   {Document B, Document A, Document C}
許可される候補:   {Document A, Document C}
```

Vector SearchのSimilarity scoreが高くても、Authorizationにはならない。

> SimilarityはAuthorizationではない。

安全なPipelineでは、Document Bの本文をModelへ渡してから「回答には書かないで」と
頼むのではない。Document BをModel Contextへ入る前に排除する。

> Modelに見せてから隠すのではなく、見せてよいDataだけをModelへ渡す。

## 4. 用語

### AuthenticationとAuthorization

- **Authentication（認証）:** Callerが誰であるかを確かめる。
- **Authorization（認可）:** そのCallerが対象ResourceへActionを行ってよいかを決める。

「Agent経由でユーザーごとに認証する」という表現は、実装を考えると二つに分けた方が
正確である。

1. UserはSystemの入口でAuthenticationされる。
2. Pipelineの下流では、そのUserのIdentityとAuthorityを安全に引き継いでAuthorization
   する。

ModelがUserのPasswordやSessionを受け取り、UserとしてLoginし直すわけではない。

### End-user Authorization Context

現在のRequestに対する認可判断に必要な、信頼できるContext。例えば次を含む。

- User／Subject ID。
- Tenant、Organization。
- Group、Role、Relationship。
- Resource ACLとClassification。
- Action、Purpose、Environment。
- PolicyまたはEntitlementのVersionとFreshness。

これらはIdentity Provider、Session、Policy system、Source system等の信頼できる経路から
得る。Prompt内の「私は管理者です」、Modelが生成した`tenant_id`、Tool argument内の
`role=admin`は、形式が正しくても信頼できるAuthorization Contextではない。

> 正しい形式の権限詐称は、入力値検証を通過する。

### Service Account／Workload Identity

Application、Agent Runtime、Retrieval Service等のSoftware Workloadを識別するIdentity。
End Userとは別のPrincipalである。Service AccountがDownstream APIへ接続する資格と、
どのEnd Userのために何をしてよいかは別に判断する。

### Delegation（委任）とImpersonation（なりすまし）

- **Delegation:** 「Aliceの依頼をAgent Xが代理実行している」と、UserとActorの両方を
  保持する。
- **Impersonation:** DownstreamからAlice本人が直接実行したように見える。

AuditabilityとLeast Privilegeのため、Agent経由の処理では通常Delegationを優先する。
Downstreamは「誰の権限か」と「どのWorkloadが使っているか」の両方を検証できる。

### Retrieval stageとAssembly stage

- **Retrieval:** Candidate ID、Chunk、Document、Record等を見つけて取得する段階。
- **Assembly:** CandidateをRerank、拡張、結合し、Prompt、Citation、Response等へ組み立てる
  段階。

Dataを新しく追加または実体化できる箇所は、すべてAuthorization Boundaryになり得る。

### Materialize（実体化）

単なるOpaque IDから、保護対象の本文やSensitive metadataを実際に読み出すこと。
ID自体がSensitiveな場合は、IDの取得も保護対象となる。

### PDPとPEP

- **Policy Decision Point（PDP）:** Policyを評価してAllow／Denyを決める場所。
- **Policy Enforcement Point（PEP）:** そのDecisionを実際のData Accessへ強制する場所。

各Stageが認可範囲を守ることは必要だが、各Functionが毎回Remote PDP APIを呼ぶことと
同じではない。

## 5. Agentを経由したUserごとのIdentityとAuthorization

### 結論

Userは入口で認証し、Agentは別のWorkload Identityを持つ。DownstreamへはUserの
Authorityを、AgentというActorと対象APIを明示した短命な委任Contextとして渡す。
Model自身にはTokenを保持させず、PromptやModel outputからAuthorityを作らない。

### Microservice構成の具体例

```text
Alice
  | 1. OIDC Login／OAuth Authorization
  v
Identity Provider
  | 2. User SessionまたはAccess Token
  v
Application／Agent Gateway  <---->  Agent RuntimeのWorkload Identity
  | 3. Token Exchange／On-Behalf-Of
  v
Security Token Service
  | 4. Retrieval API専用の短命なDelegated Token
  v
Retrieval API (PEP)  <---->  PDP／Source ACL
  | 5. Aliceに許可されたQuery constraint
  v
Vector DB／Document API
```

各段階の役割は次である。

1. BrowserやClientは、OIDC Authorization Code flow（Public Clientでは通常PKCEを併用）
   等によりUserを認証し、OAuth Access TokenまたはApplication Sessionを確立する。
   Web ApplicationではServer-side Sessionを使う構成もある。
2. GatewayはTokenまたはSessionを検証し、AliceというPrincipalをServer側の信頼できる
   Request Contextへ結び付ける。
3. Agent RuntimeもmTLS、SPIFFE/SPIRE、Cloud Workload Identity等で別途認証される。
4. Token ExchangeまたはOn-Behalf-Of flowにより、対象をRetrieval APIに限定した短命な
   Tokenを得る。
5. Retrieval APIはTokenの署名、Issuer、Audience、有効期限、Subject、Actor、Scope等を
   検証し、現在のSource ACLまたはPDPに照らしてQueryを制約する。

OAuth 2.0 Token Exchange（RFC 8693）は、この委任を表す一つの標準的な選択肢である。
概念的には次の情報を保持する。

```text
subject:  Alice                     誰のAuthorityか
actor:    rag-agent                 誰が代理実行しているか
audience: document-retrieval-api    どこでだけ使えるか
scope:    documents.read            何ができるか
tenant:   tenant-a                  どのSecurity domainか
expiry:   5 minutes later           いつまで使えるか
```

実際のClaim名とPolicyはIdentity基盤によって異なる。RFC 8693を使えば自動的に安全に
なるわけではない。Security Token Serviceは、AgentがAliceの代理としてそのScopeを得て
よいかを確認し、Audienceを限定し、RevocationとSession終了の反映方法を別途定める。

元のUser Tokenを、対象Audienceを確認せず複数のServiceへそのまま転送するToken
Passthroughは避ける。TokenをPrompt、Model Context、Toolの自由記述引数へ含めない。
Retrieval APIへのCredentialは、信頼できるGatewayまたはRuntimeがRequestへ付与する。

### よりSimpleな構成も正しい

Agent OrchestrationとRetrievalが一つのTrusted Backend内にあるなら、毎回Token Exchangeを
導入する必要はない。Server-side Sessionから作った型付きのRequest Contextを、Modelが
変更できないApplication code pathでPEPまで渡せばよい。

```text
RequestContext
  - authenticated_user_id
  - tenant_id
  - authorization_scope
  - policy_revision
```

重要なのはTechnologyの数ではなく、User Contextを失わず、ModelやAgent出力で上書き
できず、Data Access直前で強制されることである。

Asynchronous Jobでは、User、Actor、Resource、Action、Tenant、Job ID、有効期限を結び
付けた短命なJob capabilityまたは署名済みTask Contextを使う方法がある。Long-running
Jobでは、実行時に権限が失効していないかを再評価する。

> 設計のSimpleさは、Identity Contextを翻訳・複製・Cacheする箇所を減らす。
> その結果、認可を落とす経路も減る。

## 6. Vector化時のChunk Label

### ChunkごとにLabelを持たせる考え方は正しい

Vector SearchがChunkを最小のRetrieval単位とするなら、元Documentの認可に必要な
metadataを各Chunkへ関連付けるのが一般的である。

```text
chunk_id
source_resource_id
parent_id
tenant_id
owner_id
allowed_group_ids または acl_reference
classification
source_revision
authorization_metadata_revision
```

ただし、LabelはAuthorization Decisionそのものではない。Labelは、現在のUserの
Entitlementと照合するための入力である。

```text
Chunk metadata: tenant=tenant-a, allowed_group=project-a
Current user:   tenant=tenant-a, groups={project-a, all-employees}
Decision:       allow
```

### LabelのSourceとIntegrity

Labelは、ModelやEnd Userに作らせない。Ingestion PipelineがDocument SystemのACL、
Owner、Tenant、Classification等のAuthoritative metadataから付与する。

次も必要になる。

- 元Document IDとChunkのLineageを保持する。
- ACL変更時にChunk metadataを更新または無効化する。
- Metadata revisionまたはPolicy revisionによりStalenessを検出する。
- Ingestion権限を制限し、別TenantのLabelを付けるMetadata spoofingを防ぐ。
- ACLが異なるSectionを、同じParentとして無条件に展開しない。

ACL文字列をEmbedding vectorへ意味情報として埋め込んではならない。Similarityは厳密な
Authorization比較を保証せず、ACL変更にも弱い。Filter可能なStructured metadata、
別のAuthorization Index、またはSource systemのACLとして管理する。

### Chunkごとの巨大なUser一覧は必須ではない

許可Userが多い場合、各Chunkへ全User IDを複製すると更新が難しい。代わりに次を使える。

- Tenant IDとGroup／Role ID。
- Source DocumentのACLへのReference。
- Relationship-based AuthorizationのObject ID。
- Policyで評価するClassificationとAttribute。
- Tenant別のCollection／Namespace。

どの方式でも、Authoritative ACLの変更を検索結果へいつ反映するかを決める。

### C5.2.7との境界

C5.2.7は、Classification LabelがDownstreamのDerived Artifactへ伝播するPropertyを扱う。
C5.2.2は、そのLabelやACLを使ってEnd UserのAuthorityをRetrieval／Assembly全体で
強制するPropertyを扱う。

```text
C5.2.7: Labelを失わず運ぶ
C5.2.2: Labelを含むTrusted ContextでAccessを実際に制限する
```

## 7. Vector DB検索時に「都度認可」するとは何か

### 短い答え

各Requestと、保護Dataを新たに追加または実体化できるStageでは、現在のEnd Userの
Authorityが必ず効いている必要がある。ただし、Chunkごと、FunctionごとにRemote PDPを
呼ぶ必要がある、という意味ではない。

### 方法1: Query-time metadata pre-filter

Trusted User ContextからFilterを作り、Vector similarity searchの候補生成前または同時に
適用する。

```text
tenant_id = "tenant-a"
AND allowed_group_ids intersects {"project-a", "all-employees"}
```

長所は、Unauthorized Chunk本文をRetrieval Serviceへ返さず、対象Candidate内でTop-kを
計算できること。短所は、Vector DBのFilter semantics、Metadata integrity、ACL更新遅延、
複雑なRelationship表現に依存することである。

### 方法2: Collection／Namespace／IndexによるHard partition

TenantまたはSecurity domainごとに検索空間を分け、Trusted IdentityからRouting先を
決める。

長所は、他TenantのDataをQuery対象にできないSimpleで強いBoundaryを作りやすいこと。
短所は、Tenant数、Shared Document、Cross-tenant検索、運用CostによってCollection管理が
複雑になることである。

実務では、TenantをHard partitionし、その中のDocument-level ACLをmetadata filterで
制御するHybridが使いやすい場合がある。

### 方法3: External PDPが許可Candidateを制約する

Retrieval ServiceがPDPまたはAuthorization serviceから、許可Object ID、Filter、
Relationship、Capability等を得てVector queryへ適用する。

長所は、複雑なRBAC、ABAC、ReBACを中央で評価できること。短所は、Latency、Availability、
大量Objectの表現、Decision cacheとRevocationの設計が必要になることである。

一件ずつPDPへ問い合わせるのではなく、Query用ConstraintへCompileする、Batchで判断する、
短い有効期限のCapabilityを使う等の方法がある。

### 方法4: Source systemで本文取得前に再認可する

Vector DBがOpaqueなCandidate IDだけをTrusted Retrieval Serviceへ返し、Document APIが
現在のUser Contextで再認可してから本文を返す。

長所は、Source ACLを最終的なAuthorityにできること。短所は、追加Call、Latency、Batch化、
Top-kの精度に注意が必要なことである。Unauthorized Candidateを後から除くと、許可された
Candidateが十分に残らずRecallが低下することがある。

この方式が安全なのは、本文とSensitive metadataがAuthorization前にBoundaryを越えず、
Candidate ID自体がSensitiveでないか保護されている場合である。Unauthorized本文を広く
取得してModel Contextへ入れ、最後にOutputだけFilterする方式はC5.2.2を満たさない。

### 方法5: Hybrid

高いImpactを持つSystemでは、次のように複数を組み合わせる。

```text
Tenant partition
  + Query-time ACL filter
  + Source-side authorization before materialization
  + Cache hit時の再認可またはScope binding
```

全Layerを常に重ねればよいわけではない。Data sensitivity、ACL complexity、Revocation
要求、Latency、Failure modeを基に、どのBoundaryで何を保証するかを明示する。

## 8. RetrievalからAssemblyまでのEnforcement

### Stageごとの考え方

```text
User Request
  -> Vector／Keyword Retrieval
  -> Reranking
  -> Parent Expansion
  -> Secondary-source Retrieval
  -> Prompt Assembly
  -> Model Context
  -> Citation／Response／Cache
```

Rerankerが、すでにAuthorization済みの候補だけを並べ替え、削除し、新しいDataを取得
できないなら、Remote PDPの再呼出しは不要である。Rerankerの出力が入力候補より広がらない
Architectureによって、Authorizationを守れる。

> 各Stageで認可を守ることと、各FunctionでPDPを呼ぶことは同じではない。

一方、Parent Expansion、Attachment取得、Secondary Retriever、Cache hit、Fallback等は、
新しいDataを追加または実体化できる。このBoundaryでは、元のAuthorized scopeで制約
されていることを再確認またはArchitectureで保証する。

### Parent Expansionの具体例

検索精度のため、小さなChild ChunkをVector化し、検索後により大きいParent Sectionや
Documentを取得してContextを増やす処理をParent Expansionという。

```text
Employee Handbook（Parent Document）
  +-- Child 1: 全社員向け休暇制度          Aliceは閲覧可
  +-- Child 2: HR限定の懲戒手続            Aliceは閲覧不可
  +-- Child 3: HR限定の調査事例            Aliceは閲覧不可
```

Child 1がHitしたことを理由に、Service AccountでParent全体を読むとFailする。Childへの
AllowはParent全体へのAllowではない。

安全な選択肢には次がある。

- Parentを取得する前にAliceのAuthorityで再認可する。
- Aliceに許可されたSibling Chunkだけを拡張する。
- 異なるACLのSectionを同じExpansion unitへ入れない。
- Source systemへAliceのDelegated Contextを渡し、許可範囲だけ返させる。

> ChildへのAuthorizationはParent全体へのAuthorizationを意味しない。

## 9. Security Invariant

まず平易な言葉で表す。

> 各Data-bearing Stageは、現在のEnd Userが許可されたDataだけを出力し、未認可Dataを
> 一件でも追加してはならない。

ここで**Data-bearing Stage**とは、Protected contentまたはSensitive metadataを保持、
追加、返却、再利用できる段階である。

集合記号を使うなら、同じ内容は次で表せる。

```text
Stageの出力 ⊆ 現在のUserに許可されたData
```

`⊆`は「左側の要素が、すべて右側にも含まれる」という意味の**部分集合**の記号である。
左右が同じでもよい。

Aliceに許可されたDataが`{A, C}`なら、次はInvariantを守る。

```text
{A}       Pass
{C}       Pass
{A, C}    Pass
{}        Pass（Security上は安全だが、検索品質は低い可能性がある）
```

次は一件でも未認可のBを含むためFailする。

```text
{B}       Fail
{A, B}    Fail
```

Security invariantは「毎回同じ件数を返す」ことではない。Authorized setから外へ広がら
ないことである。

## 10. Threat ModelとAbuse Path

### Confused Deputy

Confused Deputyは、広い権限を持つServiceが、依頼者の権限範囲を確認せず代理操作して
しまうFailureである。

```text
低権限のAlice
  -> 質問またはPrompt Injection
  -> 全Documentを読めるrag-service
  -> Aliceには禁止されたDocument Bを取得
  -> Model Context、Citation、Cache、Responseへ伝播
```

Prompt InjectionはAbuse pathになり得るが、根本FailureはPromptの存在ではない。
ServiceのAuthorityとUserのAuthorityを分けず、Data Access直前で認可しなかったことに
ある。

### Stale Authorization

```text
AliceのProject A権限を剥奪
  -> Vector metadata／PDP cache／Response cacheは古いまま
  -> Aliceが以前の権限でDocument Aを取得
```

ACL変更を即時反映できない場合は、許容する最大Staleness windowを決め、期限内に更新・
失効させる。無期限に古いAllowを使い続けてはならない。

### Fail-open fallback

```text
PDP Timeout
  -> User filterを省略してService Accountだけで検索
  -> 全TenantのCandidateを返す
```

Authorization Contextが欠落、検証不能、期限切れ、またはPDPがUnavailableなら、Deny、
空のAuthorized result、または明示された安全な縮退へ倒す。

## 11. CacheはAuthorization Boundaryである

Bobが作ったResponseをQuery textだけでCacheし、同じ質問をしたAliceへ返すとFailする。
過去のBobへのAllowは、現在のAliceへのAllowではない。

```text
危険なCache key:
  hash(query_text)

改善候補:
  hash(query_text + normalized_authorization_scope + policy_revision)
```

ただし、User IDだけをKeyへ追加しても、UserのRole剥奪やDocument ACL変更を自動的には
反映しない。主な方式は二つある。

1. Principal、Tenant、Group／Role、Purpose、Policy revision等、Decisionに影響するScopeで
   CacheをPartitionし、変更時にInvalidationする。
2. Cacheへ元DataのProvenanceを保持し、Cache hit時に現在のAuthorityで再認可する。

Authorization Scope Fingerprintは、認可判断へ影響する正規化済みContextをHash等で表した
Cache partition用Identifierである。これは認可判断そのものではない。

> Cache keyはOptimization Boundaryであり、Authorization Decisionではない。

> Cacheへ保存した時点のAuthorizationは、後から読むPrincipalへ自動的には継承されない。

## 12. Pass／FailとScope Calibration

| Observation | C5.2.2 | 理由または別のProperty |
|---|---|---|
| Vector searchがTrusted User Contextから作ったConstraintで検索し、後段は候補を追加できない | Pass候補 | 全Alternate path、Cache、Failure modeも同じScopeを守る必要がある |
| Authorized Child ChunkからService Account権限だけでUnauthorized Parent本文を取得した | Fail | Parent ExpansionでUser scopeを失った |
| Unauthorized本文はModel Contextへ入ったが、最終回答へ出力されなかった | Fail | 非出力とSecurity Boundaryを越えないことは別である |
| RerankerがAuthorized候補だけを並べ替え、削除し、新Dataを取得できない | Pass候補 | PDP再呼出しではなく、OutputがAuthorized set内に保たれる設計で守る |
| Bob向けResponse cacheをQuery textだけでAliceへ返した | Fail | Cache再利用時にAliceのAuthorityを確認していない |
| Opaque IDだけを検索し、Document APIが本文取得前に現在のUserで認可した | Pass候補 | ID／metadataのSensitivityと全取得経路を確認する |
| Promptの`tenant_id`でVector filterを作った | Fail | Caller-controlled値はTrusted Authorization Contextではない |
| Retrievalは正しいが、Model servingのCross-tenant side channelからDataが漏れた | C5.2.2単独ではPassし得る | C5.3のTenant Isolationを評価する。System全体は安全でない |
| Retrievalは正しいが、Authorized Document内のPrompt Injectionで不正Tool実行した | C5.2.2単独ではPassし得る | Agent／Tool Authorization等の別Propertyを評価する |

> 出力されなかったことと、未認可DataがSecurity Boundaryを越えなかったことは別である。

## 13. このRequirementだけでは保証しないこと

C5.2.2にPassしても、次は別途評価する。

- Upstream Identity、Group membership、ACL、Classification自体が正しいこと。
- Prompt Injectionを防止または封じ込めること。
- 許可されたDataからのSensitive情報推論。
- Model weightsへのSensitive Data固定化。C5.2.3の主題である。
- Post-inferenceのOutput entitlement filtering。C5.2.4の主題である。
- Classification LabelのDownstream伝播。C5.2.7の主題である。
- Shared Model servingとComputeのTenant Isolation。C5.3の主題である。
- Poisoning、Model memorization、Unsafe Tool use、Supply-chain compromise。

C5.2.2は重要だが、「RAG全体が安全」という証明ではない。

## 14. 質疑の再構成

### 問い1: Authorized ChildからUnauthorized Parentへ展開した

**Scenario:** Aliceに許可されたChild Chunkが検索Hitした。Parent ExpansionはBroadな
Service AccountでDocument全体を取得し、その中にはAliceが読めないAppendixがある。
ModelはAppendixを回答へ出力しなかった。

**学習者の判断:** Fail。DocumentへのAccess checkなしにParentを検索したため。

**整理:** 正しい。より厳密には、Parentを取得する行為自体が常にFailなのではない。
Unauthorized Appendixが実体化され、Model Contextへ入ったことが直接のFailureである。
ChildへのAllowをParent全体へ暗黙に拡大してはならない。

### 問い2: RerankerでPDPを再度呼んでいない

**Scenario:** BackendがAliceのTrusted Authorization Contextから許可Document集合を作り、
Vector検索をその集合に限定した。Rerankerは候補を並べ替えるだけで、新しいData sourceへ
Accessできない。Reranker内ではPDPを再度呼んでいない。

**学習者の判断:** Pass。Rerankerは新しいDataを追加しない性質だから。

**整理:** 結論は正しい。一般的なRerankerは並べ替えに加えてTop-k選択や候補削除を行う
場合があるが、Security上の要点は、新しいUnauthorized Dataを追加または実体化できない
ことにある。ArchitectureによってAuthorized subsetを維持することもEnforcementである。

### 問い3: Query textだけでResponseをCacheした

**Scenario:** Bobが許可されたDocument Bから作ったResponseを、Query textだけをKeyに
Cacheした。Aliceが同じ質問をするとCache hitした。

**学習者の判断:** Fail。AliceのUser／Role情報と照らし合わせる必要がある。

**整理:** 正しい。ただしUser ID／Roleだけでは、Tenant、Group、Object ACL、Purpose、
Policy変更、Revocation等を表せないことがある。CacheをAuthority scopeへBindingするか、
Hit時にProvenanceを現在のAuthorityで再認可する。

### 問い4: `⊆`とは何か

**学習者の疑問:** Security Invariantに出てきた`⊆`の意味が分からない。

**整理:** `⊆`は部分集合を示す。左側の全要素が右側にも含まれるという意味である。
最初に自然言語で説明せず記号を提示したのは講義上の不足だった。このため本ノートでは、
自然言語、具体的な集合例、最後に記号、という順へ修正した。

### 問い5: Agent経由でUserごとにどう認証するのか

**学習者の疑問:** Vector化時にChunkごとにLabelを付ける方法を見た。Agentを経由する
Userごとの認証は、具体的にどのTechnologyで実装するのか。

**整理:** Human UserはOIDC等で入口でAuthenticationする。Agent／Serviceは別のWorkload
IdentityでAuthenticationする。DownstreamではOAuth Token Exchange／On-Behalf-Of、
Server-sideのTrusted Request Context等により、UserとAgentの両方を保持してAuthorization
する。Chunk LabelはそのDecisionの入力であり、Authenticationの代わりではない。

### 問い6: Vector DB検索時に毎回認可するのか

**学習者の疑問:** Vector DB検索時に都度認可する理解でよいか。複数の方式がありそう。

**整理:** Requestごと、および新しいProtected Dataを追加・実体化できるBoundaryごとに、
現在のUser scopeが強制される必要がある。ただし一件ごとにRemote PDPを呼ぶことは必須で
ない。Query-time filter、Hard partition、External PDP constraint、Source-side check、
Hybridから、保証とTrade-offを明示して選ぶ。

## 15. このセッションから得られた洞察

### 具体から抽象へ進む

初心者にいきなり「Pipeline全段でEnd-user Authorization Contextを維持する」と説明しても、
どのDataがどこで越境するか見えない。Alice、Bob、Document A／B、Parent Expansion、Cache
のように、ActorとDataを固定して一つのFlowを追うことで、初めてFailureが観察できる。

その後に次の抽象化を行う。

> 各Data-bearing Stageの出力は、現在のEnd Userに許可されたDataだけで構成する。

この順序なら、同じ原則をVector Search、SQL、Graph Retrieval、MCP Resource、Agent Tool、
Cache、Memory等へ応用できる。

### Technology導入よりBoundaryの一貫性が難しい

Metadata filter、PDP、Token Exchange等の個別技術は理解しやすい。一方、Systemが複雑に
なると、Identity translation、Parent Expansion、Secondary Retriever、Cache、Fallback、
Asynchronous Job等のどこかでUser Contextを落としやすい。

Security上の設計目標は、製品数を増やすことではない。Data-bearing Stageを減らし、
Identityの意味を変換する箇所を減らし、異なるACLを持つDataを同じExpansion unitへ混在
させず、Enforcement Pointを説明できる構成にすることである。

### 学習上の改善

- 初見の用語は、その場で正式名称、平易な意味、Scenario内の役割を説明する。
- 記号は自然言語の代替にせず、自然言語を補助するためだけに使う。
- 一つの具体例を最後まで追ってからSecurity Invariantへ抽象化する。
- Pass／Failだけでなく、「どのBoundaryで何が実体化されたからか」を言語化する。

## 16. 設計レビュー項目

- End UserとAgent／ServiceのIdentityを区別しているか。
- 誰のAuthorityを、どのActorが、どのDownstream Resourceに対して使うか説明できるか。
- User ContextはPromptやModel outputではなくTrusted channelから得ているか。
- Delegated TokenまたはRequest ContextはAudience、Scope、Tenant、有効期限へBindingされるか。
- Original User Tokenを対象外Serviceへ無制御にPassthroughしていないか。
- Model ContextやLogへToken、Session、Credentialを入れていないか。
- Authoritative ACL、Group、Tenant、ClassificationのSourceはどこか。
- Vector化時のChunk metadataはAuthoritative sourceから作られ、改ざんを防げるか。
- ACLが異なるSectionを同じParentへまとめ、無条件にExpansionしていないか。
- ACL変更、Group剥奪、Tenant移動がIndexとCacheへいつ反映されるか。
- Vector queryのFilterはTrusted Contextから作られるか。
- Query-time filter、Hard partition、PDP constraint、Source checkの責任分界が明確か。
- Unauthorized本文またはSensitive metadataが認可前にMaterializeされないか。
- Reranker等、Candidateを増やせないStageをArchitectureで示せるか。
- Parent Expansion、Attachment、Secondary Retriever、Citation、Cache、Retry、Fallbackを
  網羅したか。
- Authorization dependencyの障害時にUnfiltered queryへFallbackしないか。
- Cache keyへ含めないContextがDecisionを変えないと説明できるか。またはHit時に再認可
  するか。
- Cross-user、Cross-group、Cross-tenant、Revocation、Cache hit、Parent ExpansionのNegative
  testがあるか。
- Testが最終回答だけでなく、安全なTest環境でIntermediate dataを確認するか。
