# C5.3.1 Shared Model Serving Tenant Isolation 学習ノート

## 1. Requirement原文と文書の役割

- Versioned ID: `v1.0-C5.3.1`
- AISVS Verification Level: `2`
- 対象Source: AISVS v1.0。以下のReferencesに固定Revisionを示す。

> Verify that shared model serving infrastructure prevents one tenant's fine-tuning,
> inference, or embedding operations from influencing or observing another tenant's operations.

日本語訳:

> 共有Model Serving基盤が、あるTenantの追加学習、推論、Embedding生成の処理を通じて、
> 別Tenantの処理へ影響を与えたり、その処理を観測したりできないようにしていることを検証する。

本ノートは講義・質疑・訂正・洞察を後から参照する学習資料である。
原文の要求（Normative）、Researchの補足、Repositoryの解釈、対話由来の洞察を区別する。
実装済みSystemの適合証跡ではない。
既存の[Control本文](../../../control-records/c05-access-control-and-identity/v1.0-c5.3.1-shared-model-serving-tenant-isolation.md)
は別Artifactであり、この学習によってControl成熟度やMappingを変更しない。

## 2. C5における位置づけ

C5.3.1が守るのは、共有Model ServingにおけるTenant間の機密性と完全性である。
機密性は他者の情報を知れないこと、完全性は他者の処理や状態を不正に変えられないことを指す。

| Requirement | 主に確認する境界 |
|---|---|
| C5.2.2 | 検索・組立時に、利用者の権限を超えた文書を取り込まないか |
| C5.2.4 | 推論後、受取人に未認可の情報を返さないか |
| C5.3.1 | 共有Model Servingの状態や処理がTenant間で混ざらないか |
| C5.3.2 | 共有Computeを通じて他Tenantの処理を観測・干渉できないか |

この表はRepositoryのScope整理であり、AISVSがすべての境界を厳密に定義しているわけではない。
同じ情報漏えいに複数のRequirementが関連する場合は、原因と破れた保証をそれぞれ説明する。

## 3. 具体例：専用GPUでも結果が漏れる

Company AとCompany B向けに、非同期のModel推論サービスを提供する。
非同期とは、Request受付時にJob IDを返し、計算終了後に別Requestで結果を取得する方式である。

```text
Company A -> A専用GPU -> Job Aの推論結果 ─┐
                                       ├-> 共通Result Store
Company B -> B専用GPU -> Job Bの推論結果 ─┘
```

Aが自分の認証情報でBのJob IDを指定すると、Result APIは「そのIDが存在する」だけを確認し、
Bの結果を返してしまった。GPUは分かれていても、Serving結果の受け渡しでTenant境界が破れた。

修正すべき判断は次である。

```text
検証済みIdentityから確定した呼出元Tenant: A
サーバーが管理するJobの所有Tenant:      B
-> 不一致なので結果取得を拒否
```

Job IDが推測困難でも認可は必要である。URLやRequest BodyのTenant名を信頼するだけでは足りない。
結果を読み出す前に、信頼できる呼出元情報と保存された所有情報を照合する。

## 4. 用語と対象となるModel

- **Tenant:** 相互に情報・操作権限を分離する単位。会社、Workspace、Project等が該当し得る。
  組織図の部門を自動的にTenantとせず、製品が保証するSecurity Boundaryを明示する。
- **Model Serving:** 学習済みModelを読み込み、Requestを受け、推論結果を提供する基盤。
  Worker、Cache、Model選択、結果取得等を含む。ここでのWorkerは処理を実行するプロセス等を指す。
- **Inference（推論）:** 入力をModelで処理して出力すること。通常の推論だけでModel Weightが
  更新されるわけではない。WeightはModelの学習結果を保持するParameter群である。
- **Fine-tuning（追加学習）:** 既存Modelを追加Dataで調整すること。
- **Adapter:** 追加学習等で得た調整用Parameter。共通Base Modelへ組み合わせ、挙動を変える。
- **Embedding:** TextやImage等を数値Vectorへ変換すること、またはその結果。
- **KV Cache:** LLMが既に処理したTokenのAttention計算に使う中間値を保持する仕組み。
  Tokenは文章等をModelが処理する単位。Prefix Cacheは同じ冒頭部分の計算を再利用する仕組みである。
- **Response Cache:** 生成済みの回答を保存し再利用する仕組み。KV Cacheとは保存対象が違う。
- **Binding:** Requestや結果を、信頼できるTenant情報と切り離せない形で関連付けること。
- **Enforcement Point／PEP:** 認可判断を実際の読出し・実行・返却に強制する場所。

ModelはLLMに限定されない。Embedding Modelや画像を扱うModel等も、対象の共有処理を行うなら
検討する。外部クラウドサービスだけでなく、自社運用の共有推論基盤も対象になり得る。

## 5. 一般的なLLM API利用システムではどこか

学習者はTenant分離の原則を理解できた一方、GPUやAdapter中心の説明では、自分が扱う一般的な
Applicationのどこへ当てはまるかが曖昧だった。外部LLM APIを使う文書要約サービスへ置き換える。

```text
Company A / Company B
  -> 自社Application
       Login・Tenant確定
       文書検索・Prompt組立
       LLM呼出し・Job管理
       回答Cache・結果保存
  -> 外部LLM Provider
       Model実行・内部Cache・Worker・GPU
```

| 場所 | 具体的な確認 | Scope上の注意 |
|---|---|---|
| 自社の検索処理 | Aの権限でBの文書を取得しない | 主にC5.2.2。Model Serving分離の不備とは限らない |
| 自社の会話履歴 | Aの履歴をBのPromptへ付けない | 一般的なSession・Memory認可も関係する |
| 自社の共有推論Gateway | TenantとRequest、Model選択、Job、結果の対応を維持する | 共有Servingを構成する場合にC5.3.1の解釈を適用する |
| 自社の回答Cache | Aの保護情報を含む回答をBへ再利用しない | Serving結果の共有か、一般Application Cacheかを確認する |
| Provider内部 | Tenant間で推論状態、Adapter、内部Cache等を混ぜない | Providerが実装・運用し、利用者は保証範囲を確認する |

Applicationの会話履歴や保存Dataをすべて自動的にC5.3.1へ分類してはならない。
対象が共有Model Servingの状態・処理を構成していることを確認する。この対応表は教育用の
Architectureへの当てはめであり、Repositoryの正式なPattern Mappingではない。

例えばAの契約書を含む会話履歴をBのRequestへ付ければ、Providerは渡された入力を正しく処理
しただけでも漏えいする。ProviderのTenant分離保証は、自社Application内の利用者分離を代行しない。
Providerからは両社が同じAPI Accountに見える構成もあるため、双方のTenant単位を確認する。

## 6. Threat ModelとTrust Boundary

攻撃者は正規のTenant Aとして認証でき、自分のPrompt、Job指定、Adapter選択等を操作できると
仮定する。認証済みであることは、他Tenantの状態を触ってよい理由にはならない。

- AがBのJob IDを指定し、Bの結果を読む。
- AがBのAdapterを選択・置換し、BのModelの挙動を変える。
- Aの処理後に残った状態を、Worker再利用時にBが受け取る。
- 共有CacheやMetricsから、保護された他Tenantの内容・活動を推測する。
- Tenantが入力できるArtifactや不正形式のDataからServingプロセスが侵害され、分離が崩れる。

守る境界は、呼出元からGateway、GatewayからRouter・Worker、Workerから共有Store・Cache、
結果取得APIから呼出元、Workerの再利用前後である。RouterはRequestを適切なModelやWorkerへ
振り分けるComponentを指す。

ResearchはCacheの分離に加え、Adapter読込み、共有Cache保存先、通常API以外の内部・管理経路を
検討している。製品固有の設定や修正Versionを、全System共通の要件としてコピーしない。

## 7. Security Invariantと強制地点

Repositoryの解釈として、次を設計の軸にする。

> Tenant由来の処理・状態・成果物は、その所有Tenantとの対応を維持し、別Tenantが未認可で
> 読む、再利用する、変更する、または保護された活動を推測することを許さない。

| 強制地点 | 実際に行うこと |
|---|---|
| Gateway | 認証と所属確認からTenantを確定し、Callerの自己申告で上書きさせない |
| Model／Adapter選択 | RequestのTenantが対象ModelやAdapterを使用できるか確認する |
| Cache読出し | 内容・Model Version・Adapter等に加え、必要なTenant分離を維持する |
| Job／Result API | 読出し、取消し、削除、再試行でJob所有者を照合する |
| Worker再利用 | 前TenantのAdapter・Session状態等が次のRequestへ適用されないようにする |
| Log／Metrics公開 | 他TenantのPrompt、結果、保護された識別情報・活動を露出しない |

Tenant Contextが不明な場合は処理を拒否し、直前TenantやGlobalな状態へFallbackしない。
ここでFallbackとは、通常処理に失敗した場合の代替経路である。

共有された変更不能なBase Model自体は直ちにFailではない。Tenant固有の可変状態を分離できるかが
重要である。共有GPUだけでFailとせず、専用GPUだけでPassにもしない。

## 8. Cacheの講義例の補正

初回講義では、同じPrompt PrefixからAの秘密の状態がBへ再利用されるように説明したが、条件を
省略しすぎていた。同じ「要約して」という冒頭だけで、別の契約書に対応するKV状態まで正しく
一致するわけではない。正しく実装されたPrefix Cacheは一致する入力部分の計算を再利用する。

次の二つを区別する。

- **誤った結果の再利用:** 回答CacheのKeyが「質問文だけ」で、Tenantや対象文書を区別しない。
  AとBが同じ質問をすると、Aの文書に基づく回答がBへ返る。これは具体的な漏えい例である。
- **Cacheの存在を推測する観測経路:** 他Tenantが処理した入力候補を攻撃者が試し、Hit／Missに
  よる応答時間の違いから、その候補が処理済みか推測する。前提知識、測定可能性、他の負荷等の
  条件を確認する。Cache共有だけで情報復元が必ず成功すると主張しない。

前者は回答の混入、後者は挙動から秘密を推測するSide Channelの一例である。Researchが参照する
PROMPTPEEKは後者の理解に使う。性能最適化のための共有も、保護された内容や活動を露出するなら
Security Boundaryとして評価する。

## 9. Pass／Failと隣接保証

| 状況 | 学習上の判断 |
|---|---|
| 変更不能なBase Modelを共有し、Tenant固有状態と全処理経路を分離する | C5.3.1はPassし得る |
| GPUは専用だが、AがBの推論結果を取得できる | C5.3.1はFail |
| AのAdapterを適用したままBを処理する | 漏えい未確認でもC5.3.1はFail。処理への影響がある |
| Serving状態は分離済みだがHardware Side Channelは未評価 | C5.3.1のPassだけでC5.3.2をPassにはできない |
| RAG検索で未認可文書を取得したがServing状態は分離されている | 主にC5.2.2等を評価。自動的にC5.3.1のFailへまとめない |

C5.3.1とC5.3.2の境界は、RepositoryではServing層の状態・観測経路と、共有Computeに由来する
低レベルの観測・干渉を区別している。両者が重なる場合は、原因と保証範囲を記録する。
共有サービスで通常発生する許容範囲内の遅延変動を、すべて分離違反とは扱わない。

C5.3.1のPassは、認証基盤の正しさ、検索認可、Providerの学習利用方針、全脆弱性の不存在、
Hardware分離を保証しない。未評価はFailの証明でもPassの証明でもない。

## 10. 適用範囲と責任分界

複数のSecurity DomainがServing Componentや状態を共有する場合に適用を検討する。
専用FrontendやGPUの奥でCache、Queue、管理経路が共有されていれば、評価は必要である。
Servingの状態・処理がすべて単一Tenant専用ならC5.3.1は対象外になり得るが、物理Computeを
共有する場合はC5.3.2を別途検討する。

外部LLM APIの利用者は、Providerの分離設計、契約、監査資料等で確認できる保証範囲を記録する。
「クラウドだから安全」とはせず、自社側の分離とProvider側の分離を区別する。
Provider内部を直接テストできない場合、確認不能な部分を明示し、提供保証への依存として扱う。

学習者の「C5.3.2はクラウド事業者寄りでHardwareに近い」という理解はおおむね適切である。
社内の計算基盤運用者も対象になる。原文はHardware Partitioning、Confidential Computing、
専用Computeを代表例として挙げるが、技術を導入しただけでPassになるわけではない。
詳細はC5.3.2の学習で扱う。

Levelについて、C5.3.1は2、C5.3.2は3である。実装・検証の難しさや適用の状況依存性という
Level定義と整合するが、「Hardwareに近いから3」という個別理由が公式に示されたとは扱わない。

## 11. 質疑の再構成

### 問い1：論理分離は成立し、GPUだけ共有する

提示条件は、Base ModelをTenantが変更できず、Adapter、KV Cache、Job、Resultを分離し、
Worker再利用時に状態をClearする一方、Hardware Side Channelは未評価というものだった。

**学習者:** C5.3.1はPass。C5.3.2はPassとはいえない。

**整理:** 正しい。提示された分離範囲のPassと、未検証の共有Compute保証を区別できている。
実製品の適合判断には、記載条件が実際に成立しているEvidenceが必要である。

### 問い2：専用GPUだが他社のResultを取得できる

**学習者:** Fail。認証情報の然るべき値と、アクセス先のEndpointまたはResourceを検証すべき。

**整理:** 認証済みの呼出元Tenantと、サーバーが管理する結果の所有Tenantを読出し前に照合する。
Endpointの名前やIDの存在確認だけでは足りない。計算の分離と結果の受け渡しの分離は両方必要。

### 問い3：AのAdapterを適用したままBを処理する

**学習者:** Fail。

**整理:** 正しい。Promptや保存済み結果の直接漏えいがなくても、Aの追加学習が未認可でBの処理へ
影響している。実行前のAdapter所有・選択確認と、Worker切替時の状態管理が必要である。

### 所感：原則は理解したが一般的なLLM Applicationでの場所が曖昧

**学習者:** ModelはLLMだけか。クラウド共有Modelの話か。一般的なLLMサービス利用Systemでは
どこへ対応するのか。

**整理:** ModelはLLMに限らず、クラウドだけでもない。自社Applicationと外部Providerの構成を
描き、共有推論の入口、状態、結果の管理を具体化した。

**講義側の訂正:** 一般Applicationの会話履歴・結果保存をすべてC5.3.1へ含めたように読める
説明は広すぎた。共有Model Servingを構成するかを確認し、一般認可やMemory管理との境界を示す。

### 所感：他のControlsと重なりそう

**学習者:** 他のControlsやRequirementsと重複するところがありそう。AISVSの進化に期待する。

**整理:** 同じ漏えいでも、検索、出力、共有Serving状態のどこで起きたかにより保証が異なる。
複数の要件が関係することを許容し、曖昧なScopeを確定済みの上流分類として扱わない。

### 関連する洞察：Negative Testと脆弱性診断

**学習者:** Negative Testは脆弱性診断のチェックリストと同等に見える。

**整理:** 関係は深いが粒度が異なる。「Tenant分離を確認する」という項目を、Aの認証でBの
Jobを取得する操作と、結果・保護Metadataを返さないという期待結果まで具体化するとNegative
Testになる。不正な操作に加え、Tenant情報欠落、障害、Worker再利用も検証できる。
今回列挙したTestは学習上の設計であり、実行済みの脆弱性診断結果ではない。

## 12. 検証例とEvidence

正例ではAのJob結果をAが取得でき、BのRequestにはBのAdapterが適用されることを確認する。
拒否だけを確かめ、正常な処理まで壊していないかを見落とさない。

| Negative Test | 期待結果 |
|---|---|
| Aの認証でBのJob IDを指定し、取得・取消し・削除を要求 | 拒否し、Bの内容・保護Metadata・状態を変化させない |
| Request BodyのTenantをBへ変更 | 検証済みTenant Aを上書きできない |
| AからBのAdapterを選択・置換 | 拒否し、Bの設定・Model挙動を変えない |
| A処理後に同じWorkerでBを実行 | AのAdapter・会話状態・結果がBへ持ち越されない |
| 同じ質問と異なるTenant固有文書を使う | Aの回答CacheをBへ返さない |
| Tenant情報を欠落させ、再試行やFallbackを実行 | Global状態や直前Tenantへ切り替わらず拒否する |
| Tenant削除後にCacheを復元し、別Tenantから参照 | 削除済みTenantの状態を再公開しない |

Evidenceには、構成とData Flow、Tenantの確定方法、所有情報、認可設定、Cacheの分離方式、
正例・負例の結果、対象Buildと設定を使う。Provider側は資料で確認した範囲と未確認事項を残す。

## 13. 持ち帰る洞察と設計レビュー項目

> Tenant分離は、入口の認証から結果の返却、Workerの再利用まで続く保証である。

- 「何を共有するか」と「その共有を通じて何ができるか」を分けて確認する。
- 保護対象は情報だけでなく、Modelの挙動や実行状態も含む。
- 自社とProviderでTenantの意味が一致するか、境界と責任を図にする。
- Request、Model／Adapter、Cache、Job、結果の持ち主をどこで確定・照合するか確認する。
- 通常処理に加え、失敗、再試行、復元、削除、Worker切替を追う。
- C5.2.2、C5.2.4、C5.3.1、C5.3.2のどの保証を評価したかを説明する。
- 「分離されている」という主張を、操作と期待結果を持つTestへ翻訳する。
