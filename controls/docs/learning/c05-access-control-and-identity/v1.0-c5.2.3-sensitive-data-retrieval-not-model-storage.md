# C5.2.3 Sensitive Data RetrievalとModel Storage 学習ノート

## この文書について

この文書は、AISVS `v1.0-C5.2.3`を題材に行った学習セッションを、後から単独で
参照できる講義として再構成したものである。

これはControl本文、製品の適合判定、またはAISVS原文の代替ではない。次を分離する。

- **Normative:** AISVS v1.0が実際に要求していること。
- **Research:** AISVS Researchが示す脅威、検証方法、実装上の注意。
- **Repository interpretation:** 現場のArchitecture Reviewへ適用するための解釈。
- **Derived insight:** 具体例と質疑から得た、Requirement外を含むSecurity上の洞察。

学習の完了によってControl maturityは変更しない。
別途整備した[Control本文](../../../control-records/c05-access-control-and-identity/v1.0-c5.2.3-sensitive-data-retrieval-not-model-storage.md)
では、適用範囲、検証、Evidenceと保証の限界を整理している。

## 1. Normative Requirement

- Versioned ID: `v1.0-C5.2.3`
- AISVS Verification Level: `2`

> Verify that sensitive data is retrieved via retrieval pipelines (e.g., RAG
> queries, embedding lookups) to prevent permanent storage in models.

意味を崩さない日本語訳:

> Sensitive DataがModelへ恒久的に保存されることを防ぐため、そのDataをRetrieval
> Pipeline（RAG QueryやEmbedding Lookup等）から取得していることを検証する。

原文が直接求めているのは、Sensitive DataをTrainingやFine-tuningによってModelへ固定
するのではなく、必要なRequestのときに管理可能な外部Sourceから取得するArchitectureで
ある。特定のVector DB、RAG製品、DLP製品を要求しているわけではない。

ModelがSensitive DataをTaskに必要としないなら、Retrievalする必要もない。最小化して
渡さないことが第一選択である。

## 2. C5における位置づけ

C5.2.2とC5.2.3は、どちらもRetrievalを扱うが、守るPropertyが異なる。

```text
C5.2.2:
  現在のUserは、どのDataを取得してよいか

C5.2.3:
  Sensitive DataをModel Artifactへ固定せず、必要時に取得するか
```

C5.2.2へPassしていても、許可されたUserのSensitive DataをFine-tuningへ投入すれば
C5.2.3はFailする。逆に、Sensitive DataをRAGで扱っていても、End-user Authorizationを
失えばC5.2.2はFailする。

C5.2.7は、Sensitive Dataから作られたChunk、Embedding、Cache等へClassification Labelを
伝播するPropertyを扱う。C5.2.3は、どのDataをModel Trainingから排除するかというStorage
Architectureを扱う。

## 3. 最初に一つの具体Scenarioを見る

社員向けHR Assistantが次のDataを扱う。

```text
社員情報
  - 氏名
  - 給与
  - 健康情報
  - 人事評価
  - 相談履歴
```

### Failure-proneな構成

```text
社員情報
  -> Fine-tuning Dataset
  -> HR専用Model／LoRA Adapter
  -> 社員からの質問へ回答
```

Bobの相談記録を元Databaseから削除しても、学習済みModelからBob由来の情報だけを特定し、
確実に削除することは難しい。情報は一行のRecordではなく、多数のParameterへ分散して
反映され得る。Model、Adapter、Checkpoint、BackupへCopyされれば、さらにLifecycle管理が
難しくなる。

HR担当者だけがModel Endpointを呼び出せるようにしても、Record単位の削除、訂正、
Retentionを回復したことにはならない。

### 推奨される構成

```text
Alice
  -> HR Assistant
  -> AliceのAuthentication／Authorization
  -> HR APIから必要なFieldだけRetrieval
  -> 一時的なModel Context
  -> AliceへのResponse
```

Sensitive DataはAuthoritative HR Systemに残す。Requestごとに必要なFieldだけを取得すれば、
Source側でAccess Control、訂正、削除、Retention、Purpose limitationを適用できる。

ただし、Prompt、Response、Log、Cache、Trace、Feedbackへ不要なCopyを残さず、後のTraining
Datasetへ戻さないことが必要である。

## 4. Sensitive DataのOperational definition

### AISVSが定める範囲

C5.2 Researchは、ASVSのData Classificationを前提として、Sensitive Dataを識別しProtection
Levelへ分類する必要性を示す。しかしC5.2.3は、すべての組織に共通するSensitive Dataの
完全な一覧やClassification taxonomyを定義していない。

したがって、次はRepository interpretationとして用いる実務上の定義である。

> Sensitive Dataとは、漏えい、改ざん、目的外利用、必要期間を超えた保持、または
> 削除不能によって、Security、Privacy、法令、契約、または事業上の重大な影響が生じる
> Dataである。

代表例には次がある。

- 個人情報、健康情報、給与、人事評価、相談履歴。
- Credential、API Key、Token、秘密鍵。
- 顧客Data、Tenant固有Data。
- 営業秘密、未公開戦略、Source Code。
- Security設定、脆弱性情報、Incident情報。
- 契約やLicenseにより利用範囲が制限されたData。
- 法定Retention、訂正、削除、Consent、Purpose limitationの対象となるData。

情報のSensitivityは文字列だけで決まらない。単独では一般的な氏名でも、病歴、給与、
行動履歴等と結合すればSensitivityが変わる。Derived Dataが元のSensitiveな事実を保持、
推測、再識別できる場合は、元Dataと同等以上の保護が必要になり得る。

### Classification、Authorization、Model-use Policyを分ける

| 軸 | 判断する問い | 例 |
|---|---|---|
| Data Classification | 漏えい、残存、悪用された場合のImpactは何か | Public、Internal、Confidential、Restricted |
| Authorization | 誰が、どの条件で、このDataを利用できるか | 本人、HR Role、Tenant A、担当Project |
| Model-use Policy | TrainingやFine-tuningへ使用してよいか | Allowed、Prohibited、Consent required |

C5.2.3が直接扱うのは、主にData ClassificationとModel-use Policyである。Authorizationは
C5.2.2等が扱う別軸だが、Modelへ固定するとPrincipalごとのPolicyを維持できないため、
C5.2.3の重要な理由になる。

### Access-controlled DataとSensitive Dataは同義ではない

有料会員だけが読める一般記事はAccess Controlの対象だが、必ずしも機密ではない。
一方、全社員が読める未公開の買収計画は、社員間の細かいRole差がなくてもSensitiveで
あり得る。

```text
有料記事:
  Classification = Public相当の場合がある
  Authorization  = Paid member only

未公開買収計画:
  Classification = Restricted
  Authorization  = All employeesの場合もある
```

前者のTraining可否はLicenseや契約を含めて別途判断する。後者はAudienceが比較的広くても、
Modelへ固定してよいとは限らない。

### 判定に使う質問

1. 漏えい、改ざん、目的外利用による重大なImpactがあるか。
2. Record単位の削除、訂正、Retention、Consent管理が必要か。
3. User、Role、Tenant、Purpose、時点ごとに権限が変わるか。
4. Trainingへ入れた後も、それらの義務を継続して守れるか。
5. Model、Adapter、Checkpoint、Backupから対象Dataを除去できるか。

4または5を保証できず、1から3のいずれかが重要なら、C5.2.3では原則としてModelへ学習
させずRetrievalで扱うDataである。

## 5. 用語

### Model Weight

ModelがTrainingによって獲得したParameter。DatabaseのRowとは異なり、特定人物の事実が
どのParameterに保持されたかを一意に対応付けられない。

### Fine-tuning

既存Modelへ追加Dataを学習させ、特定DomainやTaskへ適応させること。Full fine-tuningだけ
でなく、Sensitive Data由来の情報を保持し得る追加Artifactも確認する。

### LoRA／Adapter

Base Model全体を更新せず、一部の追加Parameterを学習する効率的な適応方法。Base Modelを
変更していなくても、Adapterは永続的なModel Artifactであり、Sensitive Dataを学習させる
問題は残る。

### Retrieval

Inference時に外部Data Sourceから必要なDataを取得すること。Vector Searchだけでなく、
SQL、Keyword Search、Graph Database、Document API、Tool等を含み得る。

### Permanent storage in models

主にModel Weight、Fine-tuned Model、Adapter、Checkpoint等の、Training結果として残る
Model Artifactを指す。Promptへ一時的に渡すこととは区別される。

ただし、PromptがProvider Log、Response Cache、Trace、Feedback Datasetへ保存され、後から
Trainingへ使われれば、Sensitive DataがModelへ固定される経路になる。

### Data lineage

Dataがどこから来て、どのTransformationを受け、Dataset、Model、Adapter、Log等のどこへ
移動したかを追跡できる関係。Sensitive DataがTrainingへ入っていないことを確認するには、
最終DatasetだけでなくLineageが必要になる。

### De-identification

直接識別子を削除または変換し、個人との結び付きを弱める処理。メールアドレスをMaskした
だけで、給与、病歴、珍しい役職、時系列等から再識別できるなら、Sensitiveではなくなった
とは言えない。

## 6. Threat ModelとAbuse Path

### Model memorizationとExtraction

```text
Sensitive RecordをTraining
  -> Model Artifactへ反映
  -> Model Endpointを利用できるAttackerが繰り返しQuery
  -> 記憶された文字列、属性、存在情報を抽出
```

Researchは、Model inversionやMembership inferenceもThreatとして挙げる。Membership
inferenceは、特定RecordがTraining Dataに含まれていたかを推測するAttackである。Model
inversionは、Modelの挙動からTraining Dataの特徴や属性を再構成しようとするAttackである。

### Lifecycle controlの喪失

```text
Source Recordを訂正／削除
  -> Model／Adapter／Checkpointはそのまま
  -> 古い情報が引き続き出力される可能性
```

元Sourceを正しく管理しても、Model Artifactへ固定されたCopyには自動的に反映されない。

### Feedback Loop経由の再混入

```text
RAGでSensitive Dataを取得
  -> Prompt／Responseを品質改善用に保存
  -> 高評価会話を自動収集
  -> 次回Fine-tuning Datasetへ追加
  -> Sensitive DataがModelへ固定
```

最初のTraining Datasetだけを確認しても、この循環経路があれば不十分である。

### 不十分なMasking

```text
メールアドレスと電話番号だけMask
  -> 給与、病歴、社内Project、相談内容は残る
  -> Contextから個人を再識別
  -> Fine-tuningへ混入
```

形式的なPII detectorの通過と、Data Classificationの解除は同じではない。

## 7. Security InvariantとEnforcement Point

### Security Invariant

> Sensitive Dataを、Model Weight、Fine-tuning Artifact、Adapter、Checkpoint等を更新する
> Training Dataへ含めてはならない。

Sensitive DataがTaskに必要なら、次も守る。

> 現在のRequestで必要かつ認可された範囲だけを、管理可能なSourceからRetrievalする。

### Training-use default

実務上は、DataごとにTraining利用可否を明示する。

```text
training_use = explicitly_allowed
  -> Training候補にできる

training_use = prohibited または unknown
  -> Trainingを拒否する
```

これはAISVS原文の具体的なLabel schemaではなく、Repositoryが推奨するFail-closedな実装
原則である。

### 主なEnforcement Point

```text
Data Classification
  -> Dataset ingestion gate
  -> Training／Fine-tuning Job admission
  -> Model／Adapter／Checkpoint Registry
  -> Inference Retrieval
  -> Prompt／Log／Cache／Trace
  -> Feedback／Evaluation／Retraining
```

- Dataset builderは、Classification、Provenance、Training-use Policyを検証する。
- Training／Fine-tuning APIは、Dataset builderを迂回したJobも拒否する。
- Model Registryは、ArtifactのTraining lineageとClassificationを保持する。
- ProviderのData-use設定と契約により、PromptをProvider Trainingへ使わせない。
- Feedback Pipelineは、会話を自動的にTraining Datasetへ昇格させない。
- Unknown classificationや欠落したLineageをAllowへ倒さない。

複数のEnforcement Pointを置く理由は、同じPolicyを重複実装するためではない。Dataset作成、
直接Fine-tuning API、Provider側Training等の異なる入口を閉じるためである。

## 8. Pass／FailとScope Calibration

| Observation | C5.2.3 | 理由または別のProperty |
|---|---|---|
| Sensitiveな社員RecordをFine-tuningへ投入した | Fail | Model Artifactへ固定され得る |
| Sensitive DataをLoRA Adapterだけへ学習した | Fail | Adapterも永続的なModel Artifactである |
| `training_use=prohibited` Policyはあるが、Fine-tuning Jobを実行できる | Fail | Policyの存在ではなく実際のEnforcementを評価する |
| Sensitive Dataを外部HR APIからRequest時に取得し、Trainingへ使用しない | Pass候補 | Authorization、Log、Cache等の別Propertyも確認する |
| Sensitive ChunkとEmbeddingをVector DBへ保存し、Trainingへ使用しない | Pass候補 | Model Weightではないが、Vector DB自体の認可、暗号化、Retention、削除が必要 |
| RAG PromptをFeedback経由でFine-tuning Datasetへ自動投入する | Fail | Indirect pathからModelへ固定される |
| Promptを30日Logへ保持するが、契約・設定上Trainingへ使用しない | C5.2.3単独では直ちにFailとは限らない | Retention、Log Security、Privacy上の別Gapは残る |
| Access-controlledだが非Sensitiveな有料記事を学習する | ApplicabilityとLicense次第 | Access ControlとSensitivityは同義ではない |
| Sensitive Dataから十分に安全なSynthetic Dataを作り、原DataをTrainingへ入れない | Pass候補 | Transformation、再識別Risk、LineageのEvidenceが必要 |
| Retrievalを停止してもProtected SourceだけのCanaryをModelが再現する | Failの強いEvidence | Modelまたは別の永続経路へ混入した可能性が高い |

Policy document、DLP scanner、RAG componentが存在するだけではPassしない。実際に
Sensitive DataがどのTraining pathにも入らず、必要時だけRetrievalされるOutcomeを確認する。

## 9. VerificationとNegative Test

### Architecture／Data review

1. Sensitive DataのClassification sourceとOwnerを確認する。
2. Training、Fine-tuning、Adapter、Evaluation、Feedback、Provider Data-useの全経路を描く。
3. Dataset Manifest、Snapshot、Feature Store、Model Card、Artifact lineageを調べる。
4. UnknownまたはProhibited Dataを拒否するEnforcement Pointを確認する。
5. Retrieval後のPrompt、Log、Cache、TraceがTrainingへ戻る経路を確認する。
6. Source削除と権限剥奪がVector Chunk、Cache、Backupへ伝播するWindowを確認する。

### Canary test

Protected Sourceにだけ存在する、通常は偶然出現しないSynthetic Canaryを置く。

```text
employee_test_record = "ORANGE-COMET-7391"
```

期待する結果は次である。

1. 許可されたUserはRetrieval経由でCanaryを取得できる。
2. 未許可Userは取得できない。
3. Retrievalを無効にするとModelはCanaryを再現できない。
4. Sourceから削除しIndexとCacheを無効化すると取得できない。
5. Training Dataset、Adapter、Checkpoint、Feedback DatasetにCanaryが存在しない。

このTestだけで、ModelがSensitive Dataを絶対に記憶していないことを数学的に証明は
できない。Data lineage、Manifest、Job admission log、Provider設定と組み合わせてEvidenceに
する。CanaryはSynthetic Dataを使い、ProductionのSensitive DataをTestへ流用しない。

### Negative test

- `training_use=prohibited`またはMissingのRecordをDatasetへ投入し、拒否されること。
- Dataset builderを迂回してFine-tuning APIへ直接渡し、拒否されること。
- RAG ResponseをFeedbackへ高評価登録し、Training Datasetへ自動昇格しないこと。
- 直接識別子だけをMaskした再識別可能なRecordが、Non-sensitiveとして承認されないこと。
- ProviderのTraining opt-outを無効化した構成が、Production admissionで拒否されること。
- Source削除後にVector Index、Cache、Feedback、Artifact inventoryへ残るCopyを検出できること。

## 10. RAGでもDataは自動的にTransientにならない

RAGはSensitive DataをModel Weightから外へ置く。しかし、Dataが消えるわけではない。

```text
Source Document
  -> Chunk
  -> Embedding／Vector metadata
  -> Prompt
  -> Response
  -> Cache
  -> Log／Trace
  -> Feedback
```

これらはそれぞれData Assetである。Classification、Access Control、Encryption、Retention、
Deletion、Auditを別途適用する。

> Modelに保存しないことと、どこにも保存しないことは同じではない。

C5.2.3にPassしても、Vector DBやLogからSensitive Dataが漏えいすればSystem全体は安全で
ない。C5.2.3はData Lifecycle全体の代替Controlではなく、Model ArtifactへのPermanent
Storageを避けるAI固有のPropertyである。

## 11. AISVS Level 2の意味と異論

AISVSは、C5.2.3をLevel 2とした個別の理由をNormative chapterまたはC5.2 Researchで
説明していない。以下はAISVSの一般的なLevel定義とRequirementの性質からのRepository
上の推論である。

AISVS v1.0では、Level 1を基礎的かつ重要なRequirement、Level 2をより複雑なLogic、特定の
Attack前提、Layered defense等を含むRequirementとして位置付ける。Typical useでは、
Level 2をSensitive Business Data、Regulated Data、Adversarial contextを扱うAI Application
へ対応付けている。

C5.2.3がLevel 2である理由として、次が考えられる。

1. Sensitive DataをTrainingまたはFine-tuningへ使うSystemという適用前提がある。
2. Data Classificationと一般的なData Governanceが先に必要になる。
3. Dataset、Feedback、Provider、Adapter、Checkpoint等の全Lineageを検証する必要がある。
4. 「RAGを使う」という実装より、Modelへ混入していないことのEvidence作成が難しい。
5. AISVSのLevel 2のTypical useと、RequirementのSensitive Data scopeが一致する。

一方、製品SecurityのBaselineとしてはLevel 1相当に前倒しする合理性がある。

- Customer PromptやFeedbackがTrainingへ混入するRiskは広く存在する。
- Modelへ固定された後の削除は難しい。
- 最初から`unknown`と`prohibited`をTraining拒否にする方が修復より容易である。
- Secure-by-defaultなDataset admissionとして実装できる。

したがって、このRepositoryではUpstream metadataとして`verification_level: 2`を保持する。
同時に、実運用ではSensitiveまたはClassification不明のDataをDefaultでTrainingから除外する
ことをBaselineとして推奨できる。

> Verification Levelは実装優先順位ではない。

## 12. このRequirementだけでは保証しないこと

C5.2.3にPassしても、次は別途評価する。

- Retrieval時に現在のEnd UserだけへDataを返すこと。C5.2.2の主題である。
- Modelが生成したOutputからUnauthorized Dataを除外すること。C5.2.4の主題である。
- Derived ArtifactへClassification Labelを伝播すること。C5.2.7の主題である。
- Vector DB、Prompt、Log、Cache、Trace、Backupの暗号化、Access Control、Retention。
- Prompt Injection、Data Poisoning、Model extractionを包括的に防ぐこと。
- Source DataのClassification、Consent、Entitlement自体が正しいこと。
- RetrievalしたAuthorized DataからModelが不正確または有害な推論を行わないこと。

Sensitive DataをFine-tuningする正当なUse caseが存在しても、Risk acceptanceや別のControlで
C5.2.3をPassに変えてはならない。そのData pathについては非適合または明示的なException
として扱い、生成されたModel Artifactを少なくとも元Dataと同等のSensitivityで保護する。

## 13. 質疑の再構成

### 問い1: Training prohibited PolicyがあるHR専用LoRA

**Scenario:** Restrictedな社員相談記録をHR専用LoRA AdapterへFine-tuningしている。
`training_use=prohibited` Policyはあるが、Jobは実行される。元Recordを削除してもAdapterは
再学習されない。

**学習者の判断:** Pass。Training prohibitedとなっているため。

**訂正:** Fail。Policy Labelが存在するだけで、実際にはFine-tuningされている。Controlは
Documentの存在ではなくEnforcement outcomeを評価する。LoRA Adapterも永続的なModel
Artifactであり、HRだけが利用できるAccess Controlでは削除不能を修復できない。

> Policyが存在することと、Policyが強制されていることは別である。

### 問い2: RAGと30日間のProvider Log

**Scenario:** 給与情報はTrainingへ使用せず、認可済みのChunkだけをRAGで取得する。Provider
はPromptを30日間Logへ保存するが、契約・設定上Model Trainingには使用せず、Feedbackへも
追加しない。

**学習者の判断:** Pass。

**整理:** C5.2.3にはPass候補である。Sensitive DataはModel Artifactへ固定されていない。
ただしVector DBの認可、Classification Label、Logの暗号化、Access Control、Retention、
Provider設定のEvidenceは別途必要である。

> Modelに保存しないことと、どこにも保存しないことは同じではない。

### 問い3: Feedback Loop

**Scenario:** RAG Prompt／Responseを品質改善用に自動収集し、メールアドレスと電話番号だけ
Maskして毎月のFine-tuning Datasetへ追加する。給与、病歴、Project、相談内容は残り得る。

**学習者の判断:** Fail。Sensitive Dataが含まれ、学習される可能性があるため。

**整理:** 正しい。直接のTraining Datasetだけでなく、Feedback、Evaluation、Log、再学習の
全経路がTraining入口になる。明白なIdentifierだけのMaskingは、再識別可能性やBusiness
Sensitivityを除去しない。

> 個人識別子を消したことと、DataがSensitiveでなくなったことは同じではない。

### 問い4: Sensitive Dataは何を意味するか

**学習者の疑問:** 一般的な情報区分なのか、個人、Role、属性ごとのAccess Controlで横断
されるDataなのかを明確にすべきである。

**整理:** 指摘は正しい。Data ClassificationとAuthorizationは別軸であり、C5.2.3は主に
ClassificationとTraining-use Policyを扱う。両者は頻繁に重なるが同義ではない。AISVSが
完全な一覧を定義していないため、本ノートではSecurity、Privacy、法令、契約、事業Impact
に基づくOperational definitionと判定質問を追加した。

### 問い5: SimpleなのにLevel 2である理由

**学習者の所感:** 他ControlよりSimpleであり、Level 1でもよい内容に見える。

**整理:** AISVSは個別理由を示していない。適用前提、Data Classification、System全体の
Lineage、ProviderとFeedbackを含むEvidenceの複雑さからLevel 2と説明する余地はある。
一方、Failureの不可逆性とSecure Defaultとしての実装可能性から、製品Baselineでは
Level 1相当に前倒しする判断は合理的である。Upstream Levelと実装優先順位を混同しない。

## 14. このセッションから得られた洞察

1. **Sensitive DataとAccess-controlled Dataは同義ではない。** Classification、
   Authorization、Model-use Policyを分けて設計する。
2. **Policyの存在ではなくEnforcement outcomeを見る。** `training_use=prohibited`と書かれて
   いても、Jobが実行されればFailである。
3. **LoRAやAdapterもModel Artifactである。** Base Modelを変更しないことは、Sensitive
   DataのPermanent Storageを避けた証拠ではない。
4. **Training入口は一つではない。** Feedback、Evaluation、Log、Provider Data-use、
   Direct API等を含む全Lineageを確認する。
5. **Identifier maskingはDeclassificationではない。** Contextによる再識別とBusiness上の
   Sensitivityを評価する。
6. **RAGはModel WeightからDataを分離するが、Dataを消去しない。** Vector、Prompt、Cache、
   Log等へLifecycle Controlが必要である。
7. **Levelは優先順位ではない。** Level 2 RequirementをBaselineへ前倒ししてよい。

## 15. 設計レビュー項目

- 組織のData Classification taxonomyとOwnerが明確か。
- `Sensitive Data`を例示だけでなくOperationalに判定できるか。
- Classification、Authorization、Model-use Policyを別の属性として扱っているか。
- Unknown classificationまたは欠落したLineageをTrainingで拒否するか。
- Training、Fine-tuning、LoRA、Adapter、Checkpoint、DistillationのData sourceを列挙したか。
- Dataset ManifestからSource RecordまでLineageを追えるか。
- Model RegistryがArtifactごとのTraining lineageとSensitivityを保持するか。
- ProviderがPrompt、Output、Abuse LogをTrainingへ利用する条件を確認したか。
- Provider設定の変更を検出またはAdmissionで拒否できるか。
- Evaluation、Human review、Feedback、Quality improvementからTrainingへ戻る経路があるか。
- DLP Masking後も再識別可能なContextやBusiness Sensitive Dataが残らないか。
- Sensitive Dataを必要時だけRetrievalし、不要なFieldを最小化しているか。
- Source削除、訂正、RevocationがChunk、Embedding、Cache、Logへ反映されるか。
- Retrievalを無効にしたCanary testでModel memorizationの兆候を確認したか。
- Fine-tuningの例外をC5.2.3へのPassとして扱わず、ExceptionとResidual Riskを記録したか。
- AISVS Level 2を理由に、不可逆なData placementの判断を後回しにしていないか。
