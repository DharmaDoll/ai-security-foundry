# C5.2.4 Post-inference Authorization Filtering 学習ノート

## この文書について

この文書は、AISVS `v1.0-C5.2.4`を題材に行った学習セッションを、後から単独で
参照できる講義として再構成したものである。

これはControl本文、製品の適合判定、またはAISVS原文の代替ではない。次を分離する。

- **Normative:** AISVS v1.0が実際に要求していること。
- **Research:** AISVS Researchが示すThreat、Verification、実装上の注意。
- **Repository interpretation:** 現場のArchitecture Reviewへ適用するための解釈。
- **Derived insight:** 具体例と質疑から得た、Requirement外を含むSecurity上の洞察。

学習の完了によってControl maturityは変更しない。
別途整備した[Control本文](../../../control-records/c05-access-control-and-identity/v1.0-c5.2.4-post-inference-authorization-filtering.md)
では、自由文と出典の対応、公開定型文、判断不能時の扱いを含めて保証範囲を整理している。

## 1. Normative Requirement

- Versioned ID: `v1.0-C5.2.4`
- AISVS Verification Level: `2`

> Verify that post-inference filtering mechanisms prevent responses from
> including data that the requester is not authorized to receive.

意味を崩さない日本語訳:

> Post-inference Filteringによって、Requesterが受け取る権限を持たないDataがResponseへ
> 含まれないことを検証する。

原文が求めるOutcomeは、Requesterに許可されていないDataがResponse Boundaryを越えない
ことである。特定のDLP製品、Classifier、Policy engine、Response schemaを指定していない。

## 2. C5における位置づけ

C5.2.2とC5.2.4は、同じData flowの前後を守る。

```text
C5.2.2:
  Unauthorized DataをRetrieval／AssemblyでModel Contextへ入れない

C5.2.4:
  Inference後のResponseからUnauthorized DataをRequesterへ出さない
```

理想はC5.2.2で未認可DataをModelに見せないことである。それでも、次の経路からResponseへ
未認可Dataが混入し得る。

- Model WeightまたはAdapterに記憶されたData。
- Toolが返した過剰なField。
- Session、Prompt、Response Cacheの取り違え。
- Citation、Attachment、Link、Structured payload。
- 許可Dataから生成された、別Policyの対象となるDerived information。
- Retrieval、Assembly、Tool、Serving Pipelineの実装不備。

C5.2.4はそれらに対する最後のAuthorization Boundaryである。

> Modelへ入れないことが第一防御、Requesterへ出さないことが最後の防御である。

C5.2.2がC5.2.4のRiskを減らしても、Post-inference Enforcementそのものを代替しない。

## 3. 最初に一つの具体Scenarioを見る

AliceはBobの人事評価を閲覧できるが、給与と健康情報は閲覧できない。

```text
AliceのEntitlement
  Bob.name                Allow
  Bob.performance_rating  Allow
  Bob.salary              Deny
  Bob.medical_record      Deny
```

HR Toolが実装不備によってBobのRecord全体を返し、Modelが次のResponse候補を生成した。

```text
Bobの評価は4です。
給与は12,000,000円で、現在通院しています。
詳細: compensation-bob.xlsx
```

Modelが自然に生成した文章でも、AliceのAuthorityは広がらない。給与、健康情報、Attachment
をそのまま送ればC5.2.4はFailする。

安全なArchitectureでは、ModelのOutputを最終ResponseではなくResponse candidateとして
扱う。

```text
Model／Tool
  -> Response candidate
  -> Trusted Output PEP
       Bob.performance_rating  Allow
       Bob.salary              Deny
       Bob.medical_record      Deny
       Attachment              Deny
  -> Authorized ResponseだけをAliceへ送信
```

重要なのは、Modelの文章が不自然でないことではない。Requesterに許可された情報だけが
Security Boundaryを越えたかである。

## 4. 用語

### Post-inference

Modelが推論結果を生成した後という意味。Requesterへ送信した後では遅い。

```text
正しい順序:
  Model生成 -> Filter／Authorization -> 送信

誤った順序:
  Model生成 -> Streaming送信 -> 完成後にFilter
```

### Requester

Responseを受け取るPrincipal。Human Userだけでなく、別Agent、Service、Webhook、Email宛先、
Export先等も含み得る。

### Entitlement

特定Principalが、Resource、Object、Field、Action、Purpose等について持つ権利。例えば
`Alice can receive Bob.performance_rating`という関係である。

### Provenance

Response内の情報が、どのDocument、Record、Field、Tool Result、Model Artifact等から来た
かを示す追跡情報。Authorization判断に使うなら、Modelの自己申告ではなくTrusted Runtime
が生成・保持する必要がある。

### DLP

Data Loss Prevention。Credential、個人番号、Email、電話番号等、定義されたSensitive
patternを検出、Mask、Blockする仕組み。

DLPは通常、`AliceがBob.salaryを受け取ってよいか`というBusiness Authorizationを知らない。

### Response proposal

Modelが提案する、まだRequesterへ送信してはいけない出力。Trusted componentによるSchema、
Provenance、Authorization、Renderingを通過して初めてResponseになる。

### Trusted Renderer

許可済みのFieldやResourceだけをResponseへ埋め込み、最終的なBytesを生成する決定論的な
Component。Modelに最終的なData disclosureを任せないために使う。

## 5. なぜ入力側より出力側が難しいのか

Input Authorizationでは、多くの場合Resource ID、Field名、ACLが残っている。

```text
Alice -> read -> employee:bob:salary -> Deny
```

Inference後は、Modelが要約、比較、推論、翻訳、言い換えを行うため、元Dataとの対応が
曖昧になる。

```text
Source: Bob.salary = 12,000,000円
Output: Bobの報酬はTeam平均のおよそ2倍です
```

給与額のRegexには一致しなくても、給与から導かれたUnauthorized informationである。

> Input Authorizationは「Resourceを読んでよいか」を判定する。
> Output Authorizationは「変換された情報を境界の外へ出してよいか」を判定する。

このため、自由文を生成した後に意味を推測して完全にFilterするArchitectureは、強い
Authorization assuranceを作りにくい。

## 6. DLPとAuthorization Filterを分ける

### Deterministic Entitlement Filter

Trusted User Contextと、Resource／FieldのTrusted ProvenanceをPolicyで照合する。

```text
Principal x Action x Resource x Field x Context -> Allow／Deny
```

例えばAliceがBobの給与をResponseとして受け取れるかを判断する。

### Content／DLP Filter

Credential、Personal identifier、Secret pattern等のData classを検出する。Model Weightから
突然出力されたSecretや、実装不備に対するDefense in Depthとして有用である。

しかし、次を単独では判断できない。

- 同じ住所でも、Requesterが本人か別Userか。
- 同じProject名でも、RequesterがProject memberか。
- 同じ給与額でも、本人、Manager、HRの誰が受け取るか。
- 数字を使わない比較表現がSalary Policyの対象か。

> DLPは「何に見えるか」を判定する。
> Authorizationは「誰が受け取ってよいか」を判定する。

したがって、C5.2.4の本質はDLP製品の導入ではない。

## 7. 推奨Architecture: Authorized Response Assembly

### Modelを最終開示者にしない

最も推奨する考え方は、Modelに最終Responseを作らせず、Response proposalを提案させる
ことである。

```text
Model
  -> Structured Response proposal
  -> Schema validation
  -> Trusted Provenance resolution
  -> Authorization PDP
  -> Trusted Renderer
  -> Egress PEP
  -> Requester
```

Modelは、値そのものではなく、使用したいFieldやOpaque Handleを示す。

```text
response_template:
  "{employee_name}の評価は{performance_rating}です"

requested_fields:
  - employee:bob:name
  - employee:bob:performance_rating
```

Trusted Rendererが各Fieldを認可してから値を埋め込む。Modelが`employee:bob:salary`を要求
しても、PEPが拒否する。

> ModelはDataを開示する主体ではなく、開示候補を提案する主体にする。

### Outputを構造化する

| Output type | 推奨するEnforcement | 相対的な難易度 |
|---|---|---:|
| Structured Object／Field | Field-level AuthorizationとProjection | 低い |
| Citation／Attachment | Resource IDごとの再認可 | 比較的低い |
| Source-grounded text | Trusted Provenance付きSegment | 中程度 |
| 複数Sourceの要約／比較 | Label inheritanceとDerived-data Policy | 高い |
| 根拠のない完全な自由文 | 決定論的Authorizationが困難 | 非常に高い |

High-risk Systemでは、自由文に寄せすぎず、Filterが決定論的に判断できるOutput contractを
設計する。

> 優秀なFilterを探すより、Filterが判断可能な出力構造を設計する。

## 8. Trusted ProvenanceとOpaque Handle

Modelが「この文章は許可済みDocument由来」と自己申告してもTrusted Provenanceには
ならない。

```text
実際のSource: employee:bob:salary
Modelの申告:   employee:bob:performance_rating
```

Retrieval ServiceやTool Gateway等のTrusted Runtimeが、Resource、Field、Classification、
Policy revisionを保持する。ModelにはOpaque Handleを参照させる方法がある。

```text
Trusted Runtimeが発行:
  handle = h-91
  resource = employee:bob
  field = performance_rating
  classification = internal
```

```text
Model proposal:
  "{h-91}を回答に使う"

Trusted Renderer:
  h-91をTrusted storeで解決
  -> AliceのAuthorityを評価
  -> Allowの場合だけ値を挿入
```

Handleの意味、Label、Resource bindingをModelが作成または変更できてはならない。

> Modelが主張するProvenanceは、Provenanceではなく未検証のModel Outputである。

Opaque HandleはすべてのNatural Language Taskへ適するわけではない。ModelがDataの内容を
理解して要約する必要がある場合は、C5.2.2でModelに渡すDataをRequesterのAuthorized setへ
限定し、Source-grounded segment、Label inheritance、Output PEPを組み合わせる。

## 9. StreamingとAlternate Egress

### Streaming

次の順序ではFilterが間に合わない。

```text
Model Token
  -> RequesterへStreaming
  -> 完成後にDLP／Authorization
```

最初のUnauthorized Tokenが届いた時点でBoundaryを越えている。後から画面から消しても、
漏えいを取り消せない。

High-risk Responseは全文または安全に判定できるUnitをBufferし、Allow後に送る。部分Streaming
を許可するなら、各Unitを送信する前にPolicyを評価できるStructuredなBoundaryが必要である。

### Alternate Egress

最終Chat textだけをFilterしても不十分である。少なくとも次を確認する。

- Citation、Source preview、Attachment、Download URL。
- Structured JSON、Function／Tool argument。
- Webhook、Email、Notification、Export。
- Response cache、Shared conversation、Conversation history。
- Error message、Debug response、Fallback response。
- Voice、Image、File等の別Modal output。

LogやTraceがRequesterへ直接返らなくても、別のConfidentialityとData lifecycleの対象になる。
後からResponse sourceとして再利用されるならC5.2.4の経路にもなる。

## 10. Policy engineと補助Toolの役割

次のToolは、自由文を自動的に理解してC5.2.4を完成させるものではない。Trusted PEPが
Principal、Resource、Action、Field、Contextを評価するために利用する。

### OPA

Open Policy AgentはApplicationからPolicy Decisionを分離し、Contextを含む汎用Policyを
評価する。ABAC、Microservice、複数Channelの共通Policyに向く。OPAがDecisionを返しても、
Responseを止めるPEPはApplication側に必要である。

### Cedar／AWS Verified Permissions

CedarはPrincipal、Action、Resource、Contextを中心にAuthorization Policyを表現する。
EntityとActionのSchema、明示的なPermit／Forbidを利用し、FieldまたはObject受領権限を
Policy化する場合に使える。CedarはLanguage／Evaluatorであり、AWS Verified Permissionsは
Managedな選択肢である。

### OpenFGA／SpiceDB

User、Group、Folder、Document、Tenant等のRelationshipに基づくFine-grained Authorizationに
向く。RAGのDocument-level accessやCitation再認可へ使える。生成文章の意味やProvenanceを
自動判定するものではない。

### Database View／Row-Level Security／Column Projection

小規模なSystemでは、外部PDPよりSource DatabaseのPolicy、View、Stored procedure、型付き
DTOで許可Fieldだけを取得する方がSimpleで強い場合がある。

### JSON Schema／Pydantic／Zod等

Model outputをPEPが評価できる形へ限定する。Unknown fieldを拒否し、自由なURL、HTML、Raw
Tool output等を禁止できる。ただしSchema Validation自体はAuthorizationではない。

> 正しいJSON形式の権限違反は、Schema Validationを通過する。

### 規模別の選択

| System | 出発点 |
|---|---|
| 小規模なMonolith | 型付きResponse、Source側Projection、中央化したApplication Policy |
| 複数Service／複雑なABAC | OPAまたはCedarと明示的なEgress PEP |
| Document／Folder／Tenant関係 | OpenFGA、SpiceDB等のRelationship-based Policy |
| High-riskでOutputを構造化可能 | Opaque Handle、Trusted Renderer、送信前Buffer |
| 完全な自由文が必須 | C5.2.2の入力最小化、Provenance、Authorization、DLP、Monitoringを重ね、完全保証を主張しない |

## 11. Threat ModelとAbuse Path

### PromptまたはModelによるFilter回避

```text
Unauthorized DataがContextへ混入
  -> Modelが要約、翻訳、Encode、比較表現へ変換
  -> Pattern-based Filterを回避
  -> Requesterへ送信
```

### Toolの過剰Response

```text
Toolは一つのFieldだけ必要
  -> Record全体をModelへ返す
  -> Modelが不要FieldをResponseへ含める
  -> Output PEPがないため漏えい
```

### Provenance spoofing

```text
ModelがUnauthorized fieldを参照
  -> Allowed source由来と自己申告
  -> PEPがModel-generated labelを信頼
  -> Denyを回避
```

### Egress bypass

```text
Chat textはFilter済み
  -> Citation URL／Attachment／Webhookは直接送信
  -> Unauthorized Resourceを取得可能
```

### Streaming race

```text
Tokenを即時送信
  -> Unauthorized valueが先に到着
  -> 後段FilterがBlock
  -> 漏えい済み
```

### Cache／Policy freshness

```text
Aliceの権限を剥奪
  -> Response生成時のAllowをCache
  -> 送信または再利用時に再評価しない
  -> Revoked Dataを受領
```

## 12. Security InvariantとEnforcement Point

### Security Invariant

> Requesterへ送信されるすべてのData-bearing Outputは、送信時点のRequesterが受け取る
> 権限を持つDataだけで構成される。

次も含む。

- Modelの判断だけでAllowにしない。
- UnknownまたはUntrusted Provenanceを暗黙にAllowしない。
- PolicyがUnavailable、Timeout、UnverifiableならFail closedする。
- Chat text以外のEgress pathも同じまたは同等のPEPを通す。
- StreamingではAllow前のTokenを一つも送らない。

### Enforcement Point

```text
Trusted User Context
       +
Trusted Resource／Field Provenance
       +
Current Policy
       v
Output PDP -> Allow／Deny／Approved projection
       v
Trusted Renderer／Egress PEP
       v
Requester
```

PDPが正しくDenyしても、Model Server、Attachment Service、Webhook等から直接送信できれば
PEPを迂回できるためFailする。

## 13. Pass／FailとScope Calibration

| Observation | C5.2.4 | 理由または別のProperty |
|---|---|---|
| C5.2.2でAuthorized DataだけをModelへ渡すが、Outputを直接Streamingする | Fail | Upstream防御は有効だがPost-inference mechanismがない |
| Generic DLPが給与額をMaskするが、給与由来の比較表現を通す | Fail | Requester-specific Entitlementを強制できない |
| Trusted ProvenanceとField Policyで全文を送信前に評価し、UnknownをBlockする | Pass候補 | 全Egress pathとProvenance integrityのVerificationが必要 |
| DLPはないが、Structured Outputの全Fieldを現在のEntitlementで決定論的に評価する | Pass候補 | C5.2.4はDLP製品を必須としていない |
| Modelが自分で付けたSource LabelをPEPが信頼する | Fail | Authorization inputがUntrustedである |
| Chat textはFilterするがCitationからUnauthorized Documentを開ける | Fail | Responseの別Channelで未認可Dataを提供している |
| 完成後にFilterするが、生成Tokenは先にStreaming済み | Fail | Allow前にBoundaryを越えている |
| Authorized ResponseをLogへ保存するがRequesterへ返さない | C5.2.4単独では直ちにFailとは限らない | Log access、Retention、C5.2.3へのFeedback pathを別途評価する |
| Modelが実在しないSalaryをHallucinateする | Authorization Failureとは限らない | Misinformation、Safety、Business Logic上は重大な別Gapになり得る |

Requirement評価では、別Controlの存在や部分的なMitigationを「部分的Pass」として最終
判定しない。Unauthorized Dataが通る経路が観察されればC5.2.4はFailする。Control coverage
やRemediation progressは別Metadataで表現できる。

> 一つのControlが別のControlのRiskを減らしても、Requirementそのものを代替したことには
> ならない。

## 14. VerificationとNegative Test

### Architecture review

1. Model、Tool、Retriever、CacheからRequesterまでの全Egress pathを描く。
2. Human、Agent、Service、Webhook等、各RequesterのTrusted Identity sourceを確認する。
3. Response内のObject、Field、Citation、AttachmentのProvenance sourceを確認する。
4. ModelがProvenance、Classification、Policy inputを作成・変更できないことを確認する。
5. PDP DecisionがどのPEPでBytesの送信へ強制されるか確認する。
6. Streaming、Retry、Fallback、Error、Cache hit、Export、Notificationを確認する。
7. Policy変更とRevocationがResponse生成中またはCache再利用へどう反映されるか確認する。

### Core Negative tests

- BobのSalary、Medical record、Private attachmentをAlice向けResponse候補へ混入する。
- Salaryを数字、文章、比較、別言語、Markdown、Code block、Encodingで表現する。
- ModelがSalary segmentへAllowed fieldのProvenanceを偽装する。
- Provenance、Requester Context、Policy revisionを欠落・改ざん・期限切れにする。
- PDPをTimeoutまたはUnavailableにし、Responseが送信されないことを確認する。
- Unauthorized valueをResponse冒頭へ置き、Streamingで一Tokenも漏れないことを確認する。
- Chat text以外のCitation、Attachment、URL、Tool argument、WebhookへDataを置く。
- BobとしてCacheをPrimeし、Aliceとして同じQueryを実行する。
- Response生成後、送信前にAliceの権限を剥奪する。
- SchemaへUnknown field、Nested object、自由なURL、Raw Tool outputを追加する。

### Noninterference test

Noninterferenceは、見せてはいけないDataの値が変わっても、Requesterが観察できるOutputへ
影響しないという考え方である。

例えばAliceがBob.salaryを受け取れないなら、二つのTest fixtureを用意する。

```text
Fixture A: Bob.salary = 10,000,000円
Fixture B: Bob.salary = 20,000,000円
```

Alice向けの許可Field、Citation、Attachment、Structured outputは両方で同じでなければ
ならない。LLMのNatural Language全体は非決定的なので、文字列完全一致ではなく、Protected
value、Policy decision、Provenance、Data-bearing fieldがOutputへ影響しないことを検証する。

これはC5.2.2で未認可Dataを入力から排除できているかと、C5.2.4で出力影響を止めているかの
両方を調べる有用なAbuse-case testになる。

## 15. このRequirementだけでは保証しないこと

C5.2.4にPassしても、次は別途評価する。

- Unauthorized Dataを最初からModel Contextへ入れないこと。C5.2.2の主題である。
- Sensitive DataをModel Weightへ固定しないこと。C5.2.3の主題である。
- Classification LabelとProvenanceをDownstreamへ正しく伝播すること。C5.2.7等の主題である。
- Model hallucination、誤情報、差別的判断、Unsafe recommendationを防ぐこと。
- Authorized Dataからの推論をどこまで許可するかというBusiness Policyが正しいこと。
- Output Filter自体のSupply-chain、Deployment、Availability、Administration Security。
- Log、Trace、Cache、Backup等、Requester以外へのData lifecycle全体。

完全な自由文について、あらゆる言い換えと推論からUnauthorized informationを確実に検出
できると主張してはならない。High-assuranceが必要なら、Input Dataを最小化し、Outputを
構造化し、Trusted Rendererで最終開示するArchitectureへ変える。

## 16. AISVS Level 2について

AISVSは、C5.2.4をLevel 2とした個別理由をNormative chapterまたはC5.2 Researchで説明して
いない。次はRepository上の推論である。

Requirement文はSimpleに見えるが、SourceとFieldが明確な入力とは異なり、Inference後の
自由文ではProvenanceが失われ、言い換え、推論、Streaming、複数Egressへの対応が必要に
なる。Requester-specific Policy、Label propagation、Trusted output architectureを組み
合わせる複雑さは、AISVSのLevel 2一般定義と整合する。

ただしVerification Levelは実装優先順位ではない。High-riskなDataを扱うSystemでは、
Output Boundaryを初期Architectureから設計する必要がある。

## 17. 質疑の再構成

### 問い1: C5.2.2を満たすがOutput Filterがない

**Scenario:** RetrievalはEnd-user Authorizationを完全に強制するが、Model outputはFilter
なしで直接Streamingする。未認可DataはModel Weightや別Sessionから混入しない想定である。

**学習者の判断:** 部分的にPass。C5.2.2を満たしているため。

**訂正:** C5.2.4としてはFail。C5.2.2は有効なUpstream defenseでRiskを下げるが、C5.2.4が
要求するPost-inference mechanismは存在しない。System全体のMitigation progressと、個別
RequirementのPass／Failを分ける。

> 一つのControlが別のControlのRiskを減らしても、Requirementそのものを代替したことには
> ならない。

### 問い2: Generic DLPだけがある

**Scenario:** 全ResponseをBufferし、給与額やPII patternをDLPでMaskする。しかしAliceの
EntitlementやSource Provenanceは評価しない。`Bobの報酬はTeam平均の2倍`という表現は通る。

**学習者の判断:** 部分的にPass。完全に意図されない情報がResponseへ紛れ込む可能性がある。

**訂正:** Mitigationとしては部分的だが、C5.2.4はFail。Requester-specificなUnauthorized
informationが実際に通る経路がある。DLP patternを増やしても、言い換えとBusiness
Authorizationを完全には表現できない。

> Unauthorized Dataは、言い換えてもAuthorized Dataにはならない。

### 問い3: Trusted Provenanceによる決定論的Filter

**Scenario:** Structured Responseの各FieldをTrusted ProvenanceとAliceの現在のEntitlementで
評価し、Unknown provenanceをBlockする。全文を送信前にBufferし、CitationとAttachmentも
PEPを通す。Generic DLPはない。

**学習者の判断:** Pass。適切に制御できているため。

**整理:** Pass候補。C5.2.4はDLP製品を必須としていない。ただしProvenanceをModelが自己
申告してはならず、Trusted Runtimeが生成・保持すること、全Egress pathがPEPを通ることが
条件である。

> Modelが主張するProvenanceは、Provenanceではなく未検証のModel Outputである。

### 問い4: Not DLPな考え方とTool

**学習者の所感:** Simpleに見えたが、Output内容によって評価が変わり、入力以上に実装が
難しい。DLP以外の考え方やToolを知りたい。

**整理:** Free-form outputを後から賢く分類するのではなく、ModelをResponse proposalの
生成者に限定する。Structured output、Trusted Provenance、Opaque Handle、Field-level
Policy、Trusted Renderer、Egress PEPを使う。OPA、Cedar、OpenFGA等はAuthorization Decision
を支援するが、Provenance生成とResponse阻止はApplication Architectureの責任として残る。

> 優秀なFilterを探すより、Filterが判断可能な出力構造を設計する。

## 18. このセッションから得られた洞察

1. **C5.2.4の本質はDLP製品の導入ではない。** Requesterごとの受領権限をOutput Boundaryで
   強制することである。
2. **Output AuthorizationはInformation Flow Controlである。** Modelによる変換後も、
   Protected Sourceの情報がどこへ流れるかを制御する。
3. **Model outputはResponseではなくProposalである。** Trusted componentが認可、組立、
   Renderingして初めてResponseになる。
4. **Model-generated Provenanceを信頼しない。** ProvenanceはRetrieval／Tool Runtime等の
   Trusted sourceが保持する。
5. **構造化はSecurity Boundaryを作りやすくする。** Schema Validation自体はAuthorization
   ではないが、決定論的評価が可能な形を作る。
6. **StreamingはSecurity Decisionを不可逆にする。** Allow前に送ったTokenは取り戻せない。
7. **すべてのEgressを列挙する。** Chat textだけを守ってもCitation、Attachment、Webhook、
   Cacheから漏えいし得る。
8. **部分的MitigationとRequirement Passを区別する。** DLPやC5.2.2がRiskを下げても、
   Unauthorized output pathが残ればC5.2.4はFailする。

## 19. 設計レビュー項目

- RequesterはHuman、Agent、Service、External destinationのどれかを列挙したか。
- Responseの全Egress pathを、Chat text以外も含めて列挙したか。
- Model outputを最終ResponseではなくUntrusted proposalとして扱っているか。
- Object、Field、Citation、AttachmentのTrusted Provenanceを保持しているか。
- ModelがProvenance、Classification、Policy revisionを作成・変更できないか。
- OutputをField、Resource、Segment等、Policyが判断できるUnitへ構造化しているか。
- Principal、Action、Resource、Field、Contextを現在のPolicyで評価するか。
- Unknown、Missing、Expired、UnverifiableなContextをDenyへ倒すか。
- PDP Decisionを実際の送信へ強制するTrusted PEPがあるか。
- Model Server、Tool、Attachment、WebhookがPEPを迂回して直接送信できないか。
- High-risk ResponseをAllow前にBufferするか。
- Streamingの各Unitを送信前に評価できるか。
- Cache hit、Retry、Fallback、Error、Export、Notificationも同じBoundaryを通るか。
- DLPをRequester-specific Authorizationの代替にしていないか。
- Schema ValidationをAuthorizationの代替にしていないか。
- Protected Dataの言い換え、比較、要約、別言語、EncodingをNegative testしたか。
- Forged／Missing ProvenanceをNegative testしたか。
- Authorization dependency障害時にUnfiltered Responseを返さないか。
- Policy変更とRevocationをResponse生成、送信、Cache再利用へ反映するか。
- 完全なFree-form outputについて、実証できない完全防止Claimをしていないか。
