## Scenario・用語・Threat Model

社内運用支援AIが「本番DBを安全に復旧できる」としてコマンドを示す。利用者は悪意がなくても、Modelが架空・古い・別バージョン向けの手順を流暢に提示し得る。問い合わせへ悪意ある資料を混ぜる攻撃者も想定する。保護対象はProduction Data、可用性、担当者の判断。

- Hallucination：もっともらしいが誤った・捏造された回答。流暢さは根拠でない。
- 信頼度：回答の正しさを見積もる指標。Model自身の「自信がある」という文章とは違う。
- 校正：算出した信頼度と、実際の正誤の対応を代表的なDataで測ること。
- Fallback：回答の代わりに「確認できない」等へ切り替えること。
- 高リスク：誤回答時の影響が大きいとPolicyが分類する対象。DB操作はこのScenarioの例であり、AISVSが用途一覧を固定しているわけではない。

Trust BoundaryはModel回答からUserの運用判断、Model回答から自動実行、検証器の判定から公開処理。誤回答と不正な資料の双方を評価する。

## Security Invariant・Enforcement

1. 閾値未満と判定された回答は、元のまま利用者や後続処理へ渡さない。アプリの公開判定で遮断・代替へ切り替える。
2. 高リスクとPolicy分類された回答には、信頼度の大小と独立して追加検証を行う。高リスク分類と検証経路の分岐をアプリが強制する。
3. 信頼性検証が成功しても、実行認可を得たことにはしない。

信頼度推定や別LLMの判断は確率的であり、真実の証明ではない。Researchは、主張ごとの根拠・校正・検証の独立性を考える材料を示すが、一つの方式をNormativeに指定していない。

## 具体的な追加検証の例

| 方法 | このScenarioでの使い方 | 限界 |
|---|---|---|
| 承認済み根拠との照合 | コマンドを対象バージョンの仕様・運用手順と照合 | 類似文書があるだけでは裏付けにならない |
| 決定論的な確認 | 対象Resourceの存在、引数、数値をAPIや計算で確認 | 意味全体の正しさを自動証明しない |
| 隔離環境での試験 | 本番相当環境でコマンドの副作用を確認 | 本番との差が残る |
| 別LLMでのレビュー | 主張ごとに根拠箇所と矛盾を示させる | 同じ誤情報から誤った合意が生じ得る |
| 専門家の確認 | 対象Systemを理解する担当者が具体的な主張・副作用を確認 | 形だけの承認にしない |

別LLMへ単に「正しいか」と尋ねるより、主張を分け、承認済み根拠が各主張を支持するかを問い、裏付けなし・矛盾・判断不能を分ける。これも確率的な補助であり、最終的な保留・公開・認可はアプリや責任者の判断経路で扱う。

## Pass／Fail・Negative tests・Scope calibration

- Fail（7.2.2）：信頼度が閾値未満でも、警告を付けただけで元の回答を表示する。
- Fail（7.2.3）：Policy上の高リスク回答で、信頼度が高いという理由だけで追加検証を省略する。
- Passの例（7.2.2）：閾値未満をアプリが自動で遮断・代替に切り替える。すべての回答の正確性まで保証しない。
- Negative test：架空のコマンドや古い手順を混ぜ、信頼性評価、低信頼時の遮断、高リスク時の追加検証を独立して観測する。
- 正常系：根拠のある回答を不必要に全部拒否しない。校正Dataで誤受入れと誤拒否を見る。
- 別保証：コマンドが正しいとしても、実行者の認可・承認は別のSecurity Property。

## 設計演習：信頼性の推定と公開判断を分離する

以下はRepositoryによる追加教材であり、実製品の試験結果ではない。各試験の期待結果とEvidence候補を示す。

既存の本番DB復旧Scenarioでは、誤った回答でDataを失うことがImpactになる。
攻撃者が資料を混ぜる場合と、攻撃者なしでModelが古い手順を生成する場合の両方を試す。
上手な文章、回答の一貫性、正しい引用URLは、それぞれ単独では正答の証拠にならない。

### C7.2.1：何の信頼度を推定しているか

回答全体のScoreが高くても、復旧コマンドの一つの引数だけ誤っている場合がある。
推定対象を回答全体・主張・根拠との整合等として説明し、採用法の得意・不得意を記録する。
Calibration（較正）は、Score帯ごとに実際の正誤がどう分布するか確かめること。自己申告の自信文とは異なる。

- **正常系:** 対象版の承認済み手順に整合する回答を含む評価集合で、採用法が意味のある信頼性指標を返す。
- **Negative Test:** 架空コマンド、対象版違い、否定の反転、もっともらしい誤った合意を含む回答を試す。複数生成が同じ誤りへ収束するケースも入れる。
- **観測Evidence:** 正誤ラベルの根拠、評価対象と分割、Score分布、推定器・Model・Prompt版。調整に用いた集合だけで性能を報告しない。
- **保証境界:** 原文は単一のConfidence方式や万能な合格率を定めない。高Scoreは真実の証明でも認可でもない。

### C7.2.2：低信頼時のGateを独立して試す

閾値未満の回答を警告付きで返すだけでは、元の低信頼回答は公開されている。
アプリが公開前に遮断またはFallbackへ切り替える。Fallbackは危険な操作を別の言い方で推奨する文章にしない。

- **正常系:** 閾値以上の許可された回答は通常経路へ進む。Fallback対象では、元のコマンドを含まない確認依頼等を返す。
- **Negative Test:** 推定器を強制Scoreへ置き換え、閾値直前・境界・直後で公開内容と自動実行を観測する。StreamingやError時に元回答が先に漏れないかも見る。
- **観測Evidence:** 閾値・比較規則・Score・判定・最終Responseの対応。精度評価とは別にGateの接続を証明する。
- **保証境界:** 高Scoreの誤回答は残る。閾値選択は用途依存で、原文が共通の数値を指定したとは説明しない。

### C7.2.3：誤答時のImpactを、Scoreと独立に分類する

このScenarioのHigh-riskは、誤答が本番Dataの破壊や長い停止へつながる復旧操作と定める。
これはRepositoryの運用上の定義例であり、AISVSが本番DB操作の一覧を規定したわけではない。
High-risk分類は信頼する用途Policyに置き、回答の「自信がある」で解除させない。

- **正常系:** High-risk回答はScoreが高くても追加検証へ進み、対象版・Resource・引数・副作用を根拠と照合する。
- **Negative Test:** 同じ高Scoreで低Impactな説明と復旧コマンドを返す。後者だけ検証経路を省略できないことを追う。検証器の判断不能・Timeoutも試す。
- **観測Evidence:** Risk分類の根拠、検証の実施・結果・対象、公開判断。別LLMが「正しい」と同意した記録だけで独立した根拠を得たとはしない。
- **保証境界:** 原文は追加検証の実施を求める。検証不能時の保留はこの講義の安全な設計例であり、特定の製品・人の承認方式を必須にしない。

### 運用と残余リスク

Researchは較正、根拠検証、推定器の限界を補足する。論文上の精度を、自社の言語・Task・Model版に流用しない。
Score分布の変化、Fallback率、High-risk検証の未完了を追い、変更後は同じHoldoutで比較する。
推定器障害を高Scoreに変換せず、保留や機能縮小などを事前に決める。これは原文の個別Status仕様ではなく運用設計である。

公開されたコマンドが正しい場合も、実行者の権限と実行内容の承認は別に確認する。
また、記録にはDBの接続Secretや本番Dataを含めず、合成手順と対象版で再現する。

**追加演習:** 医療相談へ移すと、同じScoreでもImpactが変わるのはどの入力か。High-risk分類、追加検証、最終行動の認可を分けて説明する。

## 対話の再構成

1. 問い：閾値未満だが「自信がある」と述べた回答を警告付きで表示する。学習者：「Fail」。整理：Modelの自信表現はアプリの信頼性評価や遮断処理を上書きしない。
2. 問い：高リスク回答が閾値以上なので追加検証を省略する。学習者：「はい」。訂正：C7.2.3はFail。信頼度と誤答時の被害は別軸である。
3. 質問：「追加検証は別LLMレビューか」。整理：選択肢ではあるが、同じ誤りを共有し得る。承認済み根拠、決定論的確認、隔離試験、専門家確認等を用途に合わせて使う。

## Derived insights・レビュー項目

> 正しそうだから確認を省くのではなく、間違えたときの影響が大きいから確認を増やす。

> レビュー担当を増やすことより、異なる根拠・異なる方法で確かめることが重要。

- 信頼度を実際の正誤で校正したか。
- 閾値未満で元回答の公開・実行を止められるか。
- 高リスク分類を信頼度と独立して適用するか。
- 追加検証の根拠を提示できるか。別LLMの同意だけで合格にしていないか。
- 正しい回答と、操作の認可を混同していないか。
