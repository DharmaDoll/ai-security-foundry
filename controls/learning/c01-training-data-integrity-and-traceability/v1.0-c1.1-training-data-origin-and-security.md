# C1.1 モデルに教えるデータの中身と来歴を確かめる

## Normative Requirements

対象はAISVS v1.0（採用済み安定版の固定Revision `78775233666a2022dcfb82037e5e029116955c00`）。
Sourceの採用状態は[Registry](../../../sources/registry.yaml)を参照する。LevelはVerification Levelであり、学習難易度・文書成熟度・製品適合ではない。

### v1.0-C1.1.1

AISVS Verification Level: 1

> Verify that training data includes only features, attributes, and fields required for the model's stated purpose.

**意味を保った日本語訳:** 学習Dataが、そのModelの明示された目的に必要な特徴量・属性・Fieldだけを含むことを検証する。

### v1.0-C1.1.2

AISVS Verification Level: 2

> Verify that an up-to-date inventory is kept of every training-data source, including its origin, responsible party, license, collection method, intended use constraints, and processing history.

**意味を保った日本語訳:** すべての学習Data源について、出所、責任者、License、収集方法、意図した用途の制約、加工履歴を含む最新の台帳が維持されることを検証する。

### v1.0-C1.1.3

AISVS Verification Level: 2

> Verify that data integrity is provided when training data is stored and transferred.

**意味を保った日本語訳:** 学習Dataの保存時と転送時に、Dataの完全性が提供されることを検証する。

### v1.0-C1.1.4

AISVS Verification Level: 2

> Verify that integrity monitoring is applied to guard against unauthorized modifications or corruption of training data.

**意味を保った日本語訳:** 学習Dataの無断変更や破損を防ぐため、完全性の監視が適用されることを検証する。

### v1.0-C1.1.5

AISVS Verification Level: 3

> Verify that datasets are watermarked so their use can be attributed and any unauthorized use detected.

**意味を保った日本語訳:** Datasetの利用を帰属させ、無断利用を検出できるよう、DatasetにWatermarkが付与されることを検証する。

## このSectionで学ぶこと

学習データに不要な項目や出所不明のデータが混じり、途中で書き換えられても気付けないと、モデルの振る舞いと情報漏えいのリスクを説明できない。C1.1は、データの必要性、出所、保存・転送時の完全性、変更の監視、無断利用後の識別を別々に問う。これは**モデルの学習・追加学習に使うデータ**の話であり、RAG検索用の文書をそのままモデルへ見せることとは区別する。

この文書は学習用であり、Control本文、製品適合判定、Mappingではない。**Normative**はAISVS正規要件、**Research**は脅威や検証例の補足、**Repository interpretation**は設計レビューに使う解釈、**Derived insight**は対話から得た整理である。

## C1の中での位置づけと適用範囲

C1.1は学習データを受け入れ、保管し、追跡する入口を扱う。C1.2は人や自動処理が付けるLabel・Annotationの保護、C1.3は学習前の品質と毒入れの検査を扱う。C1.1の台帳が揃ってもLabelが正しいとは言えず、完全性が保たれても元から悪意あるデータを安全とは言えない。

**Repository interpretation:** 自社でモデルを訓練・追加学習する場合、自社が選び用意するDatasetにはC1.1が関係する。外部ベンダへfine-tuningを委託しても、自社側の項目選定や出所の説明責任は消えない。一方、既存LLMへRAGで文書を検索して渡すだけなら、通常その文書はLLMの学習データではなく、C1.1を自社アプリの直接の適合項目としない。RAGの取込み・検索・権限・汚染には別の保証が必要である。ベンダがモデル学習に利用者データを使う契約・設定がある場合は、その境界を個別に確認する。

## 具体例と用語

会社が問い合わせ履歴で独自の分類モデルを追加学習する。履歴には問い合わせ本文に加え、顧客の氏名と電話番号もある。学習データは社内で加工され、外部の学習サービスへ転送される。攻撃者は、権限を奪って保存中のDatasetの一部を書き換えるか、出所不明のデータを混ぜようとする。

- **特徴量・属性・項目:** モデルへ学習材料として渡すフィールド。問い合わせ分類に氏名や電話番号が不要なら、学習前に除く対象になる。
- **完全性:** 期待したデータが途中で意図せず、または無断で変わっていないという性質。秘密にすることとは別である。
- **SHA-256ハッシュ:** ファイルから計算する短い照合値。信頼できる元の値と比較すれば変更を検出する手掛かりになるが、攻撃者がファイルと照合値の両方を変更できるなら証拠にならない。
- **データセットのウォーターマーク:** 後から無断利用の疑いを調べるための識別用の印。ファイル改ざんを検出するハッシュとは目的が違う。識別には誤判定や除去の限界もある。
- **RAG:** 必要な文書を回答時に検索し、モデルの入力として渡す方式。文書をEmbeddingに変換することだけで、LLMの重みを学習し直したことにはならない。

## 攻撃の通り道と守る線

```text
収集元 → 受入れ・項目選択 → 保管・加工 → 転送 → 学習
           出所台帳          完全性確認    完全性確認
                             ↓
                       変更の継続監視
```

信頼境界は、外部・内部の候補Dataを、モデルに影響する承認済み学習Datasetへ入れる所と、保管・転送後のDatasetを次の学習で信頼する所にある。攻撃者が保存ファイルを書き換え、元の照合値も書き換えられるなら、ハッシュの存在だけでは防げない。

| 要件 | 守る線 | 主な検査・強制の場所 |
|---|---|---|
| C1.1.1 | 目的に不要なフィールドを学習Datasetへ含めない | Dataset Schema、Field選択、学習前の入力検査 |
| C1.1.2 | 各Sourceの権利・制約・加工履歴を追えるようにする | データ源の登録、加工Jobの履歴、Dataset版管理 |
| C1.1.3 | 保管・転送後に信頼できる元のDatasetと同じか確かめる | 署名付きManifest等の信頼できる照合基準と受領・読込時検証 |
| C1.1.4 | 無断の変更や破損を見張り、発見できるようにする | Object Store・Dataset変更Event、独立したIntegrity Monitor |
| C1.1.5 | 無断利用されたDatasetを後から識別できるようにする | Datasetの識別用の印と、その検出手順 |

署名付きManifestは実装例であってAISVSが特定形式を要求するわけではない。どの照合方式でも、基準値の信頼性と実際に学習へ使うData Versionとの結び付きが必要になる。

## PassとFailの境界

| 観察 | 判定の要点 |
|---|---|
| 問い合わせ分類に不要な顧客の電話番号が学習Datasetに残る | C1.1.1はFail。単に「後で表示しない」では学習データの最小化にならない。 |
| 台帳には出所と責任者があるが、利用条件と加工履歴がない | C1.1.2はFail。台帳の存在だけでは要求された内容が揃わない。 |
| 学習開始時にファイルのハッシュを照合するが、元の値がどこにあり、転送経路を検証するか不明 | C1.1.3は判定保留。独立した信頼可能な基準と保存・転送中の保護を確認してから評価する。 |
| 保存中の無断変更に次の学習まで気付かず、変更監視の仕組みがない | C1.1.4はFail。学習直前の照合は変更監視と同じではない。 |
| DatasetのSHA-256ハッシュはあるが、無断利用の際にそのDataset由来だと識別する印はない | C1.1.5はFail。完全性の照合値は帰属を調べるウォーターマークではない。 |

逆に、目的に必要な項目だけを取り込み、六つの台帳項目を最新に保ち、保管・転送時の完全性検証と変更監視を行い、Datasetの識別用の印を評価した経路で検出できるなら、それぞれの要件のPass候補になる。ただし、一つの対策が五要件をまとめて満たすわけではない。

## 設計演習：学習に入る最終Datasetを追う

以下はRepositoryによる追加教材であり、実製品の試験結果ではない。各試験の期待結果とEvidence候補を示す。

問い合わせ分類の例で、原本、加工CSV、転送したShard、学習Jobの入力Snapshotを別物として識別する。
Shardは大きなDatasetを分割した単位、Snapshotは特定時点の内容を固定したもの。
攻撃者が加工先を変えられる場合、収集時の検査だけでは後段の入力を説明できない。

### C1.1.1：残すFieldの必要性を目的から説明する

氏名・電話番号を画面から隠しても、学習CSVや自由記述の派生Fieldへ残れば最小化したとは言えない。
目的は「問い合わせ分類」と具体化し、各Fieldがその目的にどう必要かをOwnerが説明する。

- **正常系:** 必要な本文・分類用Fieldだけを最終Snapshotへ残し、目的に必要な分類品質を維持する。
- **Negative Test:** 不要な電話番号を新Field、理由欄、加工Cacheに置き、学習入力へ残らないか実Dataを照合する。
- **Evidence・境界:** 目的、Field単位の判断、Schema版、最終出力の検査を残す。PII Scannerは必要性を決めず、Fieldを消しても本文中の記憶・抽出Riskは残る。

### C1.1.2：台帳と実際の入力を双方向に照合する

原文の六項目は、出所、責任者、License、収集方法、利用制約、加工履歴。
台帳からDatasetを探すだけでなく、学習に入った全Sourceから対応する台帳Entryへ戻れるか確認する。

- **正常系:** 合成した二つのSourceを結合し、加工版から両方の六項目と更新内容へ辿れる。
- **Negative Test:** Notebookで追加した未登録Source、期限切れの責任者、利用制約の変更、加工履歴の空欄を混ぜる。
- **Evidence・境界:** Source一覧とSnapshotの対応、根拠となる収集記録、更新差分を残す。台帳の記載は権利や無害性の真実を自動証明しない。

### C1.1.3：内容と照合基準を同じ攻撃者に書き換えさせない

保存・転送後の実際の入力を、信頼できる元の内容へ照合する。
Hashの隣にファイルを置くだけでは、両方を書き換えられる攻撃者に対する保証にならない。

- **正常系:** 全Shardが承認Snapshotと一致し、受領・読込時にも同じ版であると確認できる。
- **Negative Test:** 保存Fileの一部変更、転送時の差替え、Shard欠落、偽の基準値を試し、学習前の照合失敗を観測する。
- **Evidence・境界:** 対象版、検証対象、基準値の管理主体、照合結果を残す。暗号化は秘密性、Hashは照合手段であり、元から汚染された正規Datasetを除けるわけではない。

### C1.1.4：読込時の照合と、変更の監視を分ける

保存後に変更された状態を、次の学習まで放置する設計と比較する。
Monitorは監視対象・基準・担当者を持ち、Event欠落や監視停止自体も気付ける運用を考える。

- **正常系:** 許可した版更新と、未承認の変更を区別して観測できる。
- **Negative Test:** 未承認の書換え、破損、通知停止、基準値変更を試す。検知までの時間と通知先を記録する。
- **Evidence・境界:** 変更Eventと検知記録を対応付ける。特定の検知時間は原文の共通値ではなく、このSystemの運用目標として決める。監視しても変更自体を禁止したことにはならない。

### C1.1.5：Datasetの利用を識別する印を評価する

Watermarkは、後に使われたDataがそのDatasetに由来するか調べる印であり、File Hashと目的が違う。
Datasetそのもの、加工されたSubset、学習済みModelの挙動など、何から検出する方式かを先に定める。

- **正常系:** 対象版に印を付け、定義した利用経路で検出できる。
- **Negative Test:** 無関係なDataset、部分抽出、再加工、印の除去を対照にして、誤検出と検出不能条件を測る。
- **Evidence・境界:** 付与・検出方式、合成対照、判定結果、適用範囲を残す。印の検出だけで利用許諾違反の法的断定や完全な盗用防止を主張しない。

### 運用・Researchと残余リスク

ResearchはFieldの正当化、台帳の欠落、保存・転送後の変更、監視、印の頑健性を補足する。
個別Catalog・Scanner・法令の記述は、原文の追加条件として自動採用しない。
Schema変更やSource追加時は、最終Snapshotを改めて照合する。古いCacheから削除済みの不要Fieldが戻る経路も試す。
検証不能なDataを成功扱いしない処理は安全な設計例であり、元のDataの品質保証とは別である。
本番の顧客情報を証拠として広く複製せず、合成Datasetと版付きのManifestで再現する。

**追加演習:** 外部学習Serviceへ委託するとき、自社が残すEvidenceと委託先へ求めるEvidenceを五要件ごとに分ける。委託は適用外やPassと同じか。

以下の対話は既存学習記録を保持したもの。上の設計演習は今回の補強教材であり、新しい学習者の回答や理解確認を創作していない。

## 対話から残す判断と訂正

**問い1:** 学習開始時にハッシュを照合するが、保存中に書き換えられても次の学習まで通知されない。C1.1.3とC1.1.4はどう評価するか。

**学習者の判断:** 「ともにFail」。

**設問の訂正:** C1.1.4はFail。C1.1.3は元のハッシュを誰が守り、保存・転送の全経路をどう照合するかが設問にないため、PassともFailとも断定できない。学習直前の信頼できる照合は完全性を支え得るが、継続監視の代わりにはならない。

**問い2:** 分類に不要な電話番号が残り、台帳には利用条件・加工履歴がない。C1.1.1とC1.1.2はどう評価するか。

**学習者の判断:** 「Fail、Pass」。

**整理:** C1.1.1はFail。C1.1.2もFailであり、出所と責任者を記録しただけでは台帳の必須項目が欠ける。

**問い3:** SHA-256ハッシュはあるが無断利用後のDataset識別用の印がない。C1.1.5はどう評価するか。

**学習者の判断:** 「Fail」。さらに、このFamilyはLLMベンダ向けか、LLM利用企業やRAGにも関係するかを確認した。

**整理:** C1.1.5はFail。C1はLLMベンダ専用ではなく、自社・委託先を問わず学習Datasetを扱うシステムに関係する。既存モデルへ文書を検索して渡すだけのRAGでは、通常その文書は学習データではない。適用外をPassと言い換えず、RAG固有のデータ保護を別に扱う。

## このSectionの本質と設計レビューの問い

**Derived insight:** C1の適用は「LLMを使う会社か」ではなく、「どのデータがどのモデルの学習・追加学習に入るか」で決まる。学習データの最小化、出所、完全性、監視、無断利用後の識別を分け、ハッシュや台帳というArtifactの存在だけで全体を保証したと考えない。

- 対象モデルは実際に学習・追加学習されるか。それとも外部LLMへRAG文書を渡すだけか。
- 残す各フィールドをモデルの目的から説明でき、不要な個人情報を除けるか。
- データ源ごとの六つの台帳項目を確認でき、加工後の版まで追えるか。
- 完全性を確かめる基準は、Datasetを書き換える主体から守られているか。保管と転送の両方を対象にしているか。
- 学習前の照合と、保存中の変更監視を混同していないか。
- ハッシュとDatasetの識別用の印を混同していないか。識別できる範囲と限界を試したか。
