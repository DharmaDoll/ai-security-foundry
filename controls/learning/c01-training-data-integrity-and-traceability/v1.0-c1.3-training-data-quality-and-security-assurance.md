# C1.3 学習データをモデルへ入れる前に何を確かめるか

## このSectionで学ぶこと

学習データが正規の経路から届き、ラベルが権限のある人によって付けられていても、内容が学習に適しているとは限らない。C1.3は、毒入れや偶発的な破損、自動ラベルの誤り、安全上問題のある内容、セキュリティ判断に使うモデルの偏りを、異なる保証として扱う。

この文書は学習用であり、Control本文、製品適合判定、Mappingではない。**Normative**はAISVS正規要件、**Research**は脅威と検証例の補足、**Repository interpretation**は現場向けの解釈、**Derived insight**は対話から得た整理である。

## C1における位置づけと用語

C1.1はデータの出所と保管・転送の保護、C1.2はラベル付けの権限と成果物の保護を扱う。C1.3は、**正規のデータでも学習結果を害する内容かもしれない**という次の問題を扱う。受入検査に合格しても、モデル公開後の監視や個々の出力の認可まで保証するわけではない。

- **毒入れ（data poisoning）:** 攻撃者が学習データへ例を混ぜ、後のモデル判断を意図した方向へずらすこと。
- **意図しない破損:** 攻撃ではなく、取り込み・変換・結合などの誤りでデータが壊れること。
- **自動ラベル:** 人が一件ずつ確定せず、別のモデルや規則で付けた学習上の答え。
- **確信度の閾値:** 自動ラベルをどの程度の確からしさで採用するかの基準。ただし、高い数値が真実を証明するわけではない。
- **整合性検査:** ラベルと元データ、別の判定、または関連レコードとの矛盾を調べること。
- **偏りのパターン:** ある集団、入力の種類、表現などに対して、安全上の見逃しや誤判定が偏って発生する傾向。ここでは公平性の議論だけでなく、セキュリティ判断の穴も含めて考える。
- **禁止する内容:** その学習用途へ投入してはいけないと組織が定めた情報や素材。何を禁止するかは、契約、法令、用途、データ取扱方針に照らして具体化する。AISVSが全組織共通の禁止リストを指定しているわけではない。
- **クリーンラベル毒入れ:** 見かけ上、データと答えの組み合わせは正しいまま、特定の合図に反応する危険な癖をモデルへ植え付ける攻撃。

## 具体例と攻撃の通り道

会社は問い合わせを「通常対応」か「不正の疑いあり」に振り分ける分類モデルを追加学習する。外部から集めた例に別モデルが自動で答えを付け、学習用データセットへ取り込む。攻撃者は、実際には通常対応でよい問い合わせを多数投稿し、その文中へ特定の短い句を自然な形で混ぜる。各例の「通常対応」というラベル自体は正しい。しかし後日、攻撃者が不正な問い合わせにも同じ句を入れると、モデルが誤って通常対応へ振り分ける可能性がある。

```text
外部投稿 → 収集・自動ラベル → 学習前検査 → 追加学習 → 不正判定
  攻撃者が操作できる       ↑                  ↑
  データと表現             受入境界            実運用の判断境界
```

同じ処理には、変換時の文字化け、誤った自動ラベル、利用を禁止された個人情報の混入も起こり得る。これらは別の失敗なので、一つの検査で全部を保証したことにはならない。

## 守る線と強制する場所

| 要件 | 守る線 | 主な検査・強制の場所 |
|---|---|---|
| C1.3.1 | 疑わしい毒入れや偶発的な破損を、無検査のまま学習へ渡さない | 収集・変換・投入時のデータ品質／異常検査 |
| C1.3.2 | 自動生成ラベルを、確信度だけで無条件採用しない | 自動ラベルの採用前に行う閾値判定と整合性検査 |
| C1.3.3 | 安全上の判断をするモデルの偏った失敗を、全体平均だけで見逃さない | 評価データと評価ゲートでの層別・条件別の検査 |
| C1.3.4 | 禁止内容を見つけても学習用集合に残す、という状態にしない | 学習データ確定前の検出と除外・隔離 |
| C1.3.5 | 正しいラベルというだけでクリーンラベル毒入れを安全とみなさない | ラベル検査とは別の毒入れ耐性評価と防御 |

**Repository interpretation:** 検査結果があっても、学習がその結果を無視して同じデータを読むなら受入境界は成立しない。疑わしい例の調査、除外、例外承認などの運用は、検査の意味を保つために設計する。ただしAISVSが、全ての疑わしいデータの自動削除や特定の検出アルゴリズムを一律に要求しているという意味ではない。

## Pass／Failと対象範囲

| 観察 | 判定の要点 |
|---|---|
| 自動生成ラベルに確信度の閾値と元データとの整合性検査を設け、矛盾や低確信の例を検出する | 評価した処理ではC1.3.2のPass候補。ただしクリーンラベル毒入れへの防御を示さないので、これだけでC1.3.5はPassしない。 |
| 毒入れ・破損の検出試験はあるが、禁止内容をフラグ付けするだけで学習に投入する | 試験した範囲でC1.3.1はPass候補。C1.3.4はFail。検出と除外の両方が必要。 |
| 不正取引を止めるモデルで全体の正解率だけを測り、条件別の見逃しの偏りを調べない | C1.3.3はFail。セキュリティ判断に使うモデルなのに偏りを評価していない。 |
| FAQへ話題タグを付けるだけで、安全上の判断やアクセス制御にそのタグを使わない | この用途ではC1.3.3は通常N/A。偏りを評価していないことを理由にFailとも、対象外なのにPassとも言わない。後でタグが安全上のゲートに使われれば再評価する。 |
| 正しいラベルの例だけを検査し、特定の句を混ぜた攻撃例に対する防御を試さない | C1.3.5の保証は示せない。ラベルの真偽と、モデルへ植え込まれる振る舞いは別の性質。 |

C1.3.1の検出はすべての毒入れを見つける保証ではなく、C1.3.5の特別な攻撃への保証を代替しない。C1.3.2は自動ラベルの質、C1.3.4は禁止内容の除外であり、目的が違う。C1.3.3はセキュリティ判断に使うモデルへ適用されるが、単なる話題整理などへ機械的に拡大しない。どの要件も、公開後のモデル出力の安全性を単独では保証しない。

## 対話から残す判断

**問い1:** 自動ラベルに確信度の閾値と整合性検査はあるが、クリーンラベル毒入れへの防御・試験はない。C1.3.2とC1.3.5はどう評価するか。

**学習者の判断:** 「pass, fail」。

**整理:** C1.3.2はその仕組みが働く範囲でPass候補。C1.3.5はFail。正しいラベルを検証できても、正しいラベルを付けた例による攻撃は残る。

**問い2:** 毒入れの検出試験はある。一方、禁止内容はフラグ付けするが、そのまま学習へ送る。C1.3.1とC1.3.4はどう評価するか。

**学習者の判断:** 「pass, fail」。

**整理:** 前者は試験した範囲でPass候補、後者はFail。C1.3.4は検出だけでなく、学習対象からの除去を問う。

**問い3:** 不正取引を止めるモデルと、FAQの話題を付けるだけのモデルがある。どちらも全体正解率しか測っておらず、偏りを評価していない。C1.3.3は両方Failか。

**学習者の判断:** 「偏りを評価してないのであればfailなのでは？」

**整理と問いの訂正:** 不正取引を止めるモデルはセキュリティ判断に使うのでFail。一方、FAQの話題付けだけで安全上の意思決定に使わないモデルは、C1.3.3の対象外、すなわちN/A。最初の問いはモデルの役割の違いを十分に強調していなかった。FAQタグが後にアクセス制御や不正検知の入力になるなら、対象範囲を改めて調べる。

## このSectionの本質と設計レビューの問い

**Derived insight:** 学習前の検査は「データは正規経路で届いたか」「ラベルは正しいか」だけでは足りない。**どの失敗を、どの段階で、どの検査が見つけ、学習投入をどう止めるか**を分けて考える。また、偏り評価の要否はモデルの名前や学習方式ではなく、その出力が実際にどの判断を左右するかで決まる。対象外は適合ではない。

- 外部から操作できるデータが学習へ到達する経路と、投入前の検査・除外点はどこか。
- 自動ラベルには確信度の閾値と整合性検査の両方があるか。高確信の誤りも試したか。
- 禁止内容は何を指すか。検出結果が実際の学習用集合へ反映されるか。
- モデルの出力は安全上の判断を左右するか。そうなら、全体平均に隠れる偏りを調べたか。
- 正しいラベルに紛れる攻撃例を、ラベル検査とは別に試したか。
- 検査が通ったことを、運用中のすべての出力が安全である証拠と誤解していないか。
