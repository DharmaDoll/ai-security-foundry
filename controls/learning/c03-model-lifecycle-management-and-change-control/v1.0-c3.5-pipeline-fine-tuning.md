# C3.5 追加学習の受渡しと、点数だけを上げる学習を監視する

## 要件と資料の役割

この文書は講義と対話の記録であり、Control本文、製品適合、Mappingではない。NormativeはAISVS正規要件、Researchは脅威・検証の補足、Repository interpretationは現場向けの解釈、Derived insightは対話から得た整理を指す。

|---|---:|---|---|
| `v1.0-C3.5.1` | 2 | versioned and integrity-verified | RLHFで使うモデルは版を管理し、学習開始前に完全性を検証する。 |
| `v1.0-C3.5.2` | 3 | reward hacking | RLHFの学習段階に、報酬ハッキングや報酬モデルへの過度な最適化の自動検知を含める。 |
| `v1.0-C3.5.3` | 3 | each stage's output | 複数段階の追加学習では、各段階の出力を次の段階が使う前に完全性を検証する。 |
| `v1.0-C3.5.4` | 3 | distinct artifacts | 追加学習のCheckpointを、それぞれ別の成果物として登録する。 |

## C3の中での位置づけ

C3.1は本番で使うモデル一式、C3.2は投入前の評価、C3.3は配備と復旧、C3.4は環境の分離を扱う。C3.5は追加学習の途中にも境界を置き、入力モデル、途中成果物、学習の方向を確認する。

自社でモデルを学習・微調整せず、外部LLMを呼び出すだけの構成では適用範囲を確認する。RAGで文書を渡すこととモデルの追加学習は異なる。C3.5.1とC3.5.2はRLHF、C3.5.3は複数段階の追加学習、C3.5.4は追加学習のCheckpointという対象の違いも保つ。

## 用語と具体例

- **RLHF（Reinforcement Learning from Human Feedback）:** 人の評価を利用する強化学習。ここでは、人の好みを学んだ報酬モデルが回答を採点し、回答するモデルが高得点を取るように学習する例を使う。
- **報酬モデル:** 回答へ点数を付ける採点役のモデル。採点役にも誤りや偏りがある。
- **報酬ハッキング:** 採点方法の抜け道を利用し、本来望んだ結果を改善せずに高得点を取ること。人間の攻撃者が直接操作する場合に限らない。
- **過度な最適化:** 採点役へ合わせすぎた結果、独立した評価や実際の用途で品質が悪化すること。
- **Checkpoint:** 学習途中で保存したモデル。学習の再開、比較、復旧に使う。
- **完全性の検証:** 使おうとする成果物が、信頼できる基準と一致し、想定外に変更されていないか確認すること。内容の安全性や評価品質の保証とは区別する。
- **ハッシュ:** ファイル内容から計算する照合用の値。比較する正解の値まで攻撃者が変更できる構成では十分な検証にならない。

社内問い合わせ用モデルを複数段階で追加学習する。開始前に入力モデルを検証し、学習途中のモデルを個別に登録する。次の段階は登録された成果物を取得してから、使う直前に検証する。

```text
入力モデル → 版・完全性の確認（C3.5.1）
           → 学習中の報酬ハッキング等を自動検知（C3.5.2）
           → 途中モデルを個別に登録（C3.5.4）
           → 次の段階が使う前に完全性を確認（C3.5.3）
```

報酬モデルが「利用者への同意」を過大評価すると、回答するモデルは誤った主張にも同意するようになるかもしれない。点数が上がっても正確さは下がる。この失敗は、ファイルが改ざんされていなくても発生する。

## 脅威と信頼境界

攻撃者が途中の保存領域を変更できる場合、第一段階の成果物を差し替え、第二段階に別のモデルを使わせられる。信頼境界は、保存領域から各学習段階が成果物を取り込む入口である。最初の入力だけを検証しても、後続の受渡しは守れない。

別の失敗は、採点役の弱点へ学習が適応することである。これは改ざんと異なる問題であり、報酬の点数を、本来の品質や安全性と同一視する判断が危険になる。

## 守る線と強制・検知の場所

| 要件 | 守る線 | 主な場所・方法の例 |
|---|---|---|
| C3.5.1 | 版や完全性を確認していないモデルでRLHFを開始しない | 学習開始時の読込み処理で、信頼できる版情報・署名・ハッシュなどと照合する |
| C3.5.2 | 報酬ハッキング等の自動検知を欠いたまま学習しない | 学習中に独立した評価を行い、報酬と品質の食い違いなどを検知する |
| C3.5.3 | 次の段階が、検証していない途中成果物を使わない | 段階ごとの取込み処理が完全性を確認し、不一致なら開始を拒否する |
| C3.5.4 | 途中モデルを区別できない成果物として扱わない | 登録先で各Checkpointを個別に識別する |

Repository interpretationとして、ファイルの照合失敗は学習処理を管理するプログラムで拒否する。モデル自身に検証を任せない。C3.5.2の検知は誤検知や見逃しを持ち得るため、完全検知を主張しない。検知後の停止・採用保留・人による調査は重要な対応設計だが、正規要件が直接求める自動検知と分けて記録する。

## Pass／Failと保証範囲

| 観察 | 評価 |
|---|---|
| 途中モデルは個別登録されているが、次の段階が検証せずに使う | C3.5.3はFail、C3.5.4は登録範囲でPass候補 |
| 改ざんした途中モデルを次の段階へ渡すと、使用前に拒否される | その経路でC3.5.3はPass候補 |
| 学習点数だけを監視し、正確さの低下や迎合との食い違いを自動検知する仕組みがない | C3.5.2はFail |
| 入力の報酬モデルは版管理・完全性検証済みだが、迎合を過大評価する | 品質の問題だけではC3.5.1のFailには直結しない |
| Checkpointを同じ名前で上書きし、各成果物として登録していない | C3.5.4はFail |

個別登録は完全性を証明しない。完全性は内容の安全性を証明しない。報酬モデルの弱点があることだけでC3.5.2を即Failにせず、要件が求める自動検知を評価する。最終モデルの投入前評価はC3.2等で別に扱う。

## 対話の再構成

**問い1:** 学習開始前の入力検証はある。途中モデルは個別登録されているが、第二段階は検証せずに読み込む。C3.5.3とC3.5.4をどう評価するか。

**学習者の判断:** 「fail, pass」。

**整理:** その通り。登録で保存したものを追跡できても、実際に読み込むファイルが登録時の内容と同じかは別に確認する。

**問い2:** 報酬の点数は上がる一方、独立した評価では正確さが下がり、迎合が増える。学習処理はこの食い違いを自動検知しない。

**学習者の判断:** 「Fail」。

**整理:** C3.5.2はFail。採点方法への適応と、本来求める品質の向上を区別する。

**問い3:** 版管理と完全性検証に成功した報酬モデルが、利用者への同意を過大評価する。これでC3.5.1もFailになるか。

**学習者の判断:** 「ならないが、、」。その後「過大評価は問題だよね。どこかで手当てする必要がある」と指摘した。

**整理:** 品質の問題だけではC3.5.1のFailにならないが、問題を放置してよいという意味ではない。予定したモデルを正しく読み込む確認と、採点役が適切に評価する確認が両方必要である。

## 過大評価への実務上の手当て

Repository interpretationとして、学習前に報酬モデル自体を試験する。例えば利用者が誤った主張をするケースで、「正しく訂正した回答」より「迎合した回答」を高く評価しないか調べる。問題があれば評価用データや採点方法を見直す。この試験をC3.5.1の完全性検証へ混ぜない。

学習中にも、報酬モデルとは独立した評価を続ける。「報酬は上がったが、正確さは下がった」という食い違いを自動検知する設計がC3.5.2に関係する。検知後の学習停止や成果物の採用保留まで運用を決めることは追加の実務上の推奨である。

## 洞察とレビューの問い

Derived insight：**正しい採点役を読み込む確認と、その採点役が正しく採点する確認は、両方必要。** 登録、完全性、品質は異なる保証であり、一つが成立しても他の問題を放置できない。

- 入力モデルの版と完全性を、実際の使用前に確認しているか。
- 各段階で改ざんした途中成果物を渡すNegative Testがあるか。
- 照合の基準値は、成果物と一緒に自由に変更できないか。
- 各Checkpointを別の成果物として辿れるか。
- 採点役が迎合や長さなどを過大評価しないか。
- 報酬の点数と独立した評価を比べ、不適切な学習の兆候を自動検知しているか。
- 検知後に誰が何を止め、何を調べるかを決めているか。
