# C4.3 端末・分散環境のAI保護

## 要件と資料の役割

この文書は講義と対話の学習記録であり、Control本文、製品適合、Mappingではない。Normativeは正規要件、Researchは脅威・検証の補足、Repository interpretationは現場向けの解釈、Derived insightは対話から得た整理である。

| ID | Level | 原文を探す短い英語句 | 日本語での意味 |
|---|---:|---|---|
| `v1.0-C4.3.1` | 1 | strong authentication mechanisms | 端末が中央基盤へ接続するとき、強い認証を行う。 |
| `v1.0-C4.3.2` | 2 | cryptographically signed | 端末やモバイルへのモデル配布時に署名し、端末側で読込み・推論前に署名またはチェックサムを検証する。 |
| `v1.0-C4.3.3` | 3 | process, memory, and file access isolation | 推論の実行環境で、プロセス・メモリ・ファイルアクセスを隔離する。 |
| `v1.0-C4.3.4` | 3 | hardware-backed key stores | ローカル保存する重みや機密パラメーターを、ハードウェアに支えられた鍵保管機構またはSecure Enclaveを使って暗号化する。 |
| `v1.0-C4.3.5` | 3 | decrypted only inside | モバイル・IoT・組込みアプリに含むモデルを保存時に暗号化し、信頼された実行環境またはSecure Enclave内だけで復号して、パッケージやファイルシステムからの直接抽出を防ぐ。 |

## C4の中での位置づけと用語

C4.1は実行環境、C4.2はAI用ハードウェア、C4.3は現場端末やモバイルへモデルを配布して動かす場面を扱う。

- **Edge（エッジ）:** ここでは工場の検査端末、カメラ、スマートフォンなど、中央データセンターの外で処理する機器。
- **Runtime（実行環境）:** モデルを読み込み、計算するソフトウェアとその保護境界。
- **チェックサム:** ファイルの内容を照合する値。モデルと正解の値を両方変更できる構成では信用できる検証にならない。
- **ハードウェアに支えられた鍵保管機構:** 専用の保護機構で鍵を扱い、通常のファイルやアプリ内へ鍵を直接置くことと区別する。
- **Secure Enclave:** 通常の実行環境から隔離して機密処理などを行う領域。機能と保護範囲は方式によって異なる。

鍵保管機構が、そのまま大きなモデルの推論も実行できるとは限らない。鍵の保護と推論の保護は構成としてつなぐ必要がある。

## 具体例：工場の検査端末へモデルを配布する

検査端末は中央サーバーからモデルを受け取り、製品の傷を判定する。攻撃者は偽の端末を接続したり、配布経路や端末内のファイルを変更したり、端末とアプリのパッケージを入手したりできると考える。

最初の境界は中央サーバーと端末の間。端末IDの文字列だけで信用せず、端末を認証する。端末ごとの証明書は方法の一例である。次に、使う端末自身がモデルを読み込む前に検証する。中央で検証済みでも、その後の差替えを見逃す可能性がある。

次の境界は端末内部。検査アプリ以外の処理が、検査アプリのメモリやファイルへ自由に触れないよう分離する。「別プロセスとして起動した」という事実だけで分離を証明しない。

最後はモデルの抽出経路。アプリへ暗号鍵を埋め込むと、モデルと一緒に鍵も取り出され得る。鍵を保護していても、復号後のモデルを通常の一時ファイルへ出せば、そこから盗まれる。

```text
配布パッケージには暗号化したモデル
        ↓
保護された鍵を使う
        ↓
信頼された実行環境の中で復号・推論
        ↓
外側のファイルへ平文モデルを残さない
```

## 守る線と強制する場所

| 要件 | 守る線 | 主な確認・強制の場所 |
|---|---|---|
| C4.3.1 | 端末の自己申告だけで中央基盤へ受け入れない | 中央基盤の端末認証 |
| C4.3.2 | 署名したという事実だけで、未検証の配布物を使わない | 端末側のモデル読込み・推論前の照合 |
| C4.3.3 | 推論処理がほかの処理のメモリ・ファイルへ自由に触れない | OS・実行環境の権限と隔離機構 |
| C4.3.4 | モデルと一緒に取得できる鍵だけで保存時保護を説明しない | ローカル保存の暗号化とハードウェア側の鍵保護 |
| C4.3.5 | 復号したモデルを取得可能な場所へ出さない | 復号から推論までの経路、キャッシュ、一時保存 |

暗号化は読出し、署名は改ざん、隔離は他の処理からのアクセスを主に扱う。それぞれ別の失敗を防ぐ。

## Pass／Failと保証範囲

| 観察 | 評価 |
|---|---|
| 端末ごとの証明書で適切に認証するが、モデルの署名・チェックサムを端末側で検証しない | 提示した条件でC4.3.1はPass候補、C4.3.2はFail |
| 鍵はハードウェアで保護するが、取得可能な一時ファイルへ平文モデルを書き出す | C4.3.5はFail。鍵保護だけで復号後の保護を説明できない |
| 署名と暗号化は適切だが、推論処理がほかのアプリのメモリ・ファイルへ自由にアクセスする | C4.3.3はFail |
| モデルを改ざんすると端末が使用前に拒否し、隔離した推論処理の境界外アクセスも拒否される | 試験した範囲でC4.3.2・C4.3.3はPass候補 |

認証は端末の健全性をすべて証明しない。正しい署名はモデルの安全な振る舞いを証明しない。鍵保管機構の保護は推論中の平文の保護を自動的に保証しない。物理的に端末を持つ攻撃者に対する保護範囲も明示する。中央APIだけを呼ぶアプリと、ローカルにモデルを配布するアプリでは適用範囲が違う。

## 対話の再構成

**問い1:** 端末ごとの証明書で認証し、モデルには配布時の署名がある。ただし端末は署名・チェックサムを検証せずに読み込む。

**学習者の判断と比較:** 「Pass,Fail」。スマホゲームと同様に、クライアントへ重要なファイルと実行を渡すため、似た対策が必要だと指摘した。

**整理:** 端末認証とモデル検証は別の保証。ゲームのコンテンツ抽出・クライアント改造に対し、AIではモデル盗用・判定改変・機密データ取得を考える。

**問い2:** 鍵はハードウェアで保護するが、復号したモデルを取得可能な一時ファイルへ書き出す。

**学習者の判断:** 「Fail」。

**整理:** C4.3.5はFail。鍵の保管場所だけでなく、復号したモデルがどこを通り、どこに残るかを見る。

**問い3:** 署名・暗号化は適切だが、推論処理はほかのアプリのファイルやメモリへ自由にアクセスできる。

**学習者の判断:** 「Fail。分離することが求められる」。

**整理:** C4.3.3はFail。モデルの保護と実行権限の制限は別に必要である。

## 洞察：スマホゲームのセキュリティとの共通点

Derived insight：**攻撃者が触れる端末へ、価値のあるファイルと実行処理を渡す。** この構造はスマホゲームと端末上のAIに共通する。署名、暗号化、鍵保護、実行時隔離は、そのどの攻撃経路を制限するかで整理できる。

ゲームで勝敗や課金の最終判断をサーバーへ置くように、AIでも端末の判定をそのまま重要操作の許可に使わない設計が考えられる。これはC4.3の直接の要求を超える設計上の洞察である。オフライン要件や遅延などにより中央へ判断を置けない場合もあり、端末の保護を不要とするものではない。

## 設計レビューの問い

- 無効な端末証明書や未登録端末は中央基盤で拒否されるか。
- モデルを差し替えると端末側が使用前に拒否するか。
- 照合する正解の値や信頼する鍵は、配布物と一緒に自由に変更できないか。
- 推論処理から境界外のファイルやメモリへアクセスできないか。
- 暗号鍵をアプリや設定から取り出せないか。
- パッケージ、キャッシュ、一時ファイルに平文モデルが残っていないか。
- 端末内の判定を重要操作へ使うとき、どこで別の認可を行うか。
