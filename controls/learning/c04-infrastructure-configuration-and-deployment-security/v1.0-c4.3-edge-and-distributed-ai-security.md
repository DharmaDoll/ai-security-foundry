### v1.0-C4.3.1

AISVS Verification Level: 1

> Verify that edge AI devices authenticate to central infrastructure using strong authentication mechanisms.

**意味を保った日本語訳:** Edge AI端末が、強い認証機構を使って中央基盤に対して認証することを検証する。

### v1.0-C4.3.2

AISVS Verification Level: 2

> Verify that models deployed to edge or mobile devices are cryptographically signed during packaging, and that the on-device runtime validates these signatures or checksums before loading or inference.

**意味を保った日本語訳:** EdgeまたはMobile端末へ配備されるModelがPackaging時に暗号学的に署名され、端末上のRuntimeが読込または推論前にその署名またはChecksumを検証することを確認する。

### v1.0-C4.3.3

AISVS Verification Level: 3

> Verify that inference runtimes enforce process, memory, and file access isolation.

**意味を保った日本語訳:** 推論Runtimeが、Process、Memory、Fileアクセスの隔離を強制することを検証する。

### v1.0-C4.3.4

AISVS Verification Level: 3

> Verify that model weights and sensitive parameters stored locally are encrypted using hardware-backed key stores or secure enclaves.

**意味を保った日本語訳:** Local保存されるModel重みと機密Parameterが、Hardware-backed Key StoreまたはSecure Enclaveを使って暗号化されることを検証する。

### v1.0-C4.3.5

AISVS Verification Level: 3

> Verify that models packaged within mobile, IoT, or embedded applications are encrypted at rest, and decrypted only inside a trusted runtime or secure enclave, preventing direct extraction from the app package or filesystem.

**意味を保った日本語訳:** Mobile、IoT、組込みアプリ内にPackageされるModelが保存時に暗号化され、Trusted RuntimeまたはSecure Enclave内でのみ復号されることで、アプリPackageやFile Systemからの直接抽出を防ぐことを検証する。

## C4の中での位置づけと用語

C4.1は実行環境、C4.2はAI用ハードウェア、C4.3は現場端末やモバイルへモデルを配布して動かす場面を扱う。

- **Edge（エッジ）:** ここでは工場の検査端末、カメラ、スマートフォンなど、中央データセンターの外で処理する機器。
- **Runtime（実行環境）:** モデルを読み込み、計算するソフトウェアとその保護境界。
- **チェックサム:** ファイルの内容を照合する値。モデルと正解の値を両方変更できる構成では信用できる検証にならない。
- **ハードウェアに支えられた鍵保管機構:** 専用の保護機構で鍵を扱い、通常のファイルやアプリ内へ鍵を直接置くことと区別する。
- **Secure Enclave:** 通常の実行環境から隔離して機密処理などを行う領域。機能と保護範囲は方式によって異なる。

鍵保管機構が、そのまま大きなモデルの推論も実行できるとは限らない。鍵の保護と推論の保護は構成としてつなぐ必要がある。

## 具体例：工場の検査端末へモデルを配布する

検査端末は中央サーバーからモデルを受け取り、製品の傷を判定する。攻撃者は偽の端末を接続したり、配布経路や端末内のファイルを変更したり、端末とアプリのパッケージを入手したりできると考える。

最初の境界は中央サーバーと端末の間。端末IDの文字列だけで信用せず、端末を認証する。端末ごとの証明書は方法の一例である。次に、使う端末自身がモデルを読み込む前に検証する。中央で検証済みでも、その後の差替えを見逃す可能性がある。

次の境界は端末内部。検査アプリ以外の処理が、検査アプリのメモリやファイルへ自由に触れないよう分離する。「別プロセスとして起動した」という事実だけで分離を証明しない。

最後はモデルの抽出経路。アプリへ暗号鍵を埋め込むと、モデルと一緒に鍵も取り出され得る。鍵を保護していても、復号後のモデルを通常の一時ファイルへ出せば、そこから盗まれる。

```text
配布パッケージには暗号化したモデル
        ↓
保護された鍵を使う
        ↓
信頼された実行環境の中で復号・推論
        ↓
外側のファイルへ平文モデルを残さない
```

## 守る線と強制する場所

| 要件 | 守る線 | 主な確認・強制の場所 |
|---|---|---|
| C4.3.1 | 端末の自己申告だけで中央基盤へ受け入れない | 中央基盤の端末認証 |
| C4.3.2 | 署名したという事実だけで、未検証の配布物を使わない | 端末側のモデル読込み・推論前の照合 |
| C4.3.3 | 推論処理がほかの処理のメモリ・ファイルへ自由に触れない | OS・実行環境の権限と隔離機構 |
| C4.3.4 | モデルと一緒に取得できる鍵だけで保存時保護を説明しない | ローカル保存の暗号化とハードウェア側の鍵保護 |
| C4.3.5 | 復号したモデルを取得可能な場所へ出さない | 復号から推論までの経路、キャッシュ、一時保存 |

暗号化は読出し、署名は改ざん、隔離は他の処理からのアクセスを主に扱う。それぞれ別の失敗を防ぐ。

## Pass／Failと保証範囲

| 観察 | 評価 |
|---|---|
| 端末ごとの証明書で適切に認証するが、モデルの署名・チェックサムを端末側で検証しない | 提示した条件でC4.3.1はPass候補、C4.3.2はFail |
| 鍵はハードウェアで保護するが、取得可能な一時ファイルへ平文モデルを書き出す | C4.3.5はFail。鍵保護だけで復号後の保護を説明できない |
| 署名と暗号化は適切だが、推論処理がほかのアプリのメモリ・ファイルへ自由にアクセスする | C4.3.3はFail |
| モデルを改ざんすると端末が使用前に拒否し、隔離した推論処理の境界外アクセスも拒否される | 試験した範囲でC4.3.2・C4.3.3はPass候補 |

認証は端末の健全性をすべて証明しない。正しい署名はモデルの安全な振る舞いを証明しない。鍵保管機構の保護は推論中の平文の保護を自動的に保証しない。物理的に端末を持つ攻撃者に対する保護範囲も明示する。中央APIだけを呼ぶアプリと、ローカルにモデルを配布するアプリでは適用範囲が違う。

## 設計演習：配布から復号後までを一つの経路で追う

以下はRepositoryによる追加教材であり、実製品の試験結果ではない。各試験の期待結果とEvidence候補を示す。

既存の工場端末Scenarioでは、攻撃者が端末・配布Package・Local Fileを入手できる場合を考える。
Device認証、配布物の完全性、Runtime隔離、保存時の鍵保護、復号後の露出は別の防御である。

### C4.3.1：端末の自己申告を認証にしない

端末IDやIPが同じだけでは正規端末を証明しない。強いCredentialを登録し、中央接続で検証する。
証明書を使う方式は一例であり、製品全体へ特定Protocolや固定有効期間を要求するものではない。

- **正常系:** 登録済み端末が更新・参照など許可した接続を行える。
- **Negative Test:** 未登録端末、期限切れ・失効Credential、IDだけ複製した端末を接続させ、拒否を観測する。
- **Evidence・境界:** 登録・更新・失効と認証結果。認証済みであることは端末の全Softwareが健全な証拠でも、全操作の認可でもない。

### C4.3.2：Packagingの署名と端末側の使用前検証を両方見る

原文は配布時署名と、端末Runtimeによる署名またはChecksum検証を区別している。
Checksumの期待値をPackageと一緒に自由に書き換えられるなら、信頼できる照合にならない。

- **正常系:** 署名した配布物を端末側が読込・推論前に検証し、正規更新が動く。
- **Negative Test:** 一Fileの変更、Cacheの差替え、照合値の同時置換、検証後の再取得を試す。中央側の検証だけで終わらないかを見る。
- **Evidence・境界:** Package版、署名対象、信頼する期待値、端末検証と実読込内容。署名が有効でも内容の安全性やReleaseの新しさまで示すとは限らない。

### C4.3.3：別Processという事実とアクセス隔離を分ける

Model実行Processと、端末上の他Processの間にあるMemory・File・操作権限を列挙する。
ServerのContainer設定をそのまま全Mobileへ要求するのではなく、対象OSの境界で確かめる。

- **正常系:** 推論が必要な資源へだけアクセスでき、他アプリも正常に動く。
- **Negative Test:** 隔離した端末試験環境で、推論Processから境界外File・Memoryへ無害なProbeを行う。逆向きの参照経路も保護Scopeに応じて確認する。
- **Evidence・境界:** OS権限、Sandbox設定、Read／Write・Process操作結果。名前やProcess分割だけを完全な分離Evidenceにしない。

### C4.3.4：保存物と鍵の両方を持ち出しても復号できないか

Hardware-backed Key Storeは鍵をHardwareの保護機構に結び付ける仕組み。
大きいModel全体をKey Store内へ保存する必要はなく、Data鍵を保護鍵でWrapする構成もある。

- **正常系:** 正規端末が必要な重み・機密Parameterを暗号化保存し、必要時に利用できる。
- **Negative Test:** Ciphertextと鍵Metadataを別端末へコピーし、アプリ内の埋込鍵や平文Data鍵で復号できないか試す。API名だけでHardware保護を推定しない。
- **Evidence・境界:** 保存対象、鍵の保護経路、Platform Evidence、復号試験。保存時保護は復号後のMemory全体の保護とは別。

### C4.3.5：復号後の平文がTrusted Runtimeの外へ出ないか

Trustedの意味を、誰のアクセスからどこまで守るかとして具体化する。
鍵がHardware保護されても、通常の一時Fileへ復号すればPackage抽出とは別の経路で盗まれる。

- **正常系:** 暗号化Packageから定義した保護Runtime内で復号・推論する。
- **Negative Test:** Package展開、更新Staging、Cache、一時File、Dumpを調べ、平文の残存・外側への書出しを確認する。
- **Evidence・境界:** 暗号化保存から復号・推論・破棄までの経路と観測。物理所有者への全耐性を主張せず、DebugやRuntime侵害の未評価範囲を明記する。

### 運用・Researchと残余リスク

ResearchはCredential Lifecycle、端末検証、鍵保護と復号後の経路を補足する。
端末の更新・Offline期間・証明書更新失敗時に、検証を省略して動かすFallbackが生じないかを見る。
鍵更新、回収、性能の制約も設計し、保存暗号化の成功をRuntime保護の成功へ広げない。

**追加演習:** 同じ原則をMobile向け音声Modelへ適用し、配布Cacheと復号済み一時Fileのどちらが、どの要件のEvidenceに必要かを整理する。

## 対話の再構成

**問い1:** 端末ごとの証明書で認証し、モデルには配布時の署名がある。ただし端末は署名・チェックサムを検証せずに読み込む。

**学習者の判断と比較:** 「Pass,Fail」。スマホゲームと同様に、クライアントへ重要なファイルと実行を渡すため、似た対策が必要だと指摘した。

**整理:** 端末認証とモデル検証は別の保証。ゲームのコンテンツ抽出・クライアント改造に対し、AIではモデル盗用・判定改変・機密データ取得を考える。

**問い2:** 鍵はハードウェアで保護するが、復号したモデルを取得可能な一時ファイルへ書き出す。

**学習者の判断:** 「Fail」。

**整理:** C4.3.5はFail。鍵の保管場所だけでなく、復号したモデルがどこを通り、どこに残るかを見る。

**問い3:** 署名・暗号化は適切だが、推論処理はほかのアプリのファイルやメモリへ自由にアクセスできる。

**学習者の判断:** 「Fail。分離することが求められる」。

**整理:** C4.3.3はFail。モデルの保護と実行権限の制限は別に必要である。

## 洞察：スマホゲームのセキュリティとの共通点

Derived insight：**攻撃者が触れる端末へ、価値のあるファイルと実行処理を渡す。** この構造はスマホゲームと端末上のAIに共通する。署名、暗号化、鍵保護、実行時隔離は、そのどの攻撃経路を制限するかで整理できる。

ゲームで勝敗や課金の最終判断をサーバーへ置くように、AIでも端末の判定をそのまま重要操作の許可に使わない設計が考えられる。これはC4.3の直接の要求を超える設計上の洞察である。オフライン要件や遅延などにより中央へ判断を置けない場合もあり、端末の保護を不要とするものではない。

## 設計レビューの問い

- 無効な端末証明書や未登録端末は中央基盤で拒否されるか。
- モデルを差し替えると端末側が使用前に拒否するか。
- 照合する正解の値や信頼する鍵は、配布物と一緒に自由に変更できないか。
- 推論処理から境界外のファイルやメモリへアクセスできないか。
- 暗号鍵をアプリや設定から取り出せないか。
- パッケージ、キャッシュ、一時ファイルに平文モデルが残っていないか。
- 端末内の判定を重要操作へ使うとき、どこで別の認可を行うか。
