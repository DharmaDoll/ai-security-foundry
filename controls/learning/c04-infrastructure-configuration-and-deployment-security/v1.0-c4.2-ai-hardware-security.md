# C4.2 AIハードウェアの保護

## Normative Requirements

対象はAISVS v1.0（採用済み安定版の固定Revision `78775233666a2022dcfb82037e5e029116955c00`）。

### v1.0-C4.2.1

AISVS Verification Level: 2

> Verify that AI accelerator (GPU) firmware is version-pinned, signed, and attested at boot.

**意味を保った日本語訳:** AI Accelerator（GPU）のFirmwareが、版固定され、署名され、起動時にAttestationされることを検証する。

### v1.0-C4.2.2

AISVS Verification Level: 3

> Verify that execution within a trusted execution environment (TEE) provides hardware-enforced isolation, memory encryption, and integrity protection.

**意味を保った日本語訳:** Trusted Execution Environment（TEE）内の実行が、Hardwareによる隔離、Memory暗号化、完全性保護を提供することを検証する。

### v1.0-C4.2.3

AISVS Verification Level: 3

> Verify that AI accelerator (GPU) integrity is validated using hardware-based attestation mechanisms before each workload executes.

**意味を保った日本語訳:** 各Workloadの実行前に、Hardwareに基づくAttestation機構を使ってAI Accelerator（GPU）の完全性が検証されることを確認する。

### v1.0-C4.2.4

AISVS Verification Level: 3

> Verify that accelerator (GPU) memory is isolated between workloads through partitioning mechanisms with memory sanitization between jobs.

**意味を保った日本語訳:** Job間のMemory Sanitizationを伴うPartition機構によって、Accelerator（GPU）のMemoryがWorkload間で隔離されることを検証する。

### v1.0-C4.2.5

AISVS Verification Level: 3

> Verify that accelerator interconnects are restricted to approved topologies and authenticated endpoints.

**意味を保った日本語訳:** Accelerator間接続が、承認済みTopologyと認証されたEndpointへ制限されることを検証する。

## C4における位置づけと具体例

C4.1はAIの実行環境、C4.2はその下にある機器とメモリ、C4.3は現場端末への配備を扱う。社内の複数部門がGPUサーバーを共同利用する例で考える。午前は人事部が機密文書を処理し、午後は開発部が外部モデルを試す。

確認箇所は五つある。GPUの中で動く制御プログラムは承認したものか。使用中のメモリを外から読んだり書き換えたりできないか。今回の処理を始める時点でも機器は適切か。前の処理のデータが次の部門へ残っていないか。複数GPUが意図した相手とだけ通信するか。

## 用語

- **アクセラレーター:** AIの計算などを高速化する機器。GPUはその一例。
- **ファームウェア:** 機器内部で動き、機器を制御するプログラム。
- **Attestation:** 機器や実行環境の状態について証拠を得て、承認した状態と照合する仕組み。
- **Workload／Job:** ここでは、モデルを動かす一まとまりの処理。
- **トポロジー:** 機器同士をどう接続するかという構成。
- **完全性保護:** 想定外の書換えを防ぐ、または検出すること。

**TEE（Trusted Execution Environment）は、保護された実行環境である。** プログラムやデータを周囲から隔離して処理する。クラウドのホスト管理者が強い権限を持っていても、ハードウェアの保護機構で内部へのアクセスを制限する構成がある。

イメージは「建物の管理者でも中を覗けない、施錠された作業室」。室内のプログラムはデータを使えるが、室外からの読出しや書換えを制限する。ただしTEEは総称であり、実際の保護範囲は方式によって異なる。C4.2.2では、名前だけでなく隔離・暗号化・完全性保護をそれぞれ確認する。室内のプログラムが情報を外へ送る問題は別に守る。

## 脅威の通り道

攻撃者が隣のJobを実行できる場合、他の部門のGPUメモリや、終了後に残った内容を読もうとする。別の脅威では、機器の管理経路や接続先を操作し、未承認のファームウェアや機器へ機密データを渡させる。信頼境界は、起動時、各処理の開始前、処理間のメモリ、機器間の通信にある。

## 守る線と確認・強制の場所

| 要件 | 守る線 | 確認・強制の場所 |
|---|---|---|
| C4.2.1 | 承認していないファームウェアを正常な起動状態として扱わない | 版設定、署名検証、起動時の証拠照合 |
| C4.2.2 | TEEという名称だけで三つの保護が成立したと判断しない | ハードウェア設定と証拠、外側からのアクセス試験 |
| C4.2.3 | 起動時の過去の証拠だけで各処理前の検証を代替しない | 各処理前の証拠取得と検証 |
| C4.2.4 | 実行中の隣の処理にも、後から使う処理にもデータを渡さない | メモリ分割とJob切替時の消去 |
| C4.2.5 | 未承認の接続構成や未認証の相手へ機器間通信を許さない | 接続設定と接続先認証 |

Repository interpretationとして、証拠の不合格時に処理開始や鍵配布を拒否する構成が考えられる。検証と、その結果を使う実行制御をつなぐ。機器の機能名だけでなく、対象の構成で保証する性質を確認する。

## Pass／Failと保証範囲

| 観察 | 評価 |
|---|---|
| ファームウェアは承認版、署名・起動時の検証もあるが、Job前には検証しない | C4.2.1は提示条件でPass候補、C4.2.3はFail |
| 実行中はメモリを分離するが、Job終了後に前の人事文書を次のJobが読める | C4.2.4はFail |
| 承認済みの機器間接続と接続先認証があるが、TEEにメモリ暗号化がない | C4.2.5は提示条件でPass候補、C4.2.2はFail |
| 次のJobで既知の試験データを探索しても取得できず、実行中の相互アクセスも拒否される | 試験した範囲でC4.2.4はPass候補 |

署名が正しくても承認した版かは別の確認。メモリを解放しても中身を消したとは限らない。メモリ分離やTEEは、モデルの安全な出力やアプリケーションの認可を保証しない。ハードウェアの攻撃範囲や残る脇道は、方式ごとに確認する。クラウド利用者は自分で機器を設定できない場合でも、Providerの責任範囲と得られる証拠を確認する。

## 設計演習：起動・各Job・同時利用・引渡しを分ける

以下はRepositoryによる追加教材であり、実製品の試験結果ではない。各試験の期待結果とEvidence候補を示す。

既存の人事部と開発部がGPUを共有する例で、同時に使う隣のJobと、次に使うJobを別の攻撃者として考える。
起動時の検証は各Job前の検証と違い、通信の暗号化はDevice常駐Memoryの暗号化とも違う。

### C4.2.1：承認版、署名、起動時の証拠を三つとも見る

FirmwareはGPU内部の制御Program。署名が正しい旧版や、管理画面の表示だけを承認状態の証拠にしない。
固定した版と実測値、署名のTrust Root、Boot時の検証結果を対応付ける。

- **正常系:** 承認版で起動し、署名とBoot Attestationが成立する。
- **Negative Test:** 承認外の正規署名版、無効署名、古い起動Reportを試す。設定値だけでなく実機Evidenceの判定を観測する。
- **Evidence・境界:** 機器Identity、承認版、測定版、署名・起動判定。起動後の全Jobの完全性をこれだけで主張しない。

### C4.2.2：TEEの三つの性質を機種・Modeごとに確認する

必要な性質はHardwareによる隔離、Memory暗号化、完全性保護。
CPU-GPU間Bufferの暗号化があっても、GPU常駐Memoryも暗号化されるとは限らない。

- **正常系:** 対象構成で三性質を裏付けるEvidenceが得られ、必要な推論も動く。
- **Negative Test:** 一性質のないMode、Debug設定、対象外Memoryを残す構成を比較し、CCという製品名だけで合格にしない。
- **Evidence・境界:** 機種・Firmware・Driver・Mode、保護対象のMemory、機能別の根拠。名前から全Memory暗号化や全Side Channel耐性を推定しない。

### C4.2.3：今回使う機器を各Workload前に検証する

古いReportや別GPUのReportをReplayできると、今回の実行環境を確認したことにならない。
Hardwareに基づく証拠、対象Identity、鮮度、許可基準を結び付ける。

- **正常系:** 各Jobの前に、割り当てた実GPUの証拠を検証する。
- **Negative Test:** Job間で機器を変更する、旧証拠を再提示する、不許可の測定値を返すケースで、検証・鍵配布等の接続を観測する。
- **Evidence・境界:** Workload ID、機器Identity、証拠・基準版、検証時点。Nonceや失敗時の鍵配布停止は実装例であり、原文の固定Protocolではない。

### C4.2.4：同時アクセスと次利用者への残存を独立に試す

Partitionは資源を分ける仕組み、Sanitizationは引渡し前に残る情報を消去・無害化する処理。
Memory FreeというAPIが返ることだけで、前利用者のDataが読めないとは言えない。

- **正常系:** 二つのJobが必要な計算を行え、境界を越えたRead／Writeができない。
- **Negative Test:** 無害な既知Patternを前Jobで書き、通常終了・異常終了・Job切替後に次Jobから探す。同時にPeer Memory経路のアクセスも試す。
- **Evidence・境界:** 分割設定、書込場所、終了条件、消去・探索結果。単一の探索で未取得だったことを全Memory・全攻撃の不在証明にしない。

### C4.2.5：Topologyの承認と接続相手の認証を分ける

TopologyはGPUやSwitchをどう結ぶかという構成。
暗号化されたLinkでも未承認のPeerへ繋がるなら、接続の許可範囲を示せない。

- **正常系:** 承認した機器とRouteだけで正常処理が成立する。
- **Negative Test:** 未認証Peer、承認外Link、管理経路からのRoute追加を試し、接続拒否と構成差分を観測する。
- **Evidence・境界:** 承認構成、実Inventory、相手Identity、接続結果。特定Interconnect仕様の全機能を原文の必須条件として追加しない。

### 運用・Researchと残余リスク

ResearchはHardware方式の差、転送暗号化と常駐Memory、残存情報、機器接続の問題を補足する。
Firmware・Driver・Mode更新時には基準値とJob前検証を再確認し、失敗を無効化してAvailabilityを戻す例外経路を点検する。
Cloud利用者が実機Probeを実行できない場合、Providerの責任範囲と機能別Evidenceを確認し、未確認をPassへ変えない。

**追加演習:** メモリPartitionが有効でも異常終了後に既知Patternが残った場合、同時隔離と引渡しのどちらにGapがあるか。

## 対話の再構成

**問い1:** 起動時の確認はあるが、各Job前には起動時の結果を使い続ける。

**学習者の判断:** 「Pass,Fail」。

**整理:** C4.2.1とC4.2.3は確認時点が異なる。

**問い2:** 実行中のメモリは分離されるが、次のJobが前の人事文書の断片を読める。

**学習者の判断:** 「Fail」。

**整理:** 同時に隣の部屋を覗けないことと、次に入った人が前の資料を読めないことの両方が必要。

**問い3:** 接続構成・接続先認証はある。一方、TEEの隔離と書換え保護はあっても、メモリ暗号化がない。

**学習者の判断と疑問:** 「Pass,Fail。TEEって何ですか？」。

**整理:** C4.2.5はPass候補、C4.2.2はFail。TEEを保護された作業室として説明し、名称と実際の保護性質を分けた。学習者は説明後に理解を確認した。

## 洞察と設計レビューの問い

Derived insight：**同時に使う人との境界と、次に使う人との境界は別に守る。** この考え方はGPU以外の共有メモリ、一時保存領域、再利用する実行環境にも応用できる。

- ファームウェアは承認版で、署名と起動時の証拠を確認できるか。
- 起動時と各処理前の検証を区別しているか。
- TEEの隔離、暗号化、完全性保護を別々に確認したか。
- 隣のJobのメモリを読む試験と、終了後の残りを読む試験があるか。
- 機器間の接続構成と接続先認証を確認できるか。
- Providerが担当する保証と、自分たちが確認できる証拠を明示したか。
