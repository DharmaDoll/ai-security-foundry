# 共有資源の再利用は、次の利用者への安全な引渡しである

## 中心となる洞察

実行中の二つの処理を分離できても、終了した処理の状態が次の処理へ残ることがある。
共有資源には、同時利用者間の境界に加えて、前の利用者から次の利用者へ切り替わる時の境界がある。

> 隣の利用者から守る試験と、次の利用者へ残さない試験を分ける。

これは既存の資源再利用・状態初期化の問題である。AIではモデル、Adapter、会話Context、GPUメモリなど、
再利用される状態が複数の層に分かれ、Request終了だけでは引渡しの完了を判断しにくい。

## 再利用できるモデル

```text
Aが利用中
  -> Aの処理を停止し、遅延した書込みも止める
  -> 残存状態を消去／無効化し、所有者と設定を切り替える
  -> Bへ渡せる条件を確認する
  -> Bが利用開始

途中で失敗 -> Bへ割り当てず、隔離・再初期化・調査へ
```

これは状態遷移を考えるモデルであり、特定の消去方式を指定するものではない。
再割当ての条件は、前利用者の秘密・権限・設定が次の利用者から到達不能であることとして定める。
意図して共有する状態は、共有のPolicyと所有範囲を別途明示する。

## 具体例

| 再利用する資源 | 引渡しで見落としやすい状態 | 起こり得る失敗 |
|---|---|---|
| GPUの処理領域 | 前Jobの入力や中間データ | 次のJobが機密断片を取得する |
| 推論Worker | Adapter、会話Context、Tenant設定 | Bの要求へAの設定や内容が混ざる |
| Tool実行環境 | 一時ファイル、認証情報、遅延処理 | Bの処理がAの権限や成果物を使う |

これらは一般化した設計上の失敗例であり、個別製品の脆弱性を主張しない。
「メモリを解放した」「プロセスを終了した」という操作名だけで、次の利用者から読めないとは判断しない。

## 設計レビューと検証への応用

- 割当て、実行、終了、清掃、再割当ての各状態と担当する強制点を示す。
- 正常終了だけでなく、Crash、Timeout、Cancel、清掃失敗、再試行を通した引渡しを確認する。
- Aへ既知の非機密な試験データを入れ、Bが利用可能な経路から取得できないことを試す。
- Aの遅延処理が、Bへの再割当て後に書込みや副作用を起こせないことを試す。
- 清掃失敗時にはBへ渡らず、正常な清掃後にはBの正規処理が動くことを確認する。
- 割当ての世代、清掃結果、再割当て可否を追跡し、ログ自体へ前利用者の秘密を記録しない。

## 限界と関連Artifact

試験データを取得できなかった一回の結果は、全メモリ領域やSide Channelの不存在を証明しない。
資源ごとの保護方式、Providerとの責任分界、確認できない範囲を残す。
可用性との調整は必要だが、清掃が未確認の状態を成功として再割当てする理由にはしない。

- [Tenant間の観測と干渉](shared-isolation-means-no-observation-or-interference.md)は共有中の情報伝達を広く扱う。本書は**利用者切替時の引渡し条件**を掘り下げる。
- [利用停止・消去・再出現防止](retirement-is-more-than-deletion.md)は保存済みStateの終了を扱う。本書は資源を次の処理へ渡す状態遷移を扱う。
- [PrivilegeのLifecycle](privilege-is-a-lifecycle-not-a-token-field.md)と併せて、Dataだけでなく権限の残留も確認する。

## Slide-ready summary

- 同時に読めないことと、次に読めないことは別。
- 終了の通知だけで、安全な引渡しは完了しない。
- 再割当て前の条件と、清掃失敗時の扱いを設計する。
