# 復旧するのはファイルではなく、整合したシステムの状態

## 中心となる洞察

モデルの重みを旧版へ戻しても、Adapter、安全性設定などが新版のままなら、以前の状態へ戻ったとは限らない。
各部品が個別に正しいことと、組み合わせが検証済みであることは別である。

> 復旧の完了は、戻したファイルではなく、戻った組み合わせで判断する。

これは構成管理や依存関係を含めた復旧という既存の問題である。AIでは、重み以外の設定、追加学習用部品、
外部サービスや実行中の状態も振る舞いへ影響し、「モデルの版」だけでは復旧対象を表せない場合がある。

## 具体例

新版モデルの問題を検知し、旧版の重みへ戻す。しかし安全性モデルの設定は新版のまま残った。
旧重みと新設定の組み合わせを試験していなければ、既知の旧版へ戻ったとは説明できない。
個々のファイルの署名が正しいことも、組み合わせの妥当性を証明しない。

```text
検証した旧版：旧重み ＋ 旧Adapter ＋ 旧設定
        ↓ 新版で問題が発生
不完全な復旧：旧重み ＋ 新Adapter ＋ 新設定
必要な確認  ：対象部品と依存関係が、承認した復旧構成へ揃ったか
```

## 再利用できるモデル

復旧対象を、部品ごとの独立した版番号ではなく、互換性を確認する範囲として定義する。
その範囲に何を含めるかは、実際に振る舞いを決める依存関係から判断する。

| 場面 | 復旧で整合性を確認する組み合わせの例 |
|---|---|
| モデルの配備 | 重み、Adapter、Tokenizer、設定、安全性用モデル |
| RAGの変更 | Embeddingモデル、対応するIndex、検索設定 |
| Agentの変更 | 実行コード、Toolの入出力仕様、それに依存する設定 |

最初の行はC3.3の学習を起点とし、残りはRepositoryによる応用例である。列挙したすべてを常に一括で戻すという意味ではない。
変更しない部品との互換性を確認できる場合もある。権限失効や緊急の安全設定を、古い状態へ機械的に巻き戻さない。

## 設計レビューと検証への応用

- 復旧単位に含める部品と版、外部依存、互換性条件を記録する。
- 復旧操作の完了通知と、実際にロードされた構成の一致を分けて確認する。
- 一部の部品だけを戻し損ねる試験を行い、不整合を成功扱いしないかを見る。
- 復旧途中にも要求が来る場合、混合状態で処理しない切替・停止の方法を決める。
- 構成の照合に加え、正規処理と重要な拒否動作を確認する。
- 外部APIを旧版へ戻せない場合は代替先や停止方法を定め、戻せない依存を明示する。

## 限界と隣接する洞察

以前の構成が、現在の脅威や入力に対しても安全とは限らない。撤回済みモデルや脆弱な依存へ戻すことを、
過去に動いていたという理由だけで正当化しない。復旧で、既に行った送金や外部送信などの副作用も自動的には戻らない。

- [共有資源の安全な引渡し](resource-reuse-is-a-security-handoff.md)：前利用者の状態を次利用者へ残さない条件を扱う。
- [実際に利用されるPayloadを検査する](validation-must-cover-effective-payload.md)：検査対象と使用対象の対応を扱う。
- 本書：復旧時の部品間の整合性と、復旧完了の判定を扱う。

## Slide-ready summary

- 個別に正しい部品でも、組み合わせは未検証かもしれない。
- 復旧対象は依存関係で定義し、実際に動く構成を照合する。
- 過去の構成への復旧と、現在の安全性の確認は別に行う。
