# 端末で推論できることと、重要操作を許可できることは別である

## 中心となる洞察

攻撃者が操作できる端末へモデルと実行処理を渡すとき、モデルを盗ませない対策、推論処理を改変させない対策、
推論結果で重要操作を許可する判断を分ける。モデルの署名や暗号化が適切でも、中央基盤が受け取る判定結果まで
正しいとは限らない。

> 推論を端末へ置いても、その判定に伴う権限まで無条件に端末へ渡さない。

これは、スマホゲームでクライアントの申告だけを勝敗や課金の最終判断にしない考え方との共通点である。
AIでは保護対象にモデルの重みや機密入力が加わり、推論結果自体にも誤判定があり得る。
端末の保護を強くすることと、結果を使う側の認可を強くすることは、異なる失敗経路を減らす。

## 前提と具体例

工場の検査端末がローカルモデルで傷を判定し、中央基盤へ「出荷可」を送信する。
攻撃者は端末のアプリや通信処理を操作しようとする。モデルの署名検証が正常でも、判定後の送信処理を
差し替えられるなら、別の製品の結果を再送したり、推論をせずに「出荷可」と申告したりできる可能性がある。

これは個別製品の脆弱性の主張ではなく、モデルの配布・読込みだけを検証した設計で見落とし得る経路である。
端末認証は送信主体を確認するが、今回の検査が正しく行われたことまで自動的に証明しない。

## 再利用できるモデル

```text
モデル配布物の検証
  -> 端末での読込み・推論
  -> 結果と対象・時点・処理IDの対応付け
  -> 中央基盤が結果を受信
  -> 独立したPolicyで重要操作を認可
  -> 出荷などの副作用
```

中央基盤では、認証された端末の担当範囲、対象製品、処理の状態、結果の再利用可否などを照合する。
端末が申告した値を、そのまま照合の正解として使わない。
高影響の操作では、独立した検査、信頼された経路の測定値、人による確認など、必要な追加証拠をThreat Modelから決める。
中央に判断を置くだけでは、偽造された推論結果の問題は解消しない。

## 設計レビューと検証への応用

- 端末が改変された場合、モデル抽出、判定改変、結果の偽造、重要操作の悪用のどこまで可能かを分ける。
- 正規端末から別の対象の結果を送信しても、その対象への操作権限を得られないか試す。
- 過去の正常結果の再送や、推論を経由しない直接の結果送信を試す。
- 判定値だけを変えても、重要操作の認可や追加検証を迂回できないか確認する。
- 正規の処理が必要な範囲で成功し、重複送信や検証失敗が安全に処理されることも確認する。
- モデル版、対象、処理ID、認可判断を追跡し、機密入力の過剰なログ保存は避ける。

これらの試験はプロトコル上の抜け道を確認するもので、推論の意味的な正しさを証明するものではない。

## オフライン運用と限界

遅延、通信断、Privacyの要件によって、中央での判定や再検査を使えない場合がある。
その場合は端末側の強制点が重要操作を直接守る。許可する操作範囲、回数・期間の上限、
再接続時の照合、取り消せない副作用を明示し、端末侵害時に残るRiskを評価する。
後日の照合は、すでに起きた不可逆な被害を防ぐものではない。

ハードウェアによる保護や実行環境の証拠はAssumptionを強め得るが、対象・時点・構成・結果との結び付きを確認する。
仮に正しいモデルを正しく実行した証拠があっても、入力の真実性やモデルの誤判定は別に残る。

## Slide-ready summary

- モデルを守る、推論を守る、操作を許可する、を分ける。
- 認証済み端末から来た結果でも、そのまま重要操作の許可にしない。
- 正しい実行の証拠と、正しい入力・判断の証拠は別。
