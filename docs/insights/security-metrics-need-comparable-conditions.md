# 安全性の数字には、比較できる測定条件が必要である

## 中心となる洞察

失敗率や攻撃成功率が同じでも、安全性が同じとは限らない。何を試し、何を失敗と判定し、
どの境界を観測したかが変われば、数字の意味も変わる。

> 数字だけを比較しない。その数字を作った条件を比較する。

これは実験条件と母集団を揃える既存の考え方である。AIではモデル、入力形式、判定器、
後段のFilterなどが独立に更新されるため、改善と測定方法の変化を取り違えやすい。

## 具体例

旧版のモデルで100問中4問が有害な回答になった。新版では難問50問を除き、残り50問中2問が有害になった。
両方とも4%だが、新版が同程度に安全とは言えない。試験対象の構成が変わり、除いた難問への挙動は未確認である。

```text
観測した割合
  = 失敗と判定した件数 / 評価対象に含めた件数

比較の条件
  = 試験集合 ＋ 判定方法 ＋ 対象境界 ＋ 実行条件
```

問題は分母の件数だけではない。同数の100問でも、画像攻撃を文章の容易な質問へ置き換えれば比較条件は変わる。
一方、試験集合を変更した事実から、担当者が意図的に成績を操作したと断定することもできない。
変更理由と履歴を確認し、観測した差と意図についての推測を分ける。

## 再利用できる確認モデル

| 確認する条件 | 取り違えの例 | 比較時に残すもの |
|---|---|---|
| 試験集合と構成 | 難しい攻撃を除いて平均を比較する | 集合の版、カテゴリ別件数、追加・除外理由 |
| 判定方法 | 判定器の更新をモデルの改善として扱う | 判定器・基準の版、同じ出力への判定差 |
| 対象境界 | 旧版のモデル単体と新版のFilter込み製品を比較する | 観測点と構成、各境界の結果 |
| 実行条件 | 質問回数や再試行条件の違う攻撃成功率を比べる | 試行数、設定、攻撃者が使える情報・能力 |
| 基準値 | 不均衡な在籍推定データで50%を偶然の基準にする | 集団の構成、比較するBaselineとその理由 |

最後の行はC11.2の学習を起点とし、他の行はC11.1の整理を一般化したもの。
常に同じ試験集合を使い続けるという意味ではない。新しい攻撃を追加しながら、共通集合の結果と
追加集合の結果を分けて示すなど、何を比較できるかを説明する。

## 設計レビューと検証への応用

- 安全性の主張に、対象モデル・製品構成、試験集合、判定方法、実行条件を添える。
- 試験の未実行、失敗、Timeout、判定不能を黙って分母から落としていないか確認する。
- 難問の除外や判定器の変更を試し、比較不能な結果を「悪化なし」と扱わないか確認する。
- 全体の平均に加え、重要な攻撃カテゴリや入力形式ごとの結果を確認する。
- 同じ条件でも試行数やばらつきを示し、小さな差を確実な改善と断定しない。
- 試験実行の完了、弱点の発見、対策の効果、公開可否を別の判断として記録する。

測定条件が異なる場合は、共通条件で再評価するか、比較の限界を明示する。
試験対象を増やしたために失敗率が上がったなら、製品が悪化したのか、以前は見えていなかった弱点を
発見したのかを分ける。その区別のために失敗例と条件を残す。

## 限界と関連Artifact

比較条件が揃っても、未知の攻撃や本番の全入力への安全性は証明できない。
固定集合への適応や判定器の誤りも残る。測定可能性は、認可や実行時の隔離を置き換えない。

## Slide-ready summary

- 同じ4%でも、同じ安全性とは限らない。
- 分母の件数だけでなく、構成・判定方法・観測境界を見る。
- 弱点を発見したことと、製品が悪化したことを分ける。
