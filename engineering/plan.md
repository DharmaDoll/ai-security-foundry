# Engineering ナレッジベース段階的整備計画

- ステータス: proposal
- 対象範囲: `engineering/` のみ
- 計画基準日: 2026-09-01

## 1. 目的と境界

`engineering/` は、安全な AI システムを設計、構築、テスト、運用するための
実装指向の入口である。エンジニアが次の問いに答えられることを目的とする。

- 具体的なアーキテクチャやユースケースで何が失敗し得るか。
- どの資産、主体、データフロー、信頼境界が重要か。
- LLM、エージェント、ツール、外部依存物が誤動作しても、どのセキュリティ特性を
  維持しなければならないか。
- 決定論的な強制をどこで行うべきか。
- どのセキュアデフォルト、封じ込め境界、運用上の対策を選ぶべきか。
- ネガティブテストや悪用ケースを含め、セキュリティ特性をどう検証するか。
- 対策後にどの制約と残余リスクが残るか。

この領域には、再利用可能なエンジニアリング知識、参照アーキテクチャ、実装指針、
理解に有用な場合に限る最小例、セキュリティテスト、運用指針を置く。外部フレーム
ワークの章立てではなく、安定したエンジニアリング概念とシステム境界で整理する。

次の事項は主たる責務の外とする。

- 保証要件の正本を定義すること。
- 外部フレームワーク全体を複製、またはその構造をミラーすること。
- マッピング数やカバレッジ率を最大化するために内容を構成すること。
- 製品固有のポリシー、組織固有のリスク受容、機密な配備情報を保持すること。
- 証拠なしに、ある実装がコントロールを満たすと断定すること。
- モデルへの指示、分類器、自然言語による推論を決定論的な認可境界として扱うこと。

すべてのパターンに実行可能コードが必要なわけではない。該当するセキュリティ境界が
アプリケーションコードの外にある場合、アーキテクチャ、ポリシー、設定、テスト設計が
適切な成果物になり得る。

## 2. `controls/` との違い

両領域は独立した視点であり、双方がそれぞれの根拠で成立した後に、第三の派生成果物である
マッピングによって接続する。

| 観点 | `engineering/` | `controls/` |
| --- | --- | --- |
| 主な問い | このユースケースをどう安全に設計、実装、テスト、運用するか | どのセキュリティ特性を保証し、その有効性をどう評価するか |
| 出発点 | 具体的なユースケース、資産、主体、信頼境界、悪用ケース | コントロール要件と権威ある上流ソース |
| 主な成果物 | アーキテクチャ、セキュアデフォルト、実装指針、テスト、運用方法、制約 | 要件の解釈、セキュリティ目的、検証方法、証拠への期待 |
| 整理原則 | 安定した技術、信頼境界、エンジニアリング上の問題 | コントロールファミリーと保証要件 |
| 外部フレームワーク | 根拠あるマッピングのための文脈と証拠 | 主たる要件ソースと補助ソース |
| 完了の基準 | 明示した範囲でセキュリティ不変条件が強制され、検証可能である | 保証特性と許容できる証拠が十分に定義されている |

どちらも他方に従属しない。一つのパターンは複数のコントロールに対応しても、ある
コントロールの一部だけを扱っても、現時点で対応先を持たなくてもよい。一つの
コントロールが複数パターンに対応したり、エンジニアリング上の空白を示したりしても
よい。これらを記録し、リポジトリ構造の強制やカバレッジの誇張は行わない。

## 3. Patternの定義、発見、領域の責務

### Patternの定義

Engineering Patternは、複数のシステムで繰り返し現れるセキュリティ上の設計問題、または
単一製品を超えて一般化できる実際の攻撃・失敗シナリオと、それに対する再利用可能な
セキュリティ不変条件、解決原則、検証方法をまとめたものである。フレームワーク要件の
言い換えや、単一製品の設定例はPatternではない。

### Patternの発見手順

Pattern候補は次の順序で発見する。

```text
システム類型と具体的ユースケース
  -> 資産、主体、信頼境界、データフロー
  -> インシデント、攻撃経路、失敗モード
  -> 複数システムに共通する問題のクラスタ
  -> セキュリティ不変条件
  -> 再利用可能な解決原則
  -> Pattern候補
```

候補の段階ではControl IDやフレームワーク対応を発見根拠にしない。候補一覧を作る場合は、
一つのLandscapeまたはcatalogに、問題、観測されたシステム類型、攻撃シナリオ、信頼境界、
不変条件、解決原則、適用条件、根拠ソースを記録する。候補ごとのディレクトリや
プレースホルダー文書は作らない。

ControlやAISVS Researchは、独立して発見されたPatternの脅威・検証を後から補強できるが、
Controlが存在すること自体をPattern作成理由にしない。

現在の候補比較とPattern化前のGateは
[`docs/pattern-landscape.md`](docs/pattern-landscape.md)に記録する。
候補の抽出、cluster、split／merge、再利用性検証には、
[`docs/pattern-discovery.md`](docs/pattern-discovery.md)を使用する。

### 領域の責務

既存の10個のトップレベル領域を安定した分類として維持する。各領域は、開発者が
そこで解決策を探すと期待される問題を所有し、共有事項は複製せずリンクする。

| 領域 | 所有するセキュリティ問題 | 連携先と境界 |
| --- | --- | --- |
| `llm/` | モデル入出力の信頼、プロンプトとデータの分離、構造化出力の検証、モデルルーティング、安全でないフォールバック、モデル対話境界での直接・間接プロンプトインジェクションの封じ込め | データ処理方針は `data-security/`、出力が行動を起こす場合は `agents/` を使う。認可ポリシー自体は所有しない。 |
| `rag/` | 安全な取り込みと索引化、コーパスの信頼、認可を伴う検索、テナント分離、文書・メタデータ完全性、出所、検索汚染、失効済みアクセス、取得内容の安全な利用 | 主体とポリシーは `identity-and-authorization/`、分類と流出制御は `data-security/`、モデル境界は `llm/` を使う。類似度は認可ではない。 |
| `agents/` | 計画から行動への境界、ツール選択と実行、委任された行動、承認フロー、能力の最小化、サンドボックス、エージェント間の行動完全性、障害の封じ込め、影響範囲の縮小 | 権限は `identity-and-authorization/`、プロトコル固有挙動は `mcp/`、行動証拠は `observability/` を使う。一般的なエージェント行動の安全性を所有し、個別プロトコル全体は所有しない。 |
| `mcp/` | MCP クライアント、サーバー、ツール、リソースの信頼境界、プロトコルとトランスポート、認証、トークンの audience と scope、能力発見、サーバー・ツールの出所、安全でないメタデータ、下流への confused deputy | 一般的なツール実行は `agents/`、アイデンティティ規則は `identity-and-authorization/` を再利用する。MCP 固有の挙動を所有し、参照した仕様バージョンを明記する。 |
| `skills/` | スキルの出所、要求権限、外部指示と外部リソース、導入、レビュー、分離、依存物完全性、バージョン、更新、失効、振る舞い層のサプライチェーンリスク | 成果物管理は `model-and-supply-chain/`、実行時対策は `agents/` を再利用する。スキル固有のライフサイクルと振る舞いへの影響を所有する。 |
| `memory/` | メモリ読み書きの認可、テナント分離、出所、汚染、保持、削除、復旧、古い・失効済みアクセス、永続コンテキストの安全な取得 | `data-security/` の方針と `identity-and-authorization/` の強制を再利用し、メモリ固有の永続化とライフサイクルを所有する。 |
| `identity-and-authorization/` | 主体定義、ワークロード・サービスアイデンティティ、認証コンテキスト、決定論的認可、委任、資格情報の scope と audience、テナント結合、権限ライフサイクル、失効、confused deputy の防止 | 他領域は具体的なフローにこれらを適用する。エージェント計画、検索順位、プロトコル固有動作は所有しない。 |
| `data-security/` | データ分類、最小化、テナント・プライバシー境界、暗号化、秘密・機微コンテキスト、保持、出力開示、流出制御、ログ・ツール経由の漏えい | RAG、memory、LLM、observability が個別パイプラインへ適用する。共有データ方針と保護プリミティブを所有する。 |
| `model-and-supply-chain/` | モデル、アダプター、データセット、依存物、イメージ、ツール成果物、ビルドの出所と完全性、署名、スキャン、固定、展開、ロールバック、侵害対応 | スキル固有の振る舞いと権限は `skills/` が所有する。実行時のエージェント・ツール認可はこの領域の外である。 |
| `observability/` | セキュリティイベントと証拠モデル、行動・判断監査、出所の記録、異常検知、インシデント再構成、プライバシーを考慮したテレメトリ、対応フック、緊急停止 | 各パターンは必要な信号を定義し、この領域は共通のテレメトリ意味論と対応アーキテクチャを所有する。領域別ログ一覧を重複させない。 |

これらは互いに排他的なリスク分類ではない。一つのシステム経路が複数領域を横断して
よい。パターンの配置先は、主たるユースケースと、開発者が最初に解決策を探す場所で
決める。

## 4. 横断的関心事と重複回避

各パターンには一つの主たる配置先を定める。副次的な関心事は、関連パターンや
マッピングへのリンクで表現し、同じ規範的ガイダンスを複数領域へコピーしない。

| 横断的関心事 | 主たる所有領域 | 他領域での扱い |
| --- | --- | --- |
| 主体、委任、トークンの scope と audience、ポリシー判断 | `identity-and-authorization/` | 具体的なアイデンティティと強制点を示し、共有プリミティブへリンクする。 |
| 分類、テナント境界、最小化、保持、流出制御 | `data-security/` | 共有方針を再定義せず、領域固有のデータフローへ適用する。 |
| 監査イベント、相関、証拠完全性、検知、対応フック | `observability/` | 各パターンは必要な信号と不可視になる障害を示し、共通のイベント・証拠指針へリンクする。 |
| 成果物の出所、固定、更新、署名、ロールバック | `model-and-supply-chain/` | スキル、モデル、データセット、ツールに固有のライフサイクルだけを特殊化する。 |
| モデル入出力の信頼とプロンプトインジェクション封じ込め | `llm/` | RAG、agents、MCP、skills、memory は固有の非信頼チャネルと強制境界を記述する。 |
| 行動承認のライフサイクルと安全なツール実行 | `agents/` | 承認者の主体・ポリシーは identity、プロトコル固有制約は MCP が補う。 |
| サンドボックスと分離 | 具体的な実行ユースケース | 分離対象のランタイム近傍に強制を置く。複数パターンで安定した共通要件が確認されてから共有化する。 |
| 障害処理、失効、ロールバック、緊急停止 | 具体的なパターンと関連ライフサイクル領域 | ローカルな安全側障害を定義し、共通の運用機構へリンクする。 |

新規パターン作成前に、次を記録する。

1. 具体的なユースケースと想定読者。
2. 主たるセキュリティ境界。
3. 読者が最初に探すディレクトリ。
4. 複製せずリンクすべき関連領域。
5. 別タスクとすべき共有プリミティブの不足。

横断文書は、少なくとも二つの具体的パターンが同じ安定した規則を必要とし、集約が
不整合を減らし、かつ領域固有の脅威を隠さない場合にのみ作る。

## 5. パターン成熟度モデル

既存のライフサイクル語彙を使い、競合する別のステータス体系は導入しない。

| ステータス | 移行条件 | 意味 |
| --- | --- | --- |
| `draft` | 具体的なユースケース、範囲、所有者または想定所有者、初期の脅威分析がある | 有用な作業中の文書。主張と推奨事項は人間によるセキュリティレビューを完了しておらず、構造的に未完成でもよい。 |
| `reviewed` | 本計画の成熟条件を対象範囲について満たし、技術面・セキュリティ面の正確性が人間にレビューされ、記録されている | レビュー済み指針として利用できるが、必ずしもリポジトリのデフォルトではない。 |
| `recommended` | `reviewed` であり、名前付き所有者、持続可能な検証証拠、直近の実質的変更の作成者とは別の人間によるプロダクトセキュリティ承認がある | 対象範囲についてセキュアデフォルトまたは Golden Pattern として採用された状態。フレームワーク整合だけでは移行できない。 |
| `deprecated` | 新規作業で選ぶべきでなくなった | 理由、日付、対象範囲、可能なら代替・移行先とともに履歴として保持する。 |

ステータスはレビューと採用の成熟度を表し、配備環境の準拠を表さない。`recommended`
は明示した前提と境界についてのみ成立する。上流ソースの draft、beta、stable、rolling、
superseded などの成熟度は別の属性であり、マッピングと参照に記録する。

## 6. 成熟したエンジニアリングパターンの Definition of Done

対象範囲について構造的に成熟したパターンは、次を含む。

1. 具体的なユースケース、セキュリティ問題、非目標、前提、適用条件。
2. 関連する資産、アクター、人間・ワークロードのアイデンティティ、信頼境界、データフロー。
3. 現実的な攻撃者能力、脅威、失敗モード、悪用ケース。
4. 脅威に結び付いた、明示的かつ可能な限り実装非依存のセキュリティ不変条件。
5. 認識可能な程度に説明された、安全でない、または失敗しやすい設計。
6. 各決定論的強制点と安全側の障害動作を示す推奨アーキテクチャ。
7. 最小権限、狭い能力、封じ込め、資格情報・データ境界を維持する実装指針。
8. 理解を実質的に改善する場合に限る最小の安全・危険例。危険例は明確に表示する。
9. 内部関数呼び出しではなく不変条件を検証する、正常、拒否、悪用、境界、障害モードのテスト。
10. 必要な監査証拠、検知信号、対応フック、失効、復旧上の考慮事項。
11. 制約、設計を無効にし得る依存・前提、絶対的な防止を主張しない残余リスク。
12. 上流本文のコピーではなく、権威ある一次参照と簡潔なリポジトリ独自の解釈。
13. レビューメタデータ、必要な場合の名前付き所有者、意味のある変更履歴。
14. 秘密、内部識別子、組織の機密情報を含まず、意図的な危険例を本番向けに見せないこと。

`reviewed` には、人間による技術・セキュリティレビューの記録も必要である。
`recommended` には、成熟度モデルに定めた追加承認と証拠が必要である。実行可能コードは
任意だが、検証可能なセキュリティ特性は必須である。

Mapping assessmentはこのDefinition of Doneの外にある独立成果物である。Patternはmapping
assessmentの有無や結果にかかわらず成熟できる。Patternから参照する場合は、`mappings/`
配下の正本へリンクし、評価状態や関係の詳細を重複管理しない。

## 7. 開発優先順位

優先順位は、潜在的な被害、領域横断の再利用性、リポジトリの推論手順を学習できる
度合いで決める。領域の重要度ランキングではない。

### 優先度1: エージェント行動、アイデンティティ、可観測性

`identity-and-authorization/` のアイデンティティモデルと `observability/` の証拠要件を
利用し、`agents/` から始める。エージェントからツールへの実行は、非信頼なモデル出力、
外部副作用、資格情報、委任権限、承認、障害封じ込めが交差する。ここで得た不変条件は、
MCP、skills、その他の行動可能な AI システムで再利用できる。

### 優先度2: 認可を伴う RAG とデータ分離

次に、マルチテナント検索のパターンを開発する。主体の結合、検索前認可、出所、汚染耐性、
失効済みアクセス、データ流出を扱う。「類似度やモデルコンテキスト内のメタデータが
認可になる」という危険な前提への再利用性の高い反例となる。

### 優先度3: 非信頼コンテンツの封じ込めと MCP 認可

間接プロンプトインジェクションに対する LLM 境界パターンと、MCP 固有の認可パターンを
一つずつ開発する。LLM パターンは完全なフィルタリングを主張せず封じ込めを中心にする。
MCP パターンは一般的な agent と identity の不変条件を再利用しつつ、トークン、audience、
能力発見、同意、下流リソースのプロトコル固有境界を扱う。MCP は更新が速いため、各
パターンが分析した権威ある仕様の正確なバージョンを固定する。

### 優先度4: 永続状態と振る舞い層のサプライチェーン

memory の汚染とテナント分離を扱い、その後に共有サプライチェーンプリミティブを使って
skill の導入・更新ガバナンスを扱う。行動、identity、data、observability の基盤を再利用し、
再定義しない。

`identity-and-authorization/`、`data-security/`、`model-and-supply-chain/`、
`observability/` の単独パターンは、空のカテゴリを埋めるためではなく、具体的な利用側から
安定した共有問題が明らかになった時点で作る。

## 8. 初期 Golden Pattern

初期 Golden Pattern として `engineering/domains/agents/secure-tool-execution/` を選ぶ。最初の計画範囲は、
認証済みユーザーに代わってエージェントが内部ツールの行動を提案し、その行動が機微情報を
読み取るか外部副作用を起こし得るユースケースとする。詳細なパターン内容と実装は次の
開発フェーズまで作らない。

これはControlとの対応ではなく、内部ツールを使うagent、MCP経由のtool execution、
業務workflow automationなどで反復する行動認可問題と、実害につながるconfused deputy・
過剰権限・不正tool invocationの攻撃経路を根拠とする暫定選定である。Phase 0のLandscapeで
少なくとも二つの独立したシステム類型または信頼できる攻撃・インシデント根拠を確認できない
場合は、Golden Patternを再選定する。

このパターンは、次の事項を一つの限定されたユースケースで扱うため代表性が高い。

- モデル出力とツール引数を非信頼入力として扱うこと。
- ユーザー、アプリケーション、エージェント、ツール、下流リソースの主体を明示すること。
- モデル外部で決定論的認可を行うこと。
- 最小権限、狭い能力、スコープ付き資格情報、audience・テナント結合を行うこと。
- ツール許可リスト、引数・スキーマ検証、安全側障害を扱うこと。
- 高影響・不可逆行動を承認対象にしつつ、承認を認可の代替にしないこと。
- 侵害されたモデル、ツール、依存物を封じ込めること。
- 正常、拒否、テナント越境、権限、異常入力、障害モードのテストを扱うこと。
- 起点となる主体、ポリシー判断、承認行動、ツール呼び出し、結果を結ぶ監査証拠を扱うこと。
- 残余リスクを明示し、後続のmapping assessmentがコントロール全体の充足を
  過大主張しないために必要な境界を示すこと。

この選択は領域の責務分担も試せる。一般的な行動安全性は `agents/` に置き、identity、
MCP 固有挙動、data、supply chain、observability は複製せず関連領域へ接続する。この
パターンから得た知見でテンプレートと指針を改善してから、二つ目へ進む。

## 9. 脅威、コントロール、外部フレームワーク、実装例、テストとの接続

Pattern自体の依存方向は次のとおりとする。

```text
具体的なユースケースと信頼境界
  -> 脅威と悪用ケース
  -> セキュリティ不変条件
  -> アーキテクチャと決定論的強制
  -> 実装指針と最小例
  -> セキュリティテストと運用証拠
```

Controlは別経路で要件解釈、保証特性、検証、証拠期待を成熟させる。両者が独立して
理解可能になった後にだけ、`mappings/`で関係を評価する。

接続には次の規則を適用する。

- 脅威はパターンが必要な理由を説明する。MITRE ATLAS やリスク分類は、攻撃者能力や
  失敗分析を明確にする場合に使い、広いマッピングを強制するためには使わない。
- controls は保証特性を表す。パターンの不変条件、強制点、検証、制約が明確になった後に
  のみマッピングする。
- Control inventoryやframework coverageをPattern候補の発見入力にしない。
- 外部フレームワークは、ソースのバージョン・状態を伴う証拠と文脈である。読者が先に
  フレームワークを読まなくてもパターンを理解できなければならない。
- マッピングは `direct`、`partial`、`context` を明記し、技術的根拠を示す。上流変更時は
  歴史的識別子を保持する。
- 実装例は不変条件を示すものであり、それ自体は証明ではない。不要な依存や危険な汎用能力を
  持ち込まない。
- テストは、一つの関数へ引数が渡ったかではなく、テナント越境行動が拒否されたかのような
  観測可能なセキュリティ結果を検証する。
- 設定の存在と、有効な強制の証拠を区別する。ポリシー判断、ネガティブテスト結果、実行時
  監査記録、分離試験、レビュー記録などを適切に使う。
- 適切なコントロールやエンジニアリング関係がなければ、別タスクの空白として記録する。
  弱いマッピングを創作せず、実装へ合わせるために `controls/` を変更しない。
- Mappingの成否はPattern成熟度を決めない。`assessed-no-match`または`gap`は有効な評価結果である。

ソースは役割を混同せず、次のように使い分ける。

| ソース種別 | `engineering/` での役割 |
| --- | --- |
| OWASP AISVS | セキュリティ不変条件と検証方法が明確になった後に接続する、主要な control / verification backbone |
| MITRE ATLAS | 攻撃者の行動、能力、手順を脅威分析へ補う adversary taxonomy |
| OWASP GenAI LLM Top 10、Agentic Applications Top 10、MCP Top 10、Agentic Skills Top 10 | 各技術領域のリスクと失敗モードを検討するための risk taxonomy。要件標準の代替にはしない |
| OWASP AI Exchange | 一次ソースと技術的根拠を補う supplementary knowledge。単独で規範的要件とは扱わない |
| 公式プロトコル・技術仕様 | 該当する境界の規範的挙動を確認する一次ソース。利用した版と成熟状態を固定する |

現行プロトコル、フレームワーク、製品挙動に依存する前に、権威あるソース、バージョン、日付、
成熟状態を確認する。特に MCP は、パターンに適用する公式仕様を明記する。本計画の作成時に
確認した仕様は `2026-07-28` である。source registry の変更が必要になった場合は別の
リポジトリ保守タスクとし、本変更には含めない。

## 10. 段階的ロードマップ

別々の所有者とレビュー能力が明示的に割り当てられない限り、実質的に開発中のパターンは
同時に一つとする。各フェーズに終了条件を設け、将来フェーズのプレースホルダーを作らない。

### Phase 0: 計画の確立

- 領域の責務、成熟度、Definition of Done、優先順位について合意する。
- システム類型、攻撃シナリオ、反復する設計問題から、
  [`docs/pattern-landscape.md`](docs/pattern-landscape.md)を更新する。
- 候補LandscapeにはControl由来の候補やPatternプレースホルダーを作らない。
- Landscapeの根拠からGolden Patternの暫定選定を検証し、必要なら再選定する。
- 既存のリポジトリ指示とテンプレートに矛盾せず、レビュー可能になった時点で終了する。

### Phase 1: Golden Pattern の設計

- 安全なエージェント・ツール実行と権威あるソースを調査する。
- 具体的なユースケース、資産、主体、信頼境界、データフロー、攻撃者能力、悪用ケース、
  不変条件、アーキテクチャ、安全側障害、証拠、テスト計画を定義する。
- `draft` とし、実装コードから始めない。
- 各不変条件に強制点と実行可能な検証があることをアーキテクチャ・脅威レビューで確認して
  終了する。

### Phase 2: Golden Pattern の検証と成熟

- 失敗モードと推奨設計を示すために必要な最小例だけを追加する。
- 不変条件を検証する正常、拒否、悪用、越境、運用テストを実装する。
- 制約、参照、所有者、レビューメタデータを記録する。
- 人間のレビューを記録してから `reviewed` へ移行する。独立した人間のプロダクト
  セキュリティ承認と持続可能な証拠が揃ってから `recommended` へ移行する。
- 再利用可能なレビュー知見を、適切な template、engineering docs、testing guidance、または
  狭い範囲の AGENTS.md へ反映する。

### Phase 3: 認可を伴うマルチテナント検索

- 一般的な RAG カタログではなく、一つの具体的なユースケースを選ぶ。
- Golden Pattern で得た identity、強制、テスト、証拠の知見を再利用する。
- 検索固有の脅威、出所、汚染、失効、テナント境界だけを追加する。
- 同じレビューゲートを通過してから次のパターンを選ぶ。

### Phase 4: 非信頼コンテンツ境界と MCP 境界

- LLM 境界で間接プロンプトインジェクションを封じ込めるパターンを一つ開発する。
- その成熟後、正確な公式仕様バージョンに固定した MCP 認可・委任パターンを一つ開発する。
- 一般的なツール実行と identity パターンを再利用し、MCP 固有要件を分離する。

### Phase 5: memory と振る舞い層サプライチェーン

- 永続 memory の汚染とテナント分離を扱うパターンを一つ開発する。
- 次に、共有される出所、権限、分離、ロールバックを使った skill 導入・更新パターンを作る。
- 独立した共有 supply-chain パターンは、具体的な作業から安定性と再利用性が証明された場合に
  のみ作る。

### Phase 6: ナレッジベースの運用

- 権威あるソースの変更時にマッピングと参照を再検証する。
- 新しいフレームワーク構造を暗黙にミラーせず、意味差分と影響をレビューする。
- 古い証拠、壊れたテスト、置換済み依存物、未解決の空白、インシデント由来の知見を追跡する。
- 有用な履歴を削除せず、代替先とともに deprecated にする。
- 各パターンの成熟後、得られたリスク、採用状況、レビュー能力から次の優先順位を見直す。

進捗は、持続可能な検証を持つセキュリティ不変条件、安全なデフォルトの採用、レビュー証拠の
品質と経過時間、解決したエンジニアリング上の空白、後続パターンで再利用された知見で測る。
文書数とフレームワークカバレッジ率は成功指標にしない。

## 11. 指針を置く場所

| 配置先 | 置く内容 | 他へ置く内容 |
| --- | --- | --- |
| ルート `AGENTS.md` | リポジトリ全体の目的、ソースの役割、Git・worktree 安全性、共通マッピング・レビュー規則、全体の Definition of Done | 領域固有の脅威詳細や一パターンのアーキテクチャ |
| `engineering/AGENTS.md` | 簡潔で強制可能な手順、中心的なセキュリティ原則、スコープ規律、詳細指針への導線 | 長い解説、完全な脅威一覧、パターン内容の重複 |
| 領域別 `AGENTS.md` | その領域で反復する固有要件、権威ある固有仕様、不変条件の種類、レビュー・テスト上の落とし穴 | 共通規則や、具体的な作業前に想像だけで作る指示 |
| `engineering/docs/` | security principles、lifecycle、testing、sources、候補Landscape、調査記録など、複数領域で安定して使う資料 | 個別Pattern本文や外部標準のコピー |
| `engineering/domains/` | 安定したEngineering Domainと、そのDomainを主配置先とする個別Pattern | 横断資料、Framework別分類、同一Patternの重複配置 |
| 領域別 `README.md` | 領域の範囲、責務境界、隣接領域との関係、実在するパターンの索引 | プレースホルダー一覧や完全なフレームワーク分類 |
| `templates/security-pattern.md` | 必須構造、検討用の問い、メタデータ、レビューゲート、任意のcanonical mapping参照欄 | mapping評価の状態・関係詳細、一つのアーキテクチャへ全パターンを誘導する規範的回答・例 |
| 個別パターン | 具体的なユースケース、脅威、不変条件、アーキテクチャ、指針、必要な例、テスト、運用、制約、参照、レビュー履歴 | mapping評価の正本、リポジトリ全体の方針、無関係な領域の指針 |
| `engineering/plan.md` | 領域の責務、優先順位、Golden Pattern の判断、ロードマップ、計画上の前提 | 詳細なパターン設計や実装コード |

反復するレビュー知見は、重複を生まず同種の誤りを防げる最も狭い永続的な配置先へ昇格する。
分類を埋めるだけの目的で領域別 AGENTS.md を作らない。

## 12. 保守性の原則とレビュー時の問い

ロードマップ全体で次の原則を適用する。

- 浅い文書を多数作るより、深くレビューされ、テスト可能な一つのパターンを優先する。
- 安定したエンジニアリング概念を、変化するフレームワーク分類から分離する。
- Pattern候補をControl inventoryではなく、反復するシステム問題と攻撃シナリオから発見する。
- 主たるパターンを正本とし、副次領域はリンクする。
- 正しいモデル挙動の仮定より、決定論的強制と封じ込めを優先する。
- マッピングは説明可能かつバージョン対応とし、証拠が部分的なら強度を下げる。
- 例を最小化し、外部から観測可能なセキュリティ結果をテストする。
- 不確実性、ソース成熟度、残余リスクを明示する。
- 成熟度移行とセキュリティ上重要な上流変更には人間のレビューを要求する。
- 新たな抽象化を追加する前に重複を除く。
- 現在のパターンの推論、検証可能性、運用上の有用性を改善しない作業は延期する。

新規パターンの着手前に、レビュー担当者が次へ答えられなければならない。

1. ユースケースは具体的で、既存パターンと実質的に異なるか。
2. 開発者が最初に探す主たる領域はここか。
3. どの既存不変条件や共有指針を参照によって再利用できるか。
4. 完成時にどのセキュリティ結果をテスト可能にするか。
5. どの人間のレビュー担当者と長期所有者が成熟度を支えられるか。
6. レビュー可能な範囲に保つため、何を意図的に延期するか。
