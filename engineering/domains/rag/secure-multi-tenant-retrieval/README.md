# RAG検索で、利用者に許可された文書だけを渡す

**RAGでは、回答を作る前に、アプリがLLMへ渡す資料を選ぶ。この選択に利用者の閲覧権限を反映するのが、このPatternの中心である。**

社内文書への質問に答えるサービスを例に、まず登録から回答までの全体像を示す。
そのうえで、どの情報を根拠に、何を、どこでチェックするかを説明する。
状態は`draft`。設計ガイドであり、製品連携・実行検証は未実施。

## 1. RAGの全体像：資料を準備し、質問ごとに選んでLLMへ渡す

RAG（検索拡張生成）は、質問に関係する資料を検索し、その内容を使って回答を生成する方式である。
この例では、アプリが「質問＋選んだ資料」を回答用LLMの入力に組み込む。
社内文書を登録することと、LLMをその文書で追加学習することは別である。
検索と生成を組み合わせる基本的な考え方は[原論文](https://arxiv.org/abs/2005.11401v4)を参照。以下のアクセス制御設計は本PJの設計例である。

### 二つの流れを分ける

```mermaid
flowchart TB
    subgraph prep["登録・更新時：検索できる資料を準備する"]
        source["元の文書と閲覧権限"] --> ingest["文書を取り込む<br/>会社・文書ID・権限・版を対応付ける"]
        ingest --> index["検索基盤<br/>文書や検索用データを保持"]
    end
    subgraph request["質問時：その人に渡せる資料を選ぶ"]
        user["ログイン済みの利用者＋質問"] --> auth["アプリ：本人と会社を確定"]
        auth --> retrieve["検索・本文取得<br/>閲覧可能な資料から必要な部分を選ぶ"]
        retrieve --> context["アプリ：LLMへの入力を組み立てる<br/>質問＋許可した資料"]
        context --> llm["回答用LLM：資料を使って文章を作る"]
        llm --> answer["アプリ：回答・引用を利用者へ返す"]
    end
    index --> retrieve
```

**登録時**には、文書を検索しやすい形にする。長い文書を小さな本文のまとまり（chunk、以下「断片」）へ分割する場合もある。
元文書の閲覧権限と、検索用に作った断片との対応が失われると、質問時に「この断片を誰へ渡せるか」を判断できない。
文書の更新・削除・権限取消も、この対応へ反映する必要がある。

**質問時**には、アプリが利用者を確認し、その人が読める範囲で資料を検索・取得する。
選んだ本文を質問と一緒にLLMへ渡し、回答を受け取る。ここでは、回答の材料としてLLMの入力に加える資料を「コンテキスト」と呼ぶ。
LLMが回答を書き始める前に、すでに資料の選択と開示が起きている。

既存の文書検索サービスを使えば、図の登録・検索基盤の部分はそのサービスに任せられる。
自前で検索基盤を持つなら、その文書・権限の対応と更新を自分たちで管理する。この違いを第3節で選ぶ。
検索を速くするための索引をIndexと呼ぶ。以下の「会社別Index／共有Index」は、その検索用データを会社ごとに分けるか、同じ場所に持つかの違いである。

### 検索の精度と、読んでよい範囲は別の判断

キーワード検索は語句などを手掛かりに資料を探す。ベクトル検索では、文書や質問をEmbeddingという数値表現に変換し、近さを手掛かりに探す。
両方を組み合わせる方式もあるが、**どの検索方式でも「質問に関連する」と「この人が読める」は別**である。
ベクトルDBを使うこと自体が、利用者別のアクセス制御になるわけではない。

認可は、ログインした本人の情報と、管理元が持つ文書の閲覧権限で判断する。
閲覧権限を表す一覧をACL（Access Control List）と呼ぶ。以下では、文書の管理情報を指し、本文に書かれた「閲覧可」という文字は含めない。

このPatternが扱うのは、**資料の権限を検索まで引き継ぎ、未認可の本文をLLMや利用者へ渡さない設計**である。
検索精度の改善、文書内容の正しさ、Prompt Injectionの防御は、それぞれ別の設計課題として残る。
検索語の作成などにLLMを使う構成でも、閲覧権限の判断はモデル外で行う。外部のEmbedding生成や再ランキング（検索結果の並べ替え）へ送る場合は、回答用LLMより前にもデータが外へ出るため、送信許可の確認が必要になる。

## 2. 守る境界：他の会社や、同じ会社の非公開資料を回答材料にしない

会社Aと会社Bが同じRAGサービスを利用する。この例の**テナントは会社**を意味する。
会社Aの担当者A（`staff-a`）が「解約時の返金条件は？」と質問する。

| 文書 | 内容と所属 | 担当者Aへの開示 |
|---|---|---|
| A100 | 会社Aのサポート用返金手順 | 許可 |
| A200 | 会社Aの管理者向け特例 | 拒否。同じ会社でも閲覧権限がない |
| B100 | 会社Bの返金手順 | 拒否。会社が違う |

守る対象は、本文に加え、断片・タイトル・引用・検索結果のキャッシュである。

この例は**会社の一致と文書の閲覧権限の両方**を要求する。会社間共有や公開文書は扱わない。
本人・文書の識別子は、会社IDとの組で区別する。

<a id="2-失敗例似ている順に検索し後から隠す"></a>

### 失敗例：全社から探して、LLMに隠させる

**危険な設計：説明用。実装の手本にしない。**

```text
担当者Aが質問する
  → 全社の文書から、似ている順に検索する
  → 最も似ているB100をモデルへ渡す
  → 「会社Aの情報だけで答えて」と指示する
```

B100をモデルへ渡した時点で、未認可の本文を開示している。回答画面で隠しても取り消せない。
会社Aだけに絞っても、担当者Aが読めないA200は残る。**会社と文書の両方を、本文を渡す前に照合する**必要がある。

認証は「誰か」の確認、認可は「その人が何を読めるか」の確認である。
アプリが検索基盤へ接続できることは、質問した利用者が全資料を読めることを意味しない。
共有の管理者資格で全件を検索し、LLMへ「見せてよいか」を判断させる設計は、この境界を失う。

### この例の前提：権限の根拠をどこから得るか

認証基盤、所属・ACLの管理元、検索サービス、文書と断片の対応を管理する取り込み処理を信頼する。
利用者やモデルは質問・検索語・指定IDを変えられるが、管理された権限情報やDBの資格情報は変更できない前提である。
文書に「全員閲覧可」と書かれていても、それをACLにはしない。

対象は、検索から回答までの認可と、その前提となる版・権限の整合である。
取り込み全体の安全性、文書汚染、回答の正確さは[限界と追加設計](#9-限界と追加設計が必要な場面)で区別する。

## 3. 構成を選ぶ：登録と検索の責任を、どこに置くか

まず、既存の文書検索が利用者の閲覧権限を評価でき、必要な文書を検索できるかを確認する。
その機能で足りるなら、別の検索基盤へ本文やACLを複製する必要はない。
独自検索が必要な場合に、会社ごとに分けるか、共有基盤で制限するかを選ぶ。

| 構成 | 選ぶ条件 | 減らせる危険・仕組み | 残る責任・運用負担 |
|---|---|---|---|
| 利用者本人の権限で既存検索APIを使う（主例） | 対応文書・検索品質・遅延・失効反映が要件を満たす | 文書・ACLの独自複製、独自Indexと同期処理を作らずに済む | 本人と会社・接続先の結付け、本文取得も同じ権限で行うこと、送信先・キャッシュの制御 |
| 自前の検索領域を会社別に分ける | 独自検索は必要だが、会社をまたぐ検索は不要 | 一つのIndexに会社の文書を混在させずに済む | 接続先と資格情報の分離、会社内の文書ACL、Indexごとの更新・監視 |
| 共有Indexで会社と文書ACLを強制する | 基盤の集約が必要で、共有時の認可と運用を担える | Index群の管理は集約できる | 全経路の条件強制、ACL同期・失効、越境時の影響範囲、共有資源の干渉 |

これは成熟度の段階ではない。まず既存検索で足りるかを判断し、自前で持つなら会社別か共有かを選ぶ。
既存サービス内の会社別領域を使うなどの組合せもある。別Indexという名前だけでは隔離を保証せず、同じ会社のA200への認可はどの構成でも必要になる。

### 主例の配置：RAGはWebアプリのサーバーで動く

担当者AはブラウザでRAG Webアプリを使う。**検索、本文取得、LLMへの送信を行うのはWebアプリのバックエンド**である。
文書と閲覧権限は会社AのSharePointにあり、検索・取得の窓口にはMicrosoft Graphを使う。回答の生成は別のLLMサービスへ依頼する。

この例では、会社A・Bはそれぞれ別のMicrosoft Entraテナントを持ち、アプリの管理設定で「会社 → 許可するEntraテナント・SharePointサイト・文書ライブラリ」を対応付ける。
業務上の会社とEntraテナントは一般に同義ではないため、利用者が指定した会社名やメールアドレスから推測して結び付けない。同じEntraテナント内の部署分離は、この対応設定を変える別構成として考える。

| 場所 | 動くもの・保持するもの |
|---|---|
| 担当者のブラウザ | 質問・回答の画面とWebセッションCookie。Graph用tokenは置かない |
| RAGバックエンド | セッション確認、利用者別のtoken管理、検索・本文取得、LLM入力の組立て、引用の制御 |
| Microsoft Entra ID | 担当者のログインと、Graphを利用者の代理で呼ぶためのtoken発行 |
| Microsoft Graph／SharePoint | 文書の検索・取得と、その利用者が読める文書の権限評価 |
| LLM提供サービス | 許可された本文と質問から回答を生成。Graph用tokenやWebセッションは受け取らない |

既存の認可付き検索を使うと、自前DBへ文書ACLを複製せずに済む。一方で、アプリ側の会社範囲、tokenと本人の対応、LLMへの送信許可は引き続き確認する。
Microsoft Graphの利用者委任による検索は、本人が読める項目へ結果を制限する。[Graph v1.0 Search概要](https://learn.microsoft.com/en-us/graph/api/resources/search-api-overview?view=graph-rest-1.0)

### セッションとtokenの役割を分ける

| 情報 | 保持場所・送信先 | この例での役割 |
|---|---|---|
| WebセッションCookie | ブラウザ → RAGバックエンド | ログイン済みの担当者Aとサーバー側セッションを結ぶ。Graphには送らない |
| ID token | Entra ID → バックエンドの認証処理 | ログイン時の本人確認に使用。認証ライブラリで検証してセッションを作る。Graph APIの呼出資格には使わない |
| Graph用access token | バックエンドが利用者別に管理 → GraphのAuthorizationヘッダー | **担当者Aの代理として**検索・本文取得を行う。アプリへの委任許可と担当者Aの文書権限の範囲で使う |
| refresh token | 発行される場合、バックエンドの保護した利用者別token cache → Entra ID | access tokenを更新する。GraphやLLMへ送らず、更新失敗・再認証要求ではログインをやり直す |
| client secret／証明書の秘密鍵 | バックエンドの秘密管理で保持。secret認証ではsecretをEntra IDへ、証明書認証では秘密鍵を送らず署名したassertionを送る | tokenを取得するWebアプリ自体を認証する。これだけで担当者Aの文書権限は得られない |
| LLM API用の資格情報 | バックエンドのLLM接続処理 → LLMサービス | 回答モデルを利用するための資格。文書の閲覧権限とは別 |

**P1の主例はアプリ自身のaccess token、P2の主例は利用者委任のaccess tokenである。**
P1では社内APIへ別途本人と操作の対応を引き継ぐ。P2ではGraphが委任された利用者の文書権限を評価するが、アプリはそのtokenが今回のWebセッションの担当者・会社に対応することを保証する。
client secretを持つことと、client credentials方式でアプリ単独のtokenを取得することは同じではない。

## 4. ログインから回答まで：tokenを取得してから①〜⑤を通す

Webアプリのログインは、認証ライブラリを使ったOIDC＋Authorization Code Flow＋PKCEで構成する。
バックエンドがcodeをtokenへ交換し、検証した本人情報と利用者別token cacheをWebセッションへ対応付ける。CookieにはSecure・HttpOnly・用途に合うSameSiteを設定する。
OIDCの`openid`と、検索に必要なGraphの委任scopeを要求する。継続利用のためrefresh tokenを要求する場合は`offline_access`を含める。
以下は通信の要点であり、ログインのstate・nonce・PKCEの検証やセッション管理を省略してよいという意味ではない。[EntraのAuthorization Code Flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)

```mermaid
sequenceDiagram
    actor Browser as 担当者Aのブラウザ
    participant App as RAG Webバックエンド
    participant Entra as Entra ID
    participant Graph as Microsoft Graph／SharePoint
    participant Model as 許可されたLLMサービス
    Browser->>App: ログイン開始
    App-->>Browser: 会社設定に対応するテナントのログインへリダイレクト
    Browser->>Entra: ログイン・必要な同意（管理者同意済みの場合もある）
    Entra-->>Browser: Webアプリのcallbackへ認可code
    Browser->>App: callback（code・state）
    App->>Entra: code交換（PKCE＋client認証）
    Entra-->>App: ID token・Graph用access token・refresh token（発行時）
    Note over App: 本人を検証し、利用者別token cacheとセッションを対応付ける
    App-->>Browser: WebセッションCookie
    Browser->>App: ① Cookie＋「返金条件は？」
    App->>App: 本人・会社・token cacheのアカウントを照合
    App->>Graph: ② 検索（担当者Aの委任access token）
    Graph-->>App: 閲覧可能な検索結果
    App->>App: 会社Aの許可サイト・文書か確認
    App->>Graph: ③ A100の本文取得（同じ担当者Aの委任資格）
    Graph-->>App: 本文取得応答（ダウンロードの詳細は③参照）
    App->>App: ④ 文書の版・権限の有効性・送信先を確認
    App->>Model: 質問＋許可されたA100の本文（tokenは含めない）
    Model-->>App: 回答
    App->>App: ⑤ 権限の有効性と引用を確認
    App-->>Browser: 回答＋アプリ経由の引用
```

①〜⑤はすべてバックエンド側の責務である。Graphが文書権限を評価する処理と、アプリが本人・会社・送信先を確認する処理を組み合わせる。
**確認できなければ止める。** Graph用tokenの取得失敗時に、共有管理者やアプリ単独のtokenで代行しない。

### ① 本人と会社を確定する

RAGバックエンドがCookieに対応するWebセッションを確認し、会社の利用許可とログイン時に検証したEntraの本人・テナントを照合する。
会社Aの設定、担当者Aのアカウント、Graph用の委任scopeを指定してtokenを取得する。MSAL等のtoken cacheはアプリ・テナント・アカウントを区別し、「最後にログインした人」のtokenを共有しない。Graph宛てaccess tokenをアプリが独自に解析して本人確認の代用にしない。[利用者別token cache](https://learn.microsoft.com/en-us/entra/msal/python/advanced/msal-python-token-cache-serialization)、[access tokenを受け取る側の責務](https://learn.microsoft.com/en-us/entra/identity-platform/access-tokens)
画面で会社を選べる場合も、その会社への現在の所属を確認する。質問やモデルが指定した`user_id`・`tenant_id`は使わない。
質問の型・長さもここで検査する。

**次へ渡すもの：サーバーが確定した担当者A・会社Aと、検査済みの質問。**

### ② 許可された範囲で検索する

バックエンドは`POST https://graph.microsoft.com/v1.0/search/query`へ、担当者Aの委任access tokenを付けて要求する。
対象はSharePointのファイル（`entityTypes: ["driveItem"]`）。説明例の委任scopeは`Files.Read.All`とし、必要な同意を事前に整える。同名のApplication permissionや書込みscopeへ置き換えない。このscopeは担当者Aが読めないA200への権限を付与するものではない。[検索対象と権限](https://learn.microsoft.com/en-us/graph/api/resources/search-api-overview?view=graph-rest-1.0)

Graphが担当者Aの文書権限を評価する。さらにアプリが会社Aの検索領域を固定し、返された文書のサイト・ライブラリが管理設定の許可範囲に入るか確認する。
本人が別の共有サイトを読めても、このサービスの会社Aの検索範囲とは限らない。検索条件だけに依存せず、範囲外の結果はLLM・応答・引用に使わない。
モデルから受け取るのは検索語だけとし、本人・接続先・資格情報・検索領域はアプリが決める。
検索語をそのまま検索式へ文字列連結しない。SharePointの検索式（KQL）を使う場合は、利用者の文字列をリテラルとして処理し、会社のサイト範囲をサーバー側で固定する。構築した式に加えて、結果のサイト・ライブラリも照合する。[GraphのSharePoint検索例](https://learn.microsoft.com/en-us/graph/search-concept-files)
A200は担当者Aの文書権限、B100は会社・テナント・サイトの対応で除外する。検索は許可範囲内で関連する資料を選ぶために使う。

既存検索の利用だけなら、アプリが検索ベクトルを作る必要はない。独自検索で外部Embeddingを使う場合は、送信先の許可を確認する。
[Embedding生成時の送信先](access-control-options.md#embedding生成も本文質問の送信先を確認する)には、文書の取り込み時と質問時の確認箇所をまとめている。

結果が不足しても認可条件を外さない。候補キャッシュを使う場合は[権限変更の扱い](#6-キャッシュと権限変更をどう扱うか)の方式とする。

**次へ渡すもの：許可条件で得た元文書IDと、取得できる場合は版・抜粋。**
検索APIが版を返さない場合は③で現在の本文と版を取得し、その本文から必要な断片を作る。版の対応を確認できない古い検索抜粋はモデルへ渡さない。

### ③ 許可された本文を取得する

検索結果の文書を、許可したサイト・ライブラリと`drive-id`／`item-id`に対応付ける。A100等は説明用の呼び名であり、実際のGraph識別子ではない。
バックエンドが同じ担当者Aの委任資格で`GET /v1.0/drives/{drive-id}/items/{item-id}`を呼び、所属先と現在の版を確認してから、同じIDの`/content`で本文を取得する。
Graphが取得要求にも利用者のアクセス制御を適用する。本文取得のためだけにアプリ単独の広いtokenへ切り替えない。[本文取得API](https://learn.microsoft.com/en-us/graph/api/driveitem-get-content?view=graph-rest-1.0)
削除・非公開・古い版・対応不明の断片は返さない。検索候補に入ったという事実だけで取得を許可しない。

この例ではA100の現在版の断片だけを取得する。タイトルや前後の段落を追加するときも同じ条件を使う。
既存検索が本文の抜粋を返す場合は②ですでに開示が始まるため、その応答にも認可が必要である。
自前のSQL検索では、②と③を一つの照合付きクエリで実行してよい。
自前で取り込む場合の準備側は[新版とACLが揃ってから公開する](implementation-notes.md#更新途中の本文を検索可能にしない)。

**次へ渡すもの：許可を確認したA100の本文・タイトルと、対応するID・版。**

<details>
<summary>GraphのダウンロードURLと版の扱い</summary>

`/content`は認証済みの一時ダウンロードURLへ302でリダイレクトする。このURL自体はAuthorizationヘッダーなしで使えるため、バックエンド内で直ちに取得し、Graph用Bearer tokenを別ホストへ転送しない。
Graphからの正規応答に由来するHTTPSのダウンロード先だけを扱い、利用者やモデルの任意URLには接続しない。取得先の制限・サイズ・タイムアウトは接続処理で管理する。
URLをログ・LLM入力・引用・共有キャッシュへ出さず、再利用時は新しいGraph要求で認可を通す。一時URLを保存しておく方式は、権限再確認の代わりにならない。[ダウンロード仕様](https://learn.microsoft.com/en-us/graph/api/driveitem-get-content?view=graph-rest-1.0)

文書の`eTag`等の版情報と取得した本文を対応付ける。取得中に版が変わった場合は破棄・再取得し、古い検索抜粋と新しい文書を混ぜない。ファイルからのテキスト抽出と断片化もバックエンドで行う。

</details>

### ④ 許可された送信先で回答を生成する

回答生成処理が、A100の断片を会社のデータ取扱方針上許可されたモデルへ送る。
「担当者Aが読める」と「外部サービスへ送れる」は別の確認である。外部再ランキングを使う場合も同じ扱いにする。

本文取得から送信まで待機した場合は、同じ利用者の委任資格で対象のGraphメタデータ取得をやり直し、閲覧の可否・会社範囲・版を再確認する。拒否・削除・判断不能なら送信しない。[文書メタデータ取得](https://learn.microsoft.com/en-us/graph/api/driveitem-get?view=graph-rest-1.0)
権限確認の時点と取消の反映期限は[権限変更の扱い](#6-キャッシュと権限変更をどう扱うか)で決める。

**次へ渡すもの：生成された回答と、モデルへ渡したすべての文書ID・版。**

### ⑤ 回答と引用を返す

回答返却前にも、モデルへ渡したすべての文書を同じ利用者の委任資格で再確認する。access tokenの期限が残っているだけでは、文書の閲覧権限が続いている証拠にしない。
途中で失効していたら、未返却の回答全体を破棄する。引用だけ消して回答本文を返してはいけない。

引用はサーバーが許可した文書一覧から組み立て、モデル指定の未知のID・URLは公開しない。
引用はRAGアプリの認可付きURLとし、担当者Aが開いたときもWebセッションと利用者別tokenを解決して③へ戻る。Graphの一時ダウンロードURLは引用として返さない。
この例では回答をまとめて返し、生成済み回答や過去の会話を自動で再利用しない。

**担当者Aへ返すもの：A100を材料にした回答と、認可付きの引用。**

## 6. 常に守る条件

| ID | 不変条件 |
|---|---|
| I1 | 質問・モデル・文書本文は、認証済み本人や所属・文書権限を上書きできない |
| I2 | 開示する各断片は、確認した権限状態で会社と文書単位の閲覧条件を満たし、元文書・版と対応する |
| I3 | 検索、候補キャッシュ、本文取得、引用の各経路で同じ閲覧制限を強制する |
| I4 | 本人・権限・対応関係を確認できないときは開示せず、全社検索や古い許可へ切り替えない |
| I5 | 利用者やモデルは、検索基盤への直接アクセスや権限情報の変更によって認可を迂回できない |
| I6 | 権限の確認時点と失効反映期限を定め、期限を超えた古い許可で新たに開示しない |

<a id="6-キャッシュと権限変更をどう扱うか"></a>

## 7. キャッシュと権限変更をどう扱うか

### 候補を再利用しても、③の認可を通す

主例はアプリ側に候補・回答キャッシュを新設しない。以下は候補キャッシュが必要になった場合の追加条件。元システム内部のキャッシュと失効特性は別途確認する。

候補キャッシュのキーには会社・利用者・検索条件を含め、文書ID・断片ID・版だけを保存する。
IDも検索サービス内で保護し、③で現在の権限による本文取得を行う。別利用者の結果を流用しない。

本例では生成済み回答をキャッシュせず、過去の会話に含まれる本文・回答も自動でモデルへ戻さない。
それらを再利用する構成では、根拠文書すべての版と権限を追跡し、再開示できるか確認する別の仕組みが必要になる。

### 取消をいつまでに反映するか決める

権限の確認時点と、取消から反映までの期限を決める。主例ではSharePointの権限変更、Graph検索・本文取得への反映、アプリ内の待機を含めて確認する。Graphへ再要求しても、上流の権限変更が即時に反映されるという保証にはならない。必要な期限を満たすことを確認できなければ、この構成をその要件に適合すると扱わない。
自前検索では所属・ACLの同期、認可キャッシュ、キューの遅延も対象にする。
期限を満たせない場合は対象範囲の検索・開示を停止する。④では待機後の再確認、⑤では回答返却前の確認を行う。

DBの読取り後にも権限は変わり得る。SQLだけで取消と送信を一つの操作にはできない。
取消と同時に進行中の送信も止める必要がある場合や、ストリーミングを使う場合は、要求取消・送信制御まで含めて設計する。
モデルや利用者へすでに送った情報の回収は保証しない。[PostgreSQL 18の分離レベル](https://www.postgresql.org/docs/18/transaction-iso.html)

<a id="8-記録検知障害対応"></a>

## 9. 記録・検知・障害対応

要求ID、主体と会社の参照、使用した文書・断片IDと版、権限の確認時刻・版、許可／拒否、キャッシュ経由か、送信先と結果を記録する。
質問全文・文書本文・回答全文・生のセッション／トークンを通常の監査ログへ保存しない。文書ID等の記録にも閲覧権限と保持期間を設定する。
試験でモデルへの送信内容を調べる場合は、ダミー文書と管理下の取得手段を使う。

会社の指定不一致、権限情報の欠落、失効反映期限の超過、検索サービスを通らないアクセスを検知対象にする。
同期障害時は対象範囲の開示を止め、該当キャッシュを無効化する。復旧時は権限と文書版の整合を確認して再開する。
外部応答には権限外文書の存在やタイトルを含めず、内部の監査記録で拒否理由を追えるようにする。

<a id="9-限界と追加設計が必要な場面"></a>

## 10. 限界と追加設計が必要な場面

- 許可された文書自体が悪意ある場合、回答への誘導は残る。ツール実行へ進む場合は[PATTERN-AGENTS-001](../../agents/secure-tool-execution/README.md)の実行認可も適用する。
- 権限管理元・検索サービス・取り込み処理の侵害や誤設定まで、この検索時チェックだけで補えない。
- 過去に正当に開示した文書、回答、モデル入力の回収は保証しない。失効後の新たな開示と区別する。
- 共有基盤の時間・件数・検索品質からの推測や性能干渉、物理分離の要件は別途評価する。
- 認可されても、外部モデルへの送信が契約・データ取扱方針上許可されるとは限らない。送信先の許可を別途確定する。
