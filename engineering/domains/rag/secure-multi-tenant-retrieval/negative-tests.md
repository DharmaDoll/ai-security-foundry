# RAG検索の認可：正常系・Negative testチェックシート

[Pattern本文](README.md)のI1〜I6を自分の実装で確認するためのシート。各行は**未実施**であり、製品の安全性認定ではない。
[実装ノート](implementation-notes.md)は、文書ACL・RLS・接続プールとN14〜N16の具体的な確認箇所を示す。
[方式比較](access-control-options.md)の外部認可・製品側認可を採用する場合は、P6・N17〜N18と既存の失効・迂回ケースも確認する。
取り込み時の公開手順はP7・N19、Embedding生成時の送信先はP8・N20で確認する。

## 使い方と前提

1. 管理下の検証環境とダミー文書を使う。担当者Aは会社Aのメンバーで、A100だけ閲覧可、A200とB100は閲覧不可とする。
2. 正常系を確認してから、対象の条件だけを変える。質問との類似度が低くて検索されなかっただけでは認可の確認にならない。
3. モデル経由に加え、検索API・本文取得・引用先を直接試す。モデルの拒否や回答画面だけでは合格にしない。
4. 「合格／不合格／未実施／対象外（理由）」と証拠を記録する。確認できない送信経路は未確認とする。

| 記録項目 | 記入欄 |
|---|---|
| 対象環境・アプリ版・DB／検索基盤の版 | 未記入 |
| 権限管理元・同期方式・ポリシー版 | 未記入 |
| 失効反映期限・権限の確認時点・進行中要求の扱い | 未記入 |
| キャッシュ方式・文書／断片の初期状態 | 未記入 |
| 実施者・日付・モデル／再ランキングの送信先 | 未記入 |
| 文書・質問のEmbedding生成先と送信許可、取り込み時の公開手順 | 未記入 |

「開示なし」は、該当要求の未認可文書の本文・タイトル・断片・引用が、利用者、モデル、外部再ランキングへ渡らないこと。
信頼する検索サービス内部の処理と、管理された監査記録は区別する。外部応答の件数やエラーから文書の存在を不用意に示さない。

## 正常系

| ID | 試すこと | 期待する結果・証拠 | 結果／証拠 |
|---|---|---|---|
| P1 | 担当者AがA100に一致する質問をする | A100の許可された断片がモデル入力へ入り、引用の会社・文書・版も一致する | 未実施 |
| P2 | 同じ本人・会社・質問で候補IDキャッシュを使う | 現在の権限による本文取得を経てA100が使われる。キャッシュヒットでも認可が省略されない | 未実施 |
| P3 | A200を読める会社Aの別担当者で、A200に一致する質問をする | A200が取得できる。同じ検索が担当者AではN2により除外される | 未実施 |
| P4 | 該当する許可文書がない質問をする | 参照できる資料がないと扱う。条件を外した検索や他社文書での穴埋めをしない | 未実施 |
| P5 | 接続プール利用時、会社A・会社Bの各担当者から、同じDB接続を順番に使って許可文書を検索する | 各担当者に自身の許可文書が返る。前の要求の会社・本人を引き継がない | 未実施 |
| P6 | 外部認可／元システムの権限連携を採用する場合、管理元でA100の閲覧を許可し、反映を確認して担当者Aで検索する | 本人・会社・権限の対応を経てA100だけが返る。認可不能による全拒否を正常な制限と取り違えない | 未実施 |
| P7 | A100の新版を管理者限定にし、本文・断片・ACLの反映を揃えて公開する | 管理者は新版を検索・直接取得でき、権限を失った担当者Aは取得できない。新版とACLの対応を記録する | 未実施 |
| P8 | 外部Embeddingを使う場合、対象会社・データ分類で送信を許可したダミー文書と質問を、それぞれ承認済みの接続先で処理する | 許可した接続先だけへ送り、取り込みと検索が成立する。全面的な送信停止を正常動作と取り違えない | 未実施 |

|---|---|---|---|---|
| N1・I1 本人・会社の偽装 | モデルの検索入力に会社Bの`tenant_id`、別人の`user_id`、任意フィルターを個別に追加する | 未許可の項目を拒否し、サーバーの本人・会社を置き換えない | 信頼する本人の参照、拒否理由、B100の開示なし | 未実施 |
| N2・I2 同じ会社の権限外文書 | A200を質問に最もよく一致する文書にし、担当者Aで検索・直接本文取得する。正常系P3と対にする | 会社が同じでもA200を除外する | 権限判断、モデル入力・応答・引用にA200なし | 未実施 |
| N3・I2 他社文書 | B100を質問に最もよく一致させ、担当者Aで検索・直接本文取得する。テスト用認可データでは文書閲覧許可だけを与え、会社不一致だけを残す場合も試す | 文書の閲覧許可だけでは会社境界を越えない | 会社の照合、B100の開示なし。単に類似検索で落ちた場合は未確認 | 未実施 |
| N4・I2/I4 条件の欠落 | 管理下のテスト用呼出経路で会社条件、次に文書ACL条件を欠落させ、実際の実行ロールで試す | 共通の認可処理やDBポリシー等で未認可本文の開示を止める | 検索条件、DBロール、モデルへ渡す直前の確認結果。欠落したまま渡れば不合格 | 未実施 |
| N5・I2 文書と断片の取り違え | 他社の同じ文書ID、異なる元文書、古い版を指す断片をテストデータに用意する | 制約で登録を拒否するか、取得時に対応不正として除外する | 会社・文書・断片・版の照合、古い本文と引用の開示なし | 未実施 |
| N6・I3 キャッシュの利用者混同 | A200を読める担当者でキャッシュを作り、担当者Aから同じ質問をする。他社利用者との組合せも試す | 別主体のキーを共有しない。候補が混入しても現在の権限で除外する | キャッシュキーの構成と再認可、A200・B100の開示なし | 未実施 |

| N9・I4 管理情報の欠落・同期障害 | 所属／ACLの取得失敗、許容期限を越えた同期停止を個別に起こす | 検索・開示を停止。古い許可や全社検索へ切り替えない | 障害理由、同期状態、キャッシュ経由も含む開示なし | 未実施 |

N3の会社条件だけを確かめるデータは、管理下の検証用に用意する。通常の管理画面が他社への閲覧許可を禁止していることと、検索側の会社照合は別に確認する。
RLSを使う場合はN4・N11で所有者・`BYPASSRLS`等の迂回条件と、通常のアプリ実行ロールを区別する。
N7〜N9・N13は、所属やACLの別経路でのキャッシュも含めて、定めた失効反映期限を測る。
外部認可では元システムからのACL同期、ラベル連携ではIndexer更新もN7〜N9の対象に含める。問い合わせ成功だけで鮮度を確認したことにしない。

## 依頼の例と結果の読み方

> 「N2は、A200を読める担当者では取得できる状態を先に作ってください。その後、担当者Aに変えた場合に、どの文書権限の条件で止まるかを見たいです。」

> 「N7は、キャッシュを消してからではなく残したまま試してください。失効が反映された後の同じ要求IDについて、本文取得とモデル送信の記録を示してください。」

> 「N4は、プロンプトで会社指定を変えるだけでなく、検索条件の組み立て漏れを想定してください。どの層が最後に開示を止めますか。」

回答に出なかっただけでも、モデルや外部再ランキングへ送っていれば不合格。
ログがないだけでは未送信の証拠にならない。管理下の送信内容・引用APIの応答と判断記録を対応付ける。
試験の合格範囲は対象版と構成に限定し、[残るリスク](README.md#9-限界と追加設計が必要な場面)を別途判断する。
