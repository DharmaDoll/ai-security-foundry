# P6：引継ぎメモの保存・再利用を確認する

[本文](README.md)と[実装例](implementation-notes.md)の①元資料 → ②要約 → ③保存 → ④再利用を確認する。全項目は製品試験未実施。採用先で`未実施`・`合格`・`不合格`・`対象外（理由）`を記録する。

## 準備と観測点

- 架空の会社A/B、利用者U1/U2、案件T-100/T-200を使う。U1はAのT-100と資料S1/S2を読める状態から始める。試験用データと隔離環境を使う。
- アプリ版、DBの分離Level、全更新経路、資料版・メモ版、期限、Session・会社切替・失効の条件を記録する。
- 読み込んだ全資料と版、保存した出所、実際のLLM入力、DB更新行数、業務API呼出し、UIの外部通信を観測する。通常ログへ秘密や本文を常時追加する方式にはしない。
- モデルが拒否する場合だけでなく、指示に従った文章・Tool要求を返す場合も試す。応答の「拒否しました」だけを強制点の証拠にしない。
- 失効・取消しのCommit後に開始する新しい読込みと、既に読み出した処理を分ける。後者を回収できたという過大な保証をしない。

レビュー依頼例：

> N1では、モデルが実際に「承認不要」と出力する結果を使ってください。安全という返答を見るのではなく、承認記録と業務API呼出しが変わらないかを見たいです。N5/N6は到着順を入れ替え、取消し・資料変更の完了後に始めた次の読込みへ旧要約が入らないことを示してください。

外部Memoryサービス・要約の多段連鎖・組織横断共有はこのチェックの対象外。追加する場合は、保持先・再投入経路・更新の同期条件に応じて確認を増やす。
