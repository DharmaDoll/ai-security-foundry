# 返信材料・確認した内容・送信APIをつなぐ

[P4本文](README.md)の①〜⑤を、既存のサポートWebアプリに組み込む例。
以下のデータと手順は要点サンプルであり、実行可能なサービスや検証済みの実装ではない。

## まず、許可と拒否の違いを見る

担当者AはT-100と、その注文1001を閲覧できる。顧客台帳は、C-100の確認済み宛先を`contact@customer.example`としている。

| 要求 | 扱い | 理由 |
|---|---|---|
| 注文1001の配送状況と予定日をC-100へ返信する | 下書きを作り、本人の確認後に送信 | 顧客・対象・開示項目・宛先が一致 |
| 注文1001の社内不正調査メモも引用する | 返信材料へ入れない | 担当者の閲覧許可は、顧客への開示許可ではない |
| 同じ顧客会社の別アドレスへ送る | 拒否し、既存の宛先確認手順へ戻す | ドメイン一致だけでは、その相手への開示許可を確認できない |
| 本文を変更し、旧版の確認記録で送る | 旧記録を無効にし、再確認 | 確認した内容と送る内容が違う |

## ①〜③：モデルが選ぶのは候補、サーバーが作るのは返信材料

モデルから受ける候補は、例えば次だけにする。宛先・開示ラベル・承認フラグ・自由文を、この入力形式には設けない。追加項目は拒否する。

```json
{"order_id": "1001"}
```

モデルにT-100の指定を任せず、Webセッションとサーバーに保存したタスクから取得する。
①でT-100・C-100・注文1001の関係を確かめ、②で業務APIの正式な項目値を取り直す。
その結果を次のように保存する。値とIDは架空で、開示ルールや保存形式は本PJの例である。

```json
{
  "packet_id": "packet-17",
  "ticket_id": "T-100",
  "customer_id": "C-100",
  "source": {"order_id": "1001", "version": "v8"},
  "release_policy_version": "p3",
  "recipient_record_version": "r4",
  "facts": {
    "delivery_status": "shipped",
    "estimated_date": "2026-10-30"
  }
}
```

③へ渡すのは`facts`と固定の返信作成指示。`facts`内にも、型・許容値を確認せず自由文を詰めない。
社内調査の要約、以前の会話、共有メモリを引き継がないことを、LLM APIへ実際に送る入力で確認する。
`packet_id`等の管理情報はサーバーに残す。ハッシュや版番号は対応付けの補助であり、内容が開示可能である証明にはならない。

## ④〜⑤：表示した内容を保存し、送る内容を固定する

サーバーが返信案を保存し、その版から画面を作る。主例では下記の送信元は担当者Aのメールアカウントに固定する。

| 保存する情報 | 取得元・意味 |
|---|---|
| 担当者、会社、T-100、C-100 | 検証済みセッションと業務DB |
| 送信元アカウント、To、空のCC・BCC、添付なし | 送信アカウント設定と確認済み顧客台帳。モデル入力を転用しない |
| 件名、本文、文字形式、送信内容の版 | サーバーが保存し、利用者へ表示する実物。変更したら新しい版 |
| 返信材料と元情報・開示ルール・宛先台帳の版 | ②で保存した記録。変更や失効を再確認できるようにする |
| 確認した本人、対象版、有効期限、使用状態 | 認証済み画面での送信操作を受けてサーバーが作成。モデルの`approved`は使わない |

送信処理は次の順で動く。

1. セッション・CSRF・現在の業務権限を検証し、要求された送信内容の版を本人のT-100に対応付ける。
2. 宛先台帳、材料の元情報、開示ルールを再確認する。変更・失効・照会不能なら保留し、必要に応じて材料作成と確認からやり直す。
3. 本人が確認した版・期限・未使用状態を照合し、共有DBで条件付き更新して、一つの送信処理だけが扱える状態にする。ブラウザから本文を再送させて差し替えない。
4. 保存済みの送信内容から、決めた項目だけでAPI要求を作る。後からモデルへ整形を依頼したり、モデルが指定したURL・追加ヘッダーを使ったりしない。
5. APIの応答に応じて状態を記録する。成功応答がないからといって、同じメールを自動的に再送しない。

承認と実行の対応付けは、[OWASPのTransaction Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html)を参考にした設計例。
現在の権限確認と外部API呼出しを一つのDBトランザクションにはできないため、取消しの反映期限と残る時間差は採用先で定める。

## 具体技術：既存の送信処理からMicrosoft Graphを呼ぶ場合

**Graphはメールを送る接続先であり、顧客に何を開示してよいかを決める場所ではない。**
主例の送信処理をMicrosoft 365へ接続するなら、担当者本人のdelegated `Mail.Send`で`POST /v1.0/me/sendMail`を呼ぶ選択肢がある。
GraphのAPI v1.0はdelegatedとapplicationの`Mail.Send`を別の権限種類として扱う。この例はdelegatedを選ぶ。
[公式のsendMail仕様](https://learn.microsoft.com/en-us/graph/api/user-sendmail?view=graph-rest-1.0)を2026-10-27に確認。実接続は未実施。

### どの資格を、誰が持つか

| 資格・記録 | 保持場所と使い道 |
|---|---|
| WebセッションCookie | ブラウザ→Webバックエンド。担当者のログインを確認する。Graphへ転送しない |
| Graph用access token | 送信側のサーバー接続処理が、担当者のEntraアカウント別に保持。GraphへのAuthorizationヘッダーにだけ付ける |
| refresh token（発行される場合） | 送信側の保護されたアカウント別トークンキャッシュ。Entraへの更新にだけ使い、モデル・ブラウザ・Graphへ渡さない |
| client資格 | 送信側のサーバー秘密管理。認可サーバーに対するアプリの認証に使う。顧客への開示許可や本人の送信操作を表さない |
| 本人が確認した送信内容の記録 | 業務DB。OAuth tokenとは別に、T-100のどの版を送ってよいかを表す |

本人のサインインと同意を経て、認証ライブラリでAuthorization Code＋PKCEを使う（[Entra公式資料](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)、更新型、2026-10-27確認）。
取得方式は[P2のWebログインと委任資格の例](../../rag/secure-multi-tenant-retrieval/README.md)も参照できるが、**調査側の検索資格にMail.Sendを追加して共用しない**。
送信側は別のclient登録・トークンキャッシュで管理し、検証済みのEntra tenant・accountをWebセッションの担当者へ結び付ける。メールアドレス文字列だけでキャッシュを選ばない。
client secretの存在はapp-onlyであることを意味しない。

Agentのツール経路には、この送信接続やトークンキャッシュを公開しない。
同じバックエンドでの関数分離は、モデルが固定ツールだけを選べるという主例の前提で使える。任意コードを実行するAgentでは別の実行主体・プロセス・通信制限が必要となり、この例の範囲を超える。

### APIへ渡すデータの形

次は⑤を通過したサーバーが組み立てるJSON本文。モデルが返したJSONをそのまま転送する例ではない。

```json
{
  "message": {
    "subject": "お問い合わせの配送状況",
    "body": {
      "contentType": "Text",
      "content": "ご注文は発送済みです。到着予定日は2026年10月30日です。"
    },
    "toRecipients": [
      {"emailAddress": {"address": "contact@customer.example"}}
    ]
  }
}
```

CC・BCC・添付・任意ヘッダーは組立て対象にしない。送信元は対応する本人の`/me`に固定する。
`Mail.Send`が有効でも、注文と顧客の対応や本文の開示可否まではこのAPI権限で決まらない。

### 送れたか不明なとき

Graphの`202 Accepted`は受付であり、配送完了を表さない。受付後に応答が失われる場合もある。
ローカルDBの一意な送信要求IDや条件付き更新は、アプリ内の並行実行を抑えるために使う。外部サービスまで含めたexactly-onceの保証にはならない。

```text
下書き → 本人が確認した版 → 送信処理が確保 → 受付済み
                                  └→ 結果不明：自動再送を止め、送信側の記録と照合
```

結果不明を未送信へ機械的に戻さない。既存メール基盤の記録で確認し、再送する場合は重複リスクと現在の開示可否を確認する。

## 自動送信が必要なら、自由文を使わない通知から始める

配送通知は、②の許可された状態値と日付を、固定テンプレートへサーバーが埋め込む構成にできる。
この場合、モデルが提案した文面・任意文字列・宛先は送らない。本文に使う項目と値域を限定し、問い合わせ・注文・宛先の対応、通知条件、回数制限をサーバーで確認する。
本人の個別送信操作の代わりに、業務責任者が定めた自動通知ルールを根拠にする別構成であり、主例の確認を単に省略する変更ではない。

詳細を確認する依頼例：

> Agentが使えるツールと、送信接続が使えるAPI・資格の一覧を並べてください。社内調査メモが返信生成へ混入する経路、宛先の変更経路、承認後の本文変更、並行送信、結果不明時の再送がどう扱われるかを、一件の試験データで説明してください。
