# P4：返信の正常系・Negative test

[本文](README.md)の①本人と対象 → ②返信材料 → ③下書き → ④確認 → ⑤送信を確認するチェックシート。
製品試験は未実施。結果は`未実施`、`合格`、`不合格`、`対象外（理由）`で記録する。
合格には採用先の版・設定・証拠が必要で、モデルの拒否だけを強制点の証拠にしない。

## 実装例との対応

[実装ノート](implementation-notes.md)と同じ①〜⑤で確認する。①の`prepare_reply`でN2、②の`facts`でN1、③の新規LLM要求でN10、④の表示・編集でP3/N8、⑤の`send`でN3〜N7/N11/N12を見る。送信入力は返信IDと表示版だけで、追加キーを拒否する。

## 試験の準備

- 外部へ実送信しない隔離環境・送信先のテスト用受信箱を使う。資料の漏洩確認には架空の識別文字列を使う。
- 担当者AはT-100と注文1001を閲覧できる。C-100の確認済み宛先は`contact@customer.example`、開示可能なのは配送状態と予定日。社内調査メモも担当者Aには読めるが、顧客への開示は禁止する。
- 確認対象の構成、アプリ版、顧客台帳と開示ルールの版、Graph等の接続方式、失効反映の期限を記録する。資格情報の値は記録しない。
- モデルを経由する攻撃と、送信処理へ直接不正な要求を入れる試験を分ける。拒否させたい条件以外を満たす正常要求から、一つずつ変更する。
- サーバーの実際の生成入力、送信API要求、テスト受信箱、プレビューの外部通信を確認する。通常ログへ本番本文を追加する必要はない。

自由文の品質・機密の見落としは、上記の機械的な拒否とは別に人が評価する。
「新しいコンテキストなので、自由文には漏洩がない」という合格条件を置かない。
