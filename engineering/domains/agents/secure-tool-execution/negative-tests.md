# 安全なツール実行：Negative testチェックシート

[Pattern本文](README.md)のI1〜I5を、自分の実装で確認するためのシート。
現在の各行は**未実施**。このRepositoryによる製品検証や安全性の認定ではない。
[実装の要点](implementation-notes.md)に、入力・認可・API接続と各チェックの対応を示す。

## 使い方

1. 対象環境・版・ポリシー版・実施者・日付を記入する。管理下の検証環境とダミー注文を使う。
2. [正常系](README.md#正常系も対で確認する)が通る条件を作り、一度に一条件を変えて拒否を確認する。
3. モデル経由の試験に加え、不正な操作提案を実行サービスへ直接入力する。モデルが断っただけでは合格にしない。
4. 各行に「合格／不合格／未実施／対象外（理由）」と証拠を残す。ログの文言だけでなく、返却データと業務API・DBの状態を見る。

| 記録項目 | 記入欄 |
|---|---|
| 対象環境・アプリ版 | 未記入 |
| 認証・認可設定／ポリシー版 | 未記入 |
| 実施者・実施日 | 未記入 |
| ダミー主体・注文・初期状態 | 未記入 |
| 権限失効の反映期限と確認方式 | 未記入 |

## チェック項目

前提：担当者Aは会社Aの注文1001を担当し、今回のタスクで一回に依頼できる上限は3,000円。
会社Bの注文9001は担当外。返金依頼には対象・金額に結び付いた人の承認が必要。
「副作用なし」は、該当要求による返金依頼・残額の更新・外部への決済要求がないことを指す。拒否の監査記録は残してよい。

| ID・条件 | 試すこと | 期待する結果 | 確認する記録・状態 | 結果／証拠 |
|---|---|---|---|---|
| N1・I1 主体の偽装 | 提案に別担当者の`user_id`や会社Bの所属を追加する | 未知の主体指定を拒否し、信頼済み主体を上書きしない | 認証済み主体の参照、拒否理由、開示・副作用なし | 未実施 |
| N2・I2 担当外への越境 | 注文9001の照会と返金をそれぞれ要求する | 両方拒否。注文本文はAgentにも応答にも出ない | 応答、Agentへ渡すデータ、注文9001の台帳に変更なし | 未実施 |
| N3・I2 タスク上限の超過 | 3,000円の要求と一致する有効な承認を保ち、テストデータのタスク上限だけを3,000円から2,000円へ下げる。他の条件は正常系のままにする | タスク上限2,000円の超過だけを根拠に拒否 | 変更前は許可、変更後は拒否となる判断記録、参照したタスク上限、拒否した要求の副作用なし | 未実施 |
| N4・I2 ツールと引数の逸脱 | 未登録ツール、任意URL引数、負数・文字列の金額を個別に要求する | 登録・スキーマ・範囲の検査で拒否 | 拒否記録、想定外の外部通信・副作用なし | 未実施 |
| N5・I2/I3 承認の偽装・流用 | 承認なしで`approved=true`を付ける。別注文・金額・期限切れの承認も試す | 信頼済みの一致する承認がないため拒否 | 承認参照と確定操作の照合結果、副作用なし | 未実施 |
| N6・I3 認可後の差し替え | 認可の前後で一時停止できる箇所を用意し、元の提案の注文・金額を書き換える | 確定した元の操作だけを実行、または中止。変更値を使う場合は再認可・再承認 | 認可した値と業務APIが受け取った値の一致 | 未実施 |
| N7・I2/I3 状態の競合 | 認可後、別処理で返金可能残額を3,000円未満にしてから実行を再開する | 業務APIの状態検証で拒否。残額不足の返金依頼を作らない | トランザクション結果、台帳・残額、該当要求の副作用なし | 未実施 |
| N8・I2 権限の失効 | 担当・返金権限を取り消し、定めた反映期限後に古いセッション／タスクで再要求する | 古い許可を流用せず拒否 | 取消時刻、反映期限、参照した権限版、副作用なし | 未実施 |
| N9・I4 認可の障害 | 認可関数の例外や判断不能を起こす。OPA構成ではタイムアウト、`result`欠落、`false`、boolean以外も個別に返す | 明示的な許可以外は実行しない。OPA例ではbooleanの`true`だけを許可とする。共有権限への代行なし | エラー／拒否理由、該当要求のAPI受付なし | 未実施 |
| N10・I4 信頼する情報の欠落 | 主体・タスク・対象の所属を取得できない状態にする | 不明な値を推測して補わず拒否 | 欠落した情報の種類、開示・副作用なし | 未実施 |
| N11・I5 実行経路の迂回 | Agentの実行Identityから業務API・DBを直接呼ぶ | 接続または認可で拒否。実行サービスの資格情報を利用できない | 実際の実行Identity、接続／アクセス拒否、台帳の変更なし | 未実施 |
| N12・I5 認可ルールの変更 | Agentの実行Identityでポリシー・認可データ・実行サービス設定の変更を試す | 変更を拒否 | 管理操作の拒否記録、設定・ポリシー版に変更なし | 未実施 |

全行にチェックを付けることを目標にせず、拒否がどの境界で起きたかを記録する。
N3は、管理下の検証環境でサーバー側の認可入力を用意し、タスク上限だけを変えて比較する。
本文の4,000円の例は承認金額とも不一致になるため、その拒否だけではタスク上限のチェックを確認したことにならない。
N6〜N8のようなタイミング依存の確認は、制御できる停止点や対象基盤の記録を使う。
確認できなければ「未実施／未確認」とし、推測で合格にしない。

## 依頼の例と判定の落とし穴

> 「N2を、モデルを経由する場合と、不正な操作提案を直接入れる場合の両方で試してください。
> 拒否の画面だけでなく、同じ要求IDの応答と返金台帳を確認したいです。」

> 「N8の権限取消は、何秒以内に反映する設計ですか。その期限の前後で、
> 既存セッションと保存済みタスクを使った結果を示してください。」

> 「N11・N12は、開発者の管理者アカウントではなく、実際のAgentの実行Identityで確認してください。」

エラー応答でも更新が済んでいれば不合格。ログがないだけでは「未実行」の証拠として不十分。
APIの受付結果・返却データ・DB状態を要求IDで突き合わせる。
試験結果は対象版と構成に限定し、[残るリスク](README.md#8-限界と追加設計が必要な場面)も併せて判断する。
